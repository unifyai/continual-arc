I'm writing to you after playing many tasks in this same stream, with the same files and rules you'll have. Here is everything I learned about how to work well in this harness. It is long, but every section earned its place by costing me a wrong attempt or a lost task first.

## The workflow that wins

1. **Write the demo pairs to `programs/task-XXXX.json` immediately** in the JSON format you see there (list of `{"input": ..., "output": ...}` with the grid rows as lists of ints). This is your evidence base. Keep it updated whenever you receive new pairs.
2. **Write the program to `programs/task-XXXX.py` with a `transform(grid)` function.** Do not hand-solve tests; make the program reproduce every demo pair *before* you predict anything. Then apply the program to the test input and submit that output.
3. **Verify by running, not by staring.** Mentally simulating a rule over a 25×29 grid is where small models (and big ones) make errors. If you can execute code, run your transform on each demo input and diff against the demo output. Zero mismatches on all kept pairs is the only acceptable bar before submitting a test prediction.
4. **Save a memory file** (e.g. `programs/task-XXXX_status.json` or a `memory_task-XXXX.json`) with the rule in plain words, the file paths, pair counts, and whether the program reproduces everything. The next instance of the same task will reuse it; I solved several repeat tasks at 0 wrong attempts purely because a previous memory held the rule.

## When demos are few and tests are ambiguous

The harness gives you a limited number of demo requests. My hard-won guidance:

- **If the rule you extracted does not constrain the test at all** — e.g. the test input has a configuration type that appears in *no* demo pair — **request demos before submitting**, not after. My clearest example: task-5c839a47. The rule ("3 = cells strictly between min and max dot per row/column") reproduced 10/10 demo pairs, but the test had a *single* dot, which every demo had ≥2. Every lone-dot extension I tried (identity, cross, row-only, col-only, all-3-except-dot, arcs, mirrors, full row) was wrong; I burned 8 attempts. If a test input is outside the demo distribution, that's the signal to ask.
- But don't over-request. Two clean pairs usually pin a rule down; a third is for tie-breaks between genuinely different hypotheses.

## Patterns I solved, as reusable templates

These are families, not one-off answers. Recognize the shape of the input and reach for the template:

- **Separators and tilings.** Grids divided by solid uniform rows/columns (one color spanning the whole grid) decompose into blocks. Templates that worked: (a) count stray-colored cells per block, output 1 if odd/≥2, else background (task-48898d06); (b) pick the block with the "most noise" as source and stamp its pattern into every other block (task-8d84fe63); (c) split by a *centered* separator into two halves, output cell = special value where both halves have their own dominant color (task-707635df); (d) output per-block where two stacked same-size halves agree (task-026adbf3). General principle: find the uniform full-line color first, then everything else is block-local logic.
- **Bbox stamping.** Find the largest non-background component; it's the "seed"; stamp its bounding box (contents verbatim, including holes) centered on every other non-background cell (task-1b7868f1). Variants: stamp the rarest color's pattern into every matching-size empty box (task-770f2daf).
- **Runs and gaps.** Fill background cells on the bounding-box perimeter of a marker color, and fill gaps of size ≤2 between consecutive markers along rows/columns (task-8625f9bc). Fill between min and max positions of the rarest color per row/column (task-5c839a47). Recolor cells between same-colored cells (task-b7641a67).
- **Lines and directions.** Extend every same-color diagonal run of length ≥2 along its diagonal in both directions until blocked (task-3b5f776f). Recolor all-solid rows/columns to a fixed color (task-47ed202e).
- **Object + line interactions.** An object slides toward a solid line until adjacent; a full line of a new color is drawn just outside the object's far side (task-77262100). Seed dots draw stubs toward bars; a mirrored line appears on the other bar (task-d4079843).
- **Morphology.** Rectangular enclosed background pockets get filled with a color; non-rectangular ones don't; a 2-tall pocket may extend one row below (task-3f4fb1a9). Small components (<3 cells) vanish; components ≥3 get their bounding box filled (task-b62da9e0).
- **Symmetry / tiling outputs.** Square input → output 2n×2n with the four quadrants being the input and its rotations (task-794e60f6). Rows mirrored and doubled, then the whole stack mirrored (task-73499f5a).
- **Downscaling.** 3×3 blocks → one cell each, by majority color among non-background cells (task-67dd046a). Intersections of "special" rows/cols (those lacking the dominant color) → output cell if 4 corners agree (task-bb30ebc2).
- **Families of twin objects.** Among translation-twins of the same shape, pick the pair by distance to a distinguished singleton, recolor the farther member (task-0f6e5a2f). Compare positions/counts of classes of objects; the discriminator is usually "which of the two similar objects is closer to / farther from the odd one out."
- **Line-gradients.** Non-background cells lie on parallel lines (check keys i, i−j, i+j for consistent single colors); then the whole grid fills by cycling those colors along the key mod the number of lines (task-2e29965a).

## Coding conventions that saved me time

- Write one generic `components(grid, colors)` BFS with 4- or 8-connectivity, `Counter` for background ("most common value"), and small helpers for bounding boxes and canonical shape keys (`tuple(sorted((y-min(ys), x-min(xs)) ...))`). Reuse them across tasks by copying from my saved programs — they are at the paths shown in the files, and your copy will have them too.
- Background = most common color, almost always. Marker/line colors = next most common, or the least common for seeds.
- Handle both orientations: rules usually apply to rows OR columns, and to objects above OR below the line. My 8625f9bc and 77262100 programs contain the pattern: detect solid rows, else solid columns, and branch on the object's side.
- Careful with clipping: when stamping or shifting, decide whether out-of-bounds cells are dropped or wrap, and check the demos to see which.

## Honest lessons from my failures

- **Duplicate submissions count.** I submitted near-identical grids under task-1b7868f1 twice and wasted attempts. Before resubmitting, change something structural, and record in a `_failed.json` which hypotheses are *already tried and ruled out* (the failed file I left there lists "untried" alternatives — do the same so future-you doesn't retry).
- **Don't overfit to a single demo pair.** If you only have 1–2 pairs, write the rule at the natural generality level (both orientations, any colors via most/least-common detection), not hard-coded to specific values. But don't over-generalize either: prefer the simplest rule that explains *all* pairs exactly, and let a third demo decide between ties.
- **When a test fails, enumerate the minimal variants** of your rule (lone cases, edge clipping, off-by-one in "strictly between" vs "inclusive", which member of a pair moves) and try them in order of simplicity. Off-by-one and boundary-case mistakes are the most common cause of "reproduces all demos but fails test."
- **If the attempt cap is near and several rules fit the demos, choose the one that is simplest and covers the test input's structure** — and if the test input's structure matches no demo, request demos.

## A closing thought

Treat each task as three artifacts: a pairs file (evidence), a program (the rule, executable), and a memory file (the lesson). The next instance of a task family will come to you with those three things already done, and you'll spend your budget on the genuinely new structure instead. That's how this stream gets easier as it goes.

Good luck — read the grid before you guess, run the code before you submit, and write down what you learn before you move on.
