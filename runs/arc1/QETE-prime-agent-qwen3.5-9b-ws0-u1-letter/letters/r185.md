## Rules of the game you should internalize

1. **Reproduce every kept demo pair before submitting anything.** Run your `transform` on each saved demo input and diff against the demo output. Zero mismatches, always. A program that reproduces all pairs but fails the test means the rule generalization is off — not that the rule is entirely wrong; refine the *edge case* handling instead of starting over.

2. **When demos don't cover a case, that's the danger zone.** The worst failure mode in the whole run: a rule verified on 10 pairs, then the test had a single dot where all demos had ≥2 dots. Eight guesses (identity, cross-shape, row-only, column-only, "everything except the dot", longer arcs, mirrored rows, dot-to-3) — all wrong. Lesson recorded there: *if your test input has a degenerate case your demos never showed, request demo pairs early rather than guessing through your attempt budget.* Most harnesses let you trade something for demos; the exchange is usually worth it when the input shape is genuinely novel relative to your demos.

3. **Negative evidence is evidence.** When a submission is rejected, record in a failed-file or memory note exactly which variants you tried and which failed (see `task-1b7868f1_failed.json`'s note: "clean anchors (13,7),(12,8) and (12,7)+0->1 untried"). Next attempt, try the *untried* neighbors of your best hypothesis, not a third guess from the same family.

4. **Beware near-duplicates.** In one failed file, two candidate outputs were identical (`sub1==sub3`) — you wasted a submission slot re-testing the same thing. Before submitting, compare your candidate outputs pairwise; never spend two attempts on the same grid.

## The recurring rule families (recognize them fast)

From the solved tasks on disk, these families came up again and again. Learn to detect them within a minute of seeing the pairs:

- **Separator-split comparison.** A full uniform row or column (all one color, not the background) splits the grid into two same-size blocks A and B. Output is same-shape: some function of A vs B cell-wise — e.g. `3` where A==B else background (task-026adbf3), or `2` where each half holds its own dominant color (task-707635df), or per-block mode/marker counting (task-48898d06, task-67dd046a's /3 downsampling, task-8625f9bc).
- **Mosaic compression.** Grid tiled by uniform separator lines; output is one cell per block, value determined by markers at block corners or stray-color counts (task-48898d06: 1 if ≥2 stray cells else bg; task-bb30ebc2: corner-marker value only if all 4 corners match).
- **Enclosed-region fill.** Flood-fill from borders to find background reachable from outside; enclosed background pockets get a fixed fill color (task-3f4fb1a9: fill with 4, plus a quirky extension where 2-row-tall pockets also recolor the wall row below). Check connectivity to the border, rectangularity, and size.
- **Shape stamping / translation.** Largest non-background component is a "seed" with a bounding box; every other non-background cell is an anchor, and the seed bbox gets stamped centered at each anchor (task-1b7868f1). Watch the details: does the stamp include 0s/holes in the bbox, does it overwrite or only fill background?
- **Line extension.** Same-color runs of length ≥2 along diagonals/antidiagonals extend in both directions until blocked (task-3b5f776f); horizontal same-row same-color pairs fill 2 between them (task-b7641a67); least-common-color "dots" get 3 strictly between min and max per row/column (task-5c839a47).
- **Arrow/anchor recoloring.** A distinctive singleton object (a thin angle with arms ≥3) acts as an arrow; among translation-twin shape pairs, the member farther from the arrow gets recolored to the arrow's color (task-0f6e5a2f). Key technique: canonical shape key = sorted relative coordinates from the component's top-left; group components by that key; act on classes of size exactly 2.
- **Periodic tiling.** Sparse colored cells consistent along a diagonal family (i+j constant, or i−j, or rows) imply the whole grid is a periodic pattern; infer period p from the observed line→color mapping (task-2e29965a).
- **Symmetry completion.** Output is a mirror/kaleidoscope construction of the input (task-73499f5a: each row becomes reverse+r, then stack reversed+original+reversed; task-794e60f6: quadrant rotations via `np.block`).
- **Shift/copy.** Shift all non-background cells down one row (task-efc2fba8); move a shape flush against a vertical separator line and draw a full-height line at its old edge (task-77262100); a band clipped at the edge gets filled where a reference band's pattern, best-shift aligned, extends past it (task-5997d753).
- **Row/column recolor.** Fully-uniform rows/cols become a fixed color (task-47ed202e); two colors map as keep-higher/lower-to-0 (task-2264bd4e).

When you see a grid, run this checklist in order: Is there a full uniform row/column? Is the background reachable from the border everywhere? Are there repeated identical shapes (compute canonical keys)? Are there two colors only, or a dominant + rare "marker" color? Is the output shape different from the input (then expect splitting/downsampling/quadrants)?

## Practical coding patterns that earned their keep

- Background = `Counter(all values).most_common(1)[0][0]`. Marker/seed color = rarest non-background (`most_common()[-1][0]`).
- Components: BFS/DFS 4-connectivity by default, but **check demos for 8-connectivity** — task-1b7868f1's seed selection needed diagonal-connected components. If 4-conn splits your "one shape" into pieces, switch.
- Canonical shape key: `tuple(sorted((y-min_y, x-min_x) for y,x in cells))`. Group components by it; classes of size 2 are "twins", size 1 is "unique".
- Helper for uniform lines: `[r for r in range(H) if len(set(grid[r]))==1]`, same for columns.
- numpy is available; `np.block`, `np.rot90`, `bincount` are handy for symmetry and tiling tasks.
- Keep programs small and pure: `transform(grid)` returns a new grid; never mutate the input list in place before copying (`[row[:] for row in grid]`).

## Test-time decision procedure

1. Extract pairs to a `programs/task-XXXX.json` file immediately (that's your permanent record).
2. Form a rule hypothesis; make it as *specific as the demos allow* but note explicitly what the demos do not determine.
3. Verify on all kept pairs; if any mismatch, refine before touching the test.
4. Look at the test input for degenerate cases your demos didn't cover (single objects, size 1, empty regions). If found — request demos first.
5. Submit; on failure, record what failed and which alternatives remain untried, then pick an untried neighbor of your best hypothesis.
