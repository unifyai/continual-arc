## How the harness works (learn this first)

Each task gives you a test input. You can request demonstration pairs, guess a transformation, and submit. Wrong submissions cost you; after ~8 wrong attempts a task is capped and lost. The most expensive mistakes I made were *submitting guesses on tests with unusual structure* before pinning the rule down. Request demos liberally early — demos are far cheaper than wrong attempts. And when you have a rule, write a `transform(grid)` Python program and verify it reproduces every kept pair before predicting the test. Almost every task I solved is stored as `programs/task-<id>.py` plus its demo pairs in `programs/task-<id>.json` — read those when you load the workspace, and keep the same convention (plus a short memory file stating the rule and status).

## The rules behind the tasks (your pattern library)

Nearly every task is one of a small family. When a new grid appears, check these in order:

1. **Count colors.** Background = most common. The rarest color is usually the "marker" or "dot". Ask: what's special about marker cells? Common answers: they delimit segments to fill; they repeat a pattern; they act as anchors.
2. **Full uniform rows/columns are separators.** Several tasks: split the grid into blocks at solid separator lines, then combine blocks. Examples I solved:
   - Two same-size halves around a centered solid line → output cell is 2 (or 3) where the halves match, else their common dominant color (task-707635df, task-026adbf3).
   - Grid of tiles separated by gridlines → output one cell per tile: a value if the tile's stray cells pass a test (odd count of a specific color, corner colors all equal), else background (task-48898d06, task-bb30ebc2).
   - Input grid = 3×3 blocks of cells; output = downsampled grid via majority of non-noise cells (task-67dd046a).
3. **Enclosed regions.** Flood-fill background from the border; any background component not touching the border is enclosed — fill it (task-3f4fb1a9: fill with 4, with a subtlety about also coloring a 1-row wall below 2-tall pockets). Variant (task-b62da9e0): a color component of size ≥3 with non-rectangular noise is "cleaned" — take its bounding box, fill with the component color, delete everything else not in such boxes.
4. **Line-drawing / sweeping.** A bar plus seed dots → extend lines from the bar through/along the dots to the grid edge, marking dots with a special color (task-d4079843). Or: extend same-color runs of length ≥2 along their diagonal (r−c) and antidiagonal (r+c) until blocked (task-3b5f776f). Or: fill background cells between two same-colored cells in a row (task-b7641a67), possibly only for gaps ≤2 plus the bounding-box perimeter (task-8625f9bc).
5. **Templates / stamping.** Find the rare-color shape, then stamp it wherever its cells would all land on background (task-770f2daf), or stamp the largest component's bbox centered on every other non-bg cell (task-1b7868f1), or stamp a pattern of 3–4 distinct colors periodically in rows/columns/diagonals (task-2e29965a: cells where (i+j)%p or (i−j)%p constant determine the color pattern; find the pattern from the nonzero diagonals and complete the grid).
6. **Analogies between twins.** Shapes occurring exactly twice as translations → one is the template, the other is recolored based on distance to a special singleton object (task-0f6e5a2f: recolor the farther twin to the arrow's color). Also "tile whose pattern differs gets copied over all other tiles" (task-8d84fe63: find the tile with the most off-pattern cells, copy its pattern to all tiles).
7. **Scale/geometry changes.** Output larger than input → expansion (task-73499f5a: each row becomes reverse(r)+r, stack rows reversed+original+reversed; task-794e60f6: 2n×2n quadrants TL=orig, TR=rot90cw, BL=rot90ccw, BR=rot180). Output smaller → downsampling by block majority or by cell-tests.
8. **Movement.** Objects slide toward a special line until adjacent, and a new line (color 8) is drawn on the far side (task-77262100). Objects shift one cell down (task-efc2fba8: shift all non-bg cells down one, clear originals). Note the trap: in one candidate I had the shift wrong by one — check exact row indices.
9. **Color remapping.** Two colors only → keep the higher color as "ink", map the lower one to 0 and everything else to the ink (task-2264bd4e). Or one color gets recolored uniformly (3, 4, or 1) based on position or structure.
10. **Symmetrize.** Mirror across an axis or make the grid symmetric about a marked feature; also compare regions left/right of a separator.

## Hard-won lessons

- **Write the program, run it on the kept demos, and diff against outputs cell by cell.** Never submit a test prediction from a rule you haven't verified on all demos. If it reproduces all demos but you're unsure about the test (unusual test structure, e.g., a lone dot where demos had several — that burned me on task-5c839a47, 8 attempts lost), request more demos *before* submitting.
- **When demos leave a case ambiguous, prefer the simplest rule that fits, but note the ambiguity in a memory file**, and if a wrong submission comes back, use the mismatch to branch: try the next-simplest variant that still fits all demos. Keep a list of variants already tried in the memory file (identity, row-only, col-only, etc.) so you never repeat one.
- **Duplicates and near-misses:** if two submissions differ by one cell, you likely have an off-by-one or a tie-break wrong. Look at the exact differing coordinates — they usually pinpoint the rule detail (e.g., inclusive vs exclusive, ≥ vs >, first vs last index).
- **Search order for the rule:** colors → connected components (4-conn for most, note one of my tasks used 8-conn; try both if 4 fails) → bounding boxes → symmetry/translation twins → full lines → periodic patterns. Grid dimensions are a big hint: equal halves, n→2n, n×n→3n×2n, thirds.
- **Output shape = the single strongest hint.** Compare output dims to input dims first, then look for which family produces that ratio.
- **Keep memories short and factual:** files, number of kept pairs, does the program reproduce all, one-line rule. Update the memory file whenever status changes. Read `harness_state.json` — it holds the same memories.
- **Two known unsolved holes:** task-5997d753 (8 attempts lost; the rule involves rare-pattern rows being recolored to 1, with a translation-alignment between two groups — my alignment scored wrong on the test; if you meet it, request demos early and consider that the fill color may depend on the pattern color) and task-5c839a47 (lone-dot behavior unknown — never submit on a degenerate test without demos).

- **Generalize beyond the literal demos, but not too far.** The right level is usually: "same structural operation, parameters read from the input" (colors, sizes, directions read from the grid, never hardcoded). All my kept programs parameterize colors and orientations this way — copy that style.
