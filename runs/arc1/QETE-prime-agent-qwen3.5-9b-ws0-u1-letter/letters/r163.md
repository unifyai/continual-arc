## The harness workflow, distilled

**Before anything else, look at the data.** When a task loads, dump the demo pairs and stare at them. Nearly every failure in this stream came from guessing a rule after 30 seconds of looking instead of 5 minutes. Check, in order:

1. **Output shape vs input shape.** Same size → it's a local recolor/fill/move task. Half size (or H//3, W//3) → downscaling by block vote (see task-67dd046a: 3×3 blocks vote on majority non-5 color). Double size → tiling/reflection (task-794e60f6: TL + rot90 + rot270 + rot180; task-73499f5a: each row becomes reverse+itself, stacked palindromically). Bigger otherwise → stamping a pattern multiple times.
2. **Is there a separator?** Full uniform rows/columns of one color are gold. They mean "split the grid" (task-026adbf3: two blocks compared cellwise; task-48898d06: gridlines divide into blocks, count strays; task-707635df: split at a *centered* separator, output where both halves hold their own dominant color). When you find separators, the answer is almost always per-block logic.
3. **Count the colors.** Background = most common. Then ask: is there exactly one rare "seed/dot" color? A "marker" color? A special output color? In this stream the output color was often a fixed small number (1, 2, 3, 4, 8) regardless of input colors — e.g. task-2264bd4e outputs 0/keep; task-5c839a47 fills 3 between dots; task-3f4fb1a9 fills 4; task-8625f9bc fills 2. Don't invent a color from the input when a small constant fits.

## Rules that keep recurring (learn these cold)

- **Fill between extremes.** Cells strictly between the min and max position of the rare color, per row/column (task-5c839a47), or between the outermost non-bg cells of each row (task-b7641a67, fills 2).
- **Enclosed background regions.** Flood-fill the bg color; regions not touching the border get recolored (task-3f4fb1a9: only *rectangular* pockets → 4, plus a 1-wide slot below 2-tall pockets).
- **Gap-filling along lines.** Same-color runs of length ≥2 extend along diagonals/antidiagonals through bg (task-3b5f776f). Gaps of size ≤2 between marker cells along rows/cols get filled (task-8625f9bc), plus the markers' bounding-box perimeter.
- **Move object to line, draw a wall.** A solid 2-line and an object: the object translates until adjacent to the line, and a full line of 8 is drawn just outside the object's far side (task-77262100).
- **Stamping.** The largest non-bg component is a seed; every other non-bg cell is an anchor and gets the seed's bbox stamped centered on it (task-1b7868f1). Or: rarest color's bbox pattern is stamped into every all-bg box of that size (task-770f2daf).
- **Lines carry colors; fill by periodicity.** If colored cells lie on lines (rows, anti-diagonals i+j, diagonals i−j), one color per line, and the lines are evenly spaced — fill the whole grid by cycling the colors with period = spacing (task-2e29965a). This is a beautiful, general pattern; check for it whenever few colored cells sit on regular lines.
- **Count strays per block.** Grid divided by uniform separator lines; each output cell = 1 (or a flag) if the block contains ≥1 (or ≥2) non-bg cells, else bg (task-48898d06, task-bb30ebc2). task-bb30ebc2's variant: output the block's corner color only where all four corner markers agree.
- **Downscale then compare.** Split into two halves; output = 3 where they agree, else the shared bg.
- **Bars and dots.** If there are 2 long same-color bars and single-cell dots: each dot draws a stub toward the nearest bar, becomes 4, and a mirrored full line is drawn across the *other* bar at the clamped index (task-d4079843).
- **Twin objects + singleton arrow.** Among exactly-twin translation pairs, pick by min distance to the singleton "arrow" object; recolor the farther one (task-0f6e5a2f). Generalize: a singleton object often selects among twins.
- **Shift everything.** Sometimes it really is just "all non-bg cells move down one row" (task-efc2fba8). Don't overthink; test the boring hypothesis first.

## Strategy that wins instances

**Verify before submitting.** You have demo pairs on disk in the `programs/` folder — load them, run your `transform`, check exact equality. A program that reproduces all kept pairs but fails the test is the common failure mode; that means the rule generalizes wrongly to the test input. Before submitting, ask: *what is unusual about the test input compared to the demos?* (e.g. a lone dot where demos had many — task-5c839a47 burned 8 wrong attempts on exactly this). Decide explicitly what your program does on that unusual case, and if you can't decide, request a demo before spending attempts.

**Demo requests are cheap; wrong attempts are expensive.** When the test input has a configuration the demos never show (single object, odd symmetry, a color missing), request a demo pair covering it. The 5c839a47 and 5997d753 files record 8 failed attempts each — all avoidable with one early demo request.

**Score hypotheses, don't pick by feel.** When a rule involves choosing an offset or alignment (task-5997d753's template shift), enumerate all candidates and score them by (mismatches, −matches, −fills) against the demos. Write the loop; don't eyeball it.

**Keep memory files consistent.** Save a memory JSON per task with: rule in one sentence, program path, pairs path, whether it reproduces all kept pairs, and *why* past attempts failed. Future you will re-read it. The `task-1b7868f1_failed.json` note format ("sub1==sub3 duplicate; X and Y untried") is exactly right — record which hypotheses are already exhausted so you never resubmit a duplicate.

**When the same task ID reappears**, load the saved program, load the saved pairs, re-verify, and only then predict the test. If the test input is a *new configuration* (different sizes, new arrangement), re-derive rather than blindly trusting the old rule — but check the old rule first; it's right more often than not.

## Concrete code habits

- bg = `Counter(v for row in g for v in row).most_common(1)[0][0]`.
- Write one `components(g, colors)` flood-fill (4- or 8-connectivity — check which by looking at the objects) and reuse it; half these tasks are "find components, classify them, apply an action to one class."
- Canonical shape key for twin detection: `tuple(sorted((y-min(ys), x-min(xs)) for y,x in cells))`.
- Guard everything: if a expected structure (separator, arrow, pair) is missing, return the grid unchanged rather than crashing.
