## First moves on any new task

1. **Dump the grid small.** Print rows compactly so you can see them as shapes, not number soup. Count colors: `Counter` over all cells. The most common color is almost always background (bg). The rarest color is almost always the "signal" — markers, seeds, dots, the object that moves or gets recolored.

2. **Find connected components** (4-connectivity first; some tasks need 8 — check my `task-1b7868f1.py` which uses 8-connectivity for the seed). For each component record: color, size, bounding box, whether it touches the border. These five facts answer most tasks.

3. **Ask: what is the same in every demo pair?** If outputs are the same size as inputs, it's a recolor/fill task. If output is smaller, it's aggregation (blocks, subgrids, counting). If larger, it's tiling/extension/mirroring. Check size first — it immediately cuts the hypothesis space by two-thirds.

## The recurring archetypes I met (with saved programs)

- **Tiling/mirror expansions** (`task-73499f5a.py`, `task-794e60f6.py`): row→reverse(row)+row, stack reversed+original+reversed; or 2n×2n = input + rot90 + rot270 + rot180. When output dims are k× or 2× input, test symmetries *first* — they're cheap to verify cell-by-cell.
- **Block aggregation** (`task-67dd046a.py`, `task-48898d06.py`): grid divided into blocks; output cell = mode of non-bg colors in block, or 1 if any stray color present, else bg. When output is ~input/3, think "summarize each block."
- **Split and compare** (`task-026adbf3.py`, `task-707635df.py`): a full uniform separator row/col splits the grid into halves; output compares cells at equal positions (equal → special color, else dominant color). If you see a solid single-color row or column, this is a top candidate.
- **Stamp/translate a shape** (`task-770f2daf.py`, `task-1b7868f1.py`): take the rare-color shape's canonical cells, stamp it at every offset where all target cells are bg, or stamp the largest component's bbox centered on every anchor cell. Very common family.
- **Fill between / fill enclosed** (`task-b7641a67.py`, `task-3f4fb1a9.py`): background cells strictly between two same-color markers in a row/col get a fixed fill color (often 2, 3, or 4); enclosed rectangular bg pockets get filled. Beware the fine print I encoded in `task-3f4fb1a9`: only *solid rectangular* pockets, and a 2-tall pocket may absorb its bottom wall only under a specific condition. Non-rectangular pockets stay unchanged — my first naive "flood fill interiors" guess failed until I added the rectangularity check.
- **Line/ray extension** (`task-3b5f776f.py`): runs of length ≥2 along diagonals extend both directions through bg until blocked. Check all four line families: rows, cols, diagonals (r−c), antidiagonals (r+c).
- **Object slides toward a barrier** (`task-77262100.py`): object moves adjacent to a solid line, then a full contrasting line is drawn on the object's far side. Handles both orientations — write the code symmetrically from the start.
- **Bbox fills and cleanup** (`task-b62da9e0.py`, `task-8625f9bc.py`, `task-aa5a69a0.py`): fill component bounding boxes, then delete everything not inside a box; or fill bg gaps of size ≤2 between marker runs *plus* the markers' overall bbox perimeter. Small details (gap ≤ 2 vs any gap; perimeter included or not) are exactly what separates correct from wrong.
- **Two-color inversion** (`task-2264bd4e.py`): embarrassingly simple once seen — map the two colors (higher stays, lower → 0 or swap roles). If exactly two colors exist, try the trivial maps before inventing geometry.

## Hard-won lessons

**Verify against every kept demo pair before submitting.** Write the check loop; run it; iterate until 0 mismatches. A program that reproduces all demos still sometimes fails the test (this happened to me on `task-5997d753` and the lone-dot case of `task-5c839a47`), but a program that fails *any* demo is guaranteed wrong. This is the single highest-value habit.

**When demos don't pin down an edge case, prefer the simplest rule.** On `task-5c839a47` a test had a single dot; I burned 8 attempts on elaborate lone-dot behaviors (identity, crosses, arcs, mirrors — all wrong). The base rule "fill strictly between min and max per row/col, else unchanged" reproduced 10/10 demos; when a test is degenerate, the degenerate case most often follows the base rule's natural boundary (i.e., "unchanged"), not a special behavior. If a test input looks like a corner case of your rule, submit the base rule applied literally.

**Request demos when stuck — they're often cheaper than guesses.** Each wrong submission costs you; a demo request gives ground truth. If after 2–3 failed hypotheses you can't distinguish two rules, request a demo targeting the ambiguity (craft the *smallest* input that discriminates, if the harness lets you influence it; otherwise just take what comes and compare).

**Keep a per-task memory file** like my `task-XXXX.mem.json`: task id, file paths, one-sentence rule, whether demos reproduce, whether solved, and *why* attempts failed. When a task reappears later in the stream (they do, or near-variants do), that file is worth more than an hour of reanalysis. Also write failed-hypothesis notes (see `task-1b7868f1_failed.json`) so you never resubmit a rejected idea.

**Write programs as data transformations, not string hacks.** Parse to lists of ints, transform, emit. Pure functions `transform(grid) -> grid` are reusable across tasks; my best files (`task-d4079843.py`, `task-5997d753.py`'s alignment search, `task-2e29965a.py`) contain genuinely general machinery: component finding, canonical-shape keys (`tuple(sorted((y-min,y, x-min,x) ...))`), translation-offset search scored by good/bad/overlap counts, and periodic-line detection (cells on each diagonal must have one color, repeating with period p).

**Score candidate alignments, don't guess them.** When a rule is "copy template A onto region B," enumerate all offsets/shifts and score each by (mismatches, −matches, −fillable) and take the best — see the `d in range(-W+1, W)` loop in `task-5997d753.py`. This pattern resolves ambiguity robustly and generalizes to rotations/reflections if you add them to the loop.

**Structural detection shortcuts that kept paying off:**
- Full uniform row/col ⇒ separator or barrier. (Note in `task-77262100`, an 8-line row appearing only in the *output* was drawn by the rule — output-only rows are part of the answer, not noise.)
- Bounding-box-perimeter membership (`len(comp) == 2*(h) + 2*(w) - 4`) ⇒ rectangle outline; hollow shapes are common.
- Exactly-two-components-of-one-color, or a color with exactly two components ⇒ twin/pair logic (compare, move, recolor the odd one — see `task-0f6e5a2f.py`, where a singleton large L-shaped "arrow" anchors the choice of which twin to recolor, by min distance to the arrow's horizontal arm).
- A color whose components are all single cells ⇒ dots/markers; dots usually seed lines between each other (min→max span, `task-5c839a47`) or get counted.
- Diagonal/anti-diagonal periodicity (`task-2e29965a.py`): if every cell on each diagonal shares one color and colors repeat with a fixed period, the answer tiles the whole grid with that assignment. Test the three line families (main diag, anti-diag, rows) in order.

**On odd/even and parity:** fills chosen by area parity (`area % 2 == 0 → 2 else 7`, `task-aa5a69a0.py`) are real. When a fill color varies between pockets, check size parity and pocket dimensions before anything fancier.

**On failed-task triage:** if you're given a task with no demos and pure guesswork, lock in the most-likely rule from structure (sizes + color counts), submit once, and if rejected, vary *one* axis at a time (fill color, inclusion of walls, orientation). Shotgun-varying wastes attempts. Track what you tried.

## Mechanical tips

- Always deep-copy: `out = [row[:] for row in g]`. Mutating the input while iterating is the most common self-inflicted bug.
- Connect helpers you'll re-type: `components(g, colors)`, `bbox(comp)`, `canon(comp)`, `most_common_color(g)`. Copy them between program files shamelessly.
- For bbox-stamping, translate by bbox *center* (`(r0+r1)//2, (c0+c1)//2`) — for even-sided shapes this is the floor of true center; be consistent between demo reproduction and test.
- When output dims differ from input, compute the mapping from the *first* demo pair exactly, and check it predicts the second pair's dims too. Dims are cheap ground truth.

You have my files at the same paths; when a new task appears, spend your first minutes scanning `programs/` for the closest archetype and adapting rather than solving from zero. Adaptation is faster and more reliable than invention.

Be systematic, verify against every pair, record what you learn, and prefer the simplest rule consistent with the evidence. Good luck.
