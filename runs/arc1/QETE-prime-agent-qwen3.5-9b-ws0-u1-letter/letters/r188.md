## The harness and the loop

You'll be given a test input grid (and possibly a handful of demo pairs) for a task like `task-1b7868f1`. Your job is to produce the output grid. General workflow that worked for me:

1. **Inspect the input.** Find the background color (most common value). Find all non-background components.
2. **Try to write a `transform(grid)` program** in `programs/task-<id>.py` that reproduces every kept demo pair exactly. If it reproduces them, it's a strong bet for the test.
3. **Save a memory file** (e.g. `memory_task-<id>.json`) summarizing the rule and paths to your program and demo pairs, so your future self can re-derive it.
4. If the rule is ambiguous on the test input specifically (e.g. a special case your demos don't cover — like a lone dot in `task-5c839a47`), don't burn 8 wrong attempts guessing exotic extensions. If the harness allows requesting demos, request them early for the ambiguous case.

## Recurring rule families (very worth memorizing)

I solved many tasks. The same families kept coming back — check these first before inventing something new:

- **Separators into blocks:** grid split by full uniform rows/columns into blocks; output aggregates per block (count stray color, majority vote, check corner equality). See `task-48898d06`, `task-bb30ebc2`, `task-67dd046a` (downsample 3x3 with majority excluding a color), `task-026adbf3` (two halves; mark where they agree).
- **Stamping/copying a seed shape:** largest non-bg component's bbox is stamped translated onto anchors (`task-1b7868f1` — beware: its test was tricky; my saved `task-1b7868f1_failed.json` has failed variants and notes like "clean anchors (13,7),(12,8) untried"). When the seed is exact, stamp the bbox *including zeros* translated by the offset from seed center to anchor.
- **Diagonal/line extension:** same-color runs of length ≥2 extend along their diagonal/antidiagonal until blocked (`task-3b5f776f`).
- **Fill enclosed background pockets** with a color (`task-3f4fb1a9` — fill 4; rectangular pockets only, with a 1-wide extension below 2-tall pockets).
- **Per-row/column dot spanning:** output color 3 strictly between min and max positions of the rarest color per row/column (`task-5c839a47`).
- **Frame/box detection:** hollow rectangles (perimeter shape, ≥3 wide and tall) get interiors filled, fill color from area parity or related signals (`task-aa5a69a0`). Also `task-b62da9e0` — fill components' bounding boxes ≥3 in some dimension, delete everything else.
- **Shifts:** shift all non-bg down one row (`task-efc2fba8`); shape moves to touch a divider line, old spot gets a marker line (`task-77262100`).
- **Mirror-and-tile constructions:** `task-73499f5a` (each row → reverse+itself, height triples: reversed/orig/reversed), `task-794e60f6` (2x2 tiling of the input with its rotations: `[[I, rot90³],[rot90¹, rot90²]]`).
- **Fill gaps between repeated marker runs** (`task-8625f9bc` — bbox of markers plus gaps between runs of ≥2).
- **Lines/rows/cols become one color** (`task-47ed202e` — uniform rows and columns become all 2). Similar: `task-2264bd4e` (two colors; keep higher, lower → 0).
- **Clipped pattern completion:** a band clipped at the edge is completed using a full reference band aligned by best shift (`task-5997d753` — 8 wrong attempts before I got it; learn: when a pattern repeats with an offset, compute best alignment shift by max overlap and fill only cells beyond the clipped copy's extent).
- **Symmetry completion:** `task-2e29965a` — colored cells lie on anti-diagonals (i+j) with periodic colors; infer period, tile the whole grid. Generalize: check each of anti-diagonal, main diagonal, row, column as the periodic key.
- **Color 3 everywhere** between two repeated copies that agree (`task-026adbf3`).
- **Row expansion:** `task-d4079843` — bars + seed dots; each dot draws a stub toward a bar and mirrors onto the other bar.

## Practical coding advice

- Use `collections.Counter` for background/mode; BFS or DFS with 4-connectivity for components (some tasks want 8-connectivity — `task-1b7868f1` used 8; check demo pairs to decide).
- Always `[row[:] for row in grid]` before mutating.
- Write the transform to be *color-agnostic* where possible: use counts, positions, shapes — not hardcoded color values — unless the demos clearly fix a semantic color (like "1 means fill-in").
- Test your program against every kept demo pair before submitting the test prediction. A program that reproduces all pairs is the single strongest predictor of success.
- When several rules fit the demos, prefer the simplest one that still reproduces them; only escalate complexity when a submission fails.

## Failure lessons to internalize

- `task-5c839a47`: 8 wrong attempts on a lone-dot test case. If your demos never show a degenerate case, don't guess — ask for demos early or pick the most conservative behavior.
- `task-1b7868f1`: near-duplicate candidate outputs. Enumerate plausible anchor choices systematically rather than resubmitting the same thing.
- `task-5997d753` and `task-0f6e5a2f`: both solved only after formalizing "which of two twin objects gets changed" precisely (e.g. distance to an arrow, alignment shift). Precisely define tie-breaking rules.

Good luck. Trust the demo pairs, write clean transforms, and save your memory files.
