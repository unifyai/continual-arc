## The harness, in brief

For each task you get a test input and can request demo pairs and submit output predictions. Your two tools are (1) writing a `transform(grid)` program in `programs/task-<id>.py` and (2) requesting demo pairs, saved to `programs/task-<id>.json`. Wrong submissions are counted against a cap, so a wrong guess costs you; requesting demos is nearly free until the cap, so when uncertain, request demos.

## The single most important lesson

The best rule is the simplest rule that explains every demo pair exactly, and it is almost always geometric or counting-based, not "clever." My successes nearly all fell into a small family of patterns:

- **Symmetry completion**: mirror rows/columns, periodic tiling by anti-diagonal (task-2e29965a: output color = periodic function of i+j), quadrants built from rotations of the input (task-794e60f6), palindromic row/col duplication (task-73499f5a: each row becomes reverse+itself, stack = reversed/orig/reversed).
- **Recolor by comparison**: split grid at a solid separator line into blocks A and B; output 3 where A==B else the common background (task-026adbf3). Or: cells where two stacked copies differ.
- **Fill/extend**: fill enclosed background pockets with a fixed color (task-3f4fb1a9); extend diagonal runs in both directions until blocked (task-3b5f776f); fill gaps of size ≤2 between markers plus the bounding box of markers (task-8625f9bc).
- **Stamp/copy a pattern**: rarest color's bbox pattern stamped into every matching empty box (task-770f2daf); largest component's bbox stamped centered at each anchor (task-1b7868f1).
- **Line-structure**: solid uniform full rows/cols are guides; output summarizes each block (task-48898d06: 1 if ≥2 strays; task-bb30ebc2: color at guide intersections); replace guide lines with 2 (task-47ed202e).
- **Move the object**: object shifts flush against a vertical line, old area becomes background, a new full line is drawn at the old edge (task-77262100).
- **Selection + recolor**: among twin-shaped pairs, pick the one farther/nearer a designated object and recolor it (task-0f6e5a2f).

So when a new task arrives, before anything else check: solid uniform lines? repeated shapes? an obvious background? symmetry? If yes to any, try the matching pattern above first — many of my saved programs are directly reusable; check `workspace/programs/` for something similar and adapt it.

## Workflow discipline

1. **Count colors.** Background = most common. The rarest non-background color is usually the "actor" (seed, dot, marker). This heuristic worked in maybe 80% of my tasks.
2. **Get demos before guessing.** One or two demo pairs turn guesswork into deduction. With demos, verify: write the program, run it on every kept pair, and only submit when it reproduces all of them. My zero-mistake tasks were exactly the ones where I verified on demos first.
3. **A program that reproduces all demos can still fail the test.** The test input often exercises a corner case the demos don't (e.g., task-5c839a47: all demos had ≥2 dots, the test had a single dot; I burned 8 attempts). When the demos are consistent but the test input has a structural feature no demo has — a lone object, an odd size, an empty region — pause and think about what the rule *should* do there, or request more demos specifically probing that case.
4. **Keep memory files.** After solving, write a short JSON note with the rule in words, the file paths, and the pair count (see my `*.mem.json` files). If a task is genuinely unsolved, record which hypotheses failed — future-you (and future tasks) benefit enormously. My note on 5c839a47 lists eight wrong hypotheses for the lone-dot case; that list is worth more than a solution.
5. **Read the saved state at the start of each task.** `programs/` holds my working programs and demo pairs; the memory files hold rules in plain words. Reuse shamelessly.

## Practical programming notes

- Write the program defensively: find background by count, find separators as rows/cols where `len(set(...))==1`, do 4-connectivity for objects unless cells clearly touch diagonally.
- Compute things like "min distance to object X" with explicit loops; don't trust subtle geometry to intuition — check it against demos.
- If no pattern matches, fall back to per-row / per-column / per-diagonal analysis: most ARC rules live along one of those axes.
- Keep a scratch counter of failed hypotheses per task so you don't resubmit the same idea with cosmetic changes — I wasted submissions that way on task-1b7868f1 (three near-identical guesses recorded in the `_failed.json` file).

## Attitude

Don't overfit to one demo pair, but do let demos kill a hypothesis fast. Simplicity beats ingenuity: if your rule needs three special cases, it's probably wrong. And when a rule looks right but the test has an element the demos never showed, that is exactly the moment to request demos rather than gamble.
