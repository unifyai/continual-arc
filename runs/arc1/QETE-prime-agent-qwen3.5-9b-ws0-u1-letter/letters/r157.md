## The workflow that works

**1. Look before you theorize.** Read every demo pair completely before writing a rule. Write a program file (`programs/task-<id>.py` with a `transform(grid)` function) and a demo file (`programs/task-<id>.json`). Save a memory file (e.g. `programs/task-<id>.mem.json`) recording the rule, the file paths, and whether your program reproduces all kept pairs.

**2. Always verify your program against every kept pair before submitting a prediction.** The single most useful habit: run your `transform` on each input in your `.json` and diff against the stored output. A program that reproduces all demos can still fail the test — but a program that fails one demo is guaranteed wrong somewhere.

**3. When demos contradict your theory, believe the demos.** Refine, don't rationalize. If a demo has a cell your rule doesn't explain, your rule is incomplete or wrong.

**4. Budget your attempts.** Each task has an attempt cap (I hit it on task-5997d753 after 8 wrong attempts — the cap was reached with a solution program in hand that simply predicted the wrong test value). If you burn attempts on near-misses, you lose the task even after solving it. If the test input looks structurally different from the demos (e.g. a lone object where demos had two), treat your first prediction as a guess and consider asking for more demos instead of guessing.

## Rules that actually occurred (learn these shapes)

From my solved tasks, here are the recurring rule families. Many future tasks are variants of these:

- **Enclosed background pockets get a fixed color (4).** Flood-fill background regions; any region not touching the grid border is filled. Often restricted to *solid rectangular* pockets — non-rectangular ones stay background. One variant: if a 2-row-tall pocket sits above a background row across its full width, that wall row also gets filled.
- **Cellular decomposition / marker grids.** Solid single-color lines (rows or columns of one uniform value) act as separators or gridlines. Common outputs: the block size, one value per block. Two variants I solved: (a) count stray-colored cells inside each block, output 1 if odd/≥2 else background; (b) find "special" rows/cols lacking the block color, output the corner-marker value where all four corners agree.
- **Compare two halves.** Grid split by a full uniform row/col into equal halves A and B: output is same shape, marker (3) where A cell == B cell, else the shared dominant color. A second variant: cell = 2 where *both* halves hold their own dominant color, else 0.
- **Downsampling.** Non-overlapping 3×3 windows: output = most common non-background (non-5) color in each window.
- **Stamping / translation.** Largest non-background component is the "seed"; every other non-background cell is an anchor — stamp the seed's bounding box translated so its center lands on that anchor. Check whether overlapping stamps overwrite or merge.
- **Symmetry assembly.** 2n×2n output from n×n input: TL = input, TR = rot90cw, BL = rot90ccw, BR = rot180.
- **Reflection doubling.** Each row → reverse(row)+row; stack = reversed, original, reversed (height triples).
- **Shifting.** All non-background cells shift down one row (or right one column); vacated cells become background. Simple, easy to miss.
- **Slide-to-line.** Object moves until adjacent to a solid separator line of color 2; a full line of color 8 is drawn just outside the object's far side. Handles both orientations and both sides — generalize, don't hardcode.
- **Gap filling.** Background cells strictly between two same-colored cells in a row (or gaps of size ≤2 between runs of the second-most-common color, plus the bounding box perimeter of all such markers) get a new color.
- **Diagonal extension.** Same-color runs of length ≥2 extend along both diagonals, filling background until blocked.
- **Line cycling fill.** Colored cells form diagonal/row lines; fill the whole grid by cycling the line colors along the perpendicular coordinate modulo the number of lines. In code: build a dict from the line key (i+j, i, or i−j) to its color, then `f(i,j) = line[key(i,j) % p]`.
- **Between-dots fill.** Rarest color = "dots"; output 3 strictly between min and max dot position per row and per column; dots themselves unchanged.
- **Dot-to-bar connections.** Two bar components of one color + single-cell dots of another: each dot draws a stub toward the nearest bar, the dot becomes 4, and a mirrored full line is drawn on the *other* bar at a clamped index derived from the dot's position along the bar.
- **Intersection tables.** Grid of blocks with line-color borders; output cell = corner marker value if the four surrounding corners are identical, else background.
- **Interpolation patterns.** Output is a periodic tiling (period = number of distinct colors); the input contains just enough anchors to determine the phase. Check i+j, i−j, and i separately for consistency.
- **Row/column domination.** If the grid has exactly two colors, keep the higher one and set the lower to 0 — or rows/columns that are a single uniform color become all-2.
- **Twin selection.** When objects come in exactly two identical shapes, some property (distance to a third "arrow" object) selects which twin is recolored.
- **L-shape/thin-angle detection.** Write a robust shape classifier: a cell whose full column-run and full row-run union equals the whole component, with the cell at a run endpoint.

## Debugging patterns that cost me points

- **Bounding box ≠ component.** A non-rectangular component's bounding box contains background and other colors. Check `len(comp) == (h_box * w_box)` when "rectangle" matters.
- **Connectivity:** decide 4-connectivity vs 8-connectivity explicitly and test both if unsure. Stamping rules often use 8-connectivity for seeds.
- **Color roles, not values.** Background = most common; marker = second most common; "dot" = least common. Never hardcode digit values unless demos force it.
- **Symmetric operations:** if a rule works top-down, check bottom-up in the demos. Objects can be on either side of a line. My slide-to-line program handles 4 cases — write all 4.
- **Clamping indices:** when a position maps onto another object's span, clamp: `min(max(x - lo, 0), hi - lo)`.
- **Zero counts:** a program reproducing demos but wrong on the test usually means the test has a structural novelty (one object instead of two, a single dot, an empty case). Make your rule degrade gracefully, and prefer the interpretation that generalizes to both.
- **Duplicate detection:** if two candidate rules produce identical outputs on all demos, don't submit both — think of a third distinguishing rule instead (I wasted attempts this way on task-1b7868f1; the winning extra hypothesis was a small offset shift).

## When stuck

- Re-examine whether the *unchanged* parts of the output matter — sometimes only one small region changes and the rest is identity.
- Count things: number of colors, sizes of components, positions modulo something.
- Try the "what is the minimal difference between input and output" question cell by cell; list every changed cell and look for a predicate (row/col parity, adjacency to color X, enclosed-ness, betweenness).
- If demos run out and you have multiple plausible rules, rank them by simplicity and by how many demo cells they explain. Submit the best one; if rejected, don't re-submit the same output with cosmetic changes.

## Final advice

Write your rule down in a memory file before coding, then code to the rule, then verify. When the program and the demos disagree, the demos win. When you solve a task, record the rule in one crisp sentence in your memory file — you'll pattern-match future tasks against those sentences faster than against code.

Good luck. Be patient, count cells, and trust the grid.
