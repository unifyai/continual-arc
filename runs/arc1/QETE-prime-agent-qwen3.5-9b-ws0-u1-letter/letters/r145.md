## The workflow that works

1. **Look at every demo pair carefully before writing code.** Count colors, find the most common (background) and least common (rare/"dot" color). Most rules hinge on these.
2. **Reproduce ALL kept demo pairs with your program before submitting a prediction.** I kept a `.json` of pairs and ran my candidate against them every time. Every failed task (task-5997d753, task-1b7868f1's early attempts) came from submitting a prediction the demos didn't pin down.
3. **If the demos leave the test case ambiguous, request more demos.** Two tasks cost me 8 wrong attempts each because a lone-dot or single-instance test case fell outside what the demos covered. If your test input has an unusual configuration (e.g., only one instance of the rare color, only one object), that's exactly when the generalization is uncertain — get a demo, don't guess.

## Recurring rule families (learn these patterns)

- **Colors:** background = most common. Rare color often the "marker/seed/dot". Common fill outputs: 1, 2, 3, 4 — the output often *introduces* a color not in the input. Don't assume outputs reuse input colors only.
- **Separators & blocks:** a full uniform row/column splits the grid. Variants: compare two halves cellwise (equal→3, else shared color — task-026adbf3); map each block to 1 if it contains stray markers (task-48898d06); tile blocks from a "template" block (task-8d84fe63); downsample blocks by majority vote ignoring background (task-67dd046a).
- **Stamps/copies:** a seed shape gets stamped at every valid location (where all its cells land on background — task-770f2daf), or stamped centered on each anchor cell / translated (task-1b7868f1: largest non-bg component = seed; every other non-bg cell = anchor; stamp seed bbox so seed center maps to anchor).
- **Slide & draw:** object moves to touch a full line of color 2, then a full line of color 8 is drawn on its far side (task-77262100). Handles both orientations.
- **Fill/gaps:** background cells between identical non-bg cells in a row become 2 (task-b7641a67); background gaps ≤2 between marker runs get filled plus the bounding-box perimeter (task-8625f9bc); enclosed rectangular pockets of background become 4, with a subtle exception for 2-row pockets whose bottom wall row is background below (task-3f4fb1a9 — read my .py; the "if pocket is 2 rows tall and row below bottom wall is background, also recolor wall" clause matters).
- **Lines & runs:** solid rows/columns become all 2 (task-47ed202e); same-color runs of length ≥2 extend along diagonals/antidiagonals until blocked (task-3b5f776f); cells strictly between min and max dot positions per row AND per column become 3 (task-5c839a47); fill 3 between min/max of rare color per row/col.
- **Symmetry:** square input → 2n×2n with TL=input, TR=rot90cw, BL=rot90ccw, BR=rot180 (task-794e60f6). Also mirror tricks: each row → reversed+original, stacked reversed/original/reversed (task-73499f5a).
- **Downshift:** shift non-background cells down one row (task-efc2fba8) — a whole task can be this simple. Check trivial hypotheses first.
- **Diagonal periodicity:** sparse diagonal lines of colored cells; the rule extends each anti/diagonal periodically to fill the whole grid (task-2e29965a: for each (i+j) or (i−j) diagonal, all cells share one color; tile it).
- **Selection by geometry:** among translation-twin pairs, recolor the one farther from a large arrow shape (task-0f6e5a2f). Occasionally the rule is about *which* object, decided by distances/sizes.
- **Two-color mapping:** with exactly two colors, higher stays, lower → 0 (task-2264bd4e). Sometimes it really is that blunt — but verify against the demo.
- **Smoothing:** small scattered noise cells get removed; components ≥3 cells get their bounding box filled; everything else → background (task-b62da9e0).
- **Hole filling:** rectangular enclosures of background inside a border get a fill color depending on area parity (task-aa5a69a0: even area → 2, odd → 7).

## Traps I fell into — avoid them

- **A rule that fits all demos can still be wrong on the test.** If any test feature is unseen in demos (single dot, one object, different parity, different orientation), pause and think about which generalization is most natural, or request a demo.
- **Don't overfit to exotic clauses.** My task-3f4fb1a9 rule needed a weird bottom-wall clause — it was real, but only after checking. Always test the *simplest* rule first; add exceptions only when a demo forces them.
- **Check exact-translation duplicates and symmetries of shapes** (canonicalize: sorted cells relative to bbox min). Many tasks group objects by identical canonical shape.
- **Dots must have distinct offsets** in line-drawing tasks (task-d4079843); permutation of bar components with "extension/either side" checks was needed there.
- **Write transform() defensively**: return the input unchanged rather than raising when no pattern matches, unless you're sure. A crash is a guaranteed wrong answer; identity sometimes isn't.

## Practical habits

- Keep `task-<id>.json` with kept pairs and a small runner to verify `transform` reproduces them; write `task-<id>.py` with a clean `transform(grid)` returning list-of-lists.
- Save a memory note with the rule in words plus file paths — future-you (and tasks reappearing as variants) benefit enormously. Several of my later wins reused earlier rules nearly verbatim.
- Name diagonal/antidiagonal keys `r-c` and `r+c` when checking line structure; use Counter for background; components via BFS/DFS 4-connectivity (occasionally 8 — check whether diagonal touching counts).
- Output size differs from input size often (halving, quartering, 3× stacking). Determine the output dimensions from the demos before anything else — they're a huge hint about the transformation type.
