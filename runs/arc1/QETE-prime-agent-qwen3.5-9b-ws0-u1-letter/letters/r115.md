## 2. Recurring rule families (learn to recognize them)

Almost every task I solved fell into one of these. Scan for them in order:

- **Separator grids:** a full row or column of one solid color splits the grid into blocks. Common rules: compare blocks cellwise (equal → 3, else background; task-026adbf3), majority vote per block after downscaling (task-67dd046a), count stray cells per block (task-48898d06), extract corner colors into a small grid (task-bb30ebc2). Also: the region *between* two blocks can be the output mask (task-707635df: AND of the two halves' nonzero masks → 2).
- **Find the minority color / the shape.** Most common color = background; the rarest non-background color is usually "the object." Find it via `Counter(...).most_common()`. Bounding boxes of connected components (4- or 8-connectivity — try both) drive half of all rules: stamp the shape elsewhere (task-770f2daf: stamp shape into every all-zero region of same size), slide shapes (task-77262100: slide object until adjacent to a line of 2s, draw a full 8-line on its far side), shift down one row (task-efc2fba8).
- **Symmetry/tile operations.** Check: 2×2 block of rotations `[[I, rot90],[rot270, rot180]]` (task-794e60f6), mirror-extend rows and stack reversed (task-73499f5a), diagonal periodic fill (task-2e29965a: cells on diagonals with consistent color, fill whole grid by `(r+c) mod L` or `(r-c) mod L`, L = number of distinct colors).
- **Enclosed regions / gaps.** Flood-fill background components from the border; those not touching the border are enclosed — fill them (color 4 in task-3f4fb1a9, but verify the fill color from demos). Gaps of ≤2 between same-colored cells in a row/column get filled (task-8625f9bc, task-b7641a67: background between two identical non-background cells in a row → 2). Interior of hollow rectangles filled by parity (task-aa5a69a0: area even → 2, odd → 7).
- **Color mapping by min/max, not by role.** In task-2264bd4e the rule was `smaller color → larger color, larger → 0` — a rule based on color *values* (sorted), not on "majority/minority." When two colors interact, try both the value-based and role-based hypotheses; value-based is often right when role-based fails.
- **Lines between markers.** Two bars of one color + dots of another (task-d4079843): draw perpendicular lines from the bar facing the dots through each dot, dot becomes 4; from the other bar draw lines at the same offsets spanning the gap. Also pairs of identical shapes: recolor the one farther from a distinguished anchor shape (task-0f6e5a2f).
- **Row/column of solid color gets recolored** (task-47ed202e: any fully-uniform row or column → 2, everything else unchanged). Cheap to test, appears often.
- **Extension/completion:** direction-continuing rays (task-3b5f776f: degree-1 cells extend outward until edge), reflections, or stamping a seed component's bounding box centered at every other non-background cell (task-1b7868f1: stamp bbox so the seed's center maps onto each anchor — note the center offset, not the top-left).

## 3. Coding patterns that save time

- Always compute `bg = Counter(all cells).most_common(1)[0][0]` first. The next rarest is usually the marker/seed.
- Flood fill (BFS/DFS) for connected components is your workhorse. Write it once, reuse it. Remember both 4-connectivity and 8-connectivity exist; when one fails on the demos, try the other before changing the rule.
- Bounding box: `r0,r1,c0,c1 = min/max` of component coordinates. Then check `len(comp) == (r1-r0+1)*(c1-c0+1)` to test "solid rectangle" vs. hollow/L-shaped — this distinction mattered in task-3f4fb1a9 (only solid pockets were filled).
- Build output as `out = [row[:] for row in grid]` and modify — never build from scratch unless the output size differs (some tasks change dimensions! task-707635df halves the height, task-794e60f6 doubles both, task-73499f5a triples). **Always check output dimensions against input dimensions in the demos before anything else.** Same size → in-place transformation. Different → tiling, downscaling, or extraction, and the ratio tells you which.
- When a rule has a free parameter (an offset, a direction, a threshold), don't guess — search over all values and pick the one reproducing the demos. If multiple work, add a principled tiebreak (e.g., smallest, or the one matching an extra property). My task-d4079843 program enumerates permutations of bars and returns the first consistent assignment; that "search and verify" shape is a good template.

## 4. How to use my files

- `programs/task-<id>.py` — runnable `transform(grid)` for solved tasks. If a new task looks similar, copy and adapt; adapting a verified program is far safer than writing from scratch.
- `programs/task-<id>.mem.json` and memory entries — the *rule in words*, often with caveats ("only rectangular pockets," "tiebreak by larger size," "handle both orientations"). Read the caveats; they encode failures I already made.
- `task-1b7868f1_failed.json` — my recorded wrong attempts for one task, with a note about which variants were tried. When you fail a task, write your own such note: what was tried, what remains. It prevents loops.
- `task-5997d753` memory says `solved: false` with a post-mortem. Read it: the lesson is *a rule that fits all demos can still be wrong* — when demos underdetermine the rule, prefer the simplest symmetric generalization and double-check edge cases (partial shapes, boundary interactions) before submitting.

## 5. Submission discipline

- One wrong attempt per rule refinement. If a submission fails, the harness usually tells you only pass/fail — so change exactly one hypothesis at a time and record it.
- Before submitting, run your program on the demos and diff against expected outputs **cell by cell**. Print the first mismatch location if any. "Looks right" is not verification.
- If a rule can't reproduce the demos at all, don't submit a partial fit — request more demos if the harness allows, or think again. A wrong submission spent on a rule you know is incomplete is a wasted attempt.
- Prefer rules that explain *why* each cell changed, not rules that hardcode positions or colors seen only in the test-adjacent context. Test grids always have new colors, sizes, and placements.

## 6. Final habits

- Keep memory entries short but complete: task id, file paths, the rule in one or two sentences, and "reproduces all kept pairs: true/false." Future-you reads these.
- Trust arithmetic over intuition: count cells, compute parities, list offsets. Most ARC rules are simple combinatorics wearing a costume.
- When stuck for a long time, step back and ask: is the output the *same size*? are colors *renamed*? are shapes *moved/copied/deleted*? is something *counted*? Nearly every rule is one of those five verbs applied to one of the structures above.
