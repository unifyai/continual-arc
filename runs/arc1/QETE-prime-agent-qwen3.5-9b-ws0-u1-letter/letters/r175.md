# The workflow, step by step

**1. Read every saved file before acting.** Your workspace persists across turns. `programs/*.py` are my solved programs, `programs/*.json` hold kept demo pairs, `memories/` and `*.mem.json` files hold rules. If the current task matches a saved task ID (e.g. the task hash appears in a memory file), **load the saved program and rerun it on the new test input.** Many of my tasks were "returning instances" of tasks I had already solved — the saved program reproduced every kept pair and solving the new test was free, 0 wrong attempts. This is the single highest-value habit: check for a saved program for THIS task hash first, always.

**2. Count the colors and find the background.** Almost every task has a dominant background color (most common cell value). Nearly every rule starts with "background = most common color." Compute it first.

**3. Extract structure: components, bounding boxes, lines.** For non-background cells, find 4-connected components. For each, note its bounding box, size, shape (normalized cell pattern — cells shifted so top-left is (0,0)). Most rules are relationships between components: "the largest one," "two of the same shape," "the one touching the border," "the singleton dot."

**4. Before submitting, verify against every kept demo pair.** I kept a discipline: run my candidate `transform` on every input in the task's `.json` and check it reproduces the stored output exactly. If it doesn't, don't submit — revise or request demos. A program that reproduces all kept pairs is right about the rule far more often than one built from a single pair.

**5. Save your work.** When a program reproduces all kept pairs, write the program to `programs/task-<hash>.py`, write the pairs you kept to `programs/task-<hash>.json`, and write a memory file recording the rule in one sentence. This is what makes future instances free. Record also what was *unresolved* (see 5c839a47 below) — future-you should not re-burn attempts on a known dead end.

# Rule families I kept seeing (memorize these shapes)

- **Stamping / copying.** One large "seed" component; every other non-background cell is an anchor; the seed's bounding box is stamped (as-is, including holes and zeros) so that the seed's center maps onto each anchor. (task-1b7868f1, 8 kept pairs.)
- **Pockets / enclosure.** Find background-colored regions *not touching the grid border* (flood fill from edges identifies the "outside"). Fill enclosed rectangular background pockets with a fixed color (often 4). Special cases: a 2-tall pocket may also fill the wall row below it. Non-rectangular pockets are left alone. (task-3f4fb1a9.)
- **Line/separator subdivision.** Full uniform rows/columns (single repeated color) split the grid into blocks. The output is one summary value per block: e.g. 1 if the block contains ≥2 stray-color cells, else background (task-48898d06); or the color at the intersection of marker rows/cols where 4 corners agree (task-bb30ebc2); or the downsampled majority of a 3×3 block (task-67dd046a). The trick is finding the separator rows/cols: a row where `len(set(row))==1` (and usually the separator color differs from background).
- **Two-block comparison.** Grid split by a centered separator into halves A and B of identical shape. Output compares them cell-by-cell: one color where they agree, another where they differ (task-026adbf3, task-707635df: 2 where *both* halves have their own dominant color, else 0).
- **Extension / rays.** Runs of length ≥2 of the same color on diagonals extend along their own diagonal until blocked (task-3b5f776f). Rows with ≥2 dots of the rarest color get 3-filled strictly between min and max (task-5c839a47). Gaps ≤2 between same-color markers along rows/cols get filled, plus the marker bounding-box perimeter (task-8625f9bc).
- **Singleton + twin pairs.** One unique singleton component is a "target"; among shape classes that occur exactly twice, pick one member by a distance/size criterion and recolor it to the target's color (task-0f6e5a2f).
- **Symmetry doubling.** Output = reverse+concatenate each row (width doubles), stacked reversed+original+reversed (height triples) (task-73499f5a); or 2n×2n output with TL=input, TR=rot90, BL=rot270, BR=rot180 (task-794e60f6). Check: if output dims are exactly 2× or 3× input dims, think mirror/rotation tiling immediately.
- **Periodic tiling from sparse hints.** Nonzero cells lie on anti-diagonals (i+j constant per color) — infer the period and tile the whole grid (task-2e29965a). Also check rows, columns, and diagonals (i−j) for the same property: each line holding exactly one color, values repeating with a period.
- **Shift by one.** All non-background cells move down one row; originals clear (task-efc2fba8). Verify which direction and whether row 0 or the last row becomes background.
- **Move-to-line.** An object shifts horizontally/vertically to become flush against a full line of a marker color; its old area becomes background, and a full line of a new color is drawn at the object's old far edge (task-77262100).
- **Color remap.** With exactly two colors, keep one and zero/replace the other — often the lower value becomes background (task-2264bd4e).
- **Pattern propagation.** A rare color's bounding-box pattern is stamped into every empty box of that size (task-770f2daf); or a block from one region is copied onto all matching regions (task-8d84fe63: find the block with the most anomalies and copy its per-index values everywhere).

# Hard-won lessons (each cost me wrong submissions)

1. **A single kept pair is a hypothesis, not a proof.** With only one pair, prefer the *simplest* rule consistent with it, and verify your test prediction mentally against it before submitting. If the test grid is structurally unlike the demo (e.g. demo has many dots, test has one), be suspicious the rule's edge case is being probed.

2. **The 5c839a47 lesson (8 wrong attempts):** when your rule handles a common case but the current test presents a rare case (e.g. exactly one dot), the edge-case behavior is unknown. Don't guess through it — if the harness lets you request demo pairs, request them, specifically ones containing the rare configuration. And record the failure modes you've already burned so you never retry identity, row-only, or column-only variants of a dead rule.

3. **Recolor vs. copy ambiguity.** When only some cells of a shape change color, determine *exactly* which cells (all? inner? the ones matching a criterion?). "Fill the bbox" and "fill only actual component cells" differ — check which the demos show. Similarly, when stamping, note whether 0-cells inside the seed bbox get stamped or skipped. My 1b7868f1 program stamps the bbox as-is including 0s; that detail was load-bearing.

4. **Distance criteria need care.** "Nearest bar" tasks: compute distance from the *dot* to the bar's span (clamped: distance is 0 when the dot is within the span's range on the cross-axis), then read the along-axis index and mirror it onto the other bar, clamping to that bar's extent (task-d4079843).

5. **Anchors are often *every* non-background cell outside the seed, not a separate list.** Don't over-engineer; the anchors may include cells that were themselves part of other stamped copies' inputs. Work from the *input* grid for anchor positions and stamp into an output copy.

6. **Bounding-box tricks:** check whether the object touches the border; whether its bbox is full-width/full-height; whether components of the same color form a thin angle/arrow (arms ≥ 3 in one direction). Shape classification (L, line, rectangle-ring `len(comp)==2*(h+w)-4`, solid bbox) recurs constantly.

7. **When output dims ≠ input dims:** immediately compute the ratio. ×2 and ×2 (mirror), ×3 (mirror-stack), 2n×2n (quadrant rotations), or block-summarization (H//k × W//k). The dims alone usually identify the family before you look at a single value.

8. **Duplicate submissions are wasted attempts.** I once submitted two candidates that differed by a trivial offset and both were wrong the same way (1b7868f1). If two hypotheses differ in one parameter, reason about which value the demos force *before* spending a submission; prefer requesting a demo over guessing between near-twins.

9. **Keep your pair files clean.** Only store pairs you've actually been shown and verified. Contaminated or hallucinated demo labels will poison future-you's verification loop.

10. **Write the rule sentence, not just the code.** Memory entries like "fill enclosed rectangular background pockets with 4; extend 1-wide slot below 2-tall pockets" are what let future instances be solved in one turn. A code file alone doesn't tell you *why* it works or where its boundary conditions are.

# A compact starter kit (pseudocode you'll want every task)

```
counts = Counter(all cells); bg = most common
comps = 4-connected components of non-bg cells  (use 8-conn only if 4-conn fails to explain demos)
for each comp: bbox, size, canonical shape key = sorted((r-r0, c-c0))
group comps by shape key -> twin pairs / unique singletons
full_rows = rows where len(set(row))==1 ; full_cols likewise
```
Start every unknown task by running this and *looking* at the numbers: how many comps, their sizes, whether sizes cluster, whether separators exist. The family usually announces itself within a minute of looking.
