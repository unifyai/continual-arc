**How to actually find the rule**

Most of the tasks I solved reduce to a small family of patterns. Learn to check these quickly, roughly in this order:

- **Background + components.** Background is almost always the most common color. Find connected components (4- or 8-connectivity — try both; the task decides). Then ask: what distinguishes the components from each other? Size, shape, count of a color, whether they touch the border, whether one is "alone" of its color. Typical outputs: recolor the farthest/nearest component to some color, extend something, fill enclosed regions.
- **Enclosed regions.** Flood-fill the background from the grid border; anything unreached is enclosed. Tasks 3f4fb1a9 and aa5a69a0 were exactly this: fill enclosed background pockets (one filled with 4, one filled with a parity-chosen color). Beware the refinement I missed at first: sometimes pockets *with a qualifying shape* (e.g., exactly 2 rows tall) also trigger a change in the wall below them. If identity fails, look for pockets that *almost* qualify.
- **Lines and separators.** Full uniform rows/columns are huge. They split the grid into blocks (48898d06: output per-block 1 if odd stray count, else background; bb30ebc2: output color at intersections of "marker" rows/cols when the four corners agree). A centered solid line means the output is one half, cellwise compared to the other half (026adbf3: 3 where halves agree; 707635df: 2 where each half holds its own dominant color).
- **Periodicity / tiling.** If colored cells are constant along diagonals (i+j) or anti-diagonals (i−j), the answer is a periodic tiling; infer the period and extrapolate (2e29965a). If the output is bigger than the input, suspect mirror-and-stack or quadrant composition: 73499f5a was `row[::-1]+row` per row and `reversed + original + reversed` vertically; 794e60f6 was TL=input with the three rotations in the other quadrants; 8d84fe63 tiled a block pattern periodically.
- **Drawing lines between markers.** Runs of ≥2 same-color cells extended along their own direction until blocked (3b5f776f: diagonals). Gaps between markers in a row filled with a color (b7641a67, 8625f9bc — note 8625f9bc *also* filled the marker bounding-box perimeter; the gap rule alone wasn't enough). Dots drawing stubs toward bars, with a mirrored line on a second bar (d4079843 — the clamped-index mirror was the hard part).
- **Stamp/translate.** One large "seed" component; every other non-background cell becomes an anchor where you stamp the seed's bounding box (1b7868f1). The trick that finally worked: stamp the bbox *as-is including interior background/zeroes*, translated so the seed's bbox center lands on the anchor.
- **Color remapping.** Sometimes it's just: keep color A, map color B to 0 (2264bd4e), or map every instance of one pattern color to another (b7641a67's "fill with 2", 67dd046a's downsample where 5 is ignored). When outputs look like inputs with only color substitutions, diff the two grids cell-by-cell and build the map explicitly.
- **Move-against-a-line.** 77262100: the shape translates to sit flush against a full vertical line, its old area becomes background, and a second full line in a new color is drawn where the shape's far edge used to be.

**A tie-breaking habit that paid off repeatedly**

When several components/pairs are candidates, "closest to a distinguished object wins, with the *other* member of the pair acted on" showed up twice (0f6e5a2f: among exact-translation twin pairs, pick the pair whose nearer member is closest to the arrow; recolor the farther member). I lost attempts by acting on the near member when the rule was to act on the far one, and vice versa. When a rule says "nearest X does something," check whether the something happens *to* X or *to its partner*.

**Things that cost me attempts — don't repeat them**

- **Lone/unusual cases in the test.** My worst failure (5c839a47) was a rule solid over 10 demo pairs ("fill 3 strictly between min and max dot per row/col") whose test grid had a *single* dot. Every extension I guessed was wrong: identity, drawing a full cross, row-only, col-only, everything. The lesson: if the test input has a structural property no demo had (a lone dot, a component count of 1, an odd grid size), **stop and think before submitting**, and don't burn the attempt budget on a combinatorial guess of extensions. If demos are cheap to request in your harness, request them when a structural edge case appears.
- **Duplicate submissions.** On 1b7868f1 I burned attempts on variants that were effectively identical (a 0↔1 offset is not a new rule; neither is a clean anchor vs. an anchor implied by symmetry). Track which hypotheses you've already submitted — I keep a `failed` list in the task json with a note of *untried* hypotheses. Before submitting, re-read that note.
- **Special-casing colors.** Write rules in terms of roles (most common, least common, the color of the largest component), not hardcoded digits. The next instance of the same task often permutes colors and sizes. My 48898d06 and 0f6e5a2f programs are role-based and reused cleanly; anything hardcoded would not have been.
- **Padding/trimming assumptions.** Check whether the output can differ in size from the input early (downsampling, splitting in halves, tiling). Deciding this in the first two minutes avoids rewriting everything later.

**Concrete code patterns worth copying**

- Background: `Counter(v for row in g for v in row).most_common(1)[0][0]`.
- Components: a simple BFS/DFS over cells of a color set; keep one utility you trust, supporting 4- and 8-connectivity via a flag.
- Canonical shape key for matching components by shape: `tuple(sorted((y-min_y, x-min_x) for y,x in cells))`. Group by this key to find twin pairs.
- Run-length logic per row/column: gather indices of a color, then iterate `zip(idx, idx[1:])` for gaps.
- Always operate on `out = [row[:] for row in g]` and write into `out` while reading from `g`, so fills don't cascade into each other mid-pass. I got burned by in-place fills until I made this automatic.

**When stuck, diff**

The single most useful debugging move: for a demo pair, print the cells where input ≠ output. Most rules are "cells in some derived set get recolored to some derived color." If you can state the changed-cell set precisely in words for two or three pairs, the program writes itself. If the changed set looks like "the intersection of a row-condition and a column-condition," you're likely looking at a separator/line task.
