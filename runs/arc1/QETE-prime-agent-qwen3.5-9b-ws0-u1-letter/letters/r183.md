## 1. The harness workflow

For each task you must produce a Python program with a `transform(grid)` function (grid = list of lists of ints) and save a JSON of demo pairs you were given. Save memory files when a task is solved or clearly unsolved — I left examples of the formats (`task-XXXXX.mem.json`, `*_status.json`). A memory entry in `harness_state.json` persists across tasks; update it. The most valuable habit: **keep a JSON of the demo pairs you were given, and a program that reproduces every kept pair.** Before you submit a prediction on a test input, run your program on every kept demo pair and check it reproduces all of them. Almost every one of my wrong submissions came from submitting a guess that my own program could not reproduce.

## 2. The universal first moves

Almost every ARC task here is about a background color, some objects, and a rule. Start every task the same way:

1. Count colors. The **most common color is almost always background (bg)**. Find the rarest non-background color too — it is usually the "marker," "seed," or "dot" that drives the rule.
2. Find connected components (I wrote both 4-connected and 8-connected versions; many tasks use 8, e.g. task-1b7868f1 uses 8-connected in its components function — note that). Compute each component's bounding box, size, and shape signature: `tuple(sorted((y-min(y), x-min(x)) for cells))`. Shape signatures let you find **translation twins** — the same shape occurring twice, which is the core of recolor/select tasks (see task-0f6e5a2f).
3. Look for **full uniform rows or columns** (a row where `len(set(row))==1`). These are separators and gridlines. Many tasks are "grid divided by lines into blocks" (task-48898d06, task-bb30ebc2, task-026adbf3, task-707635df). If a centered separator splits the grid into two equal halves, compare the halves cell by cell.
4. Check simple symmetry operations early: mirror rows (`r[::-1]+r`), tile in 3x3 with rotations (task-794e60f6 is literally `np.block` of four rotations), periodic tiling by anti-diagonal `i+j` (task-2e29965a), shift everything down one row (task-efc2fba8). Cheap to test, often the answer.

## 3. The rule families I actually saw

Memorize these patterns; a future task will likely be a variant:

- **Fill enclosed pockets**: bg region not touching the border, and rectangular, gets filled with a fixed color (task-3f4fb1a9, color 4). Non-rectangular pockets are left alone.
- **Extension/rays**: a run of ≥2 same-colored cells on a diagonal extends along that diagonal until blocked (task-3b5f776f). Same idea horizontally/vertically: fill gaps of size ≤2 between markers in a row/column (task-8625f9bc), or fill strictly between min and max marker per row and column (task-5c839a47 — careful: a *single* dot in a row means that rule doesn't apply there; this subtlety cost me a task).
- **Stamp/copy a seed pattern**: the largest (or rarest) non-bg component is a template; every other non-bg cell is an anchor where the template is stamped, centered on it (task-1b7868f1, task-770f2daf, task-8d84fe63's block-copies). Stamping the full bounding box including interior zeros is important — copy the bbox as-is, not just the component cells.
- **Object moves relative to a line**: a shape shifts to touch a full-height line of another color; a new full line is drawn at the shape's old edge (task-77262100).
- **Select-and-recolor among twins**: find pairs of identical shapes; one gets recolored based on distance to some special object (task-0f6e5a2f: recolor the twin *farther* from a big L-shaped "arrow").
- **Counting within blocks**: grid split into blocks; output cell = 1 if a stray color appears ≥1 or ≥2 times in the block, else bg (task-48898d06 used n≥2; a sibling task used odd count — check against demos which threshold).
- **Mosaic/intersection**: output is a small grid whose cells are the colors at intersections of guide rows/columns (task-bb30ebc2).
- **Downsample**: divide the grid into k×k blocks (k=3 common); output cell = most common non-bg color in the block (task-67dd046a).
- **Color mapping**: two colors only — keep the higher, map the lower to 0 (task-2264bd4e). Simple, don't overthink.
- **Horizontal/vertical growth of rows into full lines**: rows or columns that are a single repeated color become all 2 (task-47ed202e).
- **Line + dot geometry**: dots connect toward bars with stubs and mirror lines on other bars (task-d4079843 — complicated, but shows the family: bars, seeds, distances, clamped indices).
- **Fill between same-color pattern repeats**: gap between two occurrences of a pattern gets a filler color (task-b7641a67).
- **Diagonal offset matching**: the same shape appears twice with a fixed cyclic/linear offset; fill what the shifted copy predicts beyond the other copy's edge (task-5997d753). I failed this task 8 times before solving it — the lesson: when two copies of a pattern coexist, compute the offset per row from *maximal overlap*, then trust it exactly.
- **Noise removal**: components of size ≥3 (or with big bounding boxes) are real; everything else is noise deleted to bg (task-b62da9e0). Also: rectangle outlines keep interiors filled (task-aa5a69a0 — fill inside a rectangle outline with 2 or 7 depending on area parity).
- **Resize**: output dims = dims of one half after a split, or w/3, h/3, or a block subgrid (task-707635df, task-73499f5a). Always derive output size from the demo pairs first — **output dimensions are the strongest clue in the whole puzzle.** If the output is much smaller, think blocks/downsample. If same size, think in-place recolor. If bigger, think tiling/stamping.

## 4. Method for solving an unseen task

1. Read the demo pairs. First compare **sizes**. Then diff input vs output cell by cell: which cells changed? What color did they become? What did they have in common (bg? between two markers? inside a shape? on a line?)? The set of changed cells tells you the rule more than anything else.
2. Write the simplest hypothesis that explains pair 1. Test on pair 2. If it fails, don't patch with special cases — the rule is usually clean and symmetric. Special-casing is how I lost tasks.
3. If cells change to a single new color, ask: is the new color determined by the object (its own color), or fixed (task-chosen, like 2, 3, 4, 7)? Fixed colors often have meaning: 4 = fill color in several tasks, 2 = fill/gap color, 3 = "between" color, 1 = completion color, 8 = drawn line. These are conventions of this slice of ARC, not guarantees, but they bias you correctly.
4. When a test input is unlike the demos (e.g. demos always had ≥2 markers, test has 1), **do not guess blindly**. If the harness lets you request demo pairs, request them early — a lone-edge-case guess burned 8 attempts on task-5c839a47. Guessing identity for an unseen configuration is rarely right; the rule almost always still applies in some graceful way, or there's a second clause you haven't seen. Request data.
5. Track your wrong attempts. If a task has cost you several failed submissions, stop, save a memory file describing what you tried (I did this in `task-5c839a47_status.json` with a list of failed hypotheses), and switch strategy rather than re-guessing variants of the same idea.

## 5. Coding discipline

- Write pure-Python `transform(grid)` — no file I/O inside, no prints. Keep it deterministic.
- Always copy: `out=[row[:] for row in grid]`, and compute the rule from the *original* grid while writing to the copy. Mutating while reading is my most common bug.
- Reuse my component-finder code from task-1b7868f1.py or task-b62da9e0.py — it is short and correct. Bounding boxes and shape signatures I already wrote in task-0f6e5a2f.py.
- Verify `transform` against every kept pair programmatically before predicting. If any pair fails, the rule is wrong — fix it, don't submit.

## 6. Mindset

You are smaller than I am; you will not out-reason exotic rules on the first look. Your advantages are discipline and procedure: size analysis first, diff second, simplest hypothesis third, reproduce-all-pairs check fourth, memory fifth. The tasks are mostly clean and mechanical — one object type, one operation, one selection criterion. When your hypothesis feels complicated ("recolor unless, except when, plus a clamp"), it is probably wrong; keep simplifying until one sentence describes the rule.

Do not rush to submit. A wrong submission is expensive; a memory file is free. Leave your own notes the way I left mine — the next model after you will read them, exactly as you are reading this now.

Good luck. Work slowly, diff carefully, and trust the demos.
