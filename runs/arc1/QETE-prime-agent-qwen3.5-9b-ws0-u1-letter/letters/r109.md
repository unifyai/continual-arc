## The workflow that works

1. **Save everything to the right paths.** Put demo pairs in `workspace/programs/task-<id>.json` (as a list of `{"input": ..., "output": ...}`), your program in `task-<id>.py`, and a memory note in `memory_task-<id>.json` or the harness memory store. When you return to a task (or it reappears), your saved files are the only continuity you have. A memory note with the *rule in one sentence* is worth more than the code itself — I could re-derive a program from a crisp rule statement far faster than from reading code.

2. **Verify before you submit.** Never submit a prediction from a program that doesn't reproduce every kept demo pair exactly, cell for cell. Write a small loop: run `transform` on each input, compare to the output. If any pair fails, your rule is wrong (or incomplete) — go back to the grid, don't patch blindly.

3. **Ask for demos when unsure** (if the harness allows demo requests). It's cheaper to spend a demo request than a wrong submission. I ran out of attempts on task-5997d753 partly because I committed too early on a rule that fit the demos but not the test. Fitting all demos is necessary, not sufficient — prefer the rule that is *simplest and most principled*, not the one with the most special-cases that happens to fit.

4. **Keep a failed-attempts note.** When a submission fails, record what you tried (see `task-1b7868f1_failed.json` — I logged which anchor variants were untried). On retries, test the *untried* variants, not permutations of the failed one.

## Rule patterns I've confirmed (study these)

These are the transformations I actually solved. Notice how many are "structural" — about connectivity, bounding boxes, separators — not about specific colors.

- **Color remaps by role**: min→max, max→0 (task-2264bd4e). Check min/max of the color set first before assuming majority/minority roles.
- **Line/row-column detection**: a row or column with a single uniform value is a *separator* or a *line* (tasks 47ed202e, 026adbf3, 707635df, 8d84fe63, 48898d06). Splitting the grid into blocks separated by uniform rows/cols is a hugely reusable move. 026adbf3: split into two blocks, output 3 where they agree. 707635df: AND of two regions' nonzero masks. 48898d06: per-block parity of a stray color.
- **Enclosed regions**: flood-fill background components; ones not touching the border are "pockets" (3f4fb1a9, aa5a69a0). Fill them (color by parity in aa5a69a0's case). Watch for special cases — pockets that are rectangular vs. non-rectangular, or that absorb an adjacent wall row.
- **Stamping / translation of a seed shape**: find the largest or distinctive non-background component, get its bounding-box pattern, and stamp it (or its bbox fill) at anchor points (1b7868f1, 770f2daf, b62da9e0). The anchor is usually every other non-bg cell or bbox centers.
- **Lines drawn through dots from bars** (d4079843): perpendicular projection, offsets preserved, dot becomes a special color (4).
- **Symmetry / self-tiling**: 794e60f6 is a 2×2 block of rotations; 73499f5a is reverse+double rows and mirrored stacking. When output dims are exact multiples of input dims, try tiling/mirroring/rotation constructions immediately.
- **Downsampling**: 67dd046a — divide into 3×3 blocks, take the mode of non-noise color. When output is roughly input/3 (or /2), think block-mode or block-majority.
- **Diagonal periodicity** (2e29965a): cells on diagonals r+c or r−c mod L carry a repeating pattern; try both directions, derive the period from the clue cells.
- **Movement toward a line** (77262100): object translates until adjacent to a special line, then another line is drawn on the far side. Efc2fba8: a block shifts down one row unless already "stable" (gap below == gap above + 1).
- **Gap filling** (8625f9bc, b7641a67, 5c839a47): fill background gaps of small size between markers, or cells strictly between two markers in their row/column.
- **Inheritance/copy from a reference**: 8d84fe63 — one block has content; tile it into all blocks. 5997d753 — full-pattern rows act as reference rows for other rows.

## How to find the rule fast

- **Compute the obvious statistics first**: grid dims in/out, color histogram (which is background — usually the mode), number of distinct colors, whether output dims differ (if they do, it's tiling/downsampling/extraction; if not, it's a recolor/move/fill).
- **Diff the pairs** cell by cell. List every changed cell and its (old → new). The rule lives entirely in that diff. Group changes by color, by row, by column, by component.
- **Look for geometry**: bounding boxes, straight lines, symmetric placement, distance relationships. My hardest solves came from measuring distances (e.g. 0f6e5a2f: pick the twin-shape pair whose member is nearest the arrow shape, recolor the farther twin).
- **Write general helper code once and reuse**: BFS components (4- and 8-connectivity — check which one the task uses; some tasks connect diagonally, see 1b7868f1 which needed 8-connectivity), bounding box, mode color, uniform-row/col finder, bbox-fill. I rewrote these too many times; you can copy them from my saved .py files — read `task-b62da9e0.py`, `task-aa5a69a0.py`, `task-026adbf3.py`, and `task-d4079843.py` before starting; they contain clean versions of most helpers.

## Pitfalls I hit so you don't have to

- **Don't special-case your way to a demo fit.** If your rule needs three ad-hoc exceptions, it's probably wrong. Find the *reason* the exception exists.
- **Connectivity matters**: 4-connectivity failed me until I switched to 8. Try both if components look "broken".
- **Background is not always 0** — it's the most common color, whatever its value. And "noise" colors (single stray cells) often exist to be ignored or to serve as a parity/count signal (48898d06).
- **Check orientation**: horizontal vs. vertical versions of the same rule are common (bars, separators, object movement). Write your rule to handle both from the start — d4079843 and 77262100 both needed this.
- **Don't resubmit the same idea with cosmetic changes.** If attempt 1 failed, the failed JSON should tell you what's genuinely untried.
- **When the cap is near**, submit your best-supported hypothesis, not a wild guess — and make sure it at least reproduces all kept demos.

You are a small model, and that's fine: this game rewards careful diffing and simple structural rules far more than cleverness. Read the saved files, reuse the helper code, verify everything, and write down the rule in one sentence every time you solve something.

Good luck — the stream is kinder than it looks if you measure before you guess.
