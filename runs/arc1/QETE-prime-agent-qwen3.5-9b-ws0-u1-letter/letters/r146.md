## 1. The workflow that works

For each new task:

1. **Look at every demo pair before writing any code.** Do not pattern-match on the first pair alone; the third pair often kills a hypothesis built from the first.
2. **Name the roles of the colors first.** Almost every task has: a *background* (the most common color), one or more *markers/objects*, and sometimes a *separator* (a full row or column of one color). Compute the most common color; it is almost always background. Compute counts per color; the rarest is often the "dot" or "seed" or "rare shape."
3. **State the rule in one plain sentence before coding.** If you cannot, you are not ready. Write that sentence into a memory file so your future self (and the grader of your reasoning) can see it.
4. **Write a `transform(grid)` function in `programs/task-<id>.py` and verify it reproduces every kept demo pair.** If it does not reproduce all of them, the rule is wrong, not the demo. Go back and look at the pair that broke.
5. **Save the demo pairs you keep in `programs/task-<id>.json`** and a memory note in `programs/task-<id>.mem.json` or `memory_task-<id>.json`. Include the *rule sentence* in the note. In my run, half my value came from re-reading my own rule notes on later tasks.
6. **Request demos when a test input looks structurally different from the demos** (e.g., demos always had two dots, the test has one). This is the single most important timing lesson: request *early*, not after burning wrong attempts. I lost task-5c839a47 entirely because the demos all had ≥2 dots and the test had one; I spent 8 wrong attempts guessing what a lone dot should do instead of asking for demos on turn one.

## 2. Rule families that recur

These are the families I met; when a new task arrives, check them in this order:

- **Recolor by role.** Simple color maps: lower color → 0, higher stays (task-2264bd4e); uniform rows/columns → 2 (task-47ed202e); cells between two identical markers in a row → 2 (task-b7641a67); enclosed rectangular pockets of background → 4 (task-3f4fb1a9).
- **Fill between dots.** The rarest color's cells act as endpoints; fill strictly between the min and max endpoints along each row and column (task-5c839a47). Beware lone dots — see §5.
- **Extend runs.** Same-color runs of length ≥2 on diagonals/antidiagonals extend through background until blocked (task-3b5f776f). Same idea horizontally/vertically elsewhere.
- **Tile the grid.** 2n×2n outputs made of the input and its rotations (task-794e60f6: TL=input, TR=rot90, BL=rot90ccw, BR=rot180); row r → reverse(r)+r, stacked block, reversed block, block (task-73499f5a); diagonal stripes assigned by key(i,j) mod p (task-2e29965a — scan for anti-diagonal, row, and main-diagonal consistency).
- **Blockify / miniaturize.** Grid cut by full uniform separator rows/columns into blocks; output one cell per block: parity of a stray color (task-48898d06), mode color ignoring a fixed color (task-67dd046a, 3×3 downsampling), corner-equality of a 4-neighborhood template (task-bb30ebc2). Find separators as rows/columns where `len(set(row))==1`.
- **Split and compare halves.** A centered solid separator splits the grid into two same-size blocks A and B; output compares them cell-by-cell (3 where equal, else the blocks' common color) — task-026adbf3; or 2 where both halves have their own dominant color at the same spot — task-707635df.
- **Stamp / translate a seed shape.** Largest non-background component is the seed; every other non-background cell is an anchor; stamp the seed's bounding box centered (or corner-aligned) at each anchor (task-1b7868f1). Or stamp at every offset where the stamp's cells all land on background (task-770f2daf). The difference between "anchor = every non-bg cell" vs "every non-bg cell except the seed" is exactly the kind of thing the 4th or 5th demo pair disambiguates — look for it.
- **Two same-shape objects, pick one by a relation to a third.** Singleton large thin angle = arrow; among exact-translation twin pairs, recolor the member *farther* from the arrow's horizontal arm (task-0f6e5a2f). Generalizes: "two copies of a shape + one special object ⇒ keep one, recolor the other."
- **Object slides to a line.** Object moves until adjacent to the solid 2-line; a full 8-line is drawn just outside the object's far side (task-77262100). Handle both orientations and both sides.
- **Gap-filling with a fixed color.** Background gaps ≤2 between consecutive markers on any row/column, plus the markers' bounding-box perimeter → 2 (task-8625f9bc).
- **Dominant component survives.** Components of ≥3 cells keep their color and get their bounding box filled; everything else becomes background (task-b62da9e0).
- **Fill a rectangular ring's interior** with a color determined by area parity: even → 2, odd → 7 (task-aa5a69a0). Detect hollow rectangles: `len(comp)==2*(h)+2*(w)-4` for bbox h×w with h,w≥3.
- **Shifts.** Everything non-background shifts one row down, original cleared (task-efc2fba8). Note "shift all rows down" vs "shift cells down" differ when the grid has a background color that should also move; check the demos.

## 3. Coding habits that pay

- Write small helpers once and reuse: `background(g)` via Counter; 4-connected components (BFS/DFS); bounding box of a component; `sep_rows/sep_cols` detection; symmetric comparisons.
- Always work on `out = [row[:] for row in grid]` and only write to `out`, reading from `grid`. Reading and writing the same array causes order-dependent bugs that mimic "wrong rule."
- Test your program against the saved JSON pairs programmatically before submitting. A program that reproduces 9/10 pairs means the rule is *almost* right — find the tenth, don't submit.
- Wrap risky rules in graceful fallbacks? No — do not. If your rule doesn't fire on a test input, returning the input unchanged is usually wrong; it's better that you notice the mismatch. But do make the code fail loudly for yourself during development.

## 4. Choosing between candidate rules

When two rules both fit the demos:

- Prefer the simpler one; but check whether any demo pair distinguishes them. Often one extra demo pair does.
- Prefer rules that generalize symmetrically (both orientations, both sides, both parities). Asymmetric rules that fit are usually wrong unless the asymmetry is visible in the demos.
- If you have a choice between "recolor something" and "move/resize something," look at whether output dims equal input dims. Same dims ⇒ recolor/fill almost surely. Different dims ⇒ tiling, downscaling, splitting, or stacking.

## 5. Known traps

- **Lone dots / edge cases.** If every demo has ≥2 of the seed and the test may have 1, ask for a demo before submitting. Same for 0-cell patterns, empty blocks, and grids where a separator is missing.
- **"Almost reproduces" means wrong.** One mismatched cell out of thousands is still a rejection.
- **Don't resubmit the same idea with a cosmetic tweak.** If a rule fails the test twice, request a demo or re-derive from the demos rather than guessing a parameter (I once burned the attempt cap re-choosing an offset d).
- **The bounding box of markers includes non-marker colors sometimes** (holes, 0s). Task-1b7868f1's stamps had to reproduce the seed's internal 0s exactly. Check whether interior cells of a seed are part of the shape or background.
- **Diagonal connectivity vs 4-connectivity.** Some tasks treat diagonal-touching same-color cells as one component; most don't. If component counts look off by small amounts, try 8-connectivity.
- **Which color is "background" can be a trap** when a separator color (like 6 in task-8625f9bc's first pair) is very frequent. Use structure (full uniform lines) to identify separators before declaring the most common color the background.

## 6. Memory hygiene

- Keep one memory file per task with: rule sentence, file paths, pairs kept, and reproduction status. Update it when you learn something (including failures — write down which hypotheses were rejected and why).
- Before starting a new task, glance at your old rule notes: several of my later solves were near-instant because an earlier task had the same skeleton (e.g., blockify-by-separators appeared at least three times in different clothes).

## 7. A final word

The tests are not adversarial; they are consistent with the demos. When your prediction feels like a coin flip, that is a signal that you have not extracted the real rule, not that the task is random. Go back to the demos, count colors, count components, count separator lines, and state the rule in one sentence. Most tasks in this stream reduce to one of the families above plus one twist, and the twist is usually visible in a pair you glanced at too quickly.

Work carefully, verify before submitting, ask for demos early, and write everything down.
