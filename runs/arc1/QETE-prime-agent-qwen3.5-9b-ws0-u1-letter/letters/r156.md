## 1. The workflow that works

Each task gives you a small set of input→output demonstration pairs. Your job is to (a) infer the rule, (b) write a `transform(grid)` function in `programs/task-<id>.py` that reproduces every kept pair, and (c) predict the output for a test input. Structure your work like this:

1. **Look at the grids before theorizing.** Find the background color (almost always the most common color). Find the objects (non-background components).
2. **Name the objects.** Are they rectangles? Lines? L-shapes? Single cells (dots)? How many of each? Counting things ("exactly two of this shape", "one large + many small") is the single most predictive observation.
3. **Compare in and out cell by cell.** Diff the grids. What changed? What did NOT change (just as important)? Which colors appeared/disappeared?
4. **Write the program** to reproduce the demos, run it on all of them, verify 0 mismatches, then apply to the test input.
5. **Save your demo pairs** to `task-<id>.json` and write a memory file summarizing the rule. This costs nothing and pays off if you see the task family again.

## 2. Concrete rules I've already solved — recognize them fast

Many future tasks will be variants of these. When you see a matching structure, reuse the logic immediately:

- **Stamp/copy a seed shape.** If there's one big "template" object and many small "anchor" objects: find the largest non-bg component (the seed), then at each other non-bg cell (anchor), stamp the seed's bounding box translated so the seed's center lands on the anchor, keeping the seed's exact pixel pattern including holes. Anchors themselves get overwritten by the stamp.
- **Enclosed pockets.** If the background color forms regions not touching the border, and they're solid rectangles, they get recolored (in my case to 4). Flood-fill background components from the border first — anything unreachable and rectangular gets filled. Non-rectangular enclosed pockets may be deliberately left alone; check the demos.
- **Odd-count blocks through gridlines.** If solid uniform full rows/columns divide the grid into blocks, and each block contains stray cells of a third color: output block = special value (e.g. 1) if the stray count meets a threshold, else the background.
- **Two halves compared.** If a full uniform row/column splits the grid into two same-size halves A and B: output cell = special color (e.g. 3) where A and B agree, else the common color at that position. Or (another family): cell = 2 where BOTH halves have their own dominant color.
- **Singleton + twin pairs.** If there's a unique object of a color (e.g. an L/arrow) and among the other colors exactly two identical-shape (translation-twin) objects exist, the rule is often "recolor the twin farther from the singleton with the singleton's color" (or nearer — check demos; distance can be to the singleton's arm/line, and ties broken by object size).
- **Slide-to-line.** An object moves toward a solid line (color 2) until adjacent on its own side; then a full line of color 8 is drawn just outside the object's far side (overwriting only background).
- **Quadrant mirror-rotations.** n×n input → 2n×2n output: TL = input, TR = rot90cw, BL = rot90ccw, BR = rot180.
- **Row/col run extension.** Least-common color's cells ("dots"): fill with 3 strictly between the min and max dot per row and per column; dots themselves unchanged.
- **Fill between markers.** Background cells between two same-colored cells in a row (or gaps of size ≤2 between marker cells along rows/columns, plus the bounding-box perimeter of all markers) get a special fill color.
- **Bboxes of ≥3-cell components.** Fill each multi-cell component's bounding box with its own color; delete everything else (small strays go to background).
- **Diagonal run extension.** Same-color runs (length ≥2) on diagonals (r−c) and anti-diagonals (r+c) extend in both directions along that diagonal, filling background until blocked by non-background or the edge.
- **Separator + threshold counting** (e.g. rows that are a single repeated color become all 2; likewise columns).
- **Downshift.** All non-background cells shift down one row; the vacated top becomes background. (Also seen: shift down by one — check direction against demos, this family flips around.)
- **Complete periodic patterns.** If colored cells lie on diagonal lines or rows and every line of the family carries exactly one color, complete the pattern: cycle the line colors along the perpendicular coordinate modulo the period.
- **Mosaic downscale.** Divide the grid into k×k cells; each output cell = most common non-ignored color in that cell (I ignored color 5; find which color to ignore from frequency/structure).
- **Zoom-by-majority into blocks with gridlines** — related to the above; read the block structure from uniform separator rows/cols.
- **Mirror-palindrome tiling.** Each row becomes row+reversed(row); rows stack as reversed order + original + reversed again (output height 3× input, width 2× for the row-doubling variant seen with square inputs). There's also a variant producing a different arrangement — always verify with demos.

Don't assume the test instance matches the demos exactly in every corner case (see "lone dots" below). But do assume the *core* rule is stable — it's the edge cases that vary.

## 3. Recurring micro-patterns (learn these by heart)

- **Background = most common color.** In nearly every task. `Counter(...).most_common(1)[0][0]`. Second most common is often the "marker" color.
- **Special output colors are 1, 2, 3, 4, 8** far more often than anything else. If a new color appears in outputs, it's usually one of these.
- **Solid uniform rows/columns** (`len(set(row))==1`) are structural: they're separators, lines to slide to, or the objects to recolor.
- **Bounding boxes** of components are the workhorse: compute min/max row/col of a component, check `len(comp) == area` for solid rectangles, check `len(comp) == perimeter` for hollow rectangles/frames.
- **Flood fill, 4-connectivity**, is right for most object extraction. Use 8-connectivity only when demos demand it (check whether diagonal-touching cells belong to one object).
- **Translation twins:** canonicalize a shape as `tuple(sorted((y-min(ys), x-min(xs)) for y,x in comp))` and group by that key. Groups of size exactly 2 are the interesting ones.
- **Components should be computed on single colors** first (`g[ny][nx]==c`), and on the union of non-bg colors only if the task treats touching different-colored objects as one object.

## 4. The traps that cost me submissions

**Trap 1: The lone/degenerate case.** My worst losses came here twice. In one task, all demos had ≥2 dots per row/col, and the test had a *single* dot — my extension rule predicted nonsense and 8 attempts failed before I burned out. In another, demos had the pattern color in full rows; the test had a partial row and my fallback was wrong. **Mitigation:** when the test input contains a configuration that never appears in the demos (a lone object, a different count, a different orientation), your rule is undefined there. Before guessing, ask for more demonstrations — the harness lets you request demos, and one extra demo is cheaper than a wrong submission. If you can't get demos, pick the *most conservative* prediction for undefined cases: usually identity (output = input) or background-only, and reason about which is more plausible given the rule's "spirit."

**Trap 2: Overfitting to demo-specific constants.** A fill color seen in demos (e.g. 4) is likely stable; but a *direction*, a *side*, a *tiebreak order* might not be. When demos show a rule holding for 4+ pairs across varied configurations, trust it for the test. When demos all share one configuration (e.g. all objects above the line), the test may flip it — write the rule symmetrically (handle both sides, both orientations) even though the demos only show one.

**Trap 3: Writing the rule before checking it against every demo.** Always run your `transform` on all kept pairs and diff. A rule that reproduces 9/10 demos is wrong in some detail; fix it, don't submit.

**Trap 4: Duplicated demo submissions.** If the harness rejects a submission as a duplicate of a previous failure, that attempt still counts against your cap. Track which hypotheses you've already tried (keep a `task-<id>_failed.json` note like I did, listing untried variations) so you never burn an attempt re-testing the same idea.

**Trap 5: Attempt caps are real.** Some tasks cap you (I hit caps at 8 wrong attempts). Budget: identify the rule carefully first, submit the highest-confidence program. If wrong, don't thrash — enumerate the *distinct* plausible variants (off-by-one, opposite side, swapped tiebreak) and try them in order of plausibility, tracking which you've tried.

## 5. Coding hygiene that saved me

- Write `transform(grid)` to take a list of lists of ints and return the same. Don't mutate the input; copy rows first: `out=[row[:] for row in grid]`.
- For components, a simple BFS/DFS with a `seen` matrix is fine at these grid sizes (≤30×30).
- Keep a scratch JSON of the demo pairs (`task-<id>.json`) — it makes verification scripts trivial and preserves the data across turns.
- When a rule involves "distance from A to B," decide: Euclidean or Manhattan, cell-to-cell or shape-to-shape, and *which* part of A (arm? center?). Verify against demos; these choices are where rules actually differ.
- Off-by-one on "strictly between": `range(min+1, max)` excludes both endpoints — that's usually what "between" means.
- Symmetry checks: if your rule says "the object above the line," immediately ask "what if it's below?" and code both branches. Same for left/right, rows/columns.

## 6. How to think when nothing matches

If none of my catalogued rules fit:

1. **Diff first, theorize second.** List every cell that changed and every cell that didn't. Changed cells' colors and positions often spell out the rule.
2. **Check invariants.** Is the output the same size as the input? (If smaller: downscaling/blocking. If larger: tiling/rotation/stamping.) Are all output colors present in the input? (If a new color: there's a fixed mapping or a special fill.)
3. **Look for geometry.** Lines, rectangles, diagonals, symmetry. ARC rules are almost always geometric: copy, mirror, translate, fill, count, extend.
4. **Look for logic.** If geometry fails, think in terms of conditions: "cell becomes X if it's enclosed," "if the count is odd," "if two things agree." My agreeing-halves and odd-count tasks were logical, not geometric.
5. **Consider motion.** Objects moving toward/away from a landmark (line, corner, another object) until touching, then some side effect.
6. **Consider grouping.** Cells grouped by row, column, diagonal, connected component, or shape. The rule usually acts on whole groups.
