## The harness workflow that works

1. **On seeing a task, first look for prior memory.** A file named `memory_task-<id>.json` or an entry in the harness state may mean the task (or a near-variant) was seen before. Reuse the recorded rule and program immediately — several of my fastest solves came from this.

2. **Keep demo pairs in `programs/task-<id>.json` and the solver in `programs/task-<id>.py`.** Write a `transform(grid)` function. Then **verify it reproduces every kept pair before submitting.** Many of my wrong submissions would have been caught by a quick self-check. "Program reproduces all kept pairs" is necessary but not sufficient — the test input can still differ in kind — but it catches most coding bugs.

3. **Request demos when the rule is ambiguous, and request them early.** My biggest failure, task-5c839a47, had a test grid with a *single* rare-color dot. My rule ("fill strictly between min and max dot per row/column") worked on all 10 demo pairs — every demo had ≥2 dots — but every lone-dot variant I guessed was wrong. I burned 8 attempts. Lesson: **if your rule has an edge case the demos never exercise (one object, zero objects, ties, degenerate shapes), spend a demo request to pin it down before submitting, not after.**

4. **Track wrong attempts and stop guessing wildly.** When a task accumulates failures, record in the memory file *which hypotheses were rejected* (see `task-1b7868f1_failed.json`: "sub1==sub3 duplicate; clean anchors untried"). Never resubmit a duplicate.

## Recurring rule families (learn these cold)

These cover a large share of tasks. Recognizing the family quickly is worth more than cleverness.

- **Stamping/tiling:** find the seed (largest non-background component, or rarest color), then stamp its bbox/shape at every valid position — positions where the footprint is all background, or anchored at each non-background cell (`task-770f2daf`, `task-1b7868f1`).
- **Enclosed pockets:** background regions not touching the border get recolored (usually 4). Watch for extra conditions — pockets of a particular height absorbing a wall row, only *rectangular* pockets (`task-3f4fb1a9`).
- **Hollow rectangles:** outline components whose interior is background; fill interior by a property of the area (parity: even→2, odd→7 in `task-aa5a69a0`).
- **Line completion:** dots + bars; draw lines through dots from one bar, copies from the other (`task-d4079843`). Also: fill background gaps ≤2 between markers along rows/cols and the marker bounding-box perimeter (`task-8625f9bc`).
- **Slide/touch:** an object moves until it touches a marked line, then a full new line is drawn on its far side (`task-77262100`).
- **Symmetrization:** output = input mirrored/rotated and stacked (`task-794e60f6` quarter-rotation assembly; `task-73499f5a` mirror-rows + triple stack). Check row-reversal + concatenation first.
- **Grid subdivision:** uniform separator rows/cols split the grid into blocks; output summarizes each block (count of strays, mode color, equality between two halves: `task-48898d06`, `task-026adbf3`, `task-67dd046a` downscale-by-3 mode).
- **Diagonal/pattern completion:** cells defined by a modular condition on r+c or r−c; try `key(r,c) % L` where L = number of distinct colors (`task-2e29965a`).
- **Comparison of two blocks:** equal cells → marker color; else background (`task-026adbf3`).
- **Simple recolor:** keep the "higher" color, zero the other (`task-2264bd4e`). Sometimes it really is this easy — check simple hypotheses first.

## Practical heuristics

- **Background = most common color**, almost always. Rarest color = the "agent" or seed. Compute components with 4-connectivity first; try 8-connectivity if shapes look broken.
- **Try cheap hypotheses in order:** identity → recolor map → mirror/rotate → shift by one (`task-efc2fba8` was literally "shift all rows down one") → count/parity fills → shape stamping.
- **Scan for full uniform rows/columns** early; they're usually separators or targets.
- **Verify, then submit.** Run your transform on every kept pair. If it fails, don't submit — debug.
- **When demos and test disagree in kind** (e.g., all demos have multiple objects, test has one; demos have 2 colors, test has 3), that's a signal to request a demo, not to guess.
- **Write the rule into your memory file in plain English**, not just code. Future-you (and the task list) reads that first. Include which edge cases remain unverified.

## On failure

Some tasks will beat you; I have several unsolved with 8 wrong attempts each. When that happens: record the rejected hypotheses, the rule that fits the demos, and the shape of the test case. That record is the only thing that carries forward. Cap your losses — the attempt limits are real.
