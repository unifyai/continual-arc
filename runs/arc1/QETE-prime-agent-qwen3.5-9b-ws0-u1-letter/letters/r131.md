## The harness, first

- You work on one ARC task at a time in the same workspace. Anything you write to disk (under `.../state/workspace/` and the memory store) survives and will be handed back to you in later tasks — that's how this letter reaches you. So write files deliberately: name them after the task ID (`task-<id>.py`, `task-<id>.json`, `task-<id>.mem.json`), because future-you will find them by name.
- The `.json` demo files are your ground truth. The most valuable habit in this whole game: **before you submit a prediction, run your program on every kept demo pair and verify it reproduces them exactly**. Every one of my failed tasks (e.g. `task-5c839a47`, `task-5997d753`) happened because the program matched all demos but I couldn't distinguish competing hypotheses for the test. Demos matching is necessary, not sufficient.
- When two rules both fit the demos and they disagree on the test input, that's when you lose. If the harness lets you request more demos, **request demos early, before exhausting submission attempts**, especially in exactly this ambiguous situation. I wasted all 8 attempts on `task-5c839a47` because the test had an edge case (a single dot) that no demo covered, and I burned submissions guessing. The lesson is recorded in memory: if you suspect an edge case, ask for a demo that covers it.
- There is an attempt cap on wrong submissions. Never burn attempts on guesses; always have a reason to believe a guess is more likely than the alternative, or don't submit yet.

## Recurring rules I saw (study these patterns — ARC reuses motifs)

1. **Background-component fill**: find the most common color; flood-fill components of it; components not touching the border are "enclosed" — recolor them (to 4 in `task-3f4fb1a9`, to 2 or 7 in `task-aa5a69a0` depending on parity of area). Watch for extra clauses: in `3f4fb1a9` a 2-row-tall pocket also absorbed its bottom wall row, but *only* rectangular pockets qualified.
2. **Anchor/seed stamping** (`task-1b7868f1`): the largest non-background component is the seed; every other non-background cell is an anchor; stamp the seed's bounding box translated so its center lands on the anchor, clipped to the grid. Two versions of this rule differ in whether the anchor cell's own color is preserved or overwritten — check carefully in the demos.
3. **Grid partition tasks**: full uniform separator rows/columns split the grid into blocks. Variants I met:
   - `task-48898d06`: output one cell per block; 1 if ≥2 stray-color cells, else background.
   - `task-bb30ebc2`: corners of separator lines vote; cell is the corner color if all four corners agree, else block background.
   - `task-026adbf3`: two same-size halves; output 3 where cells match, else the blocks' common color.
   - `task-707635df`: two halves; output 2 where *both* halves have their respective dominant colors.
   - `task-8d84fe63`: one block is the "complete" pattern; copy it onto all other blocks.
   Notice these are all "compare blocks cellwise and emit a small verdict" — when you see a uniform separator, your hypothesis space is small; enumerate verdict functions systematically (equality, parity, counts of strays, corner agreement).
4. **Symmetry / tiling**: `task-73499f5a` (rows mirrored+double, stacked in palindrome order); `task-794e60f6` (2n×2n quadrant = input, rot90, rot90ccw, rot180); `task-2e29965a` (diagonal cyclic pattern: value depends on `(r+c) mod L` or `(r−c) mod L`, where L = number of distinct nonzero colors — my saved solver tries both keys and checks consistency). Also: values repeating along diagonals with period = number of colors is a cheap check worth running on any "fill the zeros" task.
5. **Line-drawing** (`task-d4079843`): two bars of one color, scattered dots of another; draw perpendicular lines from the bar facing the dots through each dot (dot becomes 4), and from the far bar draw lines at the same offsets spanning the gap. When you see "bars + dots", enumerate: project onto perpendicular, use offsets relative to bar start, keep colors from the demo.
6. **Object + line** (`task-77262100`): an object slides until adjacent to a full line of 2s; a full line of 8s is drawn just outside the object's far side. Directions both ways; handle row and column orientation.
7. **Rare-color shape stamping** (`task-770f2daf`): take the least common color's cells as a shape; place it at every offset where all its cells would land on 0.
8. **Between-extremes fill** (`task-5c839a47`): for the least-common color, fill cells strictly between the min and max positions in each row and each column with 3. Verified on 10/10 demos. The unresolved question is the single-dot case — if you inherit this task again, do NOT retry identity/cross variants blindly; think about what a single dot could anchor (maybe nothing happens, maybe a full row — but all of those were already rejected).
9. **Row shifts** (`task-efc2fba8`): every non-background cell shifts down one row, top row becomes background. Trivially cheap to test.
10. **Per-row/col marker recolors** (`task-47ed202e`, `task-b7641a67`): uniform rows/cols become 2; a background cell flanked by identical non-background neighbors in a row becomes 2. "Flanked by X" patterns are common and cheap to test.
11. **Downscale / count blocks** (`task-67dd046a`): 3×3 downscale; each output cell is the most common non-5 color in its 3×3 block. Generic version: if output dims are exactly input dims divided by k, this is the first thing to try.
12. **Two-color inversion** (`task-2264bd4e`): with exactly two colors present, keep the higher one, map the lower to 0 (or vice versa per demos). If a grid has exactly two colors, always check pure remaps first — they cost nothing.

## Strategy heuristics

- **Order of hypothesis testing** for an unseen task: (a) pure color remaps; (b) output shape hints — if output dims differ from input, that constrains everything (halving → downscale-count; doubling → mirror/tiling/quadrants); (c) background-component analysis (enclosed regions); (d) separators/block comparison; (e) shape-based rules (components, bboxes, symmetric shapes); (f) exotic composed rules last.
- **The background color is almost always the most common value.** Second most common is often the "marker". Least common is often the "seed/dot". Programs that hardcode colors fail on new instances of the same task — always derive colors from counts (see `task-8625f9bc.py`, `task-77262100.py` for the pattern).
- **Write reusable helper code.** My files with clean, generic helpers (component finding, bbox, separators, offset voting) got reused across tasks with small edits. Copy `task-d4079843.py`'s `comps_of` and the count-derived background pattern into anything new.
- **Record what failed, not just what worked.** My `_failed.json` and memory notes with "untried hypotheses" lists were the difference between repeating a mistake and moving on. When you make a wrong submission, immediately write down: which rule you submitted, what the plausible alternatives were, and which you haven't tried.
- **Duplicates and near-duplicates matter** (`task-1b7868f1` notes): if two demo pairs are nearly identical, the difference between them isolates the rule's edge case. Read them against each other, cell by cell.
- **Count, then verify, then submit.** A program that reproduces 4/4 demos is a strong prior but not proof. If the demos don't cover an input property your test has (single object, odd size, no separator, etc.), treat your rule as *unvalidated* on that axis and prefer the simplest behavior that's consistent.

Good luck. The stream rewards patience and bookkeeping more than brilliance.
