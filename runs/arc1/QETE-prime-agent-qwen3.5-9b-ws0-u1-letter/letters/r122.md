## The workflow that works

1. **Read the demos slowly.** Compare input and output cell by cell. Ask: which cells changed? Which colors exist? What is the background (most common color)?
2. **Write your rule in words FIRST**, then code it. If you can't state it in one or two sentences, your code will be garbage.
3. **Verify against every kept pair before submitting.** Run your `transform` on each demo input and check the output equals the demo output exactly. Never submit a program you haven't verified — an unverified guess wastes a submission.
4. **Save memory files** for every task: the rule in plain words, the file paths, and whether the program reproduces all pairs. Future-you reads these. Write rules that generalize, not just "cell (3,5) becomes 7."

## The rule taxonomy I found (study these shapes)

Almost every task is one of these; check them in this order:

- **Downshift:** all non-background cells shift down one row (task-efc2fba8). Trivially common.
- **Stamp/tile:** a seed shape (largest non-bg component, or the rare-color shape) is stamped at every offset where its cells land on background/0 (task-770f2daf), or translated so the seed's center maps onto each anchor cell (task-1b7868f1). Components are found with 4-connectivity usually — but check 8-connectivity if 4 fails.
- **Enclosed pockets:** background regions not touching the border get filled with a fixed color (often 4); sometimes only *rectangular* pockets qualify, with special cases for 2-row-tall pockets (task-3f4fb1a9).
- **Line geometry:** a full separator line of one solid color splits the grid; compare the two halves cellwise (equal → 3 or 2, else the shared color) (task-026adbf3, task-707635df). Or a 2-line attracts an object until adjacent, and a full 8-line is drawn on the object's far side (task-77262100).
- **Between-ness:** a background cell becomes a new color if it lies strictly between two dots of the rare color in its row OR column (task-5c839a47, task-b7641a67).
- **Block compression:** grid divided by solid separator rows/cols into blocks; each block reduces to one cell via majority/count of stray colors (task-48898d06, task-67dd046a is 3×3 downsample with mode excluding one color, task-bb30ebc2 reads values from cell corners).
- **Color remap:** with exactly two colors a<b, sometimes a→b and b→0. Careful: the *role* (majority/minority) can be the wrong generalization; the min/max relation was right on task-2264bd4e. Test both hypotheses against demos.
- **Symmetry/kaleidoscope:** output = mirrored/reversed concatenations of input rows or the whole grid (task-73499f5a: row r becomes reverse(r)+r, stacked reversed/forward/reversed; task-794e60f6: 2×2 block of the grid and its three rotations).
- **Diagonal tiling:** colored clue cells lie on diagonals; find period L, build P from residues of (r+c) mod L or (r−c) mod L, try both keys, fill everything (task-2e29965a).
- **Bounding-box filling:** each connected component of size ≥3 gets its bbox filled with its color; everything else becomes background (task-b62da9e0).
- **Gap closing:** background gaps of size ≤2 between consecutive marker cells along rows/cols get a fill color, plus bbox perimeter (task-8625f9bc).
- **Arrow + twins:** the single large thin angle is an arrow; among translation-twin shape pairs, recolor the member *farther* from the arrow (task-0f6e5a2f).
- **Shape extrapolation:** rare small pattern stamped wherever the rest of the shape matches (task-770f2daf).

## Hard-won debugging lessons

- **When your rule fits demos but fails the test, the failing cell tells you the boundary of the rule.** I lost a task (5997d753) after 8 wrong attempts because I kept patching instead of re-deriving. If you're on attempt 3+ and still patching, stop. Re-derive from scratch. Ask: what single principle explains ALL demos including the ones that almost work?
- **Distinguish near-miss hypotheses.** E.g. "fill all enclosed bg regions" vs "fill only rectangular enclosed regions" — construct a tiny synthetic input that distinguishes them and check against a demo that shows the difference.
- **Don't duplicate submissions.** Keep notes (I keep a `*_failed.json`) of tried variants so you never resubmit the same thing.
- **Watch for near-duplicate demo grids** — they often differ in exactly the cell that discriminates two hypotheses. Diff them.
- **Background detection:** most common color is almost always the background. Rare color = the pattern/marker. But occasionally (770f2daf) the rule keys on the *least* common nonzero color.
- **Connectivity:** try 4-adjacency first; if components look wrong, try 8-adjacency (task-1b7868f1 needed 8).
- **Special-case honesty:** if you need an ugly special case to fit demos (like "2-row pockets also absorb their bottom wall"), state it explicitly in memory — it may be the actual rule, or it may be a sign you've misread the task.

## Practical harness tips

- Write grids as JSON lists of row-lists when saving demos; the harness format for `cand*.json` / task files is a list of rows of integers.
- When unsure between two predictions, pick the one consistent with *all* kept pairs; if both are, pick the simpler rule.
- Keep each task's files named `task-<id>.py` and `task-<id>.json` in `programs/`, and a memory note — this stream rewards accumulation.
- Counting/Counter, deque BFS, and simple loops are enough. You rarely need numpy, but `np.block`/`np.rot90` make symmetry tasks trivial.

## Mindset

You are small; be systematic instead of clever. Enumerate the taxonomy above, test hypotheses in order of simplicity, verify every submission, and write down what you learn — including failures. The tasks you've never seen will mostly be variations of the families above: look for the background, the rare color, the separator line, the enclosed region, the translation twins, or the mirror. One of them is almost always the key.
