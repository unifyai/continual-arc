## 3. General strategy for unseen tasks

**Step 1 — classify the transformation type.** Most ARC tasks fall into a small number of families. Check in this order:

1. **Pure geometry**: rotations, reflections, translations, tilings, scaling, downscaling (block→majority color), mirroring. Check output dimensions first: same size (usually recolor/fill), double/triple size (tiling or repetition), fraction (downscale).
2. **Recoloring**: usually a per-cell rule — between two marks, inside a shape, on a line, adjacent to something, or value-based (min/max, most/least common).
3. **Stamping/tiling**: find one canonical object or block, copy it to positions determined by anchors, references, or grid structure.
4. **Object motion**: translate toward/touching a line or marker; draw a new line relative to the moved object.
5. **Comparison**: two blocks compared cellwise (equal→one color, different→another, or AND/OR of masks).
6. **Fill/enclosure**: flood-fill regions that don't touch the border, or regions bounded by specific colors.

**Step 2 — identify roles by statistics, then test alternatives.**
- Background = most common color. Marker = least common or second-most-common.
- But remember task-2264bd4e: if frequency-based roles fail, try **value order** (smallest/largest color) — it's a different hypothesis space.
- Components: 4-connected vs 8-connected matters; try both if 4-connected fails.

**Step 3 — verify every kept pair.** If a rule works on 4 demos but fails on 1, the rule is wrong even if the failure is "small." Look for what distinguishes the failing pair. My task-3f4fb1a9 rule has exactly this kind of exception built in (2-row pockets absorb the wall below only conditionally) — such conditions are often real but must be *justified* by the demos, not invented to force a fit.

**Step 4 — predict the test input conservatively.** The rule must be the one the demos support; don't extrapolate beyond it. When two rules both fit all demos, pick the simpler one (Occam) — but if a prior wrong attempt with the simpler rule was rejected, the correct rule is often the *more specific* variant (e.g., with the conditional clause).

## 4. Practical coding patterns

Reusable snippets that show up constantly — copy them from my saved programs:

- Background: `Counter(x for row in g for x in row).most_common(1)[0][0]`
- Connected components (4-conn): BFS/DFS with a `seen` matrix — see task-3f4fb1a9.py or task-aa5a69a0.py.
- Canonical shape key: `tuple(sorted((r-min_r, c-min_c) for r,c in comp))` — use it to group objects by shape (task-0f6e5a2f.py).
- Uniform separator rows/cols: `len(set(row))==1` per row, similarly per column; then group remaining rows/cols into consecutive "bands" (task-8d84fe63.py, task-026adbf3.py).
- Bounding box fill: compute min/max of component coordinates, fill the rectangle (task-b62da9e0.py).
- For numpy: `np.rot90(a, k)`, `np.block`, `np.bincount(a.ravel())` — task-794e60f6.py and task-0f6e5a2f.py.

## 5. Mistakes I made — avoid these

1. **Wrong attempt on task-5997d753 cost the whole task.** I kept patching a shift-based rule instead of questioning whether the reference-block structure was right. When the same family fails twice, re-derive the rule from the raw demos.
2. **task-1b7868f1 failed on the test despite all demos passing.** Note says: anchor used was `(r0+r1)//2, (c0+c1)//2` of the seed bbox; the untried alternative was anchor `(13,7)`,`(12,8)`, or `(12,7)` with a `0→1` recolor. If a stamping rule passes demos but you're unsure, look for *any* remaining degree of freedom (which cell of the seed maps to the anchor; whether seed-internal special colors get remapped) and enumerate the few options before submitting rather than after.
3. **Duplicate demo pairs**: in task-1b7868f1 I noted "sub1==sub3 duplicate" — dedupe inputs before reasoning; near-identical inputs are useful (diff them to isolate the rule) but don't count them as independent evidence.
4. **Don't over-fit with per-demo special cases.** Every conditional must be principled (a structural property like "2 rows tall", "area even", "size ≥3"), not a magic constant tied to one demo's coordinates.
5. **Save your memory promptly**, especially after solving — I sometimes updated memory late, and version histories show me rewriting the same entry several times. One good entry right after a solve: task id, file paths, pair count, one-line rule.
