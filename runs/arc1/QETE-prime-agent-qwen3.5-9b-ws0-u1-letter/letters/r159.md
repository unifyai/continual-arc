## 1. The core workflow (never deviate)

1. **Read the kept demo pairs first.** They are the ground truth for the rule. Every pair you keep constrains the rule; a rule must reproduce ALL of them, not most.
2. **Write the rule as a program** (`transform(grid)` in `programs/task-XXXX.py`) and save demo pairs in a `.json` next to it. Verify the program reproduces every kept pair by running it before submitting a test prediction.
3. **When a test prediction is rejected, do not thrash.** Each wrong submission burns an attempt. Step back, request demos if you can, and enumerate *what dimension of the rule* you got wrong (see §4) before guessing again.
4. **Save memory files** (`memory_task-XXXX.json`, plus the harness memory store) with: files, whether the program reproduces all kept pairs, and a one-line statement of the rule. Future-you reads these. Write them clearly — they're the only thing that persists across tasks of the same ID.

## 2. Task IDs repeat — and so do rules

The stream reuses task IDs. When you see an ID you've recorded, **load your saved program and memory first**. Several of my tasks were solved in minutes because a past version of the rule still applied:

- Sometimes the same ID comes back with a *variant* — e.g. `5c839a47` first appeared with many dots, later with a single lone dot, and my "fill between min/max dot per row/column" rule was undefined for one dot. ## 3. The rule families I've cracked (check new tasks against these)

**Recolor enclosed regions (task-3f4fb1a9):** Background-colored components not touching the border are "pockets." If the pocket is a *solid rectangle*, recolor it to 4; non-rectangular pockets (e.g., L-shaped, beside a stem) are left alone. Plus: if a 2-row-tall pocket has a full row of background directly below its bottom wall, that wall row also becomes 4. General lesson: **enclosed-vs-touching-border is the most common gate in ARC recoloring rules.** Flood-fill from the border to find what's "outside."

**Tile/pattern stamping (task-770f2daf):** Take the bounding box of the rarest non-zero color; that small pattern gets stamped into every all-background box of the same size. Generalize: one small "seed" pattern + a rule for where it copies.

**Separator-split comparison (task-026adbf3):** A full uniform row or column splits the grid into two same-size blocks A and B. Output: same shape, cell = special color (e.g. 3) where A and B agree, else the blocks' dominant shared color. Also task-47ed202e: full uniform rows/cols become all-2. **Whenever a grid has full single-color rows or columns, they are almost certainly structural — separators, not objects.**

**Grid-of-blocks compression (task-bb30ebc2, task-48898d06, task-67dd046a):** A grid tiled by a repeating pattern with separator lines; output is one value per block. Variants: output = the marker color at intersections of "special" rows/cols; output = 1 if a block contains stray cells, else background; output = majority (non-background) color of each 3×3 block. If a grid looks like a fine lattice, ask "what is the coarse block grid?"

**Line/beam drawing (task-d4079843, task-5c839a47, task-3b5f776f):**
- Dots draw stub lines toward the nearest bar; the dot becomes a special color; a mirror line appears on the other bar at a clamped index.
- Dots fill cells strictly between min and max dot per row/column.
- Same-color runs of length ≥2 on diagonals extend along the diagonal both ways until blocked.
Common shape: **"thin objects define rays; rays extend/fill until blocked."**

**Translation/stamping by anchors (task-1b7868f1):** The largest non-background component is a seed; every other non-background cell is an anchor; stamp the seed's bounding box translated so the seed's center lands on the anchor. Always stamp the bbox *as-is* (including internal background and holes).

**Marker gap-filling (task-8625f9bc, task-b7641a67):** Fill background cells between nearby markers: gaps of size ≤2 between marker runs, cells on the marker bounding box, or a single background cell between two identical cells in a row. The "size ≤2" constant matters — demo pairs will show it.

**Motion toward a line (task-77262100):** An object slides toward a full separator line until adjacent on its own side; a full line of another color is drawn just outside the object's far side. Handles both orientations.

**Expansion from bottom rows (task-2e29965a, related):** Colored cells form diagonal/row lines; fill the whole grid by cycling the line colors along a perpendicular key modulo the number of lines. Also: repeating diagonal stripe patterns defined by the first few rows.

**Mirror+tessellate (task-73499f5a, task-794e60f6):** Row r becomes reverse(r)+r, height triples by reversed+original+reversed; or 2n×2n quadrant construction: TL=input, TR=rot90cw, BL=rot90ccw, BR=rot180. **When output is exactly 2× or 3× the input, it is almost always mirroring/rotation tiling — enumerate the 8 dihedral placements of the input.**

**Down-shift (task-efc2fba8):** All non-background cells shift down one row; top becomes background. Silly-simple, but don't overlook the trivial rules; check for pure translations of all objects first when little else changes.

**Bbox-cleanup (task-b62da9e0):** Components of size ≥3 get their full bounding box filled with their color; everything not filled becomes background. (De-noise-then-solidify.)

**Hole-filling by parity (task-aa5a69a0):** Hollow rectangles (ring-shaped components ≥3 wide) get interiors filled with a fill color depending on interior area parity (even→2, odd→7). Watch for *parity* and *area* conditions.

**Rarest-color tracing (task-3b5f776f / 5c839a47 pattern):** The least common color is nearly always "special" — the seed, the dot, the drawer. **Count colors first, always.** The most common is background; the runner-up or rarest usually defines the action; the action color is often a fixed small digit (2, 3, 4) not present in the input at all. **If the output contains a color absent from the input, that color is the "answer paint" — find what it marks.**

**Two-color remap (task-2264bd4e):** Two colors present: keep the higher, set the lower to 0 (or invert per pattern). Trivial but real.

**Symmetric overlay (task-47ed202e's cousin):** Rows/columns that are uniform become one color; everything else keeps a pattern. Structural cells vs. pattern cells.

## 4. When your prediction is rejected: diagnose dimensions, don't re-guess

A rejected test prediction means the rule is *mostly* right but wrong in one dimension. Enumerate explicitly, in this order:
- **Which object is selected** (largest? rarest? the one nearest something? exact twin-pairs?)
- **Which cells change** (all of them? only background? only enclosed? only within a bbox?)
- **Direction/axis** (up vs down, mirror vs rotate — I once lost on "shift down" vs some variant)
- **The trigger's edge cases** (lone objects, size-1 runs, zero gaps, ties in "nearest")
- **The fill color** (fixed constant vs. derived from input)
- **Whether unchanged things really are unchanged** (outputs often leave 90% identical — check which 10% differs cell by cell, that diff IS the rule)

That last one is the single best technique: **diff input vs output cell-by-cell, then describe the set of changed cells geometrically** (a rectangle? a line? cells enclosed by X? cells between min/max of Y?). Every rule I listed above was found exactly this way.

Also: **check for exact-translation twin pairs** — same shape occurring twice is often meaningful (one recolors toward a special object; see my `0f6e5a2f` rule: among twin pairs, recolor the member farther from a special "arrow" object).

## 5. Practical harness tactics

- **Keep programs self-contained** and deterministic; pure Python, no file I/O inside `transform`. Save candidate rules as separate files (`cand_*.json`) when comparing — but note my leftover `cand8.json` / `cand_11_7.json` files are just saved grids from a stamping task; that task family (task-1b7868f1: stamp seed bbox at anchors) kept failing on anchor placement details — the note in the failed file ("clean anchors (13,7),(12,8) untried") shows I ran out of attempts enumerating anchor variants. Don't repeat that: if a stamping rule fails twice, ask whether anchors are *the seed's own cells* vs *bbox corners* vs *centers* before trying the third variant.
- **Write failed-attempt notes** into a `_failed.json` like I did — recording "sub1==sub3 duplicate" and "untried variants" prevented me from resubmitting the same wrong answer.
- **Request demos generously when the rule is ambiguous.** Demos are cheap; wrong submissions are not. The lone-dot disaster (8 attempts) would have been 1 demo request.
- **Verify against ALL kept pairs**, including old ones from earlier in the same task ID. A rule that fits the newest pair but breaks an old one is wrong.

## 6. Mindset

- Most rules are one of: **recolor a set, copy a pattern, move an object, draw a line, compress a lattice, or tile with symmetry.** When reading new pairs, say out loud which category it looks like before coding.
- The rule usually generalizes across orientations (rows↔cols, both diagonal directions). Write code that handles the transposed case from the start — half my late-task bugs were orientation bugs.
- Beware the **off-by-one**: "strictly between" (exclusive) vs inclusive spans; gaps "≤2" vs "<2"; "adjacent to the line" vs "on the line."
- If a program reproduces all demos but the test fails twice with the same shape of rule, the failure is in an **edge case the demos can't show**. Request demos targeted at that edge case if possible.
