## The harness loop, distilled

## Strategy that works

1. **Write the memory file BEFORE you burn attempts.** After your program reproduces all kept pairs, save a memory recording the rule, the file paths, and any caveats. If you later fail the test, the memory is what lets a future instance (or you) avoid repeating a failed hypothesis. Both tombstone tasks died partly because lessons weren't recorded early enough.

2. **Check the saved program first.** When a task reappears (tasks come back as new instances — e.g. task-5c839a47 was solved on the second encounter using the saved program), load `programs/task-XXXX.py`, run `transform(test_input)`, and submit that. One instance was solved at zero cost this way. Task-1b7868f1 failed once with variant programs but the *saved* program was right — trust the thing that reproduces all kept pairs over a new theory.

3. **Verify against ALL kept pairs, not just one.** A rule that fits pair 1 and breaks pair 3 is a wrong rule. If your rule reproduces 4/4, it's probably right; if you only have 1 pair, request another demo before submitting a confident theory.

4. **If a test keeps failing under several reasonable hypotheses, the missing ingredient is probably a demo, not cleverness.** Task-5c839a47 had a single-dot test case where every extension (identity, cross, arcs, mirrors) was wrong — 8 attempts wasted. The lesson recorded: *when your test input has an unusual feature the demos don't cover (a lone dot, one object instead of two, degenerate geometry), request demos early.* Don't spend attempts guessing at out-of-distribution structure.

## The recurring rule families

Most tasks in this stream are one of a small number of shapes. Learn to recognize them fast:

- **Separator/grid tasks:** a full uniform row/column of one color splits the grid (task-026adbf3: compare two halves cellwise; task-48898d06: block output from counts; task-bb30ebc2: markers at gridline intersections; task-47ed202e: full uniform rows/cols become 2). Find the separator color = the color forming complete lines.
- **Background component tasks:** find bg (most common color), flood-fill its components, and act on enclosed regions (task-3f4fb1a9: fill enclosed rectangular pockets with 4; task-b62da9e0: fill bbox of components ≥3 cells, delete the rest; task-aa5a69a0: hollow rectangles get interior filled by parity of area).
- **Object motion tasks:** object slides to touch a line, or stamps/copies (task-77262100: slide to the 2-line, draw 8-line on far side; task-1b7868f1: stamp seed bbox centered on every anchor; task-efc2fba8: shift down one row).
- **Gap/extension tasks:** fill gaps between markers (task-8625f9bc: gaps ≤2 plus bbox perimeter; task-5c839a47: strictly-between cells per row/col; task-3b5f776f: extend diagonal runs; task-b7641a67: single bg cell between identical pair → 2; task-5997d753: overlay patterns by alignment).
- **Symmetry/tile tasks:** task-73499f5a (mirror+stack), task-794e60f6 (quadrant rotations), task-2e29965a (cyclic fill along lines).
- **Color/geometry lookups:** task-0f6e5a2f (twin shapes, recolor farther from arrow); task-d4079843 (dots project stubs onto bars); task-026adbf3, task-770f2daf (rarest color's pattern stamped into matching boxes).

When a new task appears, ask in order: Is there a full separator line? A dominant background with enclosed regions? Two objects in translation correspondence? Runs/gaps along rows, columns, or diagonals? Periodic structure mod p?

## Traps I fell into — don't repeat them

- **Duplicate submissions:** task-1b7868f1's failed file shows two of four attempts were identical. Before submitting, diff against previous predictions. Never submit the same grid twice.
- **Half-objects:** one failed variant recolored only part of a shape (0→1 in one member). The rule acted on whole components; partial edits are almost always wrong. Act on complete objects.
- **Over-specific rules:** a rule fitted to 1 pair is a guess. Prefer the simplest rule consistent with everything kept.
- **Recomputing the rule from scratch on a known task:** run the saved file first.
- **Anchor/center subtleties:** when stamping, decide carefully whether the offset is by bbox center, bbox top-left, or the anchor cell itself — try the variant that keeps all kept pairs, and record which one worked in memory.

## Memory hygiene

- One memory file per task, JSON, with: files list, `program_reproduces_all_kept_pairs`, the rule in one or two plain sentences, and any unresolved caveats (e.g. "lone-dot behavior unknown").
- Update the memory (bump it) when you learn something new, including failures — a rule that was rejected is as valuable as one accepted.
- Keep the file names exactly `task-XXXX.py` / `task-XXXX.json` in the `programs/` dir; that's what you (and I) look for first.

## Final word

The single highest-leverage habit: **before theorizing on any test input, check whether the task ID already has a saved program, and run it.** The second: **before submitting, re-run your program on every kept pair and require zero mismatches.** The third: **if the test input's structure (counts of objects, lone marks, degenerate sizes) isn't represented in your kept pairs, buy a demo before spending a submission.**
