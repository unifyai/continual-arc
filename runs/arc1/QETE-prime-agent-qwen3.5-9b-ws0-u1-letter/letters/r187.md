## The harness loop, in practice

1. **Write a hypothesis, save a program, save demo pairs.** Your program files go in `.../workspace/programs/task-<id>.py` with a `transform(grid)` function, and pairs in a sibling `.json`. The grader checks whether your program reproduces the kept demo pairs before trusting a submission.
2. **Request demos when unsure.** Getting a wrong submission costs an attempt; requesting demo pairs is usually cheaper. The one place I burned 8 attempts (task-5c839a47) was a test with a *single* dot where my multi-dot rule had nothing to say — every extension I tried was wrong. **Lesson: if your demo pairs don't cover the test's configuration (e.g. all demos had 2+ dots and the test has 1), request demos early rather than guessing.**
3. **Keep a per-task memory file.** Write a short JSON with the task id, solved status, wrong-attempt count, the rule in one sentence, and file paths. Future-you (and I) rely on these. The examples above show the format.

## Recurring rule families (with the exact tricks that solved them)

**Background + components.** Almost every task starts with: most common color = background; flood-fill 4-connected (sometimes 8-connected — task-1b7868f1 needed 8-conn for the seed) components of non-background. Classify components by shape.

**Shape twins / pairs.** When a shape class occurs exactly twice, one member is usually "selected" and transformed (recolor, erase, or both). Selectors I've seen work: nearest to a special singleton object (an "arrow" / thin angle with arms ≥ 3 in task-0f6e5a2f), farther from it, larger, or the one touching a border. Compute distance as min Manhattan over all cell pairs — cheap and reliable. Canonicalize shapes with `tuple(sorted((y-min(ys), x-min(xs))))` and group by that key.

**Stamping / tiling a seed.** One task family: the largest component is a seed; every other non-background cell is an anchor; stamp the seed's *bounding box as-is* (including holes and internal background!) translated so the seed's center maps onto the anchor. Don't try to be clever about what's "inside" the shape — stamp the raw bbox. My saved `task-1b7868f1.py` does exactly this.

**Separator-line splits.** A very common family: a full solid row/column (uniform color) splits the grid, and the output compares or merges the two halves:
- task-026adbf3: output 3 where both halves agree, else their common background.
- task-707635df: output 2 where each half holds its own dominant color; note the separator must be *centered* (2·index+1 = size) — check that.
- task-48898d06 / task-bb30ebc2: split into blocks by separator rows/cols; each output block summarizes its block (count of stray cells ≥ 2 → 1; or the color where all four corner markers agree). My saved programs handle the segment arithmetic (`segs(sz, seps)` in task-48898d06.py) — reuse it.
- task-707635df demos: sometimes the output is *smaller* than the input (one half's dimensions). Always check output dims against block dims, not input dims.

**Fills.** 
- Enclosed background pockets → color 4, but only if the pocket is a perfect rectangle (`len(comp) == (r1-r0+1)*(c1-c0+1)`); non-rectangular pockets stay unchanged (task-3f4fb1a9). Plus a subtle extension: 2-tall pockets with background below get that wall row filled too.
- Cells strictly between two dots of the rarest color, per row and per column → 3 (task-5c839a47). The rarest color is `Counter(...).most_common()[-1][0]`.
- Same-color runs (length ≥ 2) along diagonals/antidiagonals extend in both directions through background until blocked (task-3b5f776f). Runs of length 1 do NOT extend.
- Pattern colors fill the gap between consecutive occurrences in a row → 2 (task-b7641a67).

**Periodicity.** task-2e29965a: colored cells lie on anti-diagonals (i+j) with a repeating period; infer the period from the colored diagonals and tile the whole grid. Generalize: check row, column, diagonal, and anti-diagonal groupings, each requiring all values in a group to be identical.

**Object motion.** task-77262100: an object slides flush against a full vertical line of color 2, old location becomes background, and a full-height line of another color (8) is drawn at the object's *old* rightmost column. task-77262100.py shows the general recipe: find the line, find shape cells (not bg, not line), compute new position, overwrite only what's needed. Note the two "old" line and old column — outputs often leave traces of where things *were*.

**Symmetry / self-concatenation.** task-73499f5a: each row → reverse(row)+row; then stack reversed+original+reversed. task-794e60f6: a 2×2 block assembly of the input and its three rotations via `np.block`. task-67dd046a: 3×3 downscale where each output cell is the most common non-5 value in its block.

**Simple recolors.** task-2264bd4e is just "keep the higher of the two colors, map the lower to 0." task-47ed202e: any row or column that is a single uniform color becomes all 2. Don't overthink — sometimes it really is one line.

**Mosaics / blocks.** task-8d84fe63: separator rows/cols divide the grid into blocks; find the block with the largest deviation from its own mode, and copy that block's pattern onto every other block positionwise.

**Downshift.** task-efc2fba8: every non-background cell moves down one row, top row becomes background. (First guess was "shift all rows," which is equivalent here — but state the rule as cells, in case of edge interactions.)

## Practical tactics

- **Before submitting, hand-verify on one demo pair mentally** — trace a few cells. Most of my failures were off-by-one in ranges, or filling cells I shouldn't have (dots, markers, separator lines themselves are usually untouchable).
- **Check whether separator/marker colors are ever overwritten in the output.** Often they are preserved exactly; the transformation only touches background and object cells.
- **Output dims are a free constraint.** Compute what your rule predicts the output shape is; if it doesn't match, the rule is wrong. (2x2 blocks→2x2, halves→half, etc.)
- **Prefer rules that are deterministic functions of the input alone**, stated in one sentence. If your rule needs a special case for every demo pair, it's probably wrong.
- **Duplicate submissions count as attempts.** I once had sub1 == sub3 in a failed run (task-1b7868f1) — wasted attempts. Always diff your new submission against previous ones.
- **When a rule involves "distance to X," decide the tie-breaks and direction of selection carefully** — e.g. "recolor the *farther* member" vs "the nearer one" flipped a solve.
- **Multi-part grids:** many tasks combine a big texture area plus a small annotated region; the annotated region defines the operation applied to the texture (see task-8625f9bc: a marker-color object defines a bounding box and gaps to fill with color 2).
- **Use Counter and deque** — they're the workhorses. Flood fill with a stack (list-based) is fine and slightly faster than deque for our sizes.
- **Grids can be up to ~30×30; performance is never the bottleneck.** Clarity is. Write the rule as literally as possible first, optimize later.

## Failure patterns to avoid

- Assuming a single demo pair generalizes. Ask for 2–3 before locking in.
- Treating background as a fixed color (0 or most-common). Check: sometimes it's the *second* most common, or the color at grid[0][0].
- Forgetting that objects can have holes and that the holes matter (stamping bboxes preserved them).
- Filling cells that belong to dots/separators/markers — almost always those are preserved.
- When the demos show an operation on a region but the test's region is a degenerate case (single dot, empty region, boundary-touching), the degenerate behavior is often the whole point. Request demos or reason it out before submitting.
