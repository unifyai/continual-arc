## The workflow that works

1. **Look before you guess.** Print the demo grids. For small grids, actually read every cell. Most of my wrong answers came from pattern-matching on a glance instead of tracing the transformation cell by cell.
2. **Find the background first.** It's almost always the most common color. The "objects" are the connected components (4-connected unless clearly diagonal) of everything else. Many rules are of the form "background stays, objects do X."
3. **Check output dimensions immediately.** If the output is smaller than the input, you're aggregating (downsampling by 2 or 3, counting, mosaic extraction). If it's larger, you're tiling or expanding. If it's the same size, it's a recolor/shift/stamp. This one check eliminates half the hypothesis space.
4. **When the output is same-size, diff the pair.** List exactly which cells changed and which color they became. Then ask: what is the changed color *in terms of the input*? Common answers: enclosed background pockets, cells between two markers, cells on a line, cells of one recolored component, cells strictly between the min and max position of the rarest color along each row/column.
5. **Prefer the simplest rule that reproduces every demo pair.** If your rule fails even one kept pair, it's wrong — don't submit it. Write the rule into a Python `transform` and *run it against every pair you have* before submitting.

## Rules I've seen (so you recognize the family)

- Recolor enclosed/enclosed-rectangular background pockets; sometimes also extend into an adjacent slot.
- Fill between markers: the rarest color acts as endpoints; color the cells strictly between the outermost markers in each row and/or column (lone markers usually stay unchanged).
- Extend runs: contiguous same-color runs of length ≥2 on rows, columns, diagonals, or anti-diagonals extend until blocked.
- Stamping: one component is a "seed"; its bounding box is copied to every other object/anchor cell, often centered or aligned. Beware: bbox includes zeros/holes.
- Splitting: a full uniform row/column splits the grid into blocks. Then compare blocks (cell equality → one color, else another), count strays per block, or take the color at guide intersections.
- Symmetry/tiles: output = f(input, rot90(input), fliplr...), or 2×2 block of rotated copies, or row-reverse + row doubling, stacked palindromically.
- Periodic completion: sparse colored cells lie on diagonals/anti-diagonals with periodic structure; infer the period and tile it.
- Movement: an object translates to touch a line or border; its old spot is erased; sometimes a marker line is drawn at the old/far side.
- Map the colors: keep the higher (or dominant) color, set the other to 0 (or to the "3" style indicator).
- Downsample: majority (ignoring one "noise" color) per 3×3 block, or "1 if odd count of stray color else background" per cell of a coarse grid.
- Shift: all non-background cells move down one row; or rows shift by one with top becoming background.

When a task resembles a family, try that family's transform first, then specialize.

## Hard-won lessons

- **Ask for demos when you have no kept pair, or when your rule only fits one pair.** Extra pairs are cheap relative to a wrong submission. If your rule relies on an untested branch (e.g., "what if there's only one marker?"), and the test likely hits that branch, request demos first. I burned 8 wrong attempts on a lone-dot case that a single demo would have resolved. Lesson learned: **untested branches are the danger zone**, not the tested ones.
- **Keep a memory file per task** (in `workspace/programs/task-<id>_status.json` or similar) with: solved?, wrong attempts count, the rule in one sentence, paths to program and pairs JSON. When the same task id reappears later (it happens, with a new test input), your saved program + memory is a free win. I solved several reappearing tasks at 0 wrong this way.
- **Save every kept demo pair** into `programs/task-<id>.json` and verify your program reproduces all of them. A program that reproduces 4/4 pairs is far more trustworthy than your intuition.
- **Watch for contamination**: occasionally recovered "demo pairs" are not from your task. If a pair contradicts an obviously solid rule, trust the pairs you were shown in the task prompt, and note the anomaly in memory.
- **When a test prediction was rejected, don't resubmit the same idea with a tiny tweak.** Reread the demo pairs and find what phenomenon your rule explains wrongly. After a rejection, enumerate *which cells* differed, not just the count.
- **Duplicates**: before trying a new hypothesis, check your failed-attempts notes — I once recorded that two submissions were identical and used the note to pick genuinely new anchors (e.g., try different seed choices, different tie-breaks, ±1 offset) rather than near-duplicates.

## Coding practices

- Write `transform(grid)` taking a list of lists of ints, returning the same. Keep it self-contained (import inside the function is fine).
- Common utilities worth writing fresh each time: background via `Counter(...).most_common(1)[0][0]`, 4-connected components via a stack/deque flood fill, bounding boxes, canonical shape key `tuple(sorted((y-minys, x-minxs) ...))` for shape-matching and twin detection.
- Test harness pattern: load your saved pairs JSON, run transform, compare to expected, print mismatches with coordinates. Do this *every time*.
- Beware off-by-one at borders: clamp indices; when stamping, skip out-of-bounds rather than crashing.
- Beware `most_common` ties — Counter ties are insertion-ordered; if two colors have equal counts, your rule may need an explicit tiebreak (rarest = `most_common()[-1]`).

## Decision guide for a new task

- Same-size output → recolor/stamp/shift. Diff cells.
- Output = half-size or third-size → split/compare or downsample.
- Output larger → tile/reflect/expand.
- Output same dims but mostly background → count/aggregate written back, or "reconstruct from markers."
- Objects that are exact translation twins → likely one gets recolored based on proximity/distance to a distinguished object (an arrow/L-shape). Compute distances, pick by the rule the demos imply.
- Lines that appear: check whether they're at bbox borders, adjacent to a moved object, or the span between endpoints.
