## The harness, in one paragraph

Each task gives you a few demo input/output pairs and one or more test inputs. You must figure out the transformation rule, write a `transform(grid)` function in `programs/task-<id>.py`, save demo pairs in `programs/task-<id>.json`, and submit your predicted output for the test. Wrong submissions cost you; there's often a cap. You can sometimes request more demos. You have a workspace that persists across tasks — use it.

## Workflow that worked

1. **Save everything immediately.** When demos arrive, write them to `programs/task-<id>.json` *before* doing anything else. Never lose a pair to a crash or context overflow.
2. **Write the program, then verify it reproduces every demo pair exactly.** Run `transform` on each demo input and compare to the output, cell by cell, programmatically. Never submit a prediction from a rule you haven't verified against all demos.
3. **Keep a memory file per task** (`memory_task-<id>.json` or similar) with: the file paths, the rule in words, and whether the program reproduces all pairs. Future-you will thank present-you, and the harness memory (task_XXXX entries in harness_state.json) is read back into context — that's how rules survive.
4. **If the rule fits the demos but feels uncertain on the test, check whether the rule is "minimal"** — the simplest rule that explains all demos. Overfit rules that hard-code demo quirks fail on the test.

## Failure case study: task-5997d753 (my biggest waste)

I burned 8 wrong attempts and 3 demo requests. The task had *multiple regimes* (different structures appearing across demos — full pattern rows acting as references vs. shifted-block comparisons). My rule explained every demo but was one of several rules consistent with them; I guessed wrong on the test repeatedly. **Lesson:** when the demos show two distinct structures, suspect the rule is a unified principle you haven't found yet — e.g., "a value of 1 appears where a lower row predicts an upper row's pattern," not "full rows are references." Before spending wrong attempts, enumerate *competing* interpretations and ask which one generalizes. If two rules both fit all demos, prefer the one with a cleaner causal story (prediction, alignment, symmetry) over a positional one. And when stuck after a few failed submissions, ask for demos — but *study them for what distinguishes your competing hypotheses*, don't just append them.

## Another lesson: task-1b7868f1

A task where the pattern is "largest non-background component is a seed; every other non-bg cell is an anchor; stamp the seed (its whole bounding box, including interior zeros/holes) translated so the seed's center maps onto the anchor." I failed once because I only stamped at anchor *positions* with a wrong offset convention. **Lesson:** when stamping/copying shapes, be very careful about the anchor convention — is it top-left alignment, center alignment, or a specific cell of the shape? Try center-of-bbox first; it's most common. And stamp the bbox *as-is* (with holes), not the component mask.

## Common rule families I saw (build your intuition)

Across the stream, the rules clustered into families. When you see a new task, quickly check these:

- **Diagonal/periodic tiling** (task-2e29965a): colored clue cells lie on diagonals; fill the grid with `P[(r+c) % L]` or `P[(r-c) % L]` where L = number of distinct nonzero colors. Try both diagonal directions.
- **Row/col operations**: shift all rows down by one, top row becomes background (task-efc2fba8); mirror rows `r[::-1]+r` and stack reversed/original/reversed (task-73499f5a — output was exactly 3× height, 2× width with mirror symmetry).
- **2×2 rotated block** (task-794e60f6): output is `[[I, rot90cw],[rot90ccw, rot180]]` — doubling each dimension.
- **Separator-split blocks** (many tasks): a full uniform row or column (single repeated color, spanning the whole grid) splits the grid into blocks A and B. Then: output = 3 where A==B else the shared color (task-026adbf3); or output = cellwise AND of the nonzero masks recolored to 2 (task-707635df); or find which block has non-background content and tile that pattern into every block (task-8d84fe63); or compare A vs B and keep/flag.
- **Pockets and enclosures** (task-3f4fb1a9, task-aa5a69a0): find enclosed background regions (flood fill from border; components not touching border are enclosed). Fill rectangular pockets with 4; hollow rectangles get interior filled with 2 if interior area even, 7 if odd. Non-rectangular pockets are left alone.
- **Minority color stamping** (task-770f2daf): the rarest nonzero color forms a small pattern; stamp that exact pattern into every all-background region of the same size.
- **Component rectangle fill** (task-b62da9e0): fill the bounding box of each non-bg connected component with size ≥ 3 with its color; everything else becomes background. Note: check both 4-connectivity and 8-connectivity — tasks vary.
- **Two colors min/max** (task-2264bd4e): smaller color → larger color, larger → 0. Watch out: role-based rules (majority/minority) can fail here; sometimes it's literally about min/max color value.
- **Dots between dots** (task-5c839a47): a background cell becomes 3 iff strictly between two dots (rarest color) in its row or column.
- **Between identical neighbors** (task-b7641a67): background cell flanked by the same non-bg color on both sides in a row becomes 2.
- **Uniform line recolor** (task-47ed202e): rows/columns that are entirely one color get recolored to 2; rest unchanged.
- **Downscale by 3** (task-67dd046a): each 3×3 block → most common color excluding the noise color (5); noise color is ignored.
- **Bar + dots, lines and mirrors** (task-d4079843): two bars of one color, dots of another. From the bar facing the dots, draw perpendicular lines through each dot (dot becomes 4); from the opposite bar, draw lines at the same relative offsets spanning the full gap in the dot color. This one is intricate — read the program if you see a similar structure.
- **Slide object next to a separator** (task-77262100): a 2-cell-thick separator line; the object slides until adjacent to it; a parallel full line of 8s is drawn on the object's far side.
- **Gap filling between marker runs** (task-8625f9bc): markers on the perimeter of their bbox get recolored; gaps between runs of ≥2 consecutive markers along rows/cols get filled with 2.
- **Extend a line through a pattern** (task-3b5f776f): cells with exactly 1 non-bg neighbor (8-connectivity) are endpoints; extend the line through them to the grid edge in their color.
- **Row shift by one** (task-efc2fba8): output row 0 = background, output row r = input row r−1.

## Coding pitfalls I hit (don't repeat them)

- **Flood fill connectivity**: 4-neighbor vs 8-neighbor changes component counts drastically. task-1b7868f1 needed 8-connectivity for the seed. When a rule "almost" works, flip connectivity before rewriting logic.
- **`np.rot90(a, -1)` is clockwise.** `rot90(a)` is counterclockwise. `rot90(a, 2)` is 180°. Check orientation against the demo, don't trust your memory.
- **Counting colors**: `Counter(v for row in g for v in row).most_common(1)[0][0]` for background. For minority: `most_common()[-1][0]`, but when there are several rare colors, think about which one is the "object" (often the one forming a coherent connected shape, not scattered noise).
- **Bounding boxes**: always compute `min/max` over rows and columns separately. When checking "solid rectangle" vs "hollow", verify `len(comp) == (h)*(w)` for solid, or `len(comp) == 2h+2w-4` for a hollow outline.
- **Diagonal residue**: when clue cells sit on diagonals, verify consistency — the same residue class must always have the same color, or your key is wrong (try `r-c` if `r+c` fails).
- **Test your transform on the demo inputs and compare with `==` on the whole grid**, not spot checks. I caught several bugs this way (off-by-one in ranges, wrong corner, forgotten padding).
- **Integer grid, not numpy scalars**: some graders are picky; return plain Python lists of ints (`int(...)` anything from numpy).

## Strategy for unseen tasks

1. **Look at the shape change first**: does output have the same dims? Doubled? Halved? If dims change, it's likely block/tiling/scaling — check ×2 (mirror/rotate tiling), ×3 (downscale), 1/3, etc.
2. **Diff the demo pairs cell by cell.** Where do input and output differ? Those cells are the action. Cluster the differences by color and position. Most tasks touch a small set of cells.
3. **Count colors in input vs output.** New color appearing in output (like 2, 3, 4, 8) usually marks the "result" of the operation — lines drawn, matches found, enclosed regions filled.
4. **Hypothesize geometrically**: symmetry, translation, enclosure, adjacency, alignment. ARC rules are almost always geometric relationships between colored regions, not arithmetic on values (though value comparisons like min/max appear).
5. **Verify against ALL demos before submitting.** If your rule fails even one demo, it's wrong — don't submit hoping it's a demo quirk.
6. **If you have limited attempts, rank hypotheses** by simplicity and geometric plausibility, and submit the best one. Don't thrash between near-identical rules — that's how I burned 8 attempts on 5997d753. Between failures, re-examine the demos for the *distinguishing* cell(s) your rule gets wrong, and think hard about what alternative rule would produce exactly the observed output there.
7. **Request demos when genuinely stuck** — but each request is a resource. Make it count by having specific competing hypotheses in mind.

## Save state so you can resume

Your workspace persists. At minimum per task:
- `programs/task-<id>.json` — demo pairs (JSON list of {"input": [[...]], "output": [[...]]}).
- `programs/task-<id>.py` — with `transform(grid)` taking a list of lists of ints and returning the same.
- A memory entry in harness_state.json (the harness reads it back) or a `memory_task-<id>.json` file — with the rule in one sentence, the paths, and reproduction status.

Write rules in words, precisely. Vague notes like "recolor stuff based on pattern" will be useless to you two tasks later. "Fill enclosed rectangular background pockets with 4; 2-row pockets also absorb their bottom wall row if the row below it is background across the pocket width" — that's the level of precision you want.
