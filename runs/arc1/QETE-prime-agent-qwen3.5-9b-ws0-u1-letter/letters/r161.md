## 1. How this game works

You will be given an ARC task, usually with one or a few input→output pairs ("kept pairs") stored in `programs/task-<id>.json`, and a test input. You must write a program `programs/task-<id>.py` with a `transform(grid)` function that reproduces every kept pair AND makes a prediction for the test input. Wrong test submissions cost you (there's typically an attempt cap — I burned out two tasks at 8/8 wrong). Demo requests get you more pairs but are also limited; use them when a pattern is genuinely ambiguous, not when you just haven't stared hard enough.

Practical workflow that worked for me:
1. Load the JSON, print every pair side by side, diff input vs output cell by cell. Almost every task is a *local, mechanically describable* change. Enumerate exactly which cells changed and what they became.
2. Before writing code, state the rule in one English sentence that covers every changed cell. If your sentence has an "except for one cell" clause, you don't have the rule yet.
3. Write the program, run it against all kept pairs, and only submit when it reproduces all of them.
4. Check your memory files (both `harness_state.json` entries and the loose `.mem.json` / `memory_*.json` files in workspace) — several tasks recur here with new test inputs. If you have a saved program that reproduced all kept pairs, run it on the new test input. That is how most of my late tasks were solved at zero cost.

## 2. The recurring rule families

This stream's tasks cluster heavily. When a new grid arrives, check these first:

**Grid tiling / block extraction.** Grids subdivided by full uniform separator rows/columns (a row that is a single repeated color, like all-4s or all-9s). Output is usually a small grid of blocks. Count something per block: parity of stray cells (output 1 vs bg), whether the four corner markers of a block are identical, majority color of the block (ignoring a "noise" color like 5), whether two halves agree. Files: `task-48898d06`, `task-67dd046a` (3×3 downsample with majority, ignoring color 5), `task-bb30ebc2`, `task-026adbf3` (split by centered separator into two halves; output 3 where halves agree, else the shared common color), `task-707635df` (split at centered separator; 2 where each half has its own dominant color). "Centered separator" means the separator sits exactly at the middle — check `2*r+1 == H`.

**Line/cycle fill.** Colored cells lying on diagonal or anti-diagonal lines; fill the whole grid by cycling the line colors along the perpendicular direction modulo the number of lines (`task-2e29965a`). Also: find cells of the least-common color ("dots") and color 3 everything strictly between the min and max dot per row and per column (`task-5c839a47` — beware: a lone dot in the test broke this for me; if the test has a single dot, request demos early).

**Directional extension.** A run of ≥2 same-color cells along a diagonal extends in both diagonal directions until blocked by a non-background cell or the edge (`task-3b5f776f`). Similar flavors: fill background gaps of size ≤2 between markers in a row/col plus the bounding-box perimeter (`task-8625f9bc`); fill a background cell between two identical non-bg cells in a row with color 2 (`task-b7641a67`).

**Rectangles and holes.** Find a rectangle outline; fill its interior with a color chosen by parity of the area (`task-aa5a69a0`: even area → 2, odd → 7). Fill enclosed background pockets (background regions not touching the border) with 4, with a special extension for 2-tall pockets (`task-3f4fb1a9`).

**Stamping / translation.** Find the largest non-background component as a "seed"; every other non-bg cell is an anchor where you stamp the seed's bounding box (center-aligned, translating so centers coincide) (`task-1b7868f1`). The rarest non-zero color's bounding-box pattern gets stamped into every all-zero box of the same size (`task-770f2daf`).

**Geometry transforms.** 2n×2n output from n×n input: TL=input, TR=rotate90cw, BL=rotate90ccw, BR=rotate180 (`task-794e60f6`). Mirror+concatenate: each row becomes reverse(r)+r, and rows stack reversed/normal/reversed (`task-73499f5a`). Simple shift: all non-background cells move down one row (`task-efc2fba8`).

**Objects interacting with a line.** An object slides until it touches a full line of color 2, then a full line of color 8 is drawn just beyond the object's far side (`task-77262100`). Two bars of one color plus single-cell dots: each dot draws a stub toward its nearest bar and turns into 4, and a mirrored line appears on the other bar at the corresponding index (`task-d4079843`).

**Selection/recolor.** Among translation-twin shape pairs, pick the pair closest to a designated object and recolor the farther member (`task-0f6e5a2f`). Map two colors: keep the higher one, zero the lower (`task-2264bd4e`). Uniform rows/columns become all-2 (`task-47ed202e`). Connected components of a color with size ≥3 become solid blocks; everything not in such a block is erased to background (`task-b62da9e0`).

**Symmetrization.** Rows or columns that would need a pattern copied; find the block whose pattern of deviations from its mode is largest and copy it everywhere (`task-8d84fe63`).

**Background noise fields.** Most common color is bg; a "line" color defines gridlines; markers scattered in noise cells; the answer lives in the intersections of special rows/cols (`task-bb30ebc2`).

When a new task looks like none of these, my best generic advice: identify the background (most common color), list the non-background components (4-connectivity unless the drawing clearly requires 8), and ask "what relation holds between changed cells and their neighbors / rows / columns / other objects?" Count things: sizes, counts per row, counts of each color. Parity, min/max position, and "strictly between" appear over and over.

## 3. Traps I fell into — don't repeat them

- **A rule that fits all demos can still be wrong on the test.** The demos are sparse. If two different mechanisms both explain the demos, prefer the *simplest and most symmetric* one, but if any doubt remains and you have demo requests left, spend one. This cost me `task-5c839a47` (8 wrong attempts on a lone-dot test) and `task-5997d753` (8 attempts; the demo set never disambiguated the rule, and I should have requested demos sooner).
- **Tie-breaking matters.** "Largest component", "least common color", "nearest to X" all need tie-breaks. Pick tie-breaks that feel natural (larger size, then earlier in scan order) and note them.
- **Anchor semantics.** When stamping, decide carefully whether alignment is by bounding-box top-left, center, or component centroid — check against the demos, don't guess. Center-alignment via bbox was right for `task-1b7868f1`.
- **8-connectivity vs 4-connectivity.** Some tasks join diagonal touches (my stamping task used 8-conn), most use 4-conn. If the demo pair fails by exactly the diagonal cells, flip connectivity.
- **Background detection.** Most common color is nearly always bg, but check the grid corners/edges — bg is what touches the border in most of these tasks.
- **Memory contamination.** One of my memory files (`task-3f4fb1a9.json` in `memories/`) contains a note about "cross-task 'Demo pair' labels" being contamination. If a file's content looks like it belongs to a different task, trust the harness_state.json version, and always re-verify a saved program against the current kept pairs before reusing it.
- **Duplicate submissions count as attempts.** In `task-1b7868f1` I submitted near-identical variants and wasted the cap. Before each submission, list in a scratch file which hypotheses you have NOT yet tried and make the next attempt maximally different. The failed-attempts file for that task (`task-1b7868f1_failed.json`) notes untried variants — write such notes to yourself.
- **Write the rule into the memory file.** When you solve a task, save: task id, file paths, the one-sentence rule, whether all kept pairs reproduce, and any caveats (e.g. "lone-dot case unresolved"). Future-you meeting the same task family will thank present-you. I solved several tasks instantly this way.

## 4. Coding style that avoids bugs

- Always `out = [row[:] for row in grid]` and write changes to `out` while reading from `grid`. In-place mutation during scans (flood fills, extensions) causes order-dependent bugs.
- Components: a simple BFS/DFS with a seen matrix. I have a reusable `components(g, colors)` in `task-1b7868f1.py` — copy it.
- Canonical shape key for translation-twin detection: `tuple(sorted((y-min_y, x-min_x) for y,x in cells))`.
- When counting colors: `Counter(v for row in g for v in row)`; `bg = cnt.most_common(1)[0][0]`; second color = `cnt.most_common()[1][0]` only if you've confirmed only two colors exist — otherwise sort by count and take `order[1]`.
- Guard every program against "no such structure found": return the grid unchanged (or the safest fallback) rather than crashing. A crash on the test input is a wasted attempt with zero information.
- numpy is available and worth it for bincount/argmax background detection and for quick diffs, but pure Python is fine and less error-prone for small grids.

## 5. Judging when to stop

If you cannot find a rule covering every changed cell after a genuine effort, enumerate candidate rules, score each against the demos, and submit the one with zero mismatches. Never submit a program you haven't actually run against the kept pairs — "it should work" submissions were half of my failures. And if the demos truly underdetermine the answer (two mechanisms, both fit, both plausible), that is exactly the moment to request a demo pair, before spending a wrong attempt. Wrong attempts are the scarcest resource; demo requests are cheaper.

Good luck. The tasks repeat more than they seem to on first glance — the workspace you inherit is your biggest asset. Keep it accurate, keep it current, and read it before you start every task.
