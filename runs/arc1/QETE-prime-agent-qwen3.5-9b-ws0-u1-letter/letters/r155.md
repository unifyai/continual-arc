## The harness, concretely

You get a stream of ARC tasks. For each: you can request demo pairs (they're saved to `programs/task-<id>.json`), write a `transform(grid)` in `programs/task-<id>.py`, and submit a prediction for a test input. Wrong submissions cost you; there's an attempt cap. Memory files under `workspace/` persist across tasks — write them.

Two things mattered more than cleverness:

1. **Verify your program against every kept demo pair before submitting.** Run the program on each input and diff against the output. Almost every one of my failures came from submitting a prediction without a full round-trip check. If your program reproduces all demos but you're unsure about the test, that's the time to request more demos, not to guess.

2. **Ask for demos early when a task has a suspicious edge case.** My worst task (5c839a47) had demos where the rare "dot" color always appeared at least twice, but the test input had exactly one dot. Every extension I tried (identity, cross-filling, row-only, col-only, etc.) was wrong — 8 attempts burned on variants of an unresolved case. If your rule depends on counting something, check whether the test instance might have a count of 0 or 1 and request demos if you can't resolve it.

## Rule patterns that recurred

Most tasks in this stream are compositions of a small number of primitives. When you see a new grid, check these in rough order:

- **Background identification:** most common color; ignore it; the rest are objects. Flood-fill with 4-connectivity to find components.
- **Recolor by geometry, not by lookup:** the *output* color is almost always a fixed small value (1, 2, 3, 4, 8) determined by the rule, not derived from the input colors. E.g. "fill enclosed background pockets with 4", "paint separator lines with 2", "mark between-dots cells with 3". Don't try to learn a color mapping between input and output colors — find the *structural* predicate.
- **Lines and separators:** a full row or column of a single color splits the grid. I solved several tasks by splitting into blocks along separator rows/cols and computing a per-block value (count strays, majority vote, corner-marker equality, A==B comparison). Output is often much smaller than input — the block count tells you the output size before you know anything else.
- **Downscaling:** if input is ~3x the output in both dims, partition into 3x3 (or line-separated) blocks and reduce each. The reduction is usually "most common non-background color" or "1 if any/odd count of strays".
- **Stamping/tiling:** find the rare-color shape, find all offsets where it fits entirely on background, stamp. Or mirror/reflect: row → reverse(row)+row, stacked as block + reversed + block. Check exact symmetry patterns first — several tasks were pure "mirror and tile" and the test is free if you notice it.
- **Motion toward a line:** an object slides until adjacent to a full separator line, and a new line of a different color is drawn just outside it. Both orientations and both sides need handling; my d4079843 program does this with a permutation-over-mirrors search — steal that skeleton.
- **Diagonal/anti-diagonal runs:** extend same-color runs of length ≥2 along both diagonals until blocked. Or lines of colored cells define a periodic coloring: colors cycle along the perpendicular key (i+j, i, or i−j) modulo the number of lines.
- **Connected components ≥ threshold:** components of a non-background color of size ≥3 become their filled bounding box; everything not inside such a box resets to background (b62da9e0).

## Debugging discipline

When a program reproduces demos but you doubt the test, write the rule down in a memory file *before* guessing — the act of writing it in one sentence ("3 = cells strictly between min and max dot per row/col") exposes overfitting. A rule that has a clause like "except when there's only one" is exactly the kind that needs a demo.

Also: read the failed-attempt notes you leave yourself. My 1b7868f1 notes ("sub1==sub3 duplicate; anchors X untried") were the only reason I didn't waste attempts resubmitting the same program. Track which hypotheses you've tried and keep them distinct.

## Practicalities

- Keep `programs/task-<id>.py` as the single source of truth: a `transform(grid)` taking a list of lists of ints, returning the same. Save demo pairs to `programs/task-<id>.json` in the same format the harness uses (list of `{"input": ..., "output": ...}`) so you can reload them.
- Don't rewrite a solver from scratch if a prior task's program is close — copy it and patch the predicate. My task-d4079843 program (bar + seed dots + mirror filling) and task-77262100 (object + line) share most of their machinery.
- If a test grid looks like pure background or like the input unchanged, consider identity before anything fancy — but check first whether *anything* differs; one of my tasks' outputs differed from the input in only two cells.

You'll meet tasks I never saw. The primitives above cover most of the space I observed; the meta-lesson underneath them is: **find the minimal sentence that describes the mapping, verify it exhaustively on every pair you have, and spend attempts only on things you've verified — never on hope.**
