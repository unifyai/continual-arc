## 1. The harness, concretely

- You'll get a task ID like `task-1b7868f1`, a handful of demo input/output pairs, and eventually a test input. You must write a program (I saved mine at `.../workspace/programs/task-<id>.py` with a `transform(grid)` function taking/returning lists of lists of ints) and a prediction for the test input.
- Saving demo pairs to `task-<id>.json` and memory to `memory_task-<id>.json` is free and worth it. When a later task resembles an old one, those files are gold. I solved several tasks by pattern-matching against earlier rules.
- Wrong submissions are capped per task (I hit an 8-attempt cap on one task and had to walk away). So: never submit a rule you haven't verified against all kept demos. Verify by *running* your transform on the demos and comparing cell-by-cell, not by eyeballing.

## 2. The single most important discipline

**Reproduce all kept demos exactly, and understand *why*, before predicting the test.** A program that reproduces demos by coincidence (e.g., by hard-coding a color or a specific offset that just happens to work) will fail the test. Ask for each rule: "What is the mechanism? Would this still work if the colors were different, the shape were rotated, or there were one more object?"

Corollary: the true ARC rule is almost always *simple and color-agnostic* in the right vocabulary. The right vocabulary is roles, not digits: background (most common color), rare/signal color (least common), marker color, separator line color, fill color (often 4, but check). Write programs in terms of `Counter(...).most_common()` and connected components, not `if x == 8`. I lost attempts on task-5c839a47 partly by getting stuck in digit-specific thinking.

## 3. Rules I personally confirmed on this stream (reusable templates)

Each of these reproduced all kept demos of a real task. If a new task smells like one, try that template first — but still verify.

1. **Stamp a seed shape at anchor points.** Find the largest non-background component (the "seed"); every other non-background cell is an anchor; stamp the seed's bounding box translated so its center lands on each anchor (task-1b7868f1). Watch for duplicate/near-duplicate demo pairs — I burned several attempts on this one because two demos differed by a single anchor cell.
2. **Fill enclosed background pockets with a fixed color (4).** Flood-fill background regions; those not touching the border get recolored. Watch for a follow-up quirk: if a pocket is 2 rows tall and the row below its bottom wall is background across the pocket's width, that wall row also gets recolored (task-3f4fb1a9). Non-rectangular pockets stay unchanged.
3. **Divide-and-summarize grids.** Grid tiled into blocks separated by uniform separator rows/columns; output is a small grid whose cells summarize each block (e.g., "1 if the block contains a stray non-background color, else background" — task-48898d06; or "block color where the 4 corners of special row/col intersections agree" — task-bb30ebc2). Identify separators as full rows/columns of a single color, then work block-by-block.
4. **Compare two half-grids.** A full uniform separator row/col splits the grid into same-size halves A and B; output compares them cell-by-cell: mark 3 where they agree, else the shared dominant color (task-026adbf3). Similarly, a centered solid separator line splits into two halves; output cell = 2 where both halves have their own dominant color (task-707635df).
5. **Draw lines/corridors determined by seed dots.** Given a bar (component of one color with exactly 2 components) and seed dots (rarest color), cast lines of seeds from the bar toward the dots, and also replicate the pattern on a mirror bar; cells along the line become seed color, the dot itself becomes 4 (task-d4079843). This one is intricate — read its saved `.py` if you face something similar.
6. **Slide an object against a divider, then draw a wall.** Object slides toward a full line of 2s until adjacent; then a full line of 8s is drawn just on the object's far side (task-77262100). Handles both orientations and both sides.
7. **Fill background gaps between markers ≤ 2 apart, plus bounding-box perimeters.** For the second-most-common color, fill background cells in any row/column gap of length ≤ 2 between two markers, and fill the background cells on the bounding box perimeter of all markers, with color 2 (task-8625f9bc).
8. **Extend diagonal runs.** Any contiguous same-color run of length ≥ 2 along a diagonal (r−c) or anti-diagonal (r+c) extends in both directions filling background until blocked (task-3b5f776f).
9. **Fill strictly between min and max dot per row/column.** The least-common color's cells define intervals; cells strictly between the min and max in each row and each column become 3; dots unchanged (task-5c839a47). See the caveat in §5 about lone dots.
10. **Least-common-color shape stamps itself everywhere it fits.** Extract the rare-color shape's cells; stamp it at every offset where all its cells land on background (task-770f2daf).
11. **Row/col uniformity recolor.** Any row or column that is a single repeated color becomes all 2 (task-47ed202e). Also: fill background cells strictly between two equal non-background cells in a row with a third color (task-b7641a67).
12. **Mirror-and-tile symmetry.** For square input of side n: output 2n×2n with TL=input, TR=rot90cw, BL=rot90ccw, BR=rot180 (task-794e60f6). For a single row/col input: each row becomes reverse(r)+r, and the block repeats as reversed + original + reversed (task-73499f5a). Also: output = downscale by 3, each 3×3 block → its most common non-5 color (task-67dd046a); and output = fill by cycling line colors modulo a period along anti-diagonals or rows (task-2e29965a).
13. **Simple color remaps and shifts.** Map the two colors: keep the higher, zero the lower (task-2264bd4e). Shift all non-background cells down one row, top row becomes background (task-efc2fba8). Recolor the farther of two translation-twin shapes to the singleton large thin angle's color (task-0f6e5a2f — arrow color, distance measured to the arrow's horizontal arm, tiebreak by larger size).
14. **Rectangularize + denoise.** Components of size ≥ 3 get filled to their bounding box; everything not in a filled region becomes background (task-b62da9e0). Also: cells enclosed by hollow rectangles get filled with 2 (even area) or 7 (odd area) (task-aa5a69a0).
15. **Filter-to-agreement.** Two stacked same-size blocks separated by a uniform row: output = 3 where the blocks agree cell-wise, else the most common agreeing color (task-026adbf3 — same as #4's variant).

## 4. Common ARC archetypes beyond this stream

Since you'll see unseen tasks, here are the recurring families I'd check in order:

- **Counting/quantity:** output = some count rendered as a color or repeated shape.
- **Symmetry completion:** mirror across an axis, complete a partially drawn symmetric pattern.
- **Gravity / direction of motion:** shapes fall or slide toward a border, a line, or each other; overlapping resolves by some rule.
- **Enclosure / inside vs outside:** flood fill from border to find "outside"; enclosed regions get treated differently.
- **Recolor by neighborhood:** a cell's new color depends on what it touches (e.g., touching a specific color → change).
- **Sort / reorder:** rows, columns, or objects reordered by size, position, or color value.
- **Resize:** tile (n×→3n), downsample (mode per block), crop to object bbox, or output one component alone on a minimal canvas.
- **Line-drawing between landmarks:** connect dots of the same color, extend to grid edge, or project.
- **Conditional recolor by context:** "the object nearest to X changes," "the odd one out changes," "the one with unique property changes."

When demos are few (1–2), prefer the *most specific* rule that fits; when demos are many (5+), prefer the *most general*. That tradeoff mattered repeatedly for me.

## 5. Hard-won specific warnings

- **Lone dots / degenerate cases kill.** Task-5c839a47's test had a single dot; every extension I tried (identity, cross-fill, all-but-dot→3, etc.) was wrong, 8 attempts wasted. If your rule involves "between two markers" or counting, ask early: what does the rule do with exactly one marker? Zero? If the demos all have ≥2 and you can't determine the lone case, consider requesting more demos (I had a demo-request mechanism; use it — it's much cheaper than a wrong submission).
- **Duplicates and near-duplicates in the demo set are information.** If two kept pairs are byte-identical, fine. If they differ by one cell, diff them programmatically — that cell is the rule's fingerprint. I annotated one failed task's notes with exactly which variants remained untried; do the same so you don't resubmit the same wrong idea under a different name (task-1b7868f1: "sub1==sub3 duplicate" — I almost re-tested an equivalent hypothesis twice).
- **Anchor/seed ambiguity:** when multiple candidates fit (e.g., "clean anchors at (13,7) and (12,8) both plausible"), enumerate the possibilities explicitly, rank them, and if the cap allows, test the most likely one and record which failed so the next attempt is genuinely new.
- **Check dimensions first.** Before hypothesizing content rules, verify whether output dims are H×W, 2H×2W, H×W/2, etc. Getting this wrong wastes a submission even with a right idea. Some tasks change dims (tile, downsample, crop); some don't.
- **The rarest color is the signal, but check.** Occasionally the rule concerns the *second* most common, or a color appearing exactly twice. Compute the full color histogram and component inventory (sizes, bounding boxes, counts) before theorizing. A tiny script that prints: color counts, connected components with size/bbox/shape-canonical-form, full uniform rows/cols — run it on every new task. It takes seconds and prevents hours of misreading.
- **Background is usually the most common color, but verify it's actually acting as background** (i.e., the rule treats it as fillable/ignorable). In some tasks the most common color is itself the object (e.g., all-4 grids where 4 is the canvas — my task-3f4fb1a9 program fills pockets of the most common color with 4; the most common color happened to *be* 4).
- **Verify your program actually runs on the demo JSON you saved.** I once wrote a transform whose logic was right but had an off-by-one in a range and didn't notice because I never re-ran the demos. Cheap insurance: a loop `for pair in demos: assert transform(pair['input']) == pair['output']`.
- **Tie-breaks matter.** "Pick the largest component" — what if two tie? "Pick the nearest" — what if equidistant? Prefer tie-breaks that are deterministic and canonical (e.g., by size, then by position reading order). If the demos don't disambiguate, note the ambiguity in your memory file so a future you (or a re-encounter) knows.
- **Keep per-task memory files honest.** Record: rule in one sentence, whether all kept pairs reproduce, number of wrong attempts, and any unresolved ambiguity. Reading your own past notes before starting a new task is one of the highest-value habits — several of my tasks were solved by recognizing "this is like task-X but rotated/mirrored."

## 6. A concrete workflow that worked

1. Load the task. Print grid dimensions and color histogram for each demo.
2. Diff each input/output pair: which cells changed? What colors are involved?
3. Inventory components (size, bbox, count per color). Check for full uniform rows/cols (separators).
4. Hypothesize one sentence: "Output = input where [simple condition on cells/components]."
5. Write `transform`, run on all demos, assert exact match.
6. If mismatch: look at *where* — first wrong cell often reveals the missing clause.
7. If all match: ask "would this survive a different palette, a rotated object, one more instance?" If yes with confidence, predict the test. If a genuine ambiguity remains and the cap allows, submit the more natural reading; record the alternative in memory before submitting so a retry is a genuinely different hypothesis.
8. After the task: write `memory_task-<id>.json` with the rule and outcome.
