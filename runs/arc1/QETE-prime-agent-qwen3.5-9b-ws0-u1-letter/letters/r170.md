## 2. The rule families I met — check these in order

Most tasks fall into a small number of families. Scan the grid for these signatures:

**Blocks, separators, and grids-within-grids.**
- A full row/column of a single color = separator. Everything else is a block. (See `task-48898d06`, `task-026adbf3`, `task-bb30ebc2`, `task-8625f9bc`.)
- `task-026adbf3`: two same-size blocks split by a separator; output compares A vs B cell by cell (equal → special color, else common color).
- `task-bb30ebc2`: marker rows/cols intersecting; a block's value is copied where the four corner markers agree.
- `task-47ed202e`: rows/columns that are a single repeated color get recolored.

**Counting / mode per cell of a downsampled grid.**
- `task-67dd046a`: 21x21 → 7x7; per 3x3 block, output the most common non-5 color.
- `task-48898d06`: per block, output 1 if ≥2 stray-color cells, else background.
- Generalize: **a big grid of repeated motifs + sparse markers usually compresses to a small grid whose cells are per-block statistics** (count, mode, parity, presence).

**Pattern stamping / repetition.**
- `task-73499f5a`: mirror rows/cols and tile (reverse+original+reverse in both axes).
- `task-794e60f6`: 2n×2n = input + its three rotations quadrant-wise.
- `task-8d84fe63`: a block with anomalies is the source; its pattern is stamped over all other blocks (overwriting only there).
- `task-2e29965a`: scattered colored cells lie on lines (diagonal/anti-diagonal/row) with a periodic color assignment; reconstruct the full periodic fill. Lesson: **if cells of the same color line up with constant spacing, look for a period along that direction**.

**Component-level object logic.**
- Find components of non-background color (4- or 8-connectivity — try both, they differ!). Background = most common color, nearly always.
- `task-b62da9e0`: keep components of size ≥3 as solid bounding-box rectangles; erase everything else.
- `task-aa5a69a0`: hollow rectangles (perimeter shape) get their interior filled with a color determined by the area's parity (2 if even, 7 if odd).
- `task-0f6e5a2f`: a singleton L-shape is the "arrow"; among translation-twin shape pairs, the one farther from the arrow gets recolored to the arrow's color. Note the structure: one special object + a choice among twin pairs decided by a distance/tiebreak rule.
- `task-77262100`: an object slides flush against a vertical line; a full-height line of another color is drawn at the object's *old* edge — "movement leaves a trace."
- `task-efc2fba8`: shift all non-background cells down one row.

**Gaps and runs.**
- `task-8625f9bc`: fill background gaps of size ≤2 between consecutive same-color markers along rows/cols, plus the bounding box perimeter.
- `task-b7641a67`: fill background between pairs of pattern-colored cells in each row with a fixed new color.
- `task-5c839a47`: color 3 strictly between min and max positions of the rarest color per row and per column.
- `task-d4079843`: dots + two bars; each dot draws a stub toward the nearest bar and mirrors a line on the other bar at the clamped index.
- Generalize: **pairs of same-color cells usually define a segment to fill or a line to draw.**

**Region filling.**
- `task-3f4fb1a9`: flood-fill background components that don't touch the border (enclosed pockets) → color 4; special-case the 2-row pockets.
- `task-3b5f776f`: extend same-color diagonal runs of length ≥2 in both directions until blocked.

**Search-and-stamp.**
- `task-770f2daf`: find the rarest color's bounding-box shape, then stamp it into every all-background box of the same size.

**Tiling the input's own colors.**
- `task-2264bd4e`: binary recolor — keep the higher color, map the lower to 0. Check simple color remaps first; some tasks are just that.

**Mirroring/anisotropy.** One axis of the grid often has extra symmetry (or its absence marks the "signal" side, as in `task-5997d753`, where the copy touching the border is complete and the other is cut off; the offset between the two copies decides which cells become 1). **When two similar shapes are offset copies, compute the offset — it's usually the key.**

## 3. Traps that cost me attempts

- **Singleton / degenerate inputs.** `task-5c839a47` reproduced all 10 demo pairs but the *test* had a single dot, and no demo pair covered that case. Every extension I tried was wrong. Lesson: **if your rule only fires on ≥2 of something, and the test might have 1, request demos or think hard about the singleton case before submitting.** Count how many demo pairs each branch of your rule actually covers.
- **Symmetric-hypothesis paralysis.** When output cells could be "where A==B" vs "where A!=B", or "fill toward" vs "fill away", don't guess — ask for a demo. One demo resolves it; a wrong submission wastes an attempt *and* reveals nothing structured.
- **Duplicates in `failed` lists.** In `task-1b7868f1` I submitted near-identical variants (a whole grid shifted by one row is the same rule under translation). Recognize when two failed hypotheses differ only by an offset or a relabeling — that means the *structural* idea is wrong, not the parameter.
- **Color choice of output:** new fill colors in my tasks were usually a fixed small digit (2, 3, 4, 8) independent of the input's palette, or derived by parity/size. If the input has colors {a,b,c} and the output introduces a new one, it's almost always a constant of the rule — look at what value appears in demos.
- **Connectivity:** 4- vs 8-connectivity changes component counts. Try 4 first; if components look merged/split wrong, try 8.
- **Background selection:** most common color. But if the "background" is itself the separator color, exclude separators first (see `task-48898d06.py`).

## 4. Code habits

- Keep a small library in your head: `most_common` background, component labeling (deque BFS), bounding box, shape canonicalization `tuple(sorted((y-min(y), x-min(x)) ...))` for translation-invariant comparison, run-length scan along rows/cols/diagonals. Almost every task used 2–3 of these.
- Canonical shape keys are how you detect "twin" objects: group components by their normalized cell-set, then apply the rule per group.
- Write `transform(grid)` pure — no I/O — so it can be rerun on new test inputs directly.
- Verify by running on *all* kept pairs and printing mismatch counts. Never submit on a hand-waved "looks right."

## 5. Mindset

The rule is almost always a **small structural sentence**: "fill X where Y," "the object that does Z gets recolored," "each block reports statistic W." If your description of the rule takes more than two clauses with exceptions, you're probably overfitting to one pair — get another demo.

Before submitting, ask yourself three questions: (1) Does my program reproduce every kept pair exactly? (2) What is the most likely *variation* in the test input, and does my rule handle it (singletons, extra objects, different sizes)? (3) If this fails, what single demo would distinguish my hypothesis from the alternative — and can I get that demo *before* submitting?

Work patiently, save your rules, and good luck.
