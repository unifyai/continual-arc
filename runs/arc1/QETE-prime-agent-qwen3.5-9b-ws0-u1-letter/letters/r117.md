## 1. The workflow that wins

For each task: study the demo pairs, form a rule, write a program, and verify it reproduces every kept pair *exactly* (cell-by-cell, not "approximately"). Only then submit a test prediction. The single most common cause of failure is submitting a prediction from a program that you never ran against the demos. Run it. Check every output cell. If it doesn't reproduce a kept pair, the rule is wrong — revise.

Save a `.json` of the kept pairs and a `.py` with `transform(grid)`, and write a memory file recording the rule and status. Memory files carry across your whole run — a good rule note saves you from re-deriving a solved task later.

## 2. What ARC tasks in this stream actually look like

Most tasks fall into a few families. Learn these templates; you'll recognize them fast.

**Shape propagation / stamping.** One large or special object is a "seed"; every other non-background cell is an anchor where the seed (or its bbox, translated so seed center maps onto the anchor) gets stamped. Or: a rare-color shape is stamped at every offset where its cells all land on background (task-770f2daf). Rule of thumb: find the largest component, and the odd-one-out components.

**Marker-line drawing.** Two bars of one color + dots of another: from the bar facing the dots, draw perpendicular lines through each dot (dot becomes 4); from the opposite bar, draw lines at the same offsets spanning the gap in the dot color (task-d4079843). Objects slide toward a 2-line until adjacent, with a full 8-line drawn on the object's far side (task-77262100).

**Region fill.** Fill enclosed rectangular pockets of background with 4; special case: a 2-row pocket also absorbs its bottom wall when the row below is background (task-3f4fb1a9). Fill hollow rectangle interiors with 2 if area even else 7 (task-aa5a69a0). Fill background cells on a marker's bounding box and small gaps along rows/columns between markers (task-8625f9bc: gaps of ≤2, plus the bbox perimeter).

**Line/row recoloring.** Full uniform rows/columns get a new color (task-47ed202e: uniform rows AND columns → 2). A background cell strictly between two equal non-background cells in its row → 2 (task-b7641a67).

**Symmetry / tiling.** Output = 2x2 block of rotations of the input (task-794e60f6). Or rows become reverse(row)+row and the stack is mirrored and repeated (task-73499f5a). Check output size vs input size first: doubled/tripled sizes scream tiling/mirroring.

**Mask combinations.** Grid split by a solid separator row/column into A and B; output is the cellwise AND of their nonzero masks (task-707635df), or "3 where A==B else common bg" (task-026adbf3).

**Color mapping.** With exactly two colors: smaller → larger, larger → 0 (task-2264bd4e). Diagonal periodic coloring: cells mark residues of (r+c) or (r−c) mod L; fill by pattern (task-2e29965a — try both diagonal directions and pick the consistent one).

**Downsampling.** 3x3 blocks → most common non-5 color (task-67dd046a); blocks separated by full separator lines → 1 if they contain ≥2 stray pixels else background (task-48898d06). Corner-value rules: a block's color is the value at its four corner separator-crossings (task-bb30ebc2).

**Between-dots fill.** Background becomes 3 iff strictly between two dots in its row OR column (task-5c839a47).

## 3. Practical detection recipes

- Background = most common color (Counter). Rare color = next or least common.
- Find full uniform rows/columns to detect separators; segment the grid into blocks between them; band-segment contiguous non-separator rows/cols.
- Components: use BFS/DFS with 4-connectivity by default, but 8-connectivity for tasks where diagonal shapes matter (task-1b7868f1 used 8-connectivity for the seed).
- Bounding boxes, per-row/per-column index lists, and "gaps between consecutive indices" solve an enormous fraction of tasks. Write a small library of helpers once and reuse.
- When shapes repeat, canonicalize: `tuple(sorted((r-min(r), c-min(c)) for ...))` — exact-translation twins pop out.
- Check both orientations/directions (horizontal vs vertical bar, left vs right, r+c vs r−c). Write the code to *test* which case applies rather than hard-coding one.

## 4. Common failure modes I hit — avoid them

1. **Submitting before verifying.** Verify against all kept pairs, always.
2. **Guessing roles wrong.** "Majority/minority" color roles sometimes fail where min/max color ordering succeeds (task-2264bd4e). Try multiple hypotheses and check each against demos.
3. **Wrong connectivity or bbox vs exact-shape assumption.** If a component has holes or stray pixels, don't assume a clean rectangle; check `len(comp) == bbox area`.
4. **Overfitting a quirky demo.** If one pair forces a bizarre special case, the rule is probably wrong; look for the simpler rule that covers all pairs.
5. **Test predictions on unseen inputs:** keep rules as general as the demos justify, but not more general. If two rules both fit the demos, prefer the one that's more "natural" (symmetric, size-independent, no magic constants).
6. **Wrong attempt caps are real.** I lost task-5997d753 after 8 wrong attempts because my rule fit demos but extrapolated badly. When demos are few and ambiguous, spend extra thought on which generalization is most plausible before submitting.

## 5. Code discipline

- Write pure `transform(grid)` functions taking lists of lists of ints, returning the same.
- Recolor into a copy (`out = [row[:] for row in grid]`); never mutate the input.
- Guard index arithmetic: `0 <= rr < H and 0 <= cc < W` everywhere.
- Deterministic tiebreaks: when picking "the" object among several, sort by (size, position) and be explicit.
- Sometimes the answer is "the grid is mostly unchanged" (task-efc2fba8's first read looked like identity but was actually a one-row shift of the non-background pattern). Always diff input vs output of a demo to see exactly which cells changed — this is the single best move. Do it first, every time.
