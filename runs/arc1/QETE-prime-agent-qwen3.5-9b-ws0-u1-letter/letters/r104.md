## The harness rhythm

Each task gives you demo pairs (you may request more, but requests cost) and one test input you must predict. The core loop that worked for me:

1. **Write `programs/task-<id>.py`** with a `transform(grid)` function.
2. **Write `programs/task-<id>.json`** with the demo pairs you keep (input/output grids as JSON lists of row-lists).
3. **Verify locally**: run your program on the kept demos and check it reproduces every one *exactly* before submitting. Almost every wrong submission I made was on a program that didn't even fit the demos, or fit them by accident on a fragile detail.
4. **Keep a memory file** like `memory_task-<id>.json` (and for some tasks I wrote it in `task-<id>.mem.json` — pick one convention and stick to it) recording the rule, the files, and whether the program reproduces all kept pairs. I also updated the harness memory (`memory_task_<id>` entries). Do the same: future-you reads these, and when a task family recurs (several did — see below), the saved rule is worth more than re-deriving it.

## What failed, and how to avoid it

My demos fit, but my final test prediction was wrong — the last regime (mixed rows without full pattern rows) has subtleties in how the offset is chosen. Lesson: when a program fits demos but you're unsure of the test regime, prefer the *simplest* interpretation consistent with demos, and if the harness lets you request demos before predicting, spend the request on the regime you're least sure about.
- **task-1b7868f1**: one wrong attempt from an anchor-offset guess. Lesson above: enumerate parameter variants.
- **task-3f4fb1a9**: the tricky part was that only *solid rectangular* enclosed background pockets fill with 4, plus a weird rule about 2-row pockets absorbing their bottom wall when the row below the wall is background. Narrow rules that "almost" apply are real in ARC — write the exception into memory once you find it.
- **task-73499f5a**: took 2 wrong submissions. The rule (row r → reverse(r)+r; stack reversed/original/reversed) is pure geometry and color-agnostic; when I first guessed content-dependent rules I wasted attempts. If the demo shapes scream "mirror/tile/rotate," try pure geometry first.

## Heuristics that earn their keep

- **Background = most common color** is almost always right; a "minority non-zero color" or "least common color" identifies the object/seed color (task-770f2daf, task-5c839a47).
- **Between-ness**: background cells strictly between two dots (in row or column) get recolored — appears in task-5c839a47 and task-b7641a67 in slightly different forms. When you see scattered dots, ask "what lies between pairs of them?"
- **Colors mapping**: sometimes it's role-based (majority→X), but task-2264bd4e taught me it's sometimes simply `min→max, max→0`. Test both hypotheses against demos; role-based failed there, min/max worked.
- **Uniform-row/col detection** (a row/col where `len(set(...))==1`) is the workhorse for split, block, and separator tasks. Write that 5-line helper once and reuse it.
- **Bounding boxes and connected components** (4-connectivity!) solve a surprising fraction. Keep a small component-finding function handy and paste it.
- **When output dims differ from input dims**, think: downscale by block (task-67dd046a: 3×3 block → most common non-5 color), upscale/mirror-tile (task-73499f5a, task-794e60f6, task-026adbf3's separators), or crop to the separator-defined subgrid (task-707635df, task-bb30ebc2).
- **Fill colors are usually small constants** (2, 3, 4) independent of input colors — but not always (task-aa5a69a0 chooses 2 vs 7 by parity; task-2264bd4e uses existing colors). Derive the fill from demos, don't hardcode blindly.

## Process discipline

- Before submitting, re-run the program on *every* kept pair and diff against the expected outputs character by character. Off-by-one errors (inclusive/exclusive bbox edges, `min+1` vs `min`) are my single largest error source.
- When demos fit but the rule feels arbitrary, look for the *simplest* rule that also explains why the specific constant (2, 3, 4) appears. Constants that appear across many tasks (3 for "matches", 2 for "line/AND", 4 for "line endpoint") are stream conventions worth noticing.
- Write your memory file *before* submitting the prediction, not after. If the run ends mid-task, the memory is what survives — and it's what helped me pick families back up instantly.
- Don't burn submission attempts on small tweaks of a rule that already failed twice; instead request a demo (if available) targeting the ambiguous regime, or enumerate variants offline first.

You're smaller than I am, but this game rewards careful enumeration and bookkeeping more than raw cleverness. Most of my solves came from noticing that the new task is a variant of an old one, or from patiently checking an off-by-one. Do the boring checks, keep your files tidy, and you'll do well.
