When you get a program that reproduces all kept pairs, write a small memory file like:


The rule sentence is the most valuable part — it survives even if the code is slow to re-read. Write it precisely: which colors, which geometry, what gets filled, what stays. My notes like "3 = cells strictly between min and max dot per row/column" saved re-derivations later.

## 4. Rule patterns I've seen (a mini-library)

These rule families come up over and over in ARC. When a new task arrives, scan this list mentally before inventing something from scratch:

- **Count markers per block** (task-48898d06): grid divided by solid separator rows/cols into blocks; output 1 if odd count of a stray color in the block, else background.
- **Compare two blocks split by a separator** (task-026adbf3): grid split by a full uniform row/col into two same-size halves A and B; output same shape, color 3 where A==B, else the blocks' common color.
- **Which half has the dominant color at each position** (task-707635df): split at a centered solid separator line; output 2 where BOTH halves hold their own dominant color, else 0.
- **Stamp a seed pattern** (task-770f2daf, task-1b7868f1): find the rarest/seed component, stamp its bounding-box pattern at every anchor cell (or into every all-background box of matching size).
- **Diagonal/antidiagonal extension** (task-3b5f776f): every contiguous same-color run of length ≥2 extends along its diagonal and antidiagonal in both directions, filling background until blocked by non-background or edge.
- **Fill enclosed background regions** (task-3f4fb1a9, task-b62da9e0): enclosed pockets of background become a fixed color (4), possibly with extra conditions (2-tall pockets extend one row down).
- **Fill gaps between markers** (task-b7641a67, task-8625f9bc): background cells between two markers of a pattern color in a row or column get filled with a fill color (often 2), sometimes only for gaps of size ≤ 2, sometimes plus the bounding-box perimeter of all markers.
- **Fill between min/max of a rare color per row/column** (task-5c839a47): output 3 strictly between the least-common color's min and max position per row and per column.
- **Shift rows down by one** (task-efc2fba8): all non-background content moves down one row; top row becomes background.
- **Move object flush to a line** (task-77262100): a shape shifts horizontally to sit flush against a vertical marker line; its old area becomes background; a full-height line of another color is drawn at the shape's old edge.
- **2n×2n quadrant construction** (task-794e60f6): TL = input, TR = rot90cw, BL = rot90ccw, BR = rot180.
- **Row mirror + stacking** (task-73499f5a): each row becomes reverse(row)+row; the stack is reversed rows, original, reversed again.
- **Downsample by majority vote** (task-67dd046a): 3×3 blocks collapse to one cell by majority of non-5 colors.
- **Color remapping** (task-2264bd4e): two colors present; keep the higher one as background, lower becomes 0.
- **Periodic tiling by diagonal** (task-2e29965a): output is periodic along anti-diagonals (i+j) mod period; infer the period and per-residue color from the given cells.
- **Filter by component size / rectangle-ness** (task-b62da9e0): keep components of size ≥ 3 (or exact rectangles), erase everything else to background.
- **Recolor the twin** (task-0f6e5a2f): among translation-twin shape pairs (same canonical shape occurring exactly twice), pick the pair by proximity to a distinguished singleton object; recolor the farther member.
- **Grid-of-grids reduction** (task-bb30ebc2): find the block color and the line color; locate "special" rows/cols lacking the block color; output a small grid where each cell = the color at the intersection if all four corner markers agree, else background.
- **One-cell marker replacement** (task-aa5a69a0): inside hollow rectangles of a color, fill interior background with a fill color that depends on parity of area.
- **Extend lines/dots along rows/cols to mirror positions** (task-d4079843): seed dots draw a stub toward the nearest bar, turn into 4, and a mirrored full line is drawn on the other bar at a clamped index.

When I recognized a family, I solved in one or two attempts. When I invented novel geometry from scratch, I burned attempts.

## 5. How to infer rules efficiently

- **Background first**: it's nearly always the most common color. Nearly every task is "most cells are background, a few objects change."
- **Count colors**. Rare colors are usually the actors (the seed, the dot, the marker). The second-most-common is often the object color.
- **Find solid separator rows/cols**: rows or columns of a single color (often a color different from background, e.g., all-6 rows) are grid lines. They usually define the block structure, and the output size is (#blocks) × (#blocks) or similar — output dimensions frequently differ from input dimensions. Check early whether the output is a downsampled/upsampled version of the input.
- **Look at object shapes**: Ls, rectangles, lines, hollow rectangles, single cells. Sort objects by size; there's often one distinguished object (the biggest, the only singleton of its color, the only one touching the border) that serves as an anchor or key.
- **Look for exact duplicates**: shapes occurring exactly twice with the same canonical form (translation-normalized) are a strong signal that one is the "source" and one the "target." Something about their position (distance to a key object, which is closer to a line) decides which one changes.
- **Check symmetric constructions**: mirrored rows, rotated quadrants, doubled-and-reflected grids. If the output is exactly double or triple the input in one or both dimensions, test the reflection/rotation family FIRST — it's cheap to verify.
- **Consider per-row vs per-column vs global**: many rules operate independently per row or per column (fill between min/max, fill gaps, shift by one). Try those before anything two-dimensional.

## 6. When the rule doesn't cover the test

If your rule has obvious edge cases the demos don't cover (zero objects of some type, a lone dot, ties in counts, an asymmetric grid), and demos are still requestable, **request demos** rather than guessing. This cost me 8 wrong attempts on task-5c839a47 where the test had a single dot and my two-dot rule was inapplicable. I tried identity, cross, row-only, col-only, longer arcs — all wrong. One demo pair showing the lone-dot case would have solved it in one attempt. The lesson is written in my memory file; don't repeat it.

Conversely, if demos are exhausted or limited, pick the hypothesis that is *simplest and most local* — ARC designers favor rules that a human can state in one sentence over clever multi-condition rules.

## 7. Practical coding notes

- Keep programs dependency-free: plain Python, no numpy unless necessary. Use `collections.Counter` and `deque` for flood fill.
- Structure every program as a single `transform(grid) -> grid` function taking and returning list-of-lists of ints. That's what the harness runs.
- Be careful with 4-connectivity vs 8-connectivity. My task-1b7868f1 components function uses 8-connectivity (`for dy in (-1,0,1) for dx in (-1,0,1)`); task-0f6e5a2f uses 4-connectivity. If a component-based rule fails, try the other connectivity.
- When checking "all cells equal" for a row/col, `len(set(...)) == 1` is the idiom; also check the value isn't background when needed.
- Guard division/modulo and empty-list `max()`/`min()` — test grids sometimes lack the feature your rule keys on; return the input unchanged (or your best guess) rather than crashing. A crashed program is scored as wrong.

## 8. Handling failures

When a submission is rejected:
1. Note exactly what changed between input and your (wrong) output vs. what you predicted — the diff is information about the true rule.
2. Don't thrash: after 2 wrong attempts on one hypothesis family, switch families entirely (e.g., from "fill gaps" to "stamp pattern") rather than tweaking constants.
3. Update your memory file with what was tried and rejected, so a future you doesn't retry it. I record `wrong_attempts` counts and rejected-hypothesis lists.

Note there was one task I never solved — task-5997d753 (offset copies of an object, cut off at an edge). My final program reproduced all kept pairs but the test prediction was still rejected after 8 attempts. If a task family like that returns, be humble about extrapolating: the offset semantics (cyclic shift vs plain shift, which copy is "complete") have multiple readings.

## 9. Task hygiene

- Keep one `.py` and one `.json` per task ID in `programs/`. Don't create variant files like `cand8.json` or `task-XXXX_candidate.json` unless you must — they clutter, and the harness state file is what you'll re-read later. I have leftover candidates (`cand_11_7.json`, `cand_13_7.json`) that only made things confusing.
- One failed-task file exists (`task-1b7868f1_failed.json`) that lists grids that FAILED the rule — useful as negative examples. Consider keeping such a file when you have near-miss hypotheses; knowing what's *wrong* narrows the space fast.
- When the same task returns, first check whether your old program still passes ALL current kept pairs (the harness sometimes adds new pairs). If yes, submit immediately. If a new pair fails it, the new pair tells you what to fix — that's a gift.

## 10. Mindset

ARC rewards the following loop: **look at the grids carefully → form 2–3 candidate rules → test each against all demos in your head or in code → submit the one that survives all of them**. Do not submit the first rule that seems plausible on one pair. The demo pairs exist to disambiguate; use all of them, every time.

Most tasks I solved took one careful pass through this loop. The ones that hurt were the ones where I skipped a step — submitted on one pair, or guessed at an edge case instead of requesting a demo.

Good luck. The library in section 4 plus the checking habit in section 1 will carry you through most of what comes.
