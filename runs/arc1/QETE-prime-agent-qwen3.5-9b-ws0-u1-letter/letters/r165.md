## Workflow

1. **Check for a saved program.** If `programs/task-<id>.py` exists and the memory says it reproduces all kept pairs, load its demo pairs from the `.json`, run the program on the new test input, sanity-check the output by eye, and submit. Do not rewrite a working program.
2. **If no memory exists, request demos early and for free.** Demo pairs are your ground truth. I never regret asking; I often regret guessing. Aim for at least 2–3 pairs before committing. One pair is dangerous: many rules fit one example.
3. **State the rule in words before coding.** "Fill background gaps of size ≤2 between marker cells along rows/columns, plus the bounding-box perimeter" — if you can't say it in one sentence, you don't understand it yet.
4. **Test the candidate rule against every kept pair programmatically**, not by eyeball. A rule that fits 5 of 6 pairs is wrong; the 6th pair is the discriminative one. Find which pair it fails on and what distinguishes that pair.
5. **Budget attempts.** Wrong submissions cost. If you've burned ~3 attempts with no new demos, request demos instead of guessing again. When stuck on a single ambiguous case (I lost 8 attempts on a lone-dot case once), ask for a demo targeted at exactly that ambiguity — early, not late.

## Rule families I saw (check these first)

Grids in this stream cluster into recognizable patterns. Scan for each in order:

- **Separator lines / grids.** Full uniform rows or columns of one color cut the grid into blocks. Output is often one value per block: count of stray cells, whether corners match, parity of something, the block's dominant color, or intersection colors. (`48898d06`, `bb30ebc2`, `3f4fb1a9`, `026adbf3`.) Look for rows/cols that are single-color, and for rows/cols *missing* the dominant color — both are markers.
- **Downscaling.** Blocks of size 2×2 or 3×3 → one cell. Take the most common non-background value in each block, ignoring a designated noise/background color. (`67dd046a`: 3×3 blocks, ignore 5.)
- **Comparison of two halves.** Grid split by a separator into two same-size blocks A, B. Output flags where they agree or disagree, or marks cells equal in both. (`026adbf3`: 3 where A==B, else shared background.)
- **Symmetry completion.** Output is input + mirror: each row becomes row+reverse(row), stacked with reversed copies (`73499f5a`); or 2n×2n built from TL/TR/BL/BR rotations (`794e60f6`); or mirror around a centered separator.
- **Stamping a seed everywhere.** The largest (or rarest-color, or bbox-distinct) component is a template; every other non-background cell (or every empty box of matching size) is an anchor where the template is stamped — sometimes just the bbox, sometimes the full shape including interior zeros. (`1b7868f1`, `770f2daf`.)
- **One distinguished object + a transformation of others.** A singleton with a distinctive property (largest thin angle, a bar of length ≥3) sets a target color or target line; among pairs of identical shapes (exact translation twins), recolor the farther/other one. (`0f6e5a2f`.) Canonicalize shapes as sorted relative coordinates and group by that key to find twins — this was the crucial trick there.
- **Fill toward something.** Extend same-color diagonal runs of length ≥2 until blocked (`3b5f776f`); fill gaps ≤2 between markers; fill enclosed rectangular background pockets (`3f4fb1a9`); draw stub lines from dots toward the nearest bar, dot→4, mirror the line on the second bar (`d4079843`).
- **Move/slide toward a line.** An object slides until adjacent to a full 2-line, then a full 8-line is drawn on the object's far side (`77262100`).
- **Recolor by comparison.** Two colors → keep higher, lower→0 (`2264bd4e`); uniform rows/cols → 2 (`47ed202e`); recolor all of one color to another on one side of a boundary.
- **Identity or trivial shift.** Some tasks are just "shift everything down one row" (`efc2fba8`) or pure identity. Don't over-think a grid whose output is nearly the input — diff the kept pairs and look at what actually changed. The changed cells *are* the rule.
- **Line-color interpolation.** Cells strictly between the min and max positions of the rarest color per row/col get a fixed value (`5c839a47`).

## Coding habits that paid off

- **Background = most common color**, almost always. Second-most-common is usually "the marker". But verify: some tasks designate colors by role (e.g. a full separator line color that is NOT the most common inside blocks).
- **Write one `transform(grid)` function** that takes rows of ints and returns rows of ints. Save it as `programs/task-<id>.py` immediately, and save the demo pairs as `task-<id>.json` in the same format the harness uses. Then write a small check loop over the json. This is cheap insurance: when the same task ID reappears, you replay instantly.
- **Components helper.** Write one 4-connectivity flood fill (and one 8-connectivity when cells of different colors touch diagonally — check the actual grids to decide) and reuse it everywhere.
- **Canonical shapes** as `tuple(sorted((y-min_y, x-min_x) for ...))` — the single most reusable trick for "find the two identical objects" rules.
- **Don't assume the test resembles the demos too strongly.** My recurring failure mode: rule fits all demos, test input has a degenerate case (one dot instead of two, an object at the edge, a shape already touching the line). Ask yourself: *what inputs would make my rule ambiguous or crash?* Handle edges gracefully — when in doubt, leave a degenerate case unchanged rather than erroring or filling aggressively.
- **Prefer conservative outputs.** If two rules both fit the demos, prefer the one that changes fewer cells / leaves ambiguity as background. Identity-adjacent outputs are right more often than bold fills.

## When stuck

- Diff input vs output cell-by-cell and characterize every changed cell: color before, color after, neighbors, row/col context.
- Try the rule "invert on the two colors" and "the rarest color marks where things happen" — many of these tasks are really about one or two special cells.
- Try grouping by shape, by color, by row, by column, by diagonal, before inventing exotic rules.
- If a program reproduces all demos but you must still predict a test output, double-check the test input for the degenerate feature the demos never exercised (a single occurrence, an empty region, an object at the boundary). Decide its behavior deliberately, don't let the code crash or silently do something arbitrary — and if truly uncertain, that is exactly when a demo request is worth more than a submission.
