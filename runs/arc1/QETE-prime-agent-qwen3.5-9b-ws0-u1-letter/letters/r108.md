## 1. The workflow that won

For each new task:

1. **Diff the demos cell-by-cell.** Don't eyeball grids — write out exactly which cells changed and what they became. The changed cells ARE the task; everything else is context.
2. **Check output dimensions first.** Same dims → local recolor/move/fill. Smaller → downscale/condense (task-67dd046a: 3x3 blocks → mode of non-5 colors; task-bb30ebc2: extract cell grid from line intersections; task-026adbf3: split by separator, compare two blocks). Larger → tiling/mirroring (task-794e60f6: 2x2 block of input + 3 rotations; task-73499f5a: each row becomes reverse+itself, stack reflected and tripled).
3. **Look for structure elements before objects:** full uniform rows/columns (separators — tasks 026adbf3, 707635df, 48898d06, 8625f9bc, 47ed202e all hinge on them), runs of ≥2 of one color, and thin diagonal lines.
4. **Classify the change:** fill (enclosed pockets, interiors, bboxes), move (slide/translate), recolor (value rules, between-ness), extend (stamping, tiling, drawing lines).
5. **Write the program, run it against ALL kept demos, and only submit a test prediction your program actually produces.** This one discipline is worth more than cleverness.

## 2. The rule catalog from my run (prioritize these hypotheses)

- **Value-order recolor** (task-2264bd4e): two colors a<b, a→b and b→0. I wasted an attempt on majority/minority roles; use min/max of color VALUES first when two colors interact symmetrically.
- **Between-ness** (tasks-b7641a67, 5c839a47): a background cell becomes an action color if between two same/non-background cells in its row (or column). Distinguish early: *immediately flanked* (neighbors j−1, j+1 equal) vs. *strictly between min and max* dot positions anywhere in the line. Also note axis: row-only, col-only, or both.
- **Enclosed pockets** (task-3f4fb1a9): background regions not touching the border, that are solid rectangles, get filled (with 4 there). Expect systematic exceptions — a 2-tall pocket absorbed its bottom wall only when the row below was background across the full width; non-rectangular pockets unchanged. Details like this are what separate fitting 3 demos from fitting all.
- **Hollow rectangle parity fill** (task-aa5a69a0): rectangle interiors filled with 2 if area even, 7 if odd. Parity clauses show up; check it.
- **Noise removal / bbox consolidation** (task-b62da9e0): fill bbox of each non-bg component of size ≥3 with its color; everything else → background. Variant (task-8625f9bc): fill bg cells on the bbox perimeter of markers and in gaps between runs of ≥2 markers.
- **Stamping** (tasks-1b7868f1, 770f2daf): find the template object (largest component, or minority color's bbox pattern) and stamp it — translated so its bbox *center* maps onto each anchor cell — copying the bbox as-is, holes and zeros included.
- **Object slides to a line + a full line drawn** (task-77262100): object moves until adjacent to the solid 2-line on its side; a full 8-line is drawn just outside the object's far side. Write it orientation- and side-symmetric from the start.
- **Separator + cellwise combination** (tasks-026adbf3, 707635df, 48898d06): split into blocks at uniform separator rows/cols, then output per-block: equality→3 / AND-of-nonzero→2 / stray-color-count threshold→1 or bg.
- **Diagonal periodicity** (task-2e29965a): colored cells mark diagonals; fill whole grid with P[(r+c) mod L] or P[(r−c) mod L], L = number of colors. Try both directions.
- **Conditional shift** (task-efc2fba8): one non-bg block; if bottom gap == top gap + 1, unchanged, else shift down one row. When choosing between "move" and "no-op," look for a stability/equality condition.
- **Selective line recolor** (task-47ed202e): rows/columns uniformly filled with a particular color become 2.
- **Downscale by k** (task-67dd046a): per k×k block, mode of colors *excluding* a designated don't-care color. Note the exclusion wrinkle — one color is often a wildcard.
- **Dot-and-bar drawing** (task-d4079843): from the bar facing the dots, draw perpendicular lines through each dot (dot becomes 4); from the other bar, same offsets, full span, in the dot color.

**Action colors:** 2, 3, 4 appear over and over as output-only fill colors. If your rule invents a color, guess among those first and verify.

## 3. My failures — read these files, they cost me real attempts

**task-1b7868f1** (`task-1b7868f1_failed.json`, plus cand8/cand_11_7/cand_13_7): I submitted two *near-identical* predictions (one was an outright duplicate) and my candidates differed by one or two cells. Wrong lessons to draw would be "tweak and resubmit." The right lesson: when a prediction fails, the *hypothesis* is wrong, not a parameter. Here the fix was rethinking which cells are anchors and aligning stamp bbox-center to anchor (not top-left). **Never submit the same or barely-different output twice.** Diff your new prediction against your previous submissions before submitting. Also: keep a failed-submissions file with a note about what each attempt assumed — it's how I finally saw the anchors were the problem.

**task-5997d753** (8 wrong attempts, cap reached): my rule had two regimes (full-pattern reference rows vs. best-shift alignment between first and last mixed blocks), and my alignment used a heuristic score `(mismatches, out-of-range, …)`. It fit all demos but failed the test. Lesson: when a rule requires *choosing an alignment/offset*, derive it exactly from structure (an edge, a line, an object position) rather than minimizing a heuristic. Heuristics interpolate; structure generalizes. And when attempts run low, submit your highest-structural-confidence hypothesis, not the most-tuned one.

## 4. Program-writing habits

- Keep a reusable checker: load `task-XXXX.json`, run `transform`, assert cell equality on every pair. Two minutes, saves submissions.
- `collections.Counter(...).most_common(1)[0][0]` for background; know that ties break by insertion order.
- Write a 4-connected flood-fill/DFS component helper once; you'll use it constantly.
- numpy for tiling/rotation (`np.block`, `np.rot90`, `np.rot90(a, k)`); a 2-liner for rotation-quadrant outputs.
- Write rules symmetrically (both axes, both sides) on the first pass — retrofitting symmetry costs attempts.
- Keep candidate predictions in clearly named files *with a note of the hypothesis each embodies*, and clean up debris; my leftover cand files were only useful because the failed-file note explained them.

## 5. Memory hygiene

Maintain a per-task memory file with: file paths, "program reproduces all kept pairs: yes/no," and — most importantly — a **one-line statement of the actual rule, including subtle clauses**. "Program reproduces all pairs" is nearly useless to future-you; "fill enclosed rectangular bg pockets with 4; 2-tall pockets also absorb bottom wall iff row below is bg across width" is gold. Skim your memory entries before each new task: several of my fastest solves were re-cognitions of earlier families (b7641a67 fell quickly because I'd seen 47ed202e and 5c839a47).

Also read my two memory systems side by side: the harness_state entries hold the final refined rules; the `.mem.json` files hold task-specific details. When they conflict (task-efc2fba8 has two program versions), trust the later memory version and verify against the demos yourself.

## 6. When stuck, in order

1. Count changes per color; identify output-only colors (2/3/4).
2. Count components of changed cells: one big → object-level rule (move/fill-bbox/slide-to-line); many small → local rule (between-ness, neighborhood, parity).
3. Hunt lines: full rows/cols, runs ≥2, thin diagonals.
4. Compare dims for scale/tiling.
5. Walk the catalog in §2.
6. If two rules both fit, prefer the one with fewer magic constants *unless* it ignores a demo — a rule with one ugly-but-systematic clause that fits everything beats a clean rule that fits most.
7. With one demo only, favor the most canonical rule consistent with internal structure, biased by your memory of similar past tasks.

The meta-skill: extract the minimal changed-cell set, classify it, match a family, write it general and symmetric, verify mechanically, and never gamble a submission. The families above will not cover every future task, but this search shape will.

Good luck. Be careful, be mechanical, and let your failures teach you — they're the cheapest lessons you'll ever get.
