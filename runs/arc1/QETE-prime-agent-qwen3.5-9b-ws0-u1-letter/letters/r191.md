## The harness, briefly

For each task you see a test input and can: (1) submit a prediction, (2) request demo pairs, (3) save files to `programs/task-<id>.json` / `.py` and memory files. Wrong submissions are counted and capped. When you've saved a program that reproduces all kept demo pairs, the harness checks your test prediction. Your state persists across tasks — the files I saved are already at your paths.

## Core workflow that worked

1. **Before submitting anything, write the rule down in plain words.** If you can't state the rule in one sentence ("fill enclosed rectangular background pockets with 4"), you don't understand the task and will likely guess wrong.
2. **Get demo pairs early.** One or two pairs teach more than an hour of staring at the test input. In particular: if the test input looks *unusual* (e.g., a single instance of a pattern, or a lone object), request demos immediately — don't extrapolate. My worst failure (task-5c839a47) burned 8 attempts on a lone-dot case because I kept trying extensions of a rule built on multi-dot demos. If your demos never show the test's configuration, that's a red flag, not an invitation to improvise.
3. **Write a Python `transform(grid)` program** and verify it reproduces every kept demo pair exactly, then apply it to the test. Never predict by hand when a program can do it. I saved several of these; they're readable templates.
4. **Test the rule against *every* pair**, not just the first. Rules that fit pair 1 and break pair 2 are common. My programs track `program_reproduces_all_kept_pairs: true` — earn that label before submitting.
5. **Before submitting, sanity-check your rule against the test input's structure.** Does the test have the same objects, separators, counts as the demos? If not, your rule may not apply.

## Recurring rule families on this stream

Learn these patterns — they came up again and again:

- **Separator-split grids.** A full uniform row or column splits the grid into blocks; the output summarizes each block (color at intersections, majority color, whether the two halves agree — that last one gives output `2` where both halves hold their dominant color, background elsewhere). Check for full-solid rows/cols *first*; also check for rows/cols that are a single repeated color (they often become `2` wholesale).
- **Enclosed pockets.** Flood-fill background components; ones not touching the border and rectangular get recolored (often 4). Watch for one-cell-thick slots that also get filled.
- **Sparse-dot grids.** The rarest color marks positions; output is derived per row/column (fill strictly between min and max marks, odd counts inside cells, etc.).
- **Stamping/tiling.** Find the seed (largest component, or bbox of rarest color), then stamp it at every anchor (each other non-background cell, or every empty box of matching size).
- **Mirror/periodic completion.** Output may be mirror+concatenate, or periodic along anti-diagonals — infer the period from the colored lines given.
- **Objects move toward a line** (color 2 line, or the border); a marker line (color 8) is drawn at the old position.
- **Recolor-by-relationship.** Among pairs of identical shapes, recolor the one farther from a special anchor object.

When a new task resembles one of these families, try the family's template first — but *verify* it against demos. Half-matching a template is the most common wrong answer.

## Mistakes I made so you don't

- **Duplicate submissions.** I once submitted two predictions that differed only in a single background cell choice, wasting an attempt. When two candidate rules differ on just a few cells, that's a sign the demos don't disambiguate — request another demo instead of guessing.
- **Testing rules only on demos I built them from.** Always hold out: derive the rule from pair 1, check pair 2 blind.
- **Trusting "one demo fits all."** With a single demo pair, many rules fit. With 2+ pairs, wrong rules die fast. Demos are cheap; wrong submissions are not.
- **Over-engineering.** My working programs are short: Counter for background, flood fill, bbox, translate. Resist clever distance-metric rules unless the data forces them.
- **Contamination note:** I once found labels in saved files that looked like extra demo pairs but weren't real ones. Only trust pairs you actually received through the harness this run.

## Practical habits

- Keep a small memory file per task (`task-<id>.mem.json`) with: solved?, wrong_attempts, the one-sentence rule, file paths. It saved me repeatedly when a variant of an old task reappeared.
- Name the background color (`Counter(...).most_common(1)[0][0]`) in nearly every program — it's the constant in ~80% of rules.
- Components: use 4-connectivity by default, but check 8-connectivity if components look fragmented (one task's seed bbox stamping needed it).
- When output dims differ from input dims, that itself is information: blocks, downscaling, 3× mirror-stacking, rotation tiling. Compute expected output size *before* writing the rule.
- If you've solved a similar task before, load its saved program and adapt it — but re-verify on the new demos; same surface, different rule is a real trap.

## When stuck

State the observed transformation as a minimal sentence. If you have two competing rules, find or request a demo that distinguishes them. If the test input has a configuration your demos never showed, request demos rather than guess. And when your attempts run low, prefer the simplest rule that fits all pairs over the cleverest one that fits most.

Good luck. The rules are simpler than they look; the discipline of verifying before submitting is what actually wins.
