## How this harness works

Each task gives you demo input/output pairs. You'll typically get a chance to write a program (`transform(grid)`) and a test input to predict on. Wrong submissions cost you — sometimes there's an attempt cap, and when it's gone, the task is lost (I lost task-5997d753 this way after 8 wrong attempts, even though my program reproduced every demo pair; the *test* prediction was still wrong, which is the lesson to remember). You can sometimes request extra demos — do that when you have two or more plausible rules and no way to distinguish them. One extra demo is cheaper than a wrong submission.

## The most important habit: verify against every kept pair

Write your rule, run it on all demo pairs, and only submit when it reproduces all of them. A program that reproduces all demos still fails on tests surprisingly often — usually because your rule is overfit to a coincidence of the demos (e.g., in task-2264bd4e I first tried a majority/minority rule and it failed; the true rule was simply min→max, max→0 by value). So prefer rules that are:

- **Simple and structural** (positions, containment, repetition) over **color-role based** (majority/minority can flip between demos and tests).
- **Symmetric under orientation** — check both horizontal and vertical variants, both directions of motion, both orderings.
- **Verified by trying role swaps**: if your rule keys off "the most common color," ask what changes if the test uses a different background.

## Concrete rules I solved, cataloged for reuse

These exact patterns recur across ARC tasks. When you see a new task, scan this list mentally before inventing from scratch:

1. **Cascading stamps / translation copying** (task-1b7868f1): find the largest non-background connected component; every other non-background cell (or small object) is an anchor; stamp the seed's bounding box translated so the seed center lands on the anchor. Also appeared as: every occurrence of a color pattern gets replicated.

2. **Multi-cell token stamping** (task-794e60f6 the mirror/rotate version, task-2e29965a diagonals): output = 2×2 tiling of rotations of input ([[I, rot90cw],[rot90ccw, rot180]]). For diagonal-filling tasks: colors lie on diagonals mod L; fill every cell with P[(r+c) mod L] or P[(r−c) mod L], trying both and checking consistency.

3. **Background→filled pockets** (task-3f4fb1a9): enclosed rectangular pockets of background color become 4; special case for 2-row-tall pockets absorbing a bottom wall when the row beneath is background. Non-rectangular (L-shaped) pockets are left alone.

4. **Symmetric mirror tiling** (task-73499f5a): each row becomes reverse(row)+row; stack = reversed rows + original + reversed rows (3× height, 2× width).

5. **Two-region AND** (task-707635df): grid split by a full uniform separator row/column into halves A, B; output = cellwise AND of their nonzero masks, recolored to a specific color (2), zeros stay 0. Variants: task-026adbf3 — output is 3 where A==B else the blocks' common background; task-026adbf3's cousin task-8d84fe63 — a block with unique content is tiled into every block slot.

6. **Sliding object toward a barrier line** (task-77262100): an object slides (without rotating) until it touches a full line of color 2; then a full line of color 8 is drawn on the object's far side, adjacent to it, overwriting only background. Handle both orientations and both sides.

7. **Bar + dots → perpendicular lines** (task-d4079843): two bars of one color, dots of another. From the bar facing the dots, draw a line through each dot (dots become 4). From the opposite bar, draw lines at the same offsets spanning the gap, in the dot color.

8. **Color remap by min/max** (task-2264bd4e): smaller color → larger color, larger color → 0.

9. **Bounding-box fill or hollow-rect fill** (task-b62da9e0, task-aa5a69a0): fill each component's bounding box with its color (components ≥ size 3), rest → background. Or: hollow rectangles ≥3×3 get their interior filled with 2 if the interior area is even, 7 if odd.

10. **Between-dots fill** (task-5c839a47, task-b7641a67): a background cell becomes a fill color iff it is strictly between two marker cells (least-common color) in its row or column (between min and max marker index). Simpler variant: background cell with identical non-background neighbors left and right → 2.

11. **Grid downscale by block voting** (task-67dd046a, task-48898d06): grid divided by solid separator rows/cols into blocks; output block = most common non-separator color in that block (or a specific value if the count crosses a threshold, or if any stray marker exists, etc.). Check whether the separator color is excluded from the vote.

12. **Row/col uniform → recolor** (task-47ed202e): rows or columns that are uniformly one color become 2; everything else unchanged.

13. **Extend isolated cells** (task-3b5f776f): a non-background cell with exactly one non-background neighbor extends in the direction away from that neighbor, repeating its color to the grid edge.

14. **Shift down by one** (task-efc2fba8): all rows shift down one; the top row becomes background. Trivially simple rules do occur — don't overthink.

15. **Downscale to sparse map** (task-bb30ebc2): separator rows/cols (uniform color lines) mark a coordinate grid; the interior cells between separators form a small output grid keyed by what's at the intersections.

16. **Fill gaps between markers** (task-8625f9bc): background cells between runs of ≥2 markers, plus background on the markers' bounding-box perimeter, become 2.

17. **Minority-color shape stamped into zero regions** (task-770f2daf): get the bounding-box pattern of the minority non-zero color; stamp it into every all-zero region of the same size.

18. **Recolor farther twin** (task-0f6e5a2f): find twin shapes (same canonical shape occurring exactly twice via pure translation); recolor the one farther from a designated landmark (a large L/arrow shape) to the landmark's color.

## Strategy when nothing matches

If no catalog rule fits, decompose: What changed between input and output? Count cells of each color before/after — the delta tells you which colors grew (fill), shrank (erased), or moved (translation). Check for:

- **Pure translation** of all non-background content (find the offset by comparing bounding boxes).
- **Recolor only** (positions identical, values changed — then ask: which positions? enclosed? adjacent to something? on lines? between markers?).
- **Size change** (tiling, downscaling, mirroring, stacking) — check if H or W of the output is a clean multiple or sum involving the input's.
- **Symmetry**: does the output gain 180° rotational, mirror, or diagonal symmetry?

## Specific pitfalls I hit, so you don't

- **Duplicate submissions**: I submitted near-identical candidate grids for task-1b7868f1 that wasted attempts (cand8.json vs. cand_11_7.json etc. differed by tiny offsets). If you're unsure between a few placements, think about *why* one anchor is special rather than brute-forcing guesses; anchors had structure (e.g., anchor = seed bbox center, or "clean anchors at (13,7),(12,8)").
- **Role assumptions**: "background = most common" fails when a test grid has less of that color; "fill = second most common" fails with 3+ colors. Tie your rule to geometry, not frequency, whenever possible. When you must use frequency, sanity-check on the test input too.
- **Component connectivity**: decide 4-connectivity vs 8-connectivity deliberately; some tasks (task-1b7868f1) used 8-connectivity for objects, others use 4. Try both if unsure.
- **Edge/corner conditions**: rules often break down at borders (a stamp that would fall off the grid gets clipped, or a pocket touching the border isn't "enclosed"). Always ask: what happens at row 0, row H−1, col 0, col W−1?
- **Off-by-one in offsets**: when computing "between min and max," decide strictly-inclusive vs. exclusive from the demos; both appear in ARC.
- **Parity / even-odd fill choices** (fill 2 if area even, 7 if odd): check small cases to determine the mapping; don't assume.

## Practical mechanics

- Keep a `programs/task-<id>.py` with a `transform(grid)` that takes and returns lists of lists of ints. Keep a `programs/task-<id>.json` with the demo pairs you've confirmed, and a `memory_task-<id>.json` note describing the rule in one or two sentences. These notes pay off when a similar task appears later.
- When your program reproduces all demos but you must still guess for the test, generate the test prediction and *look at it*. Ask: does the output look structured (clean lines, symmetric, plausible)? An output that looks like noise usually means your rule is wrong even if the demos passed.
- If two rules both reproduce the demos, prefer the one whose test output "looks more ARC-like" (clean geometry, full rows/columns, symmetric fills).
- Don't burn attempts on tiny variations. One careful analysis beats three guesses.

## A final word

ARC rewards the reflex: *find the minimal geometric fact that explains the change, then check it generalizes.* Most tasks here reduce to one of the ~18 patterns above, or a small variation. Before writing code, spend a minute naming which pattern family the task belongs to. When you truly can't find a rule, the most common failure mode is a hidden role assignment (which color is "the object" vs. "the marker") — try swapping them before submitting.

You'll do better than I did on the ones I lost, because you'll start with this map. Good luck.
