## 1. The single most important discipline: verify before you submit

Your program reproducing the kept demo pairs does NOT mean your rule is correct. It means the rule is *consistent with* the demos. Many rules are consistent with the same few pairs. I have burned submissions on rules that reproduced 100% of demos and were still wrong on the test — the "8/8 wrong attempts while reproducing all pairs" memory of task-5c839a47 exists precisely because of this.

So the ordering of confidence is:

- Rule reproduces all kept pairs → necessary, never sufficient.
- Rule is simple and *general-sounding* ("extend runs along diagonals", "fill enclosed pockets", "shift by one row") → better than a rule full of special cases.
- Rule makes a *strong prediction* about the test input that you can reason about independently → best.

When you have a candidate rule, write it down in one sentence. If the sentence has more than two "except when" clauses, you're probably overfitting to the demos.

## 2. Ask for demos when a structural element is underdetermined

The clearest example from my run: task-5c839a47 has a rule about dots ("least-common-color cells") with pairs of dots, and the test had a *single* dot. The per-row/column rule says nothing about a lone dot, and I guessed identity, cross, row-only, col-only, and five more variants — all wrong, 8 attempts wasted. The lesson I wrote into memory is exactly what you should internalize: **if the test input contains a configuration your demos never covered (a lone dot, a shape that appears once, a color that appears once), request demo pairs early** before you start guessing. One demo request is much cheaper than three wrong submissions.

Conversely: if your demos cover the test configuration and your program reproduces them, submit with confidence. Don't second-guess a verified program — several of my tasks (77262100, 770f2daf, 0f6e5a2f, 8625f9bc) were solved at zero or one wrong attempt purely because the program was verified against reproducing pairs first.

## 3. How to actually find the rule: a working search order

When I look at a fresh pair, I check these in roughly this order, because they cover the majority of tasks:

1. **Size change.** Does output = input dims? Output smaller (crop/mosaic/projection)? Output larger (tiling, 2x2 quadrant arrangement, doubling)?
   - Same dims: recoloring, moving, drawing lines, stamping.
   - Smaller: blocks of the input map to cells of the output. Look for full uniform separator rows/cols dividing the grid into blocks; each block maps to one output cell (task-48898d06, task-bb30ebc2, task-026adbf3, task-67dd046a are all variants of this — downsample by mode/count/match).
   - Larger by exact factor 2 or 3: tiling/quadrants. task-794e60f6: TL = input, TR = rot90cw, BL = rot90ccw, BR = rot180. task-73499f5a: rows become reverse+double, then stack reversed/original/reversed.

2. **Count the colors and their roles.** Almost always: most common = background. Then ask of each other color: is it a *marker*, a *line/bar*, a *seed*, a *rarest color*? Tasks usually have a tiny cast: bg + 1 marker + 1 fill color (often 2, 3, or 4). A good heuristic: the fill color in the output is very often a small number (1,2,3,4) that may not even appear in the input.

3. **Connectivity.** Extract connected components (4-connectivity for same-color objects; 8-connectivity when shapes look like they're touching diagonally). Count components, their sizes, their bounding boxes. Look for: a unique largest component (seed), exact-translation twins of the same shape (one gets recolored — see task-0f6e5a2f), a singleton thin angle that acts as an arrow/direction pointer.

4. **Geometry.** Bounding boxes, centers, alignment to rows/cols. Many rules are "every non-bg cell is an anchor; stamp the seed's bbox centered at it" (task-1b7868f1) or "shape moves flush to a line; old spot becomes a marker line" (task-77262100).

5. **Directional extension.** Runs of length ≥2 extending along rows/cols until blocked (task-b7641a67: fill bg gaps in rows; task-3b5f776f: extend runs along both diagonals until blocked). This family is common: *something propagates from a seed along lines until it hits something*.

6. **Enclosure and pockets.** Flood-fill the background; regions not touching the border get filled (task-3f4fb1a9: enclosed rectangular bg pockets → 4). Watch the special cases: pockets with a stem beside them, 2-tall pockets extending down.

7. **Shifts.** All non-bg cells shifted by one row/col (task-efc2fba8: everything down one, top becomes bg). Cheap to test.

When one hypothesis fails to reproduce the demos, don't throw away the *family* — throw away the *specific detail*. If "fill gaps ≤ 2" fails, try "fill all gaps". If "center stamp" fails, try "top-left stamp".

## 4. Structural conveniences that recur

- Full uniform rows/cols are nearly always *separators or guide lines*. Find them first: `rows where len(set(row))==1`, same for columns.
- The 3x3-block decomposition (task-67dd046a): output = one cell per 3x3 block, value = most common non-5 color in the block.
- Periodic tiling (task-2e29965a): if colored cells align on diagonals (i+j) or rows or difference-diagonals, the whole grid is periodic in that family; infer the period from the given colored diagonals and tile. This is a very elegant pattern to watch for — a few colored cells determine everything.
- Symmetry/mirroring: outputs that look like the input mirrored and concatenated. `r[::-1]+r` doubled, stacked with reversals, was exactly task-73499f5a.
- When output is a mosaic of one cell per block, the block's value can be: mode of block (67dd046a), parity of stray count (48898d06), cell where A==B across two halves (026adbf3), or the color at the intersection of guide row/col values (bb30ebc2).

## 5. Recurring color semantics I've observed

- 2 is very often the "fill" color for gaps/lines drawn by the transformation.
- 3 often means "match/agreement" (026adbf3: cells where two blocks agree become 3).
- 4 often means "filled pocket" or "marked seed position".
- 7 and 9 show up as textured/noisy secondary colors inside pattern bands.
- But do not hard-code this; derive roles from the pair, and note the fill color sometimes equals the second-most-common color rather than a fixed number.

## 6. Things about the harness

- Save your program to `programs/task-<id>.py` with a `transform(grid)` function, and the kept demo pairs to `programs/task-<id>.json`. Write memory files (`memory_task-<id>.json` or `<task>.mem.json` — I was inconsistent; pick one and be consistent) stating the rule in one sentence, how many pairs it reproduces, and any unresolved cases. Future-you, mid-task, reads these.
- Keep a "failed attempts" note when a task is unsolved (see my `task-1b7868f1_failed.json` — listing which hypotheses are exhausted prevented me from retrying duplicates). This saved me at least twice.
- Keep the demo JSON exactly as given — they are your regression tests. Before any submission, rerun your program over every kept pair and diff. It takes seconds and catches typos that would cost a submission.
- Names of files matter less than the habit of writing down: (a) the rule in one sentence, (b) what's verified, (c) what's unresolved.

## 7. Thinking about the test input specifically

The test input usually stresses the exact part of the rule your demos are weakest on. So after forming the rule, do this deliberately:

- For each *kind* of object/configuration in the test input, ask "do my demos cover this kind?" If not, request demos.
- Run the rule mentally (or in code) on the test input and sanity-check the output looks *plausible as an ARC answer*: mostly background with a clean, simple edit; not a weird smear. ARC answers are almost always clean. If your predicted output is messy or asymmetric in a way the demos never were, suspect your rule.
- If two rules both reproduce all demos but disagree on the test, pick the one whose test prediction is *simpler* and more consistent with the demo outputs' style (amount of background, symmetry, size).

## 8. Cost management

You have a limited budget of wrong submissions per task. My rough policy, which served me well:

- 0 wrong: submit when program reproduces all kept pairs.
- 1 wrong: don't rewrite from scratch; find the *minimal* variation of the rule that changes the test prediction in the direction of plausibility.
- 2+ wrong: stop guessing blind. Request demos if any structural element of the test is uncovered. If demos can't disambiguate, prefer the simplest remaining hypothesis and accept the loss — then write the failure down.
- Never submit the same rule twice with cosmetic changes. Keep a failed-hypotheses list per task and check it before each attempt.

## 9. A few concrete pitfalls

- 4- vs 8-connectivity: shapes that look like one object under 8-conn are two under 4-conn and vice versa. Try both if component counts look off.
- Bounding-box stamping can overwrite other objects; check whether the demos show overwriting or whether later stamps lose to earlier ones. Ordering of stamping matters and demos sometimes only reveal it in one pair.
- "Between min and max" rules (rows/cols/diagonals) exclude the endpoints. Off-by-one on strictness ("strictly between" vs "inclusive") cost me real attempts. Check every pair cell by cell, don't eyeball.
- When the rule involves a *pair* of twin shapes and a pointer, the selection (which twin is recolored) is the hard part; encode the selection criterion carefully (task-0f6e5a2f used distance to a pointer's horizontal arm, tiebreak on size).
- The seed for "stamp" rules is usually the largest non-bg component; its bbox center (not centroid) is the anchor. Centroid vs bbox-center matters when shapes are L-shaped or hollow.
