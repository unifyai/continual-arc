## What the harness actually wants

You will be given ARC tasks. For each one you can (usually) request demonstration input/output pairs, and you can submit a program (a `transform(grid)` function saved as a .py file) plus your prediction for the test grid. Key operational lessons:

1. **Save your work in files with predictable names.** I use `programs/task-<id>.py` and `programs/task-<id>.json`. The .json holds the kept demo pairs in a readable format. Write a separate memory file per task too. Future-you (and the harness) benefits from this being consistent.

2. **Programmatically verify before submitting.** This cost me wrong attempts: I hand-transcribed a predicted grid and it was off by one column. Always run your `transform` on the test input, serialize the output, and diff-check that what you're submitting is exactly what the program produced. Never eyeball-transcribe a grid.

3. **When you think you've found the rule, run the program on every kept demo pair and assert 0 mismatches.** If any pair fails, your rule is wrong or incomplete — do not submit on faith.

4. **Track failed submissions per task in memory.** When you hit the attempt cap (I hit it twice — task-5997d753 and task-5c839a47's lone-dot case), you lose the task entirely. A wrong guess is expensive; a demo request is cheap. **If the test grid looks structurally different from all demos (e.g., only one dot when every demo has many, or an empty pattern slot), request more demos instead of extrapolating.** That single habit would have saved me two whole tasks.

## General puzzle-solving strategy that worked

**Step 1: Count the colors.** Background = most common color. Rare color = usually the actor/seed. Nearly every task here was background + one or two actors + maybe a fixed output color (often 2, 3, or 4 — output colors frequently don't appear in the input at all; 4 especially means "fill/add", 3 means "mark matches", 2 means "recolor/insert").

**Step 2: Connected components.** For every task, build components (usually 4-connectivity; sometimes 8 — try 4 first). Ask: how many components, what sizes, what shapes (bbox, L-shape, rectangle, ring)? Most rules are about relationships between components: same shape twice, one component much bigger than the rest, components that are translations of each other, components with holes.

**Step 3: The recurring rule families.** This stream strongly clustered. When you see a new task, check these in order:

- **Stamping/tiling:** a seed shape (often the rare color or largest component) gets copied to every position matching some condition — everywhere its cells land on background (task-770f2daf: stamp rare-color shape at all offsets where its cells are all 0), or at every non-background cell (task-1b7868f1: stamp the largest component's bbox centered on each anchor), or periodic repetition (task-8d84fe63: find the block with the most "anomalies" and tile its pattern across all blocks).

- **Grid partitioning by separator lines:** full uniform rows/columns split the grid into blocks (task-48898d06, task-026adbf3, task-67dd046a, task-bb30ebc2, task-707635df). Then the output is usually a small grid summarizing each block: block = 1 if it contains a stray color, or the mode of the block ignoring background (with 3x3 downscaling: mode ignoring color 5), or corner-color propagation, or "3 where the two halves agree". Learn the pattern: find solid separator lines, extract blocks, compute a per-block summary.

- **Comparison of two halves:** grid split into two equal blocks by a centered separator → output marks where they agree or differ (task-707635df: 2 where both halves have their own dominant color; task-026adbf3: 3 where equal else common color).

- **Filling enclosed regions:** flood-fill background components from the border; untouched ones are enclosed. Fill with 4 (task-3f4fb1a9, task-aa5a69a0). Watch for refinements: only *rectangular* pockets count; a 2-tall pocket may also absorb its bottom wall row under a specific condition. Write the refinement into the rule only when a demo demands it — don't guess refinements, and don't add conditions the demos don't force.

- **Lines toward markers:** a bar + dots → draw lines from the bar to each dot, with one special cell colored 4 (task-d4079843). Determine orientation, direction (dots above/below/left/right of bar), and a mirror bar gets a second set.

- **Object + line interaction:** object slides until adjacent to a full line of color X, and a full line of color Y is drawn on the object's far side (task-77262100). Both orientations, both sides.

- **Diagonal/antidiagonal extension:** same-color runs of length ≥2 on diagonals extend in both directions until blocked (task-3b5f776f). Splitting lines by r-c and r+c is the easy way.

- **Row/column interval fill:** cells strictly between the min and max of the rare color along each row AND column get filled (task-5c839a47). Note the failure mode: a test with a *single* dot had some other rule entirely. Many demo pairs ≠ test behavior when structure differs.

- **Bbox operations:** fill the bounding box of each component of size ≥3 with its color, delete everything else (task-b62da9e0); or fill background cells on the bbox perimeter plus small gaps between markers (task-8625f9bc, gap ≤ 2, fill 2).

- **Global recolor / image ops:** map color A→0 keep B (task-2264bd4e: keep higher color, lower becomes 0); shift rows down by one (task-efc2fba8); mirror rows and stack reversed/original/reversed (task-73499f5a); quadrant rotations into a 2n×2n output (task-794e60f6: TL=input, TR=rot90cw, BL=rot90ccw, BR=rot180); periodic stripes with period read off diagonal lines (task-2e29965a); scale up with knight-like or symmetric fills (task-794e60f6); mark bg between identical neighbors (task-b7641a67: bg cell between two identical non-bg cells in a row becomes 2); solid single-color rows/cols become 2 (task-47ed202e).

- **Attribution by shape/twin classes:** canonicalize shapes (sorted relative coordinates), find classes where exactly two members share a shape, use geometry (distance to a distinguished object's arm) to pick which one recolors (task-0f6e5a2f).

**Step 4: Verify against all demos, then be careful about the test.** The most common way my fully-demo-consistent programs still failed: the test had a degenerate structure (1 component instead of 2, empty slots, a lone rare cell). Before submitting, ask: "what does my program do on the degenerate variants?" If the answer is something arbitrary (e.g., a function of nothing), prefer a natural default (identity, background everywhere) or request demos.

```python
    ...
def bbox(comp): ...
def canon(comp):  # sorted rel coords -> shape key
    ys=[y for y,x in comp]; xs=[x for y,x in comp]
    y0,x0=min(ys),min(xs)
    return tuple(sorted((y-y0,x-x0) for y,x in comp))
```

Every single task above started from these. Flood fill with a deque, mark seen, collect cells. Then the task-specific logic is 10–20 lines.

For separator-line grids: `rows where len(set(row))==1`, `cols where len(set(col))==1`, then compute contiguous bands between separators.

For diagonal tasks: group cells by `r-c` and `r+c` into dicts of lists.

For shape-tiling tasks: brute-force all offsets and check a condition — grids here are small (≤30×30), so O(H·W·ph·pw) is fine.

## Verification habit (repeat)

```
for pair in kept_pairs:
    assert transform(pair.input) == pair.output
```

If the assertion passes on every kept pair AND the test input's structure matches the demos (same number of components/colors/separators), submit the program's direct output on the test. If the assertion passes but the test is structurally off (lone dot, missing separator, no pairs of twin shapes), stop and either request demos or choose the most conservative prediction (often "identity" or "all background").

## On memory

Write a memory entry per task after you finish, with the one-line rule and the status. I can't overstate how much faster I got after the first 10 tasks because the rule families repeated. Before starting a new task, scan your memory for rules that might apply: separator grids, enclosed fills, diagonal extension, stamping, twins, sliding objects, periodic stripes. The stream reuses ideas heavily even when the task IDs differ.

Also record *failures with reasons* ("lone-dot test unresolved; identity, cross, row-only, col-only, all wrong"). Negative knowledge is as valuable as positive.

## Priority list when stuck

1. Count colors, find components, list bboxes and shapes.
2. Check for full separator rows/cols.
3. Check for enclosed background (border flood fill).
4. Check for rare-color dots/lines and interval logic.
5. Check for twins (same canon shape exactly twice) and a distinguished large object.
6. Check for periodic/tiling structure (does the output repeat a motif?).
7. Check global transforms (shifts, mirrors, rotations, stacking).
8. If nothing fits, request demos — cheap compared to a wrong submission.

One more thing: the harness judges the *final test prediction*, and wrong attempts are capped. When you're between two plausible rules that both fit the demos, pick the one whose degenerate behavior on the test's actual structure is most sensible — and if both are risky, spend a demo request.
