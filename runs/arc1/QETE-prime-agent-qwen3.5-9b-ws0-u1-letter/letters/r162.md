## The harness, concretely

You are solving ARC tasks one at a time. For each task you get a small number of demonstration pairs (input grid → output grid), then you must write a Python program `transform(grid)` that predicts the output for a new test input. You can ask for more demos (costly, and sometimes they never come), you can submit predictions (wrong attempts are counted, and there is a cap), and you can save memories and files to the workspace — which persist across tasks with the same task ID.

**Save aggressively.** For every task you make progress on, write:
- `programs/task-XXXX.py` — your program with a `transform(grid)` function.
- `programs/task-XXXX.json` — the demo pairs you kept, as JSON (a list of `{"input": [[...]], "output": [[...]]}`).
- A memory file (e.g. `programs/task-XXXX.mem.json`) stating: the rule in one or two sentences, whether the program reproduces all kept pairs, whether the test was solved, and anything unresolved.

The tasks recur. When a task ID reappears, the first thing I did every time was check for a saved memory and program. Several tasks were solved instantly on the second appearance because the program was already sitting in the workspace, reproducing all kept pairs. Do not re-derive from scratch what past-you already figured out.

## General strategy that worked

**1. Start by characterizing the grid.** Before hypothesizing, compute: dimensions, color histogram (which is background = most common, which colors are rare), connected components of each non-background color (4-connectivity, not 8 — 8-connectivity nearly always merges things that should be separate), bounding boxes of components, and which components share exact shapes up to translation. Most ARC rules involve: a distinguished object, repeated motifs, symmetry, counting, or spatial relations.

**2. The most common color is almost always background and is almost never meaningfully transformed.** The rule almost always concerns the non-background cells. Rarely, background pockets get filled (see below), but background cells otherwise stay background or become background.

**3. Look for "twins":** components with identical canonical shapes (translate to origin, sort cells, tuple). Many rules act on a pair of same-shaped objects: move one toward the other, recolor one, choose between them by distance to some anchor. When you find exact-translation twins, the rule very often is "pick the member that is nearer/farther to [some distinguished object or feature], and transform it."

**4. Count.** Many tasks are counting in disguise: count strays inside a block, count cells, compare counts between groups, take parity (odd/even). If you see a grid tiled into blocks by separator lines, immediately check whether the output is one value per block based on some count inside it.

**5. Separator-line tasks:** grids tiled by full uniform rows/columns are common. Extract block structure first (bands between separator lines), then ask what varies between blocks. Output is often one cell per block, or a per-block pattern copied from a source block.

**6. Symmetry and tiling outputs:** when the output is 2x or 3x the input, it's almost always mirror/rotation quilting. One task's rule: each row becomes `reverse(row)+row`, stacked as `reversed rows, original, reversed` — i.e., quadrant mirror quilting (TL=input, TR=rot90, BL=rot270, BR=rot180). Check horizontal and vertical mirror combinations first when dimensions scale by 2 or 3.

**7. Lines and runs:** diagonal runs (both r−c and r+c diagonals) of length ≥ 2 often get extended until blocked. Horizontal/vertical runs of a marker color often get gaps of size ≤ 2 filled between them. A lone dot often draws lines toward other things.

## Specific solved rules worth carrying as priors

These are rules I verified against kept demo pairs. They may reappear as family members even if the exact task differs:

- **Enclosed background pockets → fill with 4.** Component of background not touching the grid border, and rectangular (cell count == bbox area). Special case seen: a 2-tall pocket also recolors the wall row beneath it if that row is background across the pocket's width.
- **Uniform single-color rows/columns → recolor to 2.** Any row or column that is one repeated color becomes all 2s; everything else unchanged.
- **Fill between markers:** background cells strictly between two markers of the second-most-common color in the same row/column (gaps ≤ 2 in one variant) become 2; also background cells on the bounding-box perimeter of all markers.
- **Diagonal ray extension:** every same-color run of length ≥ 2 on a diagonal or antidiagonal extends in both directions through background until blocked by a non-background cell or the edge.
- **Stamp a seed:** largest non-background component is the seed; every other non-background cell is an anchor; stamp the seed's full bounding box (including its internal zeros) translated so the seed's bbox center lands on the anchor. Note it stamps the whole bbox as-is, holes included.
- **Split-and-compare:** a full uniform separator row/column splits the grid into two same-size halves A, B; output same shape: a special color (3) where A and B agree, else the blocks' shared dominant color.
- **Mirror-symmetric completion:** a centered solid separator (position r with 2r+1 = H) splits the grid; output cell = 2 where both halves have their own dominant color at mirrored positions.
- **Dot-to-line:** least common color cells ("dots"); output 3 strictly between the min and max dot per row and per column; dots themselves unchanged. **But beware:** a test with a single dot stumped me for 8 attempts — see the failure section below.
- **Blocks → dominant-per-3x3:** downsample by 3 taking the most common non-5 value per block.
- **Two-color remap:** keep the higher color, map the lower to 0.
- **Bridging identical cells:** a background cell in a row with the same non-background color on both immediate sides gets a bridge color (2).
- **Cyclic fill from lines:** colored cells lying on parallel lines (rows, diagonals); fill the whole grid cycling the line colors along the perpendicular index, mod number of lines.
- **Shift down one:** all non-background cells move down one row; originals become background; top row becomes background.
- **Object + line interaction:** an object slides until adjacent to a solid 2-line on its own side, then a full 8-line is drawn just outside the object's far side.
- **Bars and dots:** two multi-cell bars of one color plus single-cell seed dots; each dot draws a stub toward the nearest bar, turns into 4, and a mirrored full line is drawn on the other bar at the clamped corresponding index.
- **Corner-marked subgrid extraction:** rows/cols lacking the dominant block color are "special lines"; output cell = the color at a 4-corner intersection if all four corner markers agree, else background.
- **Scale-up quilting of a 1-wide motif** repeated into blocks.

These won't all recur verbatim, but they cover the *shapes* of rules: fill enclosed regions, extend runs, act on twins, act on singletons, separate-and-compare, tile/symmetrize, count-per-region, stamp a template.

If the test input visibly has a feature the demos lack (an extra color, a missing component, asymmetric placement), reason explicitly about what the rule *should* do there from first principles, not from pattern-matching to demos.

When a hypothesis is close but wrong, vary *one* detail at a time: anchor = center vs. corner; 4-connectivity vs. 8; include vs. exclude boundary; nearest vs. farthest.

## Practical habits

- **Keep a candidate file per hypothesis** (like `cand8.json`, `cand_11_7.json` in the workspace): when unsure between variants, render each variant's prediction for the test input and compare them side by side. Often the variants differ in only a few cells, and looking at *where* they differ tells you which detail the rule hinges on. Also record *failed* hypotheses in a `_failed.json` with a note about what's still untried — I did this and it saved me from resubmitting duplicates (two of my four failed candidates on one task were the same grid; my own note caught it).
- **Verify against kept pairs before ever submitting.** Run your `transform` on every kept demo pair; if even one mismatches, do not submit. A perfect-fitting program with a wrong test prediction is still better than a program that doesn't even fit the demos.
- **Write the rule down in one sentence before coding.** If you can't state it in one sentence, you don't have the rule yet; you have a patch over the demos.
- **Prefer color-agnostic implementations.** Find the background by histogram, the marker by second place, the fill colors by what's available — don't hardcode "3 means fill" unless demos force it. Tests often use different color palettes for the same rule.
- **Don't hardcode positions.** Find the separator, the object, the anchor by properties (uniformity, component size, rarity), not by fixed indices.
- **When stuck after a few attempts, reconsider the *object ontology*, not just the operation.** Maybe the "objects" aren't connected components but bbox rectangles, or maximal runs, or cells of one color grouped across components. Switching the ontology unlocked several tasks for me.
- **Track your attempt budget.** The cap is real. If you're at 5–6 wrong attempts, stop generating variations of the same idea and either request demos (if the uncovered-case flag is up) or pick the most conservative prediction consistent with the demos.
