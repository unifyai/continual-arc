## 1. The workflow you should follow every single time

The harness gives you a grid (or grids) and asks you to write a Python program `transform(grid)` that maps inputs to outputs. Over many tasks I converged on this loop, and it served me well:

1. **Look before you theorize.** Dump the demo pair(s), scan them slowly. Count colors. Find the background (almost always the most common color). Identify every non-background object and describe it to yourself in words: "three L-shaped blue shapes and one big gray L".
2. **State the rule in plain English before writing any code.** If you cannot say the rule in one sentence, you don't have it yet. Write the sentence down. Then write code that implements *that sentence*, not some code that happens to produce the right output.
3. **Verify against every kept pair.** Run your program on all demo inputs and check exact equality with all demo outputs. Never submit untested. This is the single cheapest way to avoid a wasted submission.
4. **Only then predict the test input**, and only with the same program — not with a hand-waved variant you invented for the test because the demo rule "felt incomplete."

The tasks where I lost attempts were almost all cases where I violated step 4: my program reproduced the demos, but for the test I submitted a *different*, speculative prediction instead of what my verified program would output. When your program reproduces all demos, trust it. The demos are the spec.

## 3. The recurring ARC archetypes in this stream, and how I recognized them

Most tasks in this stream fall into a small number of families. Learn to name the family fast, because the family tells you what code skeleton to reach for.

**(a) Component analysis + geometric property.** Find connected components (4-connectivity for most of these; check whether 8-connectivity matters by looking at diagonal-touching objects). Then ask: what distinguishes the components? Size, shape, being a rectangle, being an L, having a twin elsewhere in the grid, touching the border.

- *task-3f4fb1a9*: fill **enclosed** background regions (not touching the border) with 4 — but only if they are solid rectangles; a 2-row-tall rectangle also absorbs the wall row beneath it under a condition; L-shaped pockets stay unchanged. The general lesson: "enclosed region" tasks almost always mean flood-fill from the border and mark what the flood cannot reach.
- *task-aa5a69a0*: hollow rectangles get their interior filled with 2 or 7 depending on interior area parity. Detection: bbox with `len(comp) == 2*(h+1) + 2*(w-1)` for a hollow rect of bbox h×w.
- *task-b62da9e0*: fill the bounding box of each non-background component of size ≥ 3 with its color; everything else becomes background.
- *task-0f6e5a2f*: among pairs of identical shapes (same canonical form) occurring exactly twice, recolor the one farther from a special large L "arrow." The general trick of **canonicalizing shapes** (translate to origin, sort the cells, compare tuples) is worth writing once and reusing — I used it here and it's the standard tool for "two of these are twins" tasks.

**(b) Stamp / copy a pattern.** Find a seed pattern and stamp it at positions determined by anchors.

- *task-1b7868f1* (above): seed bbox stamped centered on each anchor.
- *task-770f2daf*: stamp the rare-color shape at every offset where all its cells land on 0s. Recognition cue: a small distinctive shape plus lots of empty background.
- *task-8d84fe63*: the grid is divided into blocks by separator rows/columns; the block with the most non-mode cells is the source; every other block is overwritten by the source block's pattern. Cue: periodic tiling with one deviant tile.

**(c) Mirror / tile / extend.**

- *task-73499f5a*: each row becomes reverse+original (width doubles); the output stacks reversed rows, original order, reversed again (height triples). Simple, but I got the exact stacking order wrong twice — check whether the original or the mirror comes first by reading the output's first block, not by symmetry intuition.
- *task-794e60f6*: 2n×2n output = input in TL, rot90cw in TR, rot90ccw in BL, rot180 in BR. When output dims are exactly 2× input dims, always test the four quadrants against the four rotations/reflections of the input — it's cheap and it's usually one of them.
- *task-2e29965a*: sparse colored diagonal/anti-diagonal lines define a periodic stripe pattern; the period equals the number of lines, and each cell takes the color of the line at `(i+j) % p`. Cue: output is a full tiling, input has a few colored lines.

**(d) Line / separator structure.** Look for full rows or columns of a single color — they are almost always meaningful.

- *task-48898d06* and *task-bb30ebc2*: the grid is a lattice cut by separator lines; the output summarizes each cell of the lattice (e.g., 1 if odd count of a stray color, or a color determined by corner cells). When you see gridlines, immediately think "the output is a per-block function."
- *task-026adbf3*: split into two blocks A and B by a separator; output marks 3 where A and B agree, else the common color. Cue: a uniform full row/column splitting the grid into two equal-size regions.
- *task-47ed202e*: rows or columns that are uniformly one color become all 2s. Dead simple, but note it's *any* uniform line, not just the background color's.
- *task-b7641a67*: a background cell with identical non-background neighbors on both sides in its row becomes 2. Local pattern completion.
- *task-8625f9bc*: fill background gaps of size ≤ 2 between markers in a row/column, plus the background cells on the markers' bounding-box perimeter. The "≤ 2" threshold mattered — measure gap sizes in the demos before committing to a rule.

**(e) Shift / gravity.**

- *task-efc2fba8*: every non-background cell shifts down one row; original positions cleared. When most of the output equals the input but everything moved rigidly by one step, check the four unit directions first.
- *task-77262100*: an object slides until adjacent to a full 2-line, then a full 8-line is drawn just outside the object's far side. The family "object moves toward a landmark line, then something is drawn relative to its new position" — handle both orientations and both sides in one program, as my saved `task-77262100.py` does.

**(f) Drawing / projection between dots and bars.**

- *task-d4079843*: dots of one color project lines of another color toward a bar, with the endpoint cell colored 4, and a mirror bar gets the same lines. This is the most intricate task in the set; the saved program enumerates permutations of the two bars and validity-checks (dots all on one side, distinct offsets, mirror stays in bounds) rather than reasoning geometrically. When geometry gets complicated, **enumeration + validity checks beats clever geometry**.

**(g) Scaling down / summarizing.**

- *task-67dd046a*: divide the grid into 3×3 blocks, output one cell per block = most common non-5 color in the block. Cue: output dims are exactly input dims divided by an integer.
- *task-707635df*: split at a centered solid separator; output cell = 2 where both halves have their own dominant color. Note the check `2*r+1 == H` — the separator must be exactly centered.

**(h) Color mapping.**

- *task-2264bd4e*: two colors only; keep the higher, map the lower to 0. When output shape equals input shape and only colors changed, diff the input and output cell-by-cell and build the color map first. It takes ten seconds and often *is* the whole rule.

**(i) Diff-based reasoning.** Related to (h): when in doubt, write a tiny diff routine — for every cell where input ≠ output, print `(r, c, in, out)`. Group by what changed. This cracked several tasks for me faster than any visual inspection. Also: for color-map tasks, build the map from the demos and check it's consistent and total.

## 4. Code habits that paid off

- **One generic helper file's worth of functions in your head:** background = most common color; components via stack-based flood fill; bbox of a component; canonical shape key; hollow-rectangle detection; separator row/column detection; "enclosed region" via border flood. Every task above used two or three of these. Write them cleanly once and adapt.
- **`Counter` for everything color-related.** `most_common(1)[0][0]` for background, and beware ties — if two colors have nearly equal counts, don't assume which is background; look at the grid.
- **Sort least-common color carefully.** For "dot" color I used `most_common()[-1][0]`, which is fine when the rarest color is unique, but check counts before trusting it.
- **Handle both orientations/sides.** If a rule works "downward," ask whether a demo or test could present it "upward" and make the program symmetric. My task-77262100 and task-d4079843 programs both enumerate orientations rather than hard-coding one.
- **Guard your code.** If the rule doesn't apply (no separator, no twins, no arrow), decide explicitly: return the input unchanged, or raise? For test prediction, returning the input unchanged is usually safer than crashing — but remember the lone-dot lesson: if the rule genuinely doesn't cover the test configuration, that's a signal to *request demos*, not to guess.
- **Verify literally.** `assert transform(inp) == out` for every pair. Don't eyeball 20×29 grids; you will miss a single off-by-one cell, and ARC is exact-match. I lost nothing to eyeballing once I switched to asserts, and I lost attempts before I did.

## 5. Submission and demo-request strategy

- You have a limited number of attempts and demo requests per task. Spend demo requests **when your rule has a hole the demos don't cover**, not when you're merely unsure between two rules that both fit the demos — for the latter, pick the simpler rule (Occam), verify, submit.
- When demos are few (1–2 pairs), a rule that fits them is weak evidence. Prefer the rule that also *explains why* each output cell is what it is, not just one that reproduces them. E.g., for one pair showing colors mapped, ask "is this a per-color map, or per-position, or per-shape?" before committing.
- Keep your own record as you go (I saved `*_failed.json` files with rejected candidates and a note of what was and wasn't tried). On a repeat task or a near-repeat, that record is gold: it stops you from resubmitting a known-wrong variant (I duplicated a failed submission once — pure waste).
- The attempt cap is real. If you've burned several attempts and your verified-program prediction keeps failing, stop re-deriving from scratch and re-read your diffs: the mismatch is usually a *boundary case* (lone object, single dot, off-by-one on the far edge), not a wrong rule.
