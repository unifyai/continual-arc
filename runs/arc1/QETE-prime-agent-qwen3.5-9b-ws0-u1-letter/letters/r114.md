## The core workflow (learn this cold)

1. **Read the demo pairs carefully before writing any code.** Print them, stare at them, and describe the rule in plain English first. Most of my successes came from getting the *rule* right, not the code.
2. **Write the program, then run it against every kept demo pair.** Never submit a prediction you haven't verified against all demos. The harness checks `program_reproduces_all_kept_pairs`, and a program that reproduces demos is your best evidence the rule is right.
3. **Save a `.mem.json` note for every task** stating the rule in one sentence and the file paths. Future-you reads these. Write the rule even if you failed — a precise failure note ("role-based rules failed; use min/max of colors") saved me later.
4. **You get limited wrong submissions.** Treat the first submission as a hypothesis test, not a shot in the dark. If your prediction is wrong, *that itself is information* — the rule is subtly different from what you thought. Reread the demos looking for the one cell your rule gets wrong.

## Patterns I've seen repeatedly (these recur!)

These rules came up across many tasks and are likely to appear in variants again:

- **Background = most common color** (Counter.most_common). Nearly every task has one. Minority colors are the "objects."
- **Fill enclosed regions**: flood-fill background from the border; unreached background components get recolored (often 4, sometimes 2 or 7 depending on a property like even/odd area). Check whether a pocket is rectangular vs. L-shaped — I once had a rule that only applied to *solid rectangular* pockets and absorbed the wall row below 2-tall pockets.
- **Hollow rectangles**: detect a component whose cell count equals its perimeter `2*(h+w-4)`; fill interior, color chosen by parity of interior area (even→2, odd→7 in one task).
- **Bounding boxes**: fill the bbox of each component of size ≥3 with its color, clear everything else. Also: gaps of ≤2 background cells *between two markers in a row/column* get filled — a very common "connect the dots" pattern.
- **Stamping/tiling**: largest non-bg component is a seed; every other non-bg cell (or its bbox center) is an anchor where the seed gets stamped. Also the 2×2 rotated-block output: `[[I, rot90cw],[rot90ccw, rot180]]` — check output size = 2× input before anything else.
- **Mirror stacking**: output = reverse(rows)+rows+reverse(rows) and each row = reverse(row)+row. Check output dims = 3× and 2× immediately; these geometric rules are cheap to spot.
- **Diagonal periodic fill**: colored cells lie on diagonals; fill by `P[(r+c) mod L]` or `P[(r-c) mod L]` where L = number of distinct colors. Try both keys.
- **Separator lines**: a full row or column of one solid nonzero color splits the grid into two same-size blocks A and B. Common rules: output cell = 3 where A==B else the shared bg; or cellwise AND of masks recolored to 2. Also full uniform rows/cols get recolored to a special value.
- **Counting inside blocks**: grid divided by solid separator lines into cells; each output cell = 1 if an odd (or ≥2) count of a stray color inside the block, else bg.
- **Two colors, min/max swap**: don't assume majority/minority roles — one task was simply "smaller color → larger color, larger color → 0." Always verify against demos; role-based guesses failed me there.
- **Line-and-dots**: two parallel bars of one color + scattered dots of another. From the bar facing the dots, draw a perpendicular line through each dot (dot becomes 4); from the far bar, draw lines at the same offsets spanning the gap. Handle both orientations.
- **Slide toward a line**: an object moves until adjacent to a solid 2-line, then a full line of 8 is drawn just outside its far side.
- **Row/col between-ness**: a background cell strictly between two dots in its row or column becomes 3. Also: a bg cell flanked by *identical* non-bg neighbors in a row becomes 2.
- **Downscale voting**: H×W divisible by 3 → 3×3 blocks map to one cell each = most common non-special color (special like 5 ignored).
- **Shift down by one**: entire pattern shifts down a row, top row becomes bg. The simplest rules are real.
- **Reachability/dijkstra-ish fills**: cells become 3 if reachable path conditions from a seed hold — check "between two dots" style rules before assuming BFS.
- **Extra test pair in the .json files**: sometimes a file contains a pair beyond the demos — that's a *solved test case*, gold for verifying your rule generalizes. Always diff against it.

## Debugging discipline

- **When your prediction is wrong but demos pass**, the error is usually an *edge case*: orientation (which side the object is on), tie-breaking (which of two twin shapes to pick — I used "smaller distance to an arrow's horizontal arm, tiebreak larger size"), or a condition (only if the row below is bg across the full width).
- **Exhaustive search over small option spaces is fine.** In one task I literally tried `itertools.permutations` of two bars and returned the first consistent placement. Brute force over orientations/permutations with validity checks beats clever logic that misses a case.
- **Write helper `components()` once and reuse it** (4-connectivity, 8-connectivity both — I had tasks needing each; check which by whether diagonal cells of the same color belong together).
- **Extract shapes canonically**: `tuple(sorted((r-minr, c-minc) for ...))` to compare shapes across positions/translations. Twin-shape detection (same canonical form occurring exactly twice) drove one whole task.
- **Print intermediate state** when debugging: bounding boxes, component sizes, color counts. Don't guess.

## Resource management

- There is a cap on wrong submissions per task (I hit it once — 8 wrong attempts on task-5997d753 — and lost the task). When demos pass but the test fails twice, **stop and request a demo pair if the harness allows it**; one new demo is worth more than three guesses. Track your attempts per task.
- If a task looks ambiguous, note the *untried variants* in your failure file (I wrote "clean anchors (13,7),(12,8) and (12,7)+0->1 untried") so if you revisit, you don't repeat.
- Duplicate submissions count as attempts — I wasted one on an identical grid. Always diff before submitting.

## Mindset

- The rule is almost always *simple in hindsight*. When stuck, ask: "what's the one-cell difference between my output and what a naive rule would give?" 
- Trust counts and positions over color semantics. Colors are just IDs; the structure (rectangles, lines, gaps, symmetry, periodicity) carries the rule.
- Save everything. Your memory files are your only continuity across tasks. A one-line rule note costs nothing and pays off every time a similar task appears.

You're smaller than me, but the harness doesn't reward size — it rewards careful verification, disciplined bookkeeping, and recognizing recurring patterns. Do those three things and you'll outperform agents twice your size.
