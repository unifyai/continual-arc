## 1. The most important habit: verify before you submit

This is worth more than anything else in this letter. **Run your program against every kept demo pair before you submit anything.** Load the JSON file of pairs, call `transform`, compare cell by cell. If it doesn't reproduce all of them, don't submit — fix it or request more demos. Every wrong attempt I wasted could have been avoided by this one loop. Write a tiny local checker script once and reuse it forever:

```python
import json, importlib
pairs = json.load(open("programs/task-XXXX.json"))
mod = importlib.import_module("programs.task-XXXX")
for i, p in enumerate(pairs):
    pred = mod.transform(p["input"])
    assert pred == p["output"], f"pair {i} mismatch"
```

And when it mismatches, *print* the mismatched cells. Often you'll find the rule is 95% right and one small clause is off (a wall row, an edge case, a direction flip).

Every time you keep a pair, write it to `programs/task-<id>.json` and your program to `programs/task-<id>.py`. Then write a memory note (e.g. `programs/task-<id>.mem.json`) with a one-sentence rule description. This matters because:

## 3. The workhorse toolkit — these cover most tasks

Most tasks I saw fall into a handful of families. Learn to recognize them fast:

**Background detection.** `bg = Counter(v for row in g for v in row).most_common(1)[0][0]`. Almost every task starts here. The rare color (`.most_common()[-1][0]`) is usually the "seed" or "marker".

**Connected components (4-connectivity is the default; check 8-connectivity only if 4 fails):**

```python
def components(g, colors, bg):
    H, W = len(g), len(g[0])
    cs = set(colors) - {bg}; seen = [[False]*W for _ in range(H)]; comps = []
    for r in range(H):
        for c in range(W):
            if not seen[r][c] and g[r][c] in cs:
                q = deque([(r, c)]); seen[r][c] = True; comp = []
                while q:
                    y, x = q.popleft(); comp.append((y, x))
                    for dy, dx in ((1,0),(-1,0),(0,1),(0,-1)):
                        ny, nx = y+dy, x+dx
                        if 0 <= ny < H and 0 <= nx < W and not seen[ny][nx] and g[ny][nx] in cs:
                            seen[ny][nx] = True; q.append((ny, nx))
                comps.append(comp)
    return comps
```

**Bounding boxes.** `r0, r1, c0, c1 = min(rs), max(rs), min(cs), max(cs)`. A shocking number of tasks are "fill the bbox", "move to the bbox", "stamp the bbox pattern elsewhere", or "check the component is exactly its bbox perimeter/rectangle".

**Coloring by majority/minority within regions.** Blocks separated by uniform separator rows/cols; each block reduces to one cell (majority color, or a rule like "1 if any stray non-bg inside"). See `task-48898d06.py` and `task-bb30ebc2.py` in your workspace for the band-extraction idiom:

```python
def bands(indices):
    res = []; cur = []
    for x in indices:
        if cur and x == cur[-1]+1: cur.append(x)
        else:
            if cur: res.append(cur)
            cur = [x]
    if cur: res.append(cur)
    return res
```

**Enclosed regions via flood fill from the border.** A background component that never touches the border (row 0, row H-1, col 0, col W-1) is "enclosed". See `task-3f4fb1a9.py`: enclosed rectangular pockets of bg become 4, with a subtle extra clause about 2-row pockets absorbing their bottom wall — I only found that clause by careful demo inspection.

**Diagonal periodicity.** If colored cells lie on diagonals, the grid is likely a periodic diagonal tiling: try `P[(r+c) % L]` and `P[(r-c) % L]` where L = number of distinct colors. That solved `task-2e29965a` instantly.

**Symmetry/tiling of output shape.** When output is 2x2 or 3x3 of the input, think rotations/mirrors. `task-794e60f6` was `np.block([[a, rot90(a,-1)], [rot90(a), rot90(a,2)]])`. `task-73499f5a` was `r[::-1]+r` per row, stacked reversed/original/reversed. When the output dims are exact multiples of the input dims, these families are the first thing to try.

**Line-through-dots / bar-and-dots.** Two parallel bars of one color, scattered dots of another: draw a line from the facing bar through each dot (dot becomes a special color, e.g. 4), and from the other bar draw lines at the same offsets spanning the gap. The offsets are computed relative to the bar's start; dots must have distinct offsets and all land inside the grid. See `task-d4079843.py` — it's generic for horizontal and vertical bars, both sides.

**Sliding objects toward a boundary line.** Object + a full line of a special color: object translates until adjacent to the line (only over background), then a full line of another color is drawn on the object's far side. See `task-77262100.py`.

**Stamping a shape at every valid offset.** Take the rare color's shape, slide it over the grid, and stamp where all its target cells satisfy a condition (e.g. are all 0). See `task-770f2daf.py`.

**Simple recoloring rules.** Sometimes it's embarrassingly simple: min color → max color, max → 0 (that's `task-2264bd4e` — and note: I first tried majority/minority roles and it failed; the *value order* min/max was correct. Always check both hypotheses against demos). Or "bg cell strictly between two dots in its row/col becomes 3" (`task-5c839a47`), or "bg cell with identical non-bg neighbors on both sides in a row becomes 2" (`task-b7641a67`).

**Masks of two halves.** Grid split by a full uniform row or column of one color into two equal blocks A and B: output is often a cellwise combination (AND → color 2 in `task-707635df`; equality → 3 in `task-026adbf3`). Check for the separator first: `rows = [i for i in range(H) if len(set(grid[i]))==1]`, same for cols.

**Pattern shift.** `task-efc2fba8`: every non-bg cell moves down one row. Dead simple, but I nearly overthought it.

## 4. How to actually find the rule (methodology)

When you look at a new task, work through this sequence:

1. **Compare input and output cell by cell.** List exactly which cells changed, and what from → what to. Group the changes. Are they contiguous? All one original color? All in one region? Don't stare at the whole grid — stare at the *diff*.
2. **Count colors and check sizes.** Output shape same as input? (Most common.) Different? (Then it's cropping, tiling, downsampling, or block-collapsing — look for separator lines or n×n blocks.)
3. **Check for separator lines** (uniform rows/cols) before anything else if sizes differ or structure looks blocky.
4. **Find objects** (connected components of non-bg). Note their shapes, sizes, counts. Are there duplicates (same canonical shape, translated)? Pairs of twins often mean "recolor one of them based on some criterion" (distance to something, as in `task-0f6e5a2f`).
5. **Ask: what determines each changed cell?** Is it a function of its row, its column, its neighbors, its distance to an object, whether it's enclosed, whether it's between two things? Most rules are local or geometry-based, not arbitrary.
6. **State the rule in one sentence before coding.** If you can't, get more demos.
7. **Code it, run it on all demos, diff, fix, repeat.** Only then submit.

## 5. When you're unsure, request demos

Requesting demos is cheap; a wrong submission is expensive. If you have two or three plausible rules and the demos don't discriminate between them, ask for another demo pair rather than guessing. I lost a task (`task-5997d753`) partly because I burned eight wrong attempts on variations instead of stepping back and asking what structure I was missing. The cap is real — count your attempts.

But also: don't request demos when the rule is obvious. If two demos confirm a clean rule and your program reproduces them, submit.

## 6. Traps I fell into, so you don't have to

- **Overfitting to one demo.** A rule that fits demo 1 perfectly and nothing else is usually wrong. Prefer the simpler rule that fits all demos.
- **Assuming role-based colors (majority/minority) when it's actually value-based (min/max) — or vice versa.** Test both.
- **Forgetting the grid boundary.** Many rules have special cases at edges (touching border = not enclosed; stamping must clip to the grid; a line drawn "outside" the object might be off-grid). Always handle `0 <= r < H and 0 <= c < W` in stamping loops, and always ask "what happens at the border?"
- **4 vs 8 connectivity.** If a component-based rule almost works but merges/splits things weirdly, try the other connectivity.
- **Special "hole" colors.** Some objects contain interior cells of a *different* color (e.g. a rectangle of 8s with 0s inside). When copying or stamping such an object, copy the whole bbox including the holes — `task-1b7868f1` required this. My first version dropped holes and failed.
- **Assuming the output is the input with changes.** Some tasks rebuild the whole grid from scratch (diagonal tilings, block collapses, rotations). If the diff looks like "everything changed", stop diffing and look at global structure.
- **The 2-row pocket wall clause.** Sometimes a rule has an extra conditional that only shows in one demo. Read every demo's output carefully for changes that your rule doesn't predict — those are the clause.
- **Don't submit a guess as a "final" answer when the cap is near.** If your program reproduces all demos but you're unsure about the test, reason about which plausible rule generalizes best, pick the one whose *mechanism* is most natural (ARC rules are usually conceptually simple), and go. Never submit something that fails your own demo check.

## 7. A practical workflow for each task

1. Read the demo pairs. Diff them mentally.
2. Hypothesize the rule in one sentence.
3. Write `programs/task-<id>.py` with a clean `transform(grid)`.
4. Write the kept pairs to `programs/task-<id>.json`.
5. Run the checker. Fix until all pairs pass.
6. If it passes and the rule is clean → predict the test, submit.
7. If wrong on the test → note in memory what was rejected (rule and counterexample), get more demos, refine.
8. After solving, write the memory file: task id, files, rule in one sentence, status.
