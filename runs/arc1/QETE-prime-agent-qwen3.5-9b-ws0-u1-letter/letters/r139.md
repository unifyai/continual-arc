## The single most valuable habit: verify against ALL kept pairs

Half my failures came from a program that fit one or two pairs but broke on the third. Before any submission, run your `transform` on every input in your `task-<id>.json` and assert pixel-exact equality with the outputs. If it fails on any, your rule is wrong — do not submit, go back to the grid. I recorded `program_reproduces_all_kept_pairs: true` only after that check, and you should too. A program that reproduces all kept pairs but fails the test usually means the rule has a hidden parameter (e.g. task-5997d753: my rule was right for demos but the test exercised an untested configuration; task-5c839a47: the test had a *single* dot while every demo had ≥2, and I burned 8 attempts on lone-dot extensions — all wrong).

**If your test situation differs structurally from every demo (a lone object, an unseen orientation, an unusual count), request demos before submitting if you have requests left. I learned this too late both times.**

## General solving strategy

**Inventory before hypothesizing.** Count colors; identify background (most common) and the rare color(s). List components with 4-connectivity, their sizes, bounding boxes, and whether they're solid rectangles, rings, lines, or L-shapes. Compare input and output dimensions first — same size means recoloring/moving; changed size means tiling, mirroring, or down/up-sampling.

**Symmetry and self-similarity are the most common generators.** If the output is larger, check: mirror-tile (73499f5a), rotate-tile (794e60f6), periodic diagonal completion (2e29965a), or stamping a seed shape (770f2daf, 1b7868f1). If smaller, check 3×3 downsampling by mode (67dd046a), corner-color block summarization (bb30ebc2), or separator-based comparison (026adbf3, 707635df, 48898d06).

**Line and rectangle predicates.** Many rules are about full uniform rows/columns (separators, lines to recolor) or about bounding boxes (fill, ring, slide-till-touch). I wrote a small mental checklist: full uniform lines? solid rectangles? rings (component size = 2h+2w−4)? pockets (background components not touching border)? Keep that order — pockets first check "touches border", then "is it a solid rectangle", then "height 2?".

**Counting thresholds matter and are easy to get wrong.** Odd vs even, ≥2 vs ≥3, size ≤2 gaps. When a threshold exists, try to derive it from the smallest demo pair rather than guessing.

**Distance/selection rules** (which of several similar objects gets recolored) are usually: closest to some anchor, farthest, largest, or the unique singleton. task-0f6e5a2f used "translation-twin pairs, pick by min Manhattan distance to the arrow's arm, tiebreak larger size." Enumerate candidate selection rules in that order.

## Program hygiene

- Always compute background as the most common color, never hardcode a digit — but if a demo pair contradicts it (e.g. 0 as background in 770f2daf where I special-cased `c != 0`), trust the demos.
- Write components/flood-fill once and reuse; my `task-b62da9e0.py` version is short and correct — copy it into new programs rather than rewriting BFS each time (I introduced subtle bugs by retyping).
- For "try multiple orientations" rules, write the loop over orientations and `return` on the first consistent one (see d4079843, 77262100). Don't write four copies of the logic.
- Guard everything: if your rule's precondition isn't met, returning the input unchanged is better than crashing.

## What wasted my time

- Submitting a prediction built from a program I hadn't re-run against all kept pairs after a "small fix."
- Debating among extensions for an underdetermined case instead of spending a demo request. **Demos are cheap; wrong submissions are expensive.** If two rules both fit the demos and the test looks ambiguous, request demos.
- Keeping near-miss candidate grids around without noting *why* each was rejected. My `task-1b7868f1_failed.json` note ("clean anchors (13,7),(12,8) untried") eventually rescued the task — do write one-line rejection notes into failure files, but keep them terse.
