## 1. The harness, the loop, and what actually counts

You play ARC tasks one at a time. For each task you typically have: a small set of demonstration input/output pairs (which you may request more of, up to a cap), a test input, and a limited number of submission attempts. The failure modes that actually lose games are:

- **Submitting a wrong prediction.** Wrong attempts are capped (I hit the cap on task-5c839a47 and task-5997d753; both are permanently unsolved). Do not burn attempts on guesses.
- **Spending turns building programs that reproduce the demos but not the test.** This is the single most common way to lose. A program that fits the demos perfectly means *nothing* about the test. Ask: what does the rule generalize to? Is there an element of the rule that no demo exercises (a lone dot, an odd-shaped pocket, a symmetric case)? If yes, that unexercised element is exactly where the test will bite.
- **Forgetting to write memory files.** Memory is your only cross-task asset. Write memory files early and update them.

**Hard-learned rule:** if your demos don't cover a case that plausibly appears in the test (e.g., only one instance of the key object, a degenerate shape, a single element), request a demo or make your most conservative choice rather than an ambitious one. On task-5c839a47 the test had a *single* dot where all demos had many; I tried eight clever extensions (cross, arcs, mirrors, row-only, col-only, fill-all) and all eight were wrong. If you see a degenerate test case, prefer the simplest behavior consistent with the demos, and if you have attempts left, use the *first* attempt on the most boring candidate.

## 2. Workflow that works

For each task, in order:

1. **Look before you code.** Print or mentally render the grids. Count colors. Identify the background (almost always the most common color — `Counter(v for row in g for v in row).most_common(1)[0][0]`). Identify the special/rare colors and objects.
2. **Characterize the transformation in one English sentence.** Write the sentence down (in a memory file or a comment). If you can't state it in one sentence, you don't understand it yet — get more demos rather than guessing at code.
3. **Verify the sentence against *every* demo pair, cell by cell**, before writing the program. Many of my wrong submissions came from a rule that fit demos 1–2 in my head but I never actually checked against demo 3.
4. **Write the program.** Keep it simple and deterministic. Avoid heavy heuristics with many free parameters — every free parameter is a chance to be wrong on the test.
5. **Run it on all kept demos.** It must reproduce all of them, exactly. If it doesn't, your rule sentence is wrong, not the code (usually).
6. **Ask the generalization question** (see §3), then predict the test, then submit.

Save these files per task (this is the convention the workspace uses and future-you will thank you):

- `programs/task-<id>.py` — the program with a `transform(grid)` function.
- `programs/task-<id>.json` — the kept demo pairs, so you can re-verify later.
- `programs/task-<id>.mem.json` or a memory entry — one-line rule statement, files, status, and *especially* anything unresolved.

## 3. The generalization question — the most important habit

After your program reproduces all demos, ask explicitly:

- **What inputs would make my program crash or silently return garbage?** E.g., my task-707635df program raises `ValueError` if there's no centered separator. My task-d4079843 program uses `itertools.permutations` over two bars and returns on the first consistent interpretation — what if the test's geometry admits two interpretations? Check.
- **What rule element is untested by the demos?** Zero cells of some color, a pocket of height 1, an object touching the border, two objects of equal size (tie-breaking!). Tie-breaks are a classic trap: task-0f6e5a2f needed "smallest distance to the arrow arm, tiebreak by larger size," and I only found that by staring at the demos. If the test has ties your demos never showed, pick the tiebreak that is most natural (larger, closer, first-encountered in scan order) — and if it's cheap, consider whether both options are plausible and choose the one that's most "canonical."
- **Does my rule use absolute colors or relative structure?** ARC rules are usually structural (which color is rare, which is background, which is the separator), not "3 means X." My task-2264bd4e rule was literally "keep the higher color, set the lower to 0" — a *relative* rule that happened to be right. But most tasks are structural. When in doubt, prefer the structural reading.

## 4. Rules I've actually solved — a pattern library

Study these; many future tasks will be variations. Each is stated as the one-sentence rule:

- **Symmetry completion / mirroring (task-73499f5a):** each row becomes `reverse(row)+row`; stack = reversed rows, original, reversed again. Generalizes: outputs that are 2× or 3× in one or both dimensions are almost always mirror/tiling constructions. When output dims are a multiple of input dims, think: mirror, tile, or quarter-rotate assembly.
- **Quarter rotation assembly (task-794e60f6):** 2n×2n output = input, rot90, rot90ccw, rot180 in quadrants. Whenever output is exactly 2× input in both dims, one of {mirror tiling, rotations} is nearly always the answer.
- **Shift by one (task-efc2fba8):** all non-background cells move down one row; top becomes background. Trivially simple rules exist. Don't overcomplicate.
- **Stamp a shape (task-770f2daf):** take the rare-color shape, stamp it at every offset where all its cells would land on background. Also (task-1b7868f1): the largest non-background component is the seed; every other non-background cell is an anchor; stamp the seed's bounding box translated so its center lands on the anchor. "Largest component = seed/pattern, other small components = anchors" is a very frequent ARC pattern.
- **Fill enclosed pockets (task-3f4fb1a9):** flood-fill background components from the border; components not touching the border and solid-rectangular get recolored (to 4). Watch for extra conditions (pockets 2 rows tall also absorbed their bottom wall row when the row below was background). Enclosure detection = BFS from border, inverse of what's reached.
- **Bounding-box fill (task-b62da9e0):** each non-background component of size ≥ 3 gets its full bounding box filled with its color; everything else becomes background. Note the size threshold — small stray components were noise to be erased.
- **Rectangle interiors with parity (task-aa5a69a0):** hollow rectangles (perimeter components with height ≥ 3 and width ≥ 3) get interiors filled with 2 if inner area even else 7. Parity-dependent fill colors happen. Count areas.
- **Separator-line grids (multiple tasks):**
  - task-026adbf3: full uniform row/col splits grid into two blocks A, B; output marks 3 where A and B agree, else their shared common color.
  - task-707635df: centered separator; output cell = 2 where both halves hold their own dominant color.
  - task-48898d06: grid divided by solid separator lines into blocks; each output cell counts stray-color cells in its block (threshold rule).
  - task-8d84fe63: separator lines divide into sub-grids; one sub-grid is the "clean" pattern; it's copied onto all others (find the sub-grid with the most non-mode cells — that's the source).
  - Whenever you see full uniform rows/columns, your first hypothesis should be "the lines define a tiling, and the rule operates per-cell or per-block across the tiling."
- **Recolor by adjacency (task-b7641a67):** background cell with identical non-background neighbors on both sides in a row → 2. Local pattern rules like this are common and cheap to test.
- **Slide toward a line (task-77262100):** object translates until adjacent to a full line of color 2; a full line of color 8 is drawn just outside the object's far side. "Object moves to touch a marker line; secondary marker drawn on the far side" — handle both orientations (the line may be a row or a column) and both sides.
- **Gap filling between markers (task-8625f9bc):** fill background gaps of size ≤ 2 between consecutive marker cells along rows/columns, plus background on the markers' bounding box perimeter.
- **Line drawing to dots (task-d4079843):** a bar component plus scattered dots; draw lines from the bar through each dot's offset, and mirror lines on a twin bar. The dots' *offsets along the bar* determine line positions. Geometric correspondence by projection is a recurring trick.
- **Directional extension (task-3b5f776f):** endpoint cells of shapes (degree-1 cells in the 8-neighborhood graph of non-background cells) extend as rays in their direction to the border. Find endpoints by neighbor degree, extend along the endpoint-to-neighbor vector.
- **Diagonal tiling (task-2e29965a):** colors placed on diagonals (r+c mod L or r−c mod L) determine a periodic tiling of the whole grid. If scattered colored cells are consistent along diagonals, tile by that diagonal period.
- **Downsampling (task-67dd046a):** output cell = most common non-5 color in each 3×3 block (5 = ignore/transparent). When output is roughly input/3 or input/2 in both dims, block-vote is the first thing to try. Note the "ignore color" (often 5 or 0) that doesn't vote.
- **Comparative selection (task-0f6e5a2f):** among twin shapes (identical canonical shape appearing exactly twice), recolor the one farther from a special object (the arrow). Rule shape: "find twins, find the reference object, transform the twin selected by a distance/size criterion." Canonicalize shapes by translating to min-row/min-col and sorting cells; use this to detect twins.
- **Row/col reference bands (task-5997d753):** full-pattern rows act as references; mixed rows get background cells turned to 1 where the reference has the pattern color. (This one I ultimately got wrong on the test — see §1 about degenerate cases.)

Recurring meta-patterns worth internalizing:
- **Background vs. the rest.** Almost every task starts with identifying background via most-common color.
- **Rare color = the actor.** The least common color usually marks the cells that drive the transformation.
- **Connected components with 4-connectivity**, canonicalized by sorted relative coordinates, are the universal object representation. Write one good component-finding helper and reuse it in every program (I have several in the files you inherited; copy the style).
- **Sizes and counts drive decisions:** largest component, exactly-two occurrences, size ≥ 3, even/odd area, count ≥ 2 per block.
- **Symmetry and repetition:** outputs are very often input mirrored, tiled, rotated, or stamped at multiple positions.

## 5. On writing robust `transform` programs

- Signature is `def transform(grid):` taking a list of lists of ints, returning the same. Don't mutate the input — copy first: `out=[row[:] for row in grid]`.
- Wrap fragile logic so that *some* output is always returned. If a detection step can fail, fall back to returning the input unchanged (identity) rather than raising. A wrong answer and an exception may cost the same, but an exception sometimes costs more (and always wastes a turn).
- Determinism: no randomness, no reliance on dict/set iteration order for anything semantic.
- Use the small-model-friendly structure: find bg, find special colors/objects, compute a plan, apply. My kept programs are all under ~60 lines. If yours is much longer, your rule sentence is probably wrong.
- Test your program in-process on the kept demos before predicting the test. Compare cell-by-cell and print the first mismatch location if it fails — the location of the first mismatch usually tells you which part of your rule is wrong.

## 6. Memory strategy

- When a task is solved or a rule is firmly established, write a memory entry immediately: task id, file paths, one-sentence rule, status, and any unresolved edge cases. I have entries in `system/state/agent/harness/harness_state.json` under `memory` — follow that format.
- When a task is *unsolved*, record what you tried and what was rejected. This is worth more than the rule itself: on task-5c839a47, my memory of eight rejected lone-dot hypotheses is the reason you won't repeat them. Negative knowledge compounds.
- Never rely on memory of a *specific* task's answer (you likely won't see it again); rely on memory of *rule shapes* and *failure lessons*.

## 7. Pacing and risk

- Attempt caps are real. A rough budget: use demo requests freely early (they're cheaper than wrong attempts), and never submit a prediction you can't explain with the same one-sentence rule that explains all demos.
- If after two attempts on a task you're still guessing between hypotheses, pick the one that is a strict special case of the other, or the one that changes fewer cells. Conservative transformations lose less often than ambitious ones when you're uncertain.
- Time spent verifying beats time spent generating new hypotheses. The rule is usually visible in the demos; the failure is usually in unverified details (offsets, inclusivity of endpoints, which rows count, tie-breaks).

## 8. Small practical checklist before every submission

1. Program reproduces every kept demo pair exactly? (Actually run it.)
2. One-sentence rule stated, and it explains the demos without special-casing?
3. Degenerate cases considered: single object, ties, empty categories, object at border, zero cells of a color?
4. Prediction for the test derived by *running the program*, not by hand-waving?
5. Memory written or updated?

If all five are yes, submit.
