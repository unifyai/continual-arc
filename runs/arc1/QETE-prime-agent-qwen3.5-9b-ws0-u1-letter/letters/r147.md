## First, the meta-lessons that cost me the most

**1. Ask for demos early and often when uncertain.** My single biggest failure mode was submitting a test prediction based on a rule that fit the demos but had an unresolvable ambiguity in the test case. On task-5c839a47 I burned 8 wrong attempts on a test grid with a *single dot* — a situation no demo showed. My rule covered "two or more dots" perfectly; the lone-dot behavior was guessable five different ways, and I guessed wrong eight times. If your rule has a case the demos never exercise (lone objects, zero objects, ties, boundary clipping), that's exactly when to request a demo pair *before* submitting. A demo request is cheap; a wrong submission is expensive and capped.

**2. When you're at the attempt cap, the residual risk isn't the rule — it's the edge case.** For every task, before submitting, write down explicitly: "what input would break this rule?" Then check whether the test input plausibly contains that input. If it does, request a demo or change your guess about that edge case specifically.

**3. Track your tried-and-failed hypotheses in a file.** I kept `task-1b7868f1_failed.json` with a note listing untried variants ("clean anchors (13,7),(12,8) and (12,7)+0->1 untried"). This prevented me from resubmitting duplicates (I noticed sub1 == sub3). Do this. When you get feedback that a submission was wrong, don't just patch — enumerate the alternative rules you haven't tried and rank them.

## How to actually solve these tasks

**Start with the cheapest structural probes, in this order:**
1. **Grid dimensions.** Is output = input size? Double? Half? If output is 2H×2W, think quadrant compositions (see task-794e60f6: TL=input, TR=rot90, BL=rot90ccw, BR=rot180). If it's 3H×3W or H×2W, think mirror-and-stack (task-73499f5a: each row becomes reverse+itself, then stack reversed/original/reversed).
2. **Color counts.** The most common color is almost always background. The rarest color is usually the "agent" — dots, seeds, markers. Many tasks are "the rare color does something to the background."
3. **Exact separator lines.** Scan for full rows/columns of a single color. Many tasks are "split at the separator, combine the two halves" (task-026adbf3: 3 where the halves match; task-707635df: 2 where both halves hold their own dominant color; task-8d84fe63 and task-48898d06: block-structured grids where one block is the template for the rest, or blocks encode counts).
4. **Connected components.** 4-connectivity for same-color blobs, 8-connectivity when shapes include diagonals. Compute bounding boxes. Ask: are there repeated shapes (twins)? Are there outliers (singleton large object = the "director," small objects = "actors")?

**Recurring rule families I've now seen twice or more — memorize these:**

- **Downward/upward gravity / shifting:** all non-background cells shift one row (task-efc2fba8). Check if the output is the input translated.
- **Enclosed pockets get filled:** flood-fill background regions from the border; unreached pockets fill with a constant (often 4), sometimes with corner-based rules (task-aa5a69a0: fill parity even→2, odd→7). Watch for subtlety: sometimes only *rectangular* pockets fill, and a specific- height pocket also absorbs a wall row (task-3f4fb1a9 — this took me many iterations to pin down; the exact condition was "2-row pocket whose bottom wall has pure background below it").
- **Stamps/copies:** find the largest or rarest shape; every other object of some class is an anchor where you stamp the shape's bounding box (task-1b7868f1: stamp largest component's bbox centered at each non-bg cell; task-770f2daf: stamp the rare shape at every offset where all its cells land on background/0). Variant: overwrite the *farther* member of a twin pair with the director's color (task-0f6e5a2f, distance measured to the director's arm).
- **Line drawing / rays:** runs of length ≥2 extend along their diagonal (task-3b5f776f); gaps of ≤2 between same-row markers get filled (task-8625f9bc); cells strictly between the min and max dot in a row/column get a fill color (task-5c839a47).
- **Projection/counting compression:** grid divided by solid separator lines into blocks; output is one cell per block (task-48898d06: 1 if ≥2 stray cells; task-67dd046a: downsample 3×3, mode ignoring a "noise" color; task-bb30ebc2: read the corner markers of each mega-block into a small grid).
- **Slide-toward-line:** an object moves adjacent to a full 2-line, and a full new line (8) is drawn on the object's far side (task-77262100 — handles both orientations, both sides; write it symmetric like I did).
- **Color remapping by rank:** two colors only? Map high→itself, low→0, or lowest→0 (task-2264bd4e, task-b7641a67: background between identical neighbors becomes 2). Uniform rows/cols become a constant (task-47ed202e).
- **Symmetry completion:** a diagonal of distinct colors determines a periodic tiling (task-2e29965a: each anti-diagonal has one color; tile the whole grid with period p). Also: mirroring with an inserted copy of the seed column/row.

**When the demos contradict your pet theory, drop the theory fast.** I once had a "sorting by diagonal" idea survive three demo checks before a fourth killed it. The correct move: after each demo, re-verify your program against ALL kept pairs, not just the newest. I kept pairs in `task-XXXX.json` and ran the program against all of them every time. Never submit a prediction from a program that doesn't reproduce every demo you have — that's free signal you'd be throwing away.

**Write the general program, not the demo-fitting one.** If demos only show the line-horizontal case, write the vertical case too and make the program *choose* based on the input (task-d4079843 does this with permutation + validation: try both interpretations, keep the one that's geometrically consistent — dots all on one side, distinct offsets, in-bounds mirror). Building "try candidate interpretations, filter by consistency checks, pick the one that survives" into your programs catches tasks where the test input uses the mirrored orientation.

## Coding hygiene in this harness

- Always take `bg = Counter(...).most_common(1)[0][0]`, and exclude it before reasoning about objects.
- Components: write one solid BFS/DFS helper and reuse it. Mine is in task-d4079843.py and task-b62da9e0.py — steal it.
- When stamping shapes, translate by bounding-box relative offsets, and *respect holes*: in task-1b7868f1 the seed's internal zeros had to be stamped literally, not skipped. Check demos for whether the stamp overwrites everything or only background.
- Guard every write with bounds checks; a test input may place anchors near edges (task-1b7868f1 clips stamps at the border).
- If your program finds no valid interpretation, return the input unchanged rather than crashing — an identity output sometimes scores partial credit and never crashes the harness.

## A final word on temperament

These tasks reward patience with structure over cleverness with pixels. Most solutions are 10–30 lines of Python built from: Counter, flood fill, bounding box, translate, overwrite-or-fill. When stuck, re-describe the input out loud in plain words — "there are little T-shapes and one big L" — and the rule usually names itself. And when the demos are few, prefer the rule that's *symmetric* (handles both orientations, both sides, both parities) over the one that happens to fit, because the test will find the case you didn't handle.
