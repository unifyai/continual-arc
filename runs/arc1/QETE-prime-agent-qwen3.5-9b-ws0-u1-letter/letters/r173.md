## 2. The rule catalog: shapes of rules that keep recurring

These are the rules I've actually verified against real pairs. Skim them — a future unseen task is often a *variant* of one of these families:

- **Stamping/tile propagation**: one "seed" object (largest non-background component) gets stamped, centered, at every anchor cell (task-1b7868f1); or a rare color's bounding-box pattern is stamped into every empty box of that size (task-770f2daf); or a 2n×2n grid is built from an n×n input as TL / rot90 / rot270 / rot180 (task-794e60f6).
- **Mirroring/tiling**: each row becomes reverse+itself, and the output stacks block, reversed block, block (task-73499f5a). Output was often an exact mirror/rotation composition.
- **Interpolation / between-ness**: color 3 fills cells *strictly between* the min and max position of the rarest color along each row and column (task-5c839a47).
- **Line/gap filling**: fill background between same-color runs with a fixed color (task-b7641a67); fill gaps ≤2 between markers, plus the bounding-box perimeter (task-8625f9bc); lines of solid color recolored to 2 (task-47ed202e).
- **Enclosure**: enclosed rectangular background pockets get filled (task-3f4fb1a9) — test enclosure by flood-fill from the border; anything not touching the border is enclosed.
- **Block decomposition**: grid lines (solid uniform rows/columns) cut the grid into blocks; output is one cell per block, computed from the block's contents — parity of strays (task-48898d06), majority color ignoring a mask color (task-67dd046a, 3×3 downsample), corner-marker equality (task-bb30ebc2). Also: two same-size blocks split by a separator line, output marks where they agree (task-026adbf3).
- **Movement toward a line**: a shape translates flush against a full-height line, old position becomes background, and a new full line is drawn at the old far edge (task-77262100). Also objects shift by one row down (task-efc2fba8).
- **Directed drawing from dots to bars**: single-cell dots draw stubs toward nearest bar, the dot changes color, and a mirrored line is drawn on the other bar at a clamped index (task-d4079843).
- **Ray extension**: same-color runs of length ≥2 on diagonals/antidiagonals extend in both directions until blocked (task-3b5f776f).
- **Periodic completion**: sparse diagonal/anti-diagonal coloring implies a periodic tiling; infer the period from the colored cells and tile the whole grid (task-2e29965a).
- **Overlap of two copies with an offset**: two stacked copies of one shape, offset by a cyclic shift; complete the cut-off copy (task-5997d753).
- **Noise removal**: keep only components of size ≥3 (or similar), everything else reverts to background (task-b62da9e0); concentric ring interiors get a fill color keyed to ring area parity (task-aa5a69a0); recolor based on which of a translation-twin pair is farther from an anchor object (task-0f6e5a2f).

When you meet a new task, ask: which family does it rhyme with? The extraction subroutines (component finding by BFS/DFS, most-common-color for background, bounding boxes, run splitting, per-row/column index lists) are worth memorizing — they reappear in nearly every rule.

## 3. How I actually find rules (a procedure worth copying)

1. **Identify the background** (most common color) and list *all* other colors with counts. The rarest color is usually the key actor.
2. **Extract components** (4-connectivity for single colors; 8-connectivity if shapes look loosely joined). For each: color, size, bounding box, shape signature = sorted relative cells.
3. **Look for twins**: objects with identical shape signatures at different translations. A rule often acts on a *pair* or *class* of twins, not a single object. This was the key in several tasks.
4. **Look for solid uniform rows/columns** — they are almost always separators or the axis the rule acts on. Check whether they're centered (that's a strong signal: mirrored/tiling outputs use the center).
5. **Guess a candidate rule, then immediately test it against every kept demo pair in code.** Never submit a prediction without verifying all pairs reproduce exactly, 0 mismatches. If a program reproduces all pairs, the test prediction is usually right — I only failed that once in many tasks (task-5997d753's first submission, before I understood the offset direction properly).
6. **Save the program and a memory file immediately** when it reproduces all pairs. Name them `task-<id>.py` and `task-<id>.json` (pairs) plus a `.mem.json` or similar memory note with the rule in words. Future-you meets these tasks again, and re-deriving a rule from scratch is expensive.

## 4. Where I burned attempts — learn from these

- **task-5c839a47, 8 wrong attempts on one test.** The rule was clear and verified on 10 pairs, but the test grid had only a *single* dot of the key color, and the rule family said nothing about lone dots. Identity, cross-shapes, row-only fills — all wrong. The lesson: **if your verified rule doesn't uniquely determine the test case's degenerate corner, don't burn submissions guessing.** I have no confirmation which guess would have been right; the cheaper move is to ask for demo pairs early if the harness allows it (I used demo requests successfully on task-5c839a47 and others). A degenerate input (single instance of the key object, zero instances, object touching the border) is exactly where rules go quiet.
- **task-1b7868f1**: my first rule (stamp centered at every non-bg cell) worked on demos but I wasted a run on a near-duplicate variant. The failed file `task-1b7868f1_failed.json` even records untried clean hypotheses ("clean anchors (13,7),(12,8)") — when you fail, **write down exactly what was tried and what wasn't**, so your next attempt isn't a duplicate. I duplicated a submission once (sub1==sub3) purely from sloppiness.
- **Anchor conventions matter**: in stamping tasks, whether the seed maps center-to-cell or bbox-corner-to-cell was the difference between right and wrong. If demos have multiple anchors, you can *verify the convention* against them before submitting.

## 5. Small technical habits

- Write `transform(grid)` taking a list of lists of ints and returning the same. Keep it self-contained (import inside the function if needed).
- Compare output against expected with exact element-wise equality in a quick loop over the kept-pairs JSON; print the number of differing cells per pair — a rule that's "one cell off" everywhere tells you a convention is flipped (offset sign, row/col swapped).
- Count colors with `Counter`; background = argmax. But beware tasks where the "line" color is the second most common (task-8625f9bc) — order of colors often *is* the rule's specification.
- When the output shape differs from the input, the difference itself is information: 2× width, 3× height, half size, block counts — derive the output dimensions first and let them constrain the rule (task-73499f5a, task-bb30ebc2, task-026adbf3, task-48898d06 all had output dims determined by separators).
- Note in your memory files whether a test was solved or wrong, and *why*. My most useful memories are one-sentence rules plus a failure note, not long essays.

## 6. Attitude

The rules in these tasks are always simple once found — the difficulty is choosing among a handful of simple hypotheses. Bias your search toward: color ordering, twinned shapes, separator lines, and strict-between/stamping operations, in that order. Verify against every pair, every time. Save everything. And when a rule doesn't cover the test input's situation, spend your budget on more demos, not more guesses.
