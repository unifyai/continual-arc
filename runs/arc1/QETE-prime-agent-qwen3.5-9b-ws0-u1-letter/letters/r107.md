## The single most important discipline

**Verify against every kept demo pair before submitting.** Write the program, run it on all demos, compare cell-by-cell. A program that fits 1 of 2 demos is worse than no program. My memory files repeatedly say "program reproduces all kept pairs" — make that your invariant.

Second discipline: **prefer rules that are simple and symmetric** — recolorings, geometric motions, per-row/per-column logic. ## Rules I have already learned (reusable patterns)

Scan your inherited `programs/` directory — the `.json` files hold demo pairs and the `.py` files hold working code. Patterns worth internalizing:

- **Recoloring by color order, not frequency.** In task-2264bd4e the rule was "min color → max color, max color → 0." I first tried majority/minority roles and failed. When two colors swap/transform, try ordered-by-value mappings first, and check against demos before trusting frequency-based roles.
- **Structural markers.** Full uniform rows/columns are usually separators (tasks-026adbf3, 48898d06, 8d84fe63, 707635df, 47ed202e). Finding them first and splitting the grid into blocks is often half the solution. Blocks then get compared, tiled, downscaled, or counted.
- **Objects and bounding boxes.** Connected components (decide 4- vs 8-connectivity by testing both on demos), their bounding boxes, and filling/moving/stamping boxes appear in tasks-b62da9e0, aa5a69a0, 77262100, 1b7868f1. A common shape: the object's bbox gets filled, or the object slides to touch a marker line and a new line appears on the far side.
- **Between-ness.** Cells "between" two markers in a row or column become a special color (tasks-5c839a47, b7641a67, 8625f9bc). Often the fill color is a constant like 2, 3, or 4.
- **Tiling/tiling patterns.** Output may be a rotated block of the input (794e60f6), mirrored rows/columns (73499f5a), or a diagonal residue fill (2e29965a: try both r+c and r−c mod L with L = number of colors).
- **Symmetric extension.** Each row becomes reverse+original, or the whole grid mirrors — cheap to test early.
- **Downscaling.** If the output is much smaller, look for k×k blocks mapping to one cell via majority color, parity of stray pixels (48898d06: odd count of stray color → 1), etc.

## A practical work order for each new task

1. Count colors and their frequencies. Identify background (most common) and the special colors.
2. Find full uniform rows/columns; if any, split into blocks and compare blocks.
3. Find connected components of non-background; compare their shapes, sizes, counts. Look for twins (identical shapes), singletons, largest/smallest.
4. Check simple global operations: shifts by one row/col, rotations, mirroring, doubling/tripling, recolor mappings.
5. Check local operations: a cell changes if its neighbors match some pattern (between-ness, adjacency to markers, run-gaps).
6. If output is a different size, it is almost certainly derived from blocks/tiles — find the factor.
7. Once a candidate rule reproduces all demos, restate it in one sentence. If you cannot, be suspicious.

## Handling the test input

When applying to test: if the rule depends on parameters learned from demos (like a fill color or a displacement), recompute them *from the test input itself* using the rule, don't hard-code demo values. My task-5997d753 failure came partly from anchoring on demo specifics. The rule should be a function of each grid independently.

If demos underdetermine the rule and you have submission budget, choose the hypothesis that also explains *why* each demo cell changed — think about the generator, not the pixels.

## Small code habits

- Write a helper `def eq(a,b): return a==b` comparison runner that loads each demo `.json`, runs `transform`, and prints pass/fail per pair. Use it every time.
- Prefer pure functions over mutating input grids (`out=[row[:] for row in g]`).
- Components: BFS/DFS with `seen` grid; compute bbox, size, and shape-canonical form (sorted relative coords) — canonical shape keys let you detect twins and rotations quickly.
- Handle both orientations (horizontal/vertical) in one program by testing which fits, as in task-77262100 and task-d4079843 — many rules are orientation-agnostic.
- When a rule has special cases, encode them but flag in your memory file that they are unverified.
