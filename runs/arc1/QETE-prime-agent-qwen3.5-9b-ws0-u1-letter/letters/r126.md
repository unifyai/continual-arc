## 1. The workflow that works

For each new task:

1. **Read all demo pairs first**, carefully, cell by cell if needed. Note what changed and what didn't.
2. **Form a hypothesis in words** before writing any code. State the rule as one sentence. If you can't state it crisply, you don't have it yet.
3. **Write a `transform(grid)` program** and save it to `programs/task-<id>.py`. Your saved program and demo JSON are your memory — future turns may show the same task again, and having a verified program beats re-deriving.
4. **Verify against every kept demo pair** before submitting. If your program fails even one pair, don't submit the prediction — fix the rule first.
5. **Save a memory file** when solved (e.g. `task-<id>.mem.json` with rule + files + status). Future-you should be able to reload a solved task in one line.

## 2. Rules I've actually verified (reuse these ideas)

These exact rules solved tasks in this stream. Recognize the pattern family quickly:

- **Fill enclosed rectangular pockets of background with a fill color** (task-3f4fb1a9): find background components not touching the border; only *solid rectangles* get filled; special case — a 2-row-tall pocket also recolors its bottom wall row when the row below that wall is background across the full pocket width. Non-rectangular pockets (L-shaped, beside a stem) are left alone.
- **Extend rays through dots** (task-d4079843): two bar segments of one color + scattered dots of another. From the bar facing the dots, draw a perpendicular line through each dot (dot becomes 4). From the opposite bar, draw lines at the same relative offsets spanning the full gap, in the dot color. Check dots are strictly on one side of the bar.
- **Stamp the seed bbox at every anchor** (task-1b7868f1): largest non-background component = seed; every other non-background cell is an anchor; translate the seed's bounding box so its center lands on each anchor, overwriting. Stamps can overlap — later stamps overwrite earlier ones; that's fine.
- **Background cell between two identical non-background cells becomes a special color** (task-b7641a67: same color 2; task-5c839a47: between two dots of the *least common* color in a row OR column, cell becomes 3, dots unchanged). Also task-8625f9bc: fill gaps of size ≤2 between consecutive markers along rows/columns, plus the marker-color bounding box perimeter.
- **Fill bounding box of each non-background component ≥3 cells with its color; everything else → background** (task-b62da9e0). Note: use 4-connectivity.
- **Hollow rectangles on background: fill interior with 2 if interior area is even, else 7** (task-aa5a69a0). Detect via `y1-y0>=2 and x1-x0>=2 and len(comp)==2*(h)+2*(w-2)`.
- **Mirror doubling** (task-73499f5a): each row → `row[::-1]+row`; output = reversed rows + rows + reversed rows (height triples). Works color-blind.
- **2×2 rotation tiling** (task-794e60f6): output = orig | rot90CW on top, rot90CCW | rot180 on bottom. n×n → 2n×2n.
- **Shift all non-background cells down one row** (task-efc2fba8); clear originals; top row becomes background.
- **Diagonal-modular coloring** (task-2e29965a): if the L nonzero colors are constant along diagonals `r+c mod L` or `r−c mod L`, fill the whole grid with that diagonal pattern.
- **Separator-based tasks**: a full uniform row/column of one color splits the grid.
  - task-026adbf3: two same-size blocks A,B; output 3 where A==B cellwise, else the blocks' common most-common color.
  - task-707635df: output = AND of the two halves' nonzero masks, recolored 2.
- **Solid uniform rows/cols become color 2** (task-47ed202e).
- **Rare color = seed shape; stamp it at every offset where all its cells land on 0** (task-770f2daf).
- **Counting/compression tasks**: divide by solid separator lines into blocks; output cell = 1 if odd count of stray color inside the block, else background (task-48898d06). Or downsample 3×3 blocks to their most common non-background color (task-67dd046a).
- **Compare two blocks split by a separator** (task-026adbf3) — output is the XOR/agreement pattern.
- **Object + full line of color 2** (task-77262100): object slides until adjacent to the line; a full 8-line is drawn just outside the object's far side.
- **Smallest color → 0, other → smallest** (task-2264bd4e): output = 0 where cell equals the smallest color value, else that smallest value. Simple, worth checking early.
- **Twin shapes + singleton angle** (task-0f6e5a2f): a singleton large thin L/angle is the "arrow"; among exact-translation twin pairs (same canonical shape occurring exactly twice), recolor the member *farther* from the arrow's horizontal arm to the arrow's color.

## 3. Heuristics for guessing when the rule is new

- **Background = most common color.** Almost every task. Then identify objects as connected components (4-connectivity unless touching matters).
- **Colors by rarity**: the rarest color is usually the seed/dot/signal; the second most common is usually structure.
- **Output size** is a huge clue. Same size → local recolor or object move. Double in one dimension → mirror or tiling. Half/quarter → downsample or comparison. Tripled → the mirror-stack rule.
- **What's unchanged is as informative as what changed.** Cells identical between input and output often bound the operation (e.g. pockets filled but stems untouched).
- **Check symmetric explanations first**: mirror, translate, rotate, then conditional recolor.
- **If two candidate rules both fit demos**, prefer the one with a *mechanism* (geometry, adjacency, containment) over a color lookup tied to specific values.

## 4. Common failure modes (I lost points on all of these)

- **Wrong connectivity**: use 4-connectivity for components unless diagonal touching is clearly meaningful. I once fixed a bug just by switching this.
- **Forgetting overlap/overwrite order** when stamping; generally later stamps overwrite earlier — verify with demos where stamps collide.
- **Bounding box vs. actual shape**: when a rule says "fill the bounding box", stray cells of other colors inside the box get overwritten. Check demos for protected cells.
- **Off-by-one on the separator row/col**: which side does the rule act on? Is the separator itself kept, removed, or recolored?
- **Assuming the object is a rectangle** when it's an L or a frame. Test whether `len(comp) == bbox_area` — that single check separates solid rectangles from frames/Ls, and several rules hinge on it.
- **Not verifying all demo pairs before submitting.** Always run your program on every pair. One pair failing = wrong rule, not noise.
- **Overfitting to specific colors.** Write rules in terms of "most common color", "rarest color", "the fill color 4/2/3" only when the demos confirm that constant.

## 5. Practical tips for the harness

- Keep each program self-contained: a single `transform(grid)` taking a list of lists of ints and returning the same. Import inside the function or at top — both fine.
- When you save demo JSON, save it as a list of `{"input": ..., "output": ...}` pairs exactly as I did, so a re-run can verify instantly.
- If a task resists after 2–3 serious attempts, **request more demos if the harness allows** — one extra pair usually disambiguates two competing rules faster than more thinking.
- If you hit the attempt cap on a task, write the memory file noting what was tried and what was wrong, then move on cleanly. Don't let one task eat the whole session.
- Log wrong attempts in a `_failed` file with a note (see `task-1b7868f1_failed.json`) — the near-miss hypotheses are valuable when a variant of the task reappears.

## 6. A final word

Your instinct on most tasks should be: identify background → find objects → notice what's special about them (count, shape, twins, rarity) → state the rule in one sentence → implement → verify on all demos → save program and memory. Speed comes from pattern-matching against the rule families above; accuracy comes from the verification step, which you must never skip.
