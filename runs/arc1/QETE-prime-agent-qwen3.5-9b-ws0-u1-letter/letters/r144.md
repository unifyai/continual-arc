## 1. The core workflow, every single time

For each task: read the demonstration pairs (they're in `programs/task-<id>.json` files or given to you), figure out the rule, write `transform(grid)` into `programs/task-<id>.py`, verify it reproduces every demo pair *exactly*, then submit your prediction for the test input.

The single most important discipline: **programmatically verify your program reproduces all demo pairs before predicting the test.** Run the program on each input, compare cell-by-cell with the output. Do not "eyeball" it. I lost two early submissions to transcription typos — a row shifted one column when hand-copying an answer into JSON. Never hand-write a grid; always generate it from code and write it out with a script.

## 2. How to find the rule

Start with the cheap structural hypotheses, in roughly this order of frequency — these cover a large fraction of ARC tasks:

- **Color mapping**: each color maps to another (often the two non-background colors swap, or the least common color maps to a fixed output color like 1, 2, or 3). Check color histograms of input vs. output first. If counts per color match cell-for-cell, it's almost certainly a pure recolor — find the permutation.
- **Background detection**: the background is almost always the most common color, not necessarily 0. Write `Counter(v for row in g for v in row).most_common(1)[0][0]` into your muscle memory.
- **Components and their properties**: find connected components (4-connectivity usually; sometimes 8 — try both if 4 fails) of non-background cells. Look at: how many there are, their sizes, shapes (bounding box fill ratio), whether two are exact translations of each other (canonicalize by subtracting min row/col and sorting the cell set — this detects "twins" reliably), and which one is unique/largest.
- **Lines and separators**: full rows or columns of a single uniform color often split the grid into blocks. Tasks like "each block becomes one cell based on a property" (e.g., contains a stray color or not) are common. Also: uniform rows/cols themselves get recolored (I solved a task where every uniform row/column became all 2s).
- **Enclosed regions**: flood-fill the background from the border; background cells *not* reached are enclosed pockets. A very common rule: fill enclosed pockets with a specific color (often 4). Watch for refinements — in one of my tasks, only *solid rectangular* pockets were filled, and a 2-row-tall pocket also absorbed its bottom wall row when the row below was background. Non-rectangular pockets stayed unchanged. When a simple version fits all demos but you suspect edge cases, encode the refinement that the demos support.
- **Counting/parity**: fill color can depend on area parity (even → 2, odd → 7 in one of my tasks), or count of stray pixels per block (≥2 → 1, else background).
- **Symmetry/completion**: mirror rows (r → reverse(r)+r), tile the input (input + rot90 + rot180 + rot270 for square inputs), or reflect/extend patterns. One task's answer was literally `[r[::-1]+r for r in grid]` stacked reversed-original-reversed. Simple things like this happen.
- **Diagonal runs**: same-color runs of length ≥2 on diagonals or antidiagonals extend along the diagonal until blocked. Group cells by `r-c` and by `r+c`.
- **Stamping/tiling a pattern**: find the rare-color shape, then place copies at every offset where all its cells would land on background (or on zeros). Or: one object is a "seed", every other non-background cell is an anchor, and the seed's bounding box gets stamped centered on each anchor.
- **Motion toward a line**: an object slides until adjacent to a marked line (e.g., a solid 2-row), and a full line of another color (8) is drawn just outside the object's far side.
- **Fill between markers**: within each row and column, cells strictly between the min and max positions of the rarest color become the output color. Gaps of ≤2 between same-color markers get filled, while the marker bounding-box perimeter also gets filled — variants abound; let the demos discriminate.
- **Comparison of two blocks**: if a full uniform separator splits the grid into two same-size halves A and B, the output often compares them cell-wise: output color X where they agree, the shared background where they differ (or vice versa). Check `A[r][c] == B[r][c]`.
- **Downscaling**: a large grid made of 3×3 (or 2×2, 5×5...) blocks with separator lines compresses to one cell per block; the cell value is the block's most common non-background color, or 1/0 by a presence test.
- **Shifts**: sometimes the whole transformation is "shift all non-background cells down one row" or "extend each row by mirroring". Don't overcomplicate before testing these.

## 3. Method for hypothesis testing

When you have a candidate rule, don't just check it passes — check it *fails to be overfitted*. Ask: does this rule use only information the demos legitimately contain? Is there a simpler rule that also fits? Prefer the simpler one. If two rules both fit all demos but diverge on the test input, think hard about which is more "natural" as an ARC task, and consider what a human designer intended. When a rule needs a special-case branch to fit a demo (like my two-group template-matching with best-offset search), that's acceptable, but keep the branches principled (e.g., handle both horizontal and vertical orientations symmetrically — many tasks come in both orientations, and your program should too).

A very effective technique for ambiguous tasks: enumerate hypotheses and compute, for each, its prediction on the test input. If several hypotheses agree on the test prediction, submit that with confidence. If they disagree, pick the one whose mechanism feels most general.

## 4. Asking for more demonstrations

You can request additional demo pairs. **Request them when genuinely uncertain, not as a crutch.** Good times to ask: (a) the test input hits a case absent from demos — e.g., I once had a task where all demos had ≥2 marker dots per row but the test had a single dot; I burned 8 wrong attempts guessing the lone-dot behavior. If I had requested demos the moment I noticed the mismatch, I'd have learned the rule cheaply. (b) Two very different rule families both fit the current demos. Bad times: your program already reproduces everything and you're just nervous.

Hard-won lesson, written into my memory file: *"if a test has a single dot, request demos early."* Generalize it: **if the test input has any structural feature (a lone object, a different color count, an odd dimension) that no demo exhibits, either request a demo or reason very explicitly about what the most natural extension is.** Identity ("leave it unchanged") is often wrong for these cases, but I also lost with several exotic extensions — sometimes the answer is genuinely minimal. Weigh carefully.

Also: there's a wrong-attempt cap. When you're down to your last couple of attempts, choose the prediction that the *most* independent plausible rules agree on, not the cleverest one.

## 5. Programming craft in the harness

- Write `transform(g)` taking a list of lists of ints, returning the same. Keep it self-contained; import inside the function or at top, both fine.
- Standard toolkit you'll rewrite constantly — have it ready mentally:
  - background: `Counter(...).most_common(1)[0][0]`
  - components: BFS/DFS over non-bg cells, 4-conn, collecting `(r, c)` lists
  - canonical shape key: `tuple(sorted((r-minr, c-minc) for r,c in cells))`
  - bounding box fill check: `len(comp) == (r1-r0+1)*(c1-c0+1)`
  - flood fill from border to find enclosed cells
- Copy outputs before mutating: `out = [row[:] for row in g]`. Returning the input list mutated has burned people.
- When a rule involves two objects interacting (e.g., "recolor the farther of twin pair from an arrow"), compute distances with min Manhattan over cell pairs, and define tiebreaks explicitly (larger size, etc.). Record your tiebreaks in the memory file so future-you understands.
- Permutations: when matching two objects by relative offset (like drawing lines from dots offset along a bar), enumerate both orderings/permutations and keep the consistent one; require offsets to be distinct; bounds-check everything before writing.

## 6. Using memory files

When you solve a task, write a memory file (`memory_task-<id>.json` or a status json) containing: the files, the rule in one or two precise sentences, and whether the program reproduces all kept pairs. These are for *you* — if the stream re-visits a task or a near-variant, your old rule description is worth more than the code, because variants often differ in one detail (which color fills, whether walls are absorbed, which connectivity). Write rules at the level of "fill X with Y when condition Z", not "I did the thing".

Also keep a "failed attempts" note for hard tasks (I saved `task-1b7868f1_failed.json` listing tried variants and untried anchors like "clean anchors (13,7),(12,8)"). When you fail a submission, immediately record: what you submitted, why it failed, and which untried hypotheses remain. This prevents resubmitting near-duplicates — I once noticed two of my failed submissions were identical modulo a shift.

## 7. Specific pitfalls from my run

- **Don't trust grid dims in the file header over the actual data**; count rows and columns yourself.
- **Overfitting single-pair tasks**: with only 1–2 demos, many rules fit. Prefer rules that treat colors symmetrically and handle both orientations.
- **The "second most common color" is often the marker**, but not always — sort by count and inspect; sometimes the marker is the *rarest*.
- **Output dimensions change** in some tasks (downscaling, tiling, block extraction). Compute them from the mechanism, not by copying input dims.
- **Test the zero-cell convention**: some tasks treat 0 as background, others as a real color. In one task, 0 cells inside a stamped shape's bounding box had to be stamped *as-is*, including holes.
- **When the same task ID reappears with a new test input**, load your old program, run it on the new test, and sanity-check the output against your recorded rule before submitting. My old programs solved repeat instances correctly several times — this is free points, but only if you verify rather than blindly submit.

## 8. Attitude

ARC rewards patience and enumeration over brilliance. Most tasks yield to systematically checking: recolor? components? lines? symmetry? enclosure? counting? Take ten minutes enumerating before committing to anything exotic. And keep the verification loop sacred: demos in, program, program output vs. demos, only then predict.

You are smaller than I am, but this game is mostly discipline. A careful 9B that verifies every submission and requests demos at the right moments will beat a careless giant. Be that model.
