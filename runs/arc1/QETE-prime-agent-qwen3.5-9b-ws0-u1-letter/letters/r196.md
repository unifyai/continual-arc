## The big picture: your workflow each task

1. **Ask for demo pairs early and often.** The single most valuable action is requesting demonstration input/output pairs. Every task I solved well, I solved because I had 2–10 demo pairs to check against. Programs that reproduce all kept demo pairs are usually right; programs that guess from a test input alone are usually wrong. If the harness lets you request demos, do it before you commit to a theory — but *after* you've formed a hypothesis, so you know what to look at.

2. **Write a program, not a guess.** When you submit, write a `transform(grid)` function into `programs/task-<id>.py` and let it produce the test output. Don't hand-construct the output grid unless the task is trivial. The program lets you verify against demos; hand construction has no verification.

3. **Verify against every kept pair before submitting.** Run your `transform` on each demo input and compare to the demo output cell by cell. If even one fails, your rule is wrong — go back and look at the failing pair again. Nearly every failure I had was a rule that fit the pair I focused on but not the others.

4. **Save your memory files.** After solving, write a small JSON memory like:
   `{"task": "task-XXXX", "files": [...], "pairs": n, "program_reproduces_all": true, "rule": "<one-sentence rule>"}`
   The one-sentence rule is the most important field. Tasks in this stream repeat families of rules, and re-recognizing a family saves enormous time.

## The rule families I saw — and how to recognize them

Memorize these signatures. When a new grid appears, scan it mentally against this list before inventing anything:

**1. Mosaic / block compression.** Grid divided by full solid separator rows/columns of one color into uniform-ish blocks. Output is one cell per block. Variants: output = block's dominant color; output = 1 if a stray color appears in the block, else background; output = the guide color at the intersection of the block's guide row and guide column; output = value only if all four corner markers of the block agree, else 1. Signature: full-width rows or full-height columns of a single repeated color, everything else in regular sub-rectangles. The separator color is usually the *most common repeated-line* color — find it, then segment.

**2. Two halves compared.** Grid split by one centered separator line into two same-size halves A and B. Output same size as one half: mark cell X (some fixed color like 3 or 2) where A and B *disagree* (or *agree* — check which), else background. Sometimes: mark where both halves hold their own dominant color. Signature: odd total dimension, middle row/col uniform.

**3. Dot-to-line fills.** A rare "dot" color (least common). Output fills cells *strictly between* dots along rows and/or columns (or diagonals). Important lesson: if a test grid has only ONE dot, my "between min and max" rule degenerates and I burned 8 attempts. If you see a lone dot in the test, request demos immediately and think hard about what a single dot should do (extend? stay? form a cross?).

**4. Diagonal/anti-diagonal run extension.** Same-color runs of length ≥2 extend along their diagonal direction until blocked by non-background or edge. Signature: scattered short runs that align diagonally.

**5. Periodic tiling.** Sparse colored cells determine a periodic pattern along rows, anti-diagonals (i+j), or diagonals (i−j). Output is the full periodic tiling. Method: group cells by the line key, check each line has a single color, find the period p, build a mapping from (key mod p) → color, then fill the whole grid. If any line has two colors, that's the wrong axis; try the next.

**6. Component stamping / translation.** Find the largest non-background component (the "seed"). Every other non-background cell (or component) is an anchor; stamp the seed's bounding box translated so its center (or top-left, or the anchor cell's role within the seed) maps onto the anchor. **Watch out:** the bbox may contain background-color cells and even zeros that must be copied as-is (holes are part of the pattern). This task family is common and the details of *which point maps to which* (center-to-anchor vs. anchor-role-to-anchor) are where wrong answers live — get one demo pair and check the offset exactly.

**7. Enclosed region fill.** Background-colored connected components that don't touch the grid border get filled with a color (often 4). Check rectangularity: only *solid rectangular* pockets get filled; irregular pockets stay. Sometimes an extra rule (e.g., a 2-tall pocket also colors the wall row below it if that wall sits on background).

**8. Symmetry tiles.** Output = 2×2 block of the input rotated: input, rot90×3, rot90, rot90×2 (or similar). Signature: output dims are exactly double, and one quadrant equals the input. Verify by checking whether output[0:n][0:n] == input.

**9. Mirror-and-tile.** Each row becomes row[::-1]+row (width doubles); rows stacked as reversed-block + block + reversed-block (height triples). Check: output row 0 == output row n−1 reversed pattern.

**10. Straight-line completion / rectangle borders.** Marks form a mostly-complete rectangle. Fill the bounding-box border with a fixed color (2) where background, and complete broken straight interior lines between mark cells.

**11. Recolor by comparison.** Two colors only: keep the higher one, map the lower to 0 (or to background). Trivial but easy to overthink. If the grid has exactly two colors, try this first.

**12. Single dominant transformation.** Sometimes it's just: shift everything down one row (top row becomes background); shift an object to touch a line; move a shape flush against a divider and draw a new line where it used to be. Signature: output is same size, only a small region differs from input. When output ≈ input, diff them cell by cell and describe the diff precisely — the rule is *exactly* the diff, no more.

**13. Shape twin selection.** Two components share the same canonical shape (exact translations of each other); a special large thin shape (e.g., an angle/arrow with arms ≥3) is the reference. Recolor the twin that's farther from (or nearer to) the reference. Canonicalize a component as `tuple(sorted((y-min_y, x-min_x) ...))` and group by that key.

**14. Pattern propagation from one block.** Grid of regular blocks; one block has "off-pattern" cells relative to its block's dominant color; that block's full 2D pattern gets tiled into every block.

**15. Right-edge clipped copies.** Two stacked copies of a pattern, one clipped at an edge. The complete copy is the reference; find the horizontal shift that best aligns them; fill the clipped copy's extension (color 1) where the reference pattern, shifted, extends beyond it. Alignment by max overlap-count is the robust method.

**16. Stub-and-mirror lines.** Bar(s) of one color (long straight multi-cell components) plus single-cell dots. Each dot draws a stub toward the nearest bar and turns into a fixed color; a mirrored full line is drawn on the other bar at the dot's clamped index along the bar.

## Concrete techniques that kept saving me

- **Background = most common color. Almost always.** `Counter(v for row in grid for v in row).most_common(1)[0][0]`. Non-background cells define the objects.

- **Connected components, 4-connectivity for same-color objects, 8-connectivity when parts of one object are diagonally adjacent or separated by color.** If a component looks "broken," retry with 8-connectivity, or with all non-background colors grouped together.

- **When output is same-size as input, DIFF IT.** Print, for each cell, `input→output` where they differ. Group the diffs. The rule is the diff pattern. This is the fastest route to the truth and the thing a small model most often skips.

- **When output is smaller, find the block structure.** Output height = number of row-bands, output width = number of col-bands, where bands are separated by the uniform separator lines. Then for each band-pair, figure out what single value the output cell holds.

- **Shape canonicalization for twin detection:**
  ```python
  key = tuple(sorted((y - miny, x - minx) for y, x in comp))
  ```
  Group components by key; groups of size 2 are "twins." This appears in many disguises.

- **Nearest-object computations:** mindist = min over cell pairs (Manhattan or Euclidean). Sort candidates by (distance, size, whatever the demos show). If two demo pairs disagree on tie-breaking, request another demo specifically to disambiguate.

- **Don't over-fit to one pair.** If your rule fits pair 1 perfectly but pair 2 fails at one corner, the corner detail matters — maybe it's 4- vs 8-connectivity, maybe inclusive vs. exclusive of endpoints ("strictly between" vs "between inclusive"), maybe clamp vs. wrap. Endpoint semantics are the #1 source of near-miss failures.

- **Zeros are data.** Some grids use 0 as genuine object color, not background. Never assume 0 is background — verify by counting. And in stamping tasks, zeros *inside a seed's bbox* get stamped too.

## Harness-specific lessons

- **Keep failed-task notes.** When a task goes wrong, write a `_failed.json` or memory note listing what you tried and what's untried (e.g., "clean anchors (13,7),(12,8) and (12,7)+0→1 untried"). I solved a repeat instance on a later attempt purely because I'd recorded the untried variants. Variants differ by: which cells are anchors, whether 0 cells participate, connectivity, inclusive/exclusive fills, and which member of a twin pair is recolored.

- **One task cost me 8 wrong attempts because a demo rule was right but the test had an edge case (single dot) the demos never covered.** When your demo count is small and the test input looks structurally different from all demos (different object count, lone objects, missing separator), pause. Ask for more demos before submitting. The test input itself is information: if your rule doesn't even *apply* to it (e.g., needs two dots, has one), the rule is incomplete.

- **Order of operations in your code matters for fills.** If several rules write to the same cells (e.g., diagonal extension and region fill), determine precedence from demos: usually later writes overwrite, but some tasks protect already-colored cells ("only fill background cells"). Check which by finding a demo pair where the two rules overlap.

- **Write a tiny verify script** (in your head or as a file):
  ```python
  def check(fn, pairs):
      for p in pairs:
          assert fn(p["input"]) == p["output"], "MISMATCH"
  ```
  Run it every time. An assertion failure is cheap; a wrong submission is expensive.

- **Color choice in outputs is usually a small fixed set:** 2, 3, 4, or a color present in the input. If your rule produces the right *shape* but wrong color, don't rewrite the rule — just look at which color the demos use and where it comes from (often "the seed's color," "the line's color," or a fixed constant like 4 for fills).

## On guessing under pressure

When you must submit without full confidence, rank candidate rules by: (1) reproduces all kept demos, (2) is the simplest description of the diff, (3) applies cleanly to the test input's structure. If your top rule doesn't structurally apply to the test input (right counts of objects, right separators present), prefer the next candidate — a rule that can't even parse the test input is not the rule, no matter how well it fits the demos.

And when you're stuck: request a demo pair. It is nearly always the highest-value move available. I cannot count how many times one extra pair collapsed an hour of theorizing into five minutes.
