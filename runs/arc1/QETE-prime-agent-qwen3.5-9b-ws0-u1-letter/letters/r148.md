## The rule catalog (learn these patterns cold)

ARC rules cluster into families. I solved ~20 tasks; nearly every one fell into one of these:

1. **Color substitution / inversion.** Keep the higher of two colors, map lower to 0 (task-2264bd4e). Or map X→Y globally. Check: does the output have the same shape with colors swapped?
2. **Grid tiling / reflection.** Output = input + mirror horizontally, stacked with reversed order (task-73499f5a: rows become reverse(row)+row, output = block + reversed(block) + block). Or 2n×2n from n×n: TL=input, TR=rot90cw, BL=rot90ccw, BR=rot180 (task-794e60f6). When output dims are exact multiples (2x, 3x), suspect mirror/rotation composition immediately.
3. **Super-resolution / downsample.** Divide grid into 3×3 blocks, each block collapses to one color = most common non-background color in the block (task-67dd046a, 21×21→7×7). Or blocks bounded by solid separator rows/cols, each block becomes one cell = 1 if it contains stray pixels else background (task-48898d06).
4. **Separator-split comparison.** Grid split by a full uniform row/col into two equal halves A, B; output = 3 where A cell == B cell, else the shared background (task-026adbf3). A variant: split at a centered solid line; output = 2 where both halves have *their own dominant color* at the same position (task-707635df). Check "dominant color per half" vs "same color" carefully — these look similar but differ.
5. **Line drawing / connectors.** Fill background cells strictly between two dots of the same (rare) color per row and per column (task-5c839a47: fill with 3). Fill with 2 when background-colored cells sit between two same non-bg cells in a row (task-b7641a67). Extend same-color diagonal/antidiagonal runs of length ≥2 in both directions until blocked (task-3b5f776f). Rows/columns that are a single repeated color become all 2 (task-47ed202e).
6. **Slide-until-touch + draw a line.** An object slides toward a 2-line until adjacent on its side; then a full line of a third color (8) is drawn just outside the object's far side (task-77262100). Handles both orientations and sides.
7. **Downward shift.** All non-background cells move down one row; originals cleared (task-efc2fba8). Trivially simple rule — don't overcomplicate when demos show only a one-row shift.
8. **Stamping.** The largest non-background component is a seed shape; every other non-bg cell is an anchor; stamp the seed's bounding box translated so the seed's center maps onto the anchor (task-1b7868f1). Variant: stamp a rare-color shape at every offset where all its cells would land on 0s (task-770f2daf).
9. **Twin objects + a special singleton.** Among exact-translation twin shape pairs, pick the pair whose nearer member is closest (Manhattan) to a large thin L-shaped "arrow"; recolor the *farther* member to the arrow's color (task-0f6e5a2f). The singleton's color is the key.
10. **Enclosed pockets.** Fill enclosed background regions (not touching the border) with 4 — but only solid rectangular ones; an L-shaped pocket beside a stem stays unchanged. Special case: a 2-row-tall pocket also absorbs its bottom wall row when the row below that wall is background (task-3f4fb1a9).
11. **Cleanup/denoise.** Components of size ≥3 get their full bounding box recolored and kept; everything else becomes background (task-b62da9e0). Small scattered pixels are noise; large colored regions are signal.
12. **Counting/parity fills.** Inside a rectangle outline, fill interior with 2 if the enclosed area is even, 7 if odd (task-aa5a69a0). Suspect parity/count rules when fill colors differ between similar shapes.
13. **Maze/threshold scans.** Cell becomes 3 if it lies strictly between min and max positions of the rare color along its row and column.

## Practical strategy

**First moves for any new task, in order:**
1. Compare input and output dims. Same dims → in-place recolor/stamp rule. Output 2x/3x → tiling/mirroring. Output smaller → downsample or block-collapse. Output larger → replication.
2. Diff demo outputs against inputs cell by cell. List exactly which cells changed and to what color. Half the rules I solved were visible from the diff alone.
3. Count colors. The most common is usually background. The rarest is usually the "actor" (dots, seeds, markers).
4. Check for structural lines: full rows/cols of one color (separators), the two most common colors forming a lattice (task-bb30ebc2: grid of 2-blocks separated by 4/3 lines, markers at crossings encode a compressed output grid).
5. Write the program, run it against **all** kept demo pairs, and only submit when it reproduces every one.

**On demo requests:** request demos early when unsure — they are cheaper than wrong submissions. When a rule has an ambiguous edge case (a lone dot, a pocket shape you've never seen), ask for a demo that exercises it rather than guessing. I burned 8 attempts on task-5c839a47 guessing what to do with a single dot; the correct move was to request demos immediately.

**On ambiguous rules, prefer the simplest hypothesis that fits all demos,** but test discriminating demos before submitting if any doubt remains. When two hypotheses fit, ask for one more demo pair that separates them.

**Common traps:**
- Don't assume the fill color is always the same across a task; sometimes it depends on parity, orientation, or which side (tasks 707635df, aa5a69a0, 77262100).
- Background is the *most common* color, not necessarily 0.
- Components are usually 4-connected, but check whether 8-connectivity matters (task-1b7868f1 uses 8-connection for the seed).
- "Strictly between" vs "inclusive" endpoints matters — dots themselves usually stay unchanged.
- When stamping, check clipping at borders and whether the anchor is the bbox center or the seed's own centroid.
- Offsets matter: mirror-then-concatenate (reverse+original) vs original+reverse differ; derive the exact order from demo 1 before writing code.

**Write programs defensively:** pure functions, no I/O, handle the general case (both orientations, both sides, any colors via Counter) rather than hard-coding. My task-d4079843 program tries both bar orientations with validity checks and returns on the first consistent interpretation — that generality is what made it generalize to unseen tests.

**Keep your own notes.** When you solve or fail a task, write a memory entry like mine: task id, files, the rule in one sentence, and what went wrong. If the same task reappears, that note is worth more than any inference.

You are a smaller model than I am, but that is not the bottleneck here. The bottleneck is discipline: diff the grids, count the colors, verify against every kept pair, and never submit a guess you could have tested with one more demo. Do that, and you will solve more than I did.
