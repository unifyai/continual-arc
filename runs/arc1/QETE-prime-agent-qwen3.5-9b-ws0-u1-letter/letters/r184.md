## PART 1: Working in this harness — the mechanics that matter

**Your workspace is persistent.** Everything lives under `/home/USER/runs/paper/glm-hpl-u1-turns/play/users/u000/system/state/workspace/`. Files you write there survive across turns and across tasks. Use this relentlessly:

- `programs/<task-id>.py` — your program with a `transform(grid)` function
- `programs/<task-id>.json` — the demo pairs you've collected
- `programs/<task-id>_test.json` — your test prediction, saved so you can reuse it
- Memory files like `<task-id>.mem.json` or `memory_<task-id>.json` — your notes

**Recurring tasks come back.** The same task ID can appear multiple times in the stream, sometimes with a new test input. This is huge. If you see a task ID you've seen before (e.g. `task-5c839a47`, `task-5997d753`, `task-1b7868f1`), **first thing: read your saved files.** Load your saved `transform()` and run it on the new test input. Do not re-derive the rule from scratch. Several of my tasks I solved in one submission purely because I had saved the program from the previous occurrence. If your program reproduced all kept pairs, trust it on the new instance — even when the new instance looks different (e.g. a single dot where demos had many; see the 5c839a47 story below for the limits of this).

**When re-running a saved program on a new instance, first sanity-check that the new input is the same *kind* as the demos** (same color count, same structure, e.g. same separator layout). If it's structurally different, be careful — that's exactly the case where your saved rule may not apply (that's how I burned attempts on 5c839a47: demos all had ≥2 dots, the test had one).

**Demos are precious and slow.** Requesting demos costs a turn and doesn't always give you what you need. My rough policy:

- If after inspecting the test input you have a hypothesis that fits *all* structure you can see (colors, symmetry, counts), submit first, request demos later only if wrong.
- If the grid is huge and opaque (29×27 blobs of one color with a few outliers — see efc2fba8-type tasks), spend a moment finding the smallest transformation hypothesis; often it's embarrassingly simple (shift down by one row!).
- Never request demos twice without submitting in between; the feedback from a wrong submission (which instance it failed on, how many wrong cells) is information too.

**Count your wrong attempts.** Some tasks cap attempts. Track them in a small `_status.json`. When I hit the cap on a task I stopped early and moved on with my best guess. Also: a wrong attempt usually tells you *which* cells were wrong — use that to falsify hypotheses precisely, not just "try another idea."

**Write the rule in a memory file immediately after you solve a task.** One JSON blob: task id, rule in one sentence, file paths, whether the program reproduces all kept pairs, and any caveats ("test had a lone dot and my extension was wrong — unknown what lone dots do"). Future-you thanks present-you. You'll see my saved memories at the paths in the harness state; read them at the start of any recurring task.

## PART 2: The rule catalogue — tasks I solved, and how

These are rules I verified against demo pairs. If a new instance of one of these task IDs shows up, use the saved program. If a *different* task shows a similar structure, these are good templates for guessing.

**1. Symmetry/mirror tiling (task-73499f5a).** Each row becomes `reverse(row) + row`; then the output stack is `reversed(rows) + rows + reversed(rows)`. Key insight: the output dims (3× height, 2× width) *tell you* the operation is "mirror both axes." When output size is an integer multiple of input size, check mirroring/tiling first.

**2. Rotational block tiling (task-794e60f6).** Output is 2H×2W built from `[[I, rot90(I,3)], [rot90(I), rot90(I,2)]]`. Again: output exactly 2×2 of input dims → think 90° rotations arranged around a center.

**3. Downshift by one (task-efc2fba8).** Every non-background cell shifts down one row; originals become background; top row becomes background. **Lesson: before inventing an exotic rule, test the trivial geometric ones** — shift by 1 in each of 4 directions, mirror, transpose, recolor. Cheap to try, and small models like us overfit to complex hypotheses.

**4. Periodic anti-diagonal tiling (task-2e29965a).** Colored cells live on lines of constant `i+j` (or `i`, or `i-j`); each such line has a single color; the full grid is that color pattern repeated with some period p along the line index. Algorithm: for each candidate key function (anti-diagonal, row, main diagonal), check every occupied line is monochrome, derive color per line index mod p, fill everything. **Generalizes to: sparse colored cells + periodic output ⇒ identify the period, tile.**

**5. Dot-interval fill (task-5c839a47).** Rarest color = "dots." For each row and each column containing ≥2 dots, color 3 fills strictly between the min and max dot. **Unresolved: a single dot.** I tried identity, cross patterns, row-only, column-only, all wrong across 8 attempts. If you meet this task with a lone-dot test, my only advice: request demos early, and consider that the lone dot may be a *seed for a full row or column* in some direction I never guessed. I recorded this failure so you don't repeat my 8 attempts.

**6. Diagonal run extension (task-3b5f776f).** Every contiguous same-color run of length ≥2 on a diagonal (`r-c`) or antidiagonal (`r+c`) extends in both directions, filling background until blocked. Simple, verified.

**7. Enclosed pocket fill (task-3f4fb1a9).** Background-colored regions not touching the border that form a solid rectangle get color 4; a 2-tall pocket also paints the wall row directly below if that row is background across the pocket width. Non-rectangular pockets stay unchanged. **General lesson: "enclosed region" tasks usually mean flood-fill from the border; anything unreached is enclosed. Then check shape regularity (rectangle?) to decide what happens to it.**

**8. Largest-component stamping (task-1b7868f1).** Largest non-background component = seed; every *other* non-background cell is an anchor; the seed's bounding box (with its exact contents, including internal zeros) is stamped so its center lands on the anchor. Beware overlap order — I iterate cells and overwrite; verify against demos. Variants I tried that failed on some instances are recorded in `cand8.json`/`cand_11_7.json` (offsets by ±1 row/col matter — check whether anchor is bbox center vs. a specific component cell).

**9. Marker bounding-box + gap fill (task-8625f9bc).** Marker = 2nd most common color. Fill background cells on the markers' bounding box perimeter, and background gaps of size ≤2 between consecutive markers in any row/column, with color 2. Lesson: **"draw lines through/between markers" tasks → project markers onto rows and columns, fill short gaps, and draw the bounding frame.**

**10. Two-block comparison (task-026adbf3).** A full uniform separator row/column splits the grid into two same-size halves A and B. Output: 3 where A and B agree, otherwise the most common "shared at position" color. Simpler variant: output 3 where equal else each block's dominant color. **Split-by-separator is a recurring ARC motif: look for full single-color rows/cols first, always.**

**11. Guide-line mosaic (task-bb30ebc2 / task-48898d06).** Grid divided by full uniform rows/cols into blocks; the output is a small grid where each cell summarizes its block (e.g., value at intersection of guide colors, or 1 if the block contains stray markers of a particular color, else background). When the output is much smaller than the input, think "block summarization": what statistic per block? Count of a color, presence of a color, corner colors, majority color. My bb30ebc2 version: output cell = the color where the four surrounding guide-lines' markers agree, else background.

**12. Shape moves flush to a line (task-77262100).** A solid vertical line of color 2 exists; the multi-cell object slides horizontally until flush against it (same side it started, same rows); old cells become background; a full-height line of color 8 is drawn at the object's old rightmost column. **"Object + line" tasks: the line is a wall/magnet; movement is translation only (no rotation); something gets drawn where the object was.**

**13. Two bars + dots (task-d4079843).** One color forms exactly two long bars (one horizontal, one vertical); another color forms single-cell dots. Each dot: draw a stub line from the dot toward the bar whose along-axis span is closest, recolor the dot to 4, and draw a mirrored full line on the *other* bar at the clamped index `dot_pos - bar_start`, skipping bar cells. Complex, but the reusable idea: **dots anchored to bars → connect + mirror at the corresponding position on the perpendicular bar.**

**14. Band completion (task-5997d753).** Two horizontal bands contain the same noisy pattern; one band touches the right border (the complete reference), the other is clipped at its right edge. Fill the clipped band's background cells, in color 1, where the reference pattern (best cyclic-shift aligned) extends past the clip. **Generalizes: when the same pattern appears twice, one complete and one truncated, complete the truncated one.** Find the best shift by maximizing overlap of non-background cells.

**15. Sparse-pattern stamping (task-770f2daf).** Rarest non-zero color's bounding-box pattern is stamped into every all-background box of that same size. Look for an exact-size empty region to receive a copy of a motif.

**16. Pattern fill between dots / gap fill (task-b7641a67, task-aa5a69a0, task-67dd046a).** Assorted: fill background gaps between pattern cells in a row with 2; fill hollow rectangle interiors with 2 (even area) or 7 (odd area) based on interior area parity; 3×3 downsample where each output cell is the majority non-5 color of its 3×3 block. The parity-fill (aa5a69a0) is a nice one: rectangle outline detection = component whose size equals its perimeter.

**17. Rectangular grid recolor (task-47ed202e).** Rows or columns that are a single repeated color become all 2; everything else unchanged. Trivially simple — again, check the trivial hypothesis first.

**18. Marker-connect rectangle tiling (task-48898d06, variant).** Blocks between separators: output 1 if block contains ≥2 stray markers (or odd count, per the variant), else background.

**19. Compare-overlap recolor (task-0f6e5a2f).** A singleton large thin angle (arms ≥3) is the "arrow." Among pairs of identical shapes occurring exactly twice, pick the pair whose nearer member is closest (Manhattan) to the arrow's horizontal arm; recolor the *farther* member to the arrow color. Also seen: enclosed background regions → 4 (3f4fb1a9 sibling). Reusable idea: **when a special large object exists, it disambiguates between twin copies — near twin stays, far twin transforms.**

**20. Cell-multiplicity (task-2264bd4e).** Two colors only: keep the higher-valued color, set the lower-valued one to 0 (or output the higher everywhere the lower was). Colors are ordered — "higher wins" is a real ARC motif.

**21. Downsample-by-separator (task-67dd046a).** Output cell = majority non-{given color} in each 3×3 block. **Whenever H_out = H_in/3 (or some divisor), block-vote is the first thing to try.**

## PART 3: How to *derive* an unknown rule — my decision procedure

When a genuinely new task appears, work this checklist in order. It's roughly ordered by how often each hypothesis class pays off on ARC:

1. **Inventory.** Colors (sorted by count), output dims vs. input dims. The output/input size ratio is the single most informative fact:
   - Same size → local recoloring, filling, drawing, or shifting.
   - 2× or 3× → mirroring/tiling/rotation of the input (see rules 1–2).
   - 1/2, 1/3, 1/4 → block summarization/downsampling (rules 11, 18, 21).
   - Different aspect entirely → extraction of a subgrid, or reconstruction from blocks.

2. **Find separators.** Full rows/columns of one uniform color. They almost always mean "the grid is a grid of blocks." Then ask what each output cell summarizes about its block.

3. **Find the background** (most common color) and the **rarest colors**. Rare colors are usually the *agents* (dots, markers, seeds). The interaction is usually between agents and either the background, each other, or a special large structure.

4. **Components.** Flood-fill (4-connectivity mostly; check 8 for thin diagonal objects — thin angles/diagonals often need 8-connectivity to be one component). Characterize each: size, bbox, filled-ness (len == bbox area?), shape (line? L? rectangle outline?).

5. **Count-based selection.** "Exactly two of X," "the largest Y," "the singleton Z" — ARC rules love selection by count/size/rarity. Sort components and look at the extremes.

6. **Geometric relations.** For each pair of interesting objects compute: bbox containment, overlap, translation-difference (same canonical shape?), Manhattan distance, alignment on row/col/diagonal. Twin shapes (same canonical form, different position/color) are the classic setup: one is the reference, the other gets transformed (recolored, completed, or moved).

7. **Trivial ops first.** Before anything clever, literally try: shift all content by 1 in each direction; mirror rows/cols; transpose; recolor color A→B globally; keep only color X; all-background→X. Each takes a minute and kills a whole hypothesis class.

8. **Count your colors' changes between input and output demos.** For each color: how many cells in, how many out, how many preserved positionally? A color that keeps all positions but changes value is being *recolored in place*; a color that vanishes was an *agent*; a color that appears from nothing was *drawn*. This table alone often narrows the rule to one family.

9. **When you have demos, verify the hypothesis against every pair, not just one.** A rule that fits pair 1 but not pair 3 is wrong; the failing pair is the information. I keep a tiny evaluate script pattern: run transform on each demo input, diff against the expected output, print mismatch coordinates. Mismatch *locations* tell you what aspect of the rule is off (edge? interior? one color only?).

10. **Symmetry between demo structure and test structure.** If the test input is a *degenerate case* (one dot instead of many, no separator, an empty half), your rule's behavior there is undefined by the demos — this is where wrong submissions hide. If you spot a degenerate test, either reason hard about the most natural extension, or get demos before submitting.

## PART 4: Coding hygiene for this harness

- Always work on a copy: `out=[row[:] for row in grid]`. Returning a mutated input has bitten me when I reused demos.
- Flood fill iteratively with an explicit stack/deque — grids here go up to ~30×30 but Python recursion limits are real and I've seen deep fills.
- Connectivity: implement 4-conn and 8-conn; pick by whether the objects look like thin diagonals.
- Canonical shape key: `tuple(sorted((r-minr, c-minc) for cells))` — this makes "same shape, different position" detection trivial. Reuse it constantly.
- Majority color: `Counter(v for row in g for v in row).most_common(1)[0][0]`. Rarest: `.most_common()[-1][0]`.
- When a rule involves "gaps between markers," handle both row-projection and column-projection.
- Save the rule description *with the code* as a docstring — my best programs have the rule in the docstring, which made every later reuse instant.
- When writing test predictions to a file for later reuse, also save the input alongside, so you can re-verify rather than trust blindly.

## PART 5: Meta-lessons, compressed

- **Recurring tasks + saved programs = free wins.** Check your files before thinking.
- **Degenerate test cases are where rules break.** Single dots, missing separators, empty halves — treat with suspicion.
- **Small hypotheses first.** Shift, mirror, recolor, majority-vote. Exotic comes after boring fails.
- **Mismatch coordinates from a wrong submission are gold.** Falsify precisely.
- **Dims ratio decides the operation family** before you look at any cell.
- **Colors have roles:** background (most common), agents (rarest), structure (medium, often forming lines/rectangles). Naming the roles is half the solve.
- **Keep attempts budgeted:** if a task has eaten several attempts and you're guessing, submit your best current guess rather than burning more turns on exploration.
- **Write the memory file the moment you solve.** Not later. Later becomes never.

The stream will hand you tasks I never saw. Most of them will be variations of the ~20 families above with different colors and geometries. Trust the checklist, trust your saved files, and be disciplined about verifying against all demo pairs.
