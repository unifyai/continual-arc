## How the harness works

Each task gives you an input grid and asks you to produce the output. You have limited wrong attempts before a task is marked failed, so each guess is expensive. You can request demo pairs (input/output examples) — do this early when you're unsure; a good demo pair is worth more than three wrong guesses. ## The single most important habit: save the rule in words

When you find a rule, write it precisely in the memory file, not vaguely. Compare:

- Vague: "fills in some cells"
- Precise: "output 3 = cells strictly between the min and max dot (least-common-color) positions per row and per column; dots themselves unchanged"

The precise version lets you re-derive the program if the file is lost, and lets you spot when a *new* test instance doesn't fit (e.g., a task with only ONE dot — see below). Also record which tricks failed, so you don't retry them: I once burned 8 wrong attempts on a lone-dot case because I hadn't written down that identity, cross, row-only, column-only, and several other extensions had all been rejected.

## Recurring rule families (study the saved programs)

Most tasks I saw fell into a handful of families. Learn to recognize them from the input alone:

1. **Background + objects.** Find the most common color = background. Find connected components (decide 4-connectivity vs 8-connectivity — try both if one fails). Then ask: which object is special (largest? unique color? unique shape?) and what happens to the others (recolor, move, stamp, delete)?

2. **Stamping / translation.** One large "seed" object gets copied to every anchor point (task-1b7868f1: stamp seed bbox centered on each non-bg cell; the bbox is copied *as-is*, including zeros and holes inside it). Check whether copies overwrite background only, or everything.

3. **Line/grid structure.** Look for full rows or columns of a single color — they're separators (task-48898d06, task-026adbf3, task-bb30ebc2, task-707635df). The output is often one value per block between separators: count strays, compare the two sides, take the mode, check if 4 corners match, etc. Always check whether the separator is *centered* (odd dimension, half on each side) — that signals a mirror/compare structure.

4. **Symmetry completion.** Output may be mirror(row)+row, reversed stack, rotations tiled into quadrants (task-794e60f6: TL=input, TR=rot90, BL=rot270, BR=rot180). Check output dimensions first — if 2n×2n from n×n, think rotation tiling; if 3× height, think pattern repetition.

5. **Diagonal/line extension.** Runs of length ≥2 of the same color extend along their diagonal until blocked (task-3b5f776f). Single cells do NOT extend — the length≥2 condition matters.

6. **Gap filling.** Fill background gaps between markers in a row/column, sometimes only if gap ≤ some small size (task-b7641a67, task-8625f9bc). Watch for extra conditions: also fill the bounding-box perimeter of all markers.

7. **Enclosed regions.** Flood-fill background from the border; unreachable pockets get a new color (task-3f4fb1a9, task-aa5a69a0, task-b62da9e0). Sometimes only *rectangular* pockets qualify — check the component fills its own bounding box.

8. **Periodicity.** Colored cells on anti-diagonals repeating with some period → tile the whole grid with that periodic function (task-2e29965a).

9. **Comparison of two blocks.** Grid split into two halves; output marks where they agree or disagree, possibly with a new color.

10. **Object motion.** An object moves to touch a line or edge; its old position becomes background; sometimes a trace line is drawn at its old location (task-77262100, task-efc2fba8).

## A concrete method for every new task

1. **Look at the output dimensions first.** Same size? Halved? Doubled? Tripled? This immediately narrows the family. Dimension changes are the strongest clue: 2n×2n → rotation tiling; n→3n → row mirroring + stacking; much smaller with separators → block summarization; downsample by 3 → majority vote per 3×3 block (task-67dd046a).

2. **Count colors.** Background = most common. Then list every other color and where each appears: dots? lines? rectangles? L-shapes? The *rarest* color is often the seed or the marker.

3. **Check the full-grid structure**: any uniform rows/columns (separators)? any two identical rows far apart (twin copies)? any symmetric pairs?

4. **Compare input to output cell-by-cell** (mentally or with a scratch script): which cells changed, and to what? Which stayed? "What did NOT change" is as informative as what did.

5. **Write the program defensively.** It must reproduce every kept demo pair exactly — run it on them before submitting. If it fails on even one pair, your rule is wrong; don't submit.

6. **When the rule has ambiguity** (e.g., what happens with a single dot, or zero candidates), that's exactly when to request a demo pair rather than guess. Edge cases are where I lost the most attempts.

## Codecraft tips

- Write one shared component-finder (BFS/DFS) and reuse it; most tasks need it.
- Never mutate the input grid; copy first: `out = [row[:] for row in grid]`.
- Determine background by `Counter(v for row in g for v in row).most_common(1)[0][0]`.
- When a rule needs a "most similar pair" or "nearest object", compute canonical shape keys: `tuple(sorted((y-min_y, x-min_x) for y,x in comp))` — this groups objects by shape regardless of position (see task-0f6e5a2f).
- Keep programs self-contained: import inside `transform` or at top, no external files, no `input()`. The harness runs `transform(grid)` and compares to the expected output.
- If your program reproduces all demos but you're unsure about an edge case in the test input, think hard about which interpretation the demo pairs *require* vs merely *allow*, and prefer the more constrained reading. My failed submissions were almost always on cases the demos didn't cover.

## Specific traps I fell into, so you don't

- **task-5c839a47 lone dot:** my rule needed ≥2 dots per row/col. A test with a single dot broke every extension I tried (8 attempts!). Lesson: if your rule has a degenerate case and you can get a demo, get one *before* submitting.
- **Duplicate submisks:** I recorded (in task-1b7868f1_failed.json) that two candidate grids were identical — always check your candidates differ before spending attempts on both.
- **Overwriting order matters:** when a rule both moves an object and draws a line, decide whether the line overwrites the object or vice versa; the demos fix this.
- **Bbox as-is vs bbox-nonzero:** when stamping, check whether zeros *inside* the seed's bbox are copied (holes) or whether only the object's cells are drawn. Both variants exist.
- **Fill color choice:** the "2" or "4" or "7" in fill rules is often arbitrary-looking but fixed across demos; never invent a new color that doesn't appear somewhere in the demos' outputs.

## On keeping your memory tidy

Update the memory entry for a task when its status changes (solved, failed, new insight). The harness deduplicates by task id; multiple entries accumulate, so when you update, make the newest content the authoritative summary and keep it short enough to re-read at a glance. A memory file that says "program reproduces all kept pairs; rule: <one precise sentence>" is perfect. A memory file that says "tried stuff" is useless.
