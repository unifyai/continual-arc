## The single most important habit: verify before submitting

Almost every failure I had came from predicting the test input with a rule that reproduced the demos but was subtly wrong. Before you submit:

1. **Write the program first**, run it on every kept demo pair, and only submit its output for the test.
2. **Re-derive the rule from the output, not the input.** When demos are available, don't hand-predict — the program is your prediction.
3. If a rule reproduces all demos, trust it over your intuition. If you must choose between two rules that both fit the demos, prefer the simpler one, but check it on a mental "edge case" (e.g., what happens if there's only one component? Zero dots? An odd-sized region?).

When I failed task-5997d753, my program reproduced all 6 demo pairs perfectly and I still got the test wrong — because the rule I generalized was one of several that fit. Ask: *which generalization is most "natural" for an ARC puzzle author?* Usually the answer involves symmetry, counting, or a spatial relation, not an arbitrary threshold.

## Rules I've already extracted (reusable patterns)

These appeared across multiple tasks in this stream. Recognizing them fast saves you enormous time:

- **Diagonal-periodic fill (task-2e29965a):** colored cells mark diagonal lines; fill the whole grid by `P[(r+c) mod L]` or `P[(r-c) mod L]`, where L = number of distinct colors. Try both diagonal directions.
- **Scale-down by blocks (task-48898d06, task-67dd046a):** grid divided by solid separator lines into blocks; output one cell per block. The cell value is often: majority color, odd/even count of a stray color, or most common non-noise color. Check which noise-discounting rule fits.
- **Mirror-and-tile (task-73499f5a, task-794e60f6):** output = tiling of the input with its mirror/rotations. Common shapes: `[rev(r)+r]` per row stacked reversed-orig-reversed; or 2×2 block: original | rot90 / rot270 | rot180.
- **Split-and-compare (task-026adbf3, task-707635df):** find a full solid separator row/column (often a single repeated color, sometimes centered so the two halves have equal size); compare cells at the same position in the two halves; output marks agreement (e.g., 3, or 2, or 1).
- **Line-of-sight betweenness (task-5c839a47, task-b7641a67):** a background cell becomes a special color iff it lies strictly between two same-colored "dot" cells in its row or column (between min and max dot index). This exact pattern appeared twice with different colors.
- **Fill enclosed pockets (task-3f4fb1a9):** flood-fill background regions; ones not touching the border become 4. Extra wrinkles to check: only *solid rectangular* pockets may qualify; a 2-row-tall pocket may also absorb its bottom wall row if the row below that wall is background.
- **Hollow rectangles (task-aa5a69a0):** a component equal to a rectangle perimeter gets its interior filled — with 2 if the interior area is even, 7 if odd.
- **Stamp-a-seed (task-1b7868f1, task-770f2daf):** largest (or rarest-color) component is a stamp; every other component/cell of interest is an anchor; stamp the seed (its bbox, translated so its center lands on the anchor), overwriting only within bounds. Variant: stamp at *every* offset where the stamp's cells would all land on background.
- **Slide-toward-a-line (task-77262100):** an object moves until adjacent to a full solid line of a special color; then a full line of another color is drawn just outside the object's far side. Handle both orientations and both sides.
- **Recolor by min/max (task-2264bd4e):** with exactly two colors a<b: a→b and b→0. My role-based guesses (majority/minority) failed; the min/max rule worked. **Test color-role hypotheses against demos before committing.**
- **Extend singletons (task-3b5f776f):** a non-background cell with exactly one non-background neighbor extends a ray from its neighbor through itself to the grid edge.
- **Gap-filling (task-8625f9bc):** background cells with gap ≤2 between consecutive marker cells along any row/column get filled, plus the bounding-box perimeter of all markers.
- **Downshift (task-efc2fba8):** literally shift all non-background content down one row, top row becomes background. Don't overthink simple ones.
- **Between-bars extension (task-d4079843):** two bars of one color, dots of another. From the bar facing the dots, draw a perpendicular line through each dot (the dot cell becomes 4). From the opposite bar, draw lines at the same offsets spanning the full gap, in the dot color.

## General problem-solving recipe

When a new task arrives and the rule isn't immediately obvious:

1. **Inventory the colors.** Background = most common. Usually there's one "special" fill color (often 2, 3, or 4) and structural colors.
2. **Find the objects.** Connected components (4-connectivity for same-color objects is standard; some tasks use 8-connectivity for multi-color objects — try both). Get bboxes, sizes, counts.
3. **Look for structure:** full solid lines? Repeated motifs? Translations of the same shape (canonicalize by subtracting the bbox min — shapes that appear exactly twice are usually the key pair, as in task-0f6e5a2f)?
4. **Compare input vs output dimensions.** Same size → recoloring/moving in place. Double size → tiling/mirroring. Quarter size → block downscaling. Triple → the mirror-stack pattern. Half → split-and-compare.
5. **The output is often "input plus localized changes."** Diff the demo pairs cell by cell; the changed cells tell you exactly what the rule touches.
6. **Counting and parity show up a lot** (even/odd area → color choice; odd count of strays in a block → 1 vs 0). Always check parity.

## Specific tactical advice

- **Duplicate failure tracking.** When you record failures (like my `task-1b7868f1_failed.json`), note which submissions were duplicates — I wasted attempts resubmitting the same wrong answer. Track *what you've tried* explicitly with a distinguishing note.
- **Programs are cheap; write helpers once.** My most reused snippet is component-finding (flood fill over a color or a color set). Also: bbox, canonical shape key `tuple(sorted((y-minys, x-minxs) ...))`, and `Counter(...).most_common(1)[0][0]` for background.
- **The demo-request economy matters.** Requesting more demos is sometimes right, but a wrong program that fits the demos you have is usually fixable by re-examining the *changed cells*, not by buying more demos. I only truly needed extra demos once.
- **When the grid splits, find the separator correctly.** A separator row/col has exactly one distinct value (and often it's not the background). Check centered-ness: sometimes only a *centered* separator counts (2r+1 == H).
- **Careful with 0.** Zero is frequently the background *and* the "empty" marker. In fill/stamp tasks, distinguish "cell is 0" from "cell is background color."
- **JSON structure:** your saved `.json` demo files are lists of `{"input": [...], "output": [...]}` with rows as lists of ints. Load them, don't retype grids.
- **Edge-of-grid logic:** many rules condition on touching the border (enclosed vs open regions). Always compute `touch = any(a in (0,h-1) or b in (0,w-1) for comp cells)`.

## On uncertainty

If after all this you still have multiple plausible rules and can't decide, rank them by: (a) fits all demos, (b) simplest description, (c) doesn't rely on magic constants that look coincidental (e.g., "distance exactly 3" that's really "adjacent after sliding"). Submit the best, and if the harness allows feedback, use a rejection to distinguish rules — but only after you're sure your candidates actually differ on the test input.
