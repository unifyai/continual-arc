## 1. What the harness is, in one paragraph

For each task you get a few demonstration input→output grid pairs, then a test input, and you must produce the test output by writing a Python program (`transform(grid)`) or by submitting a grid directly, depending on what the round asks. You have a limited number of wrong attempts per task before the task is locked. You can sometimes request additional demonstration pairs. ## 2. Non-negotiable habits (these prevented my worst disasters)

**Never retype a grid by hand.** This cost me a wrong attempt on task-5c839a47: I hand-typed a test grid from the log, made a single-digit typo, and the whole submission failed. Load grids from the session log or task prompt *programmatically* — parse the text with Python, don't copy-paste and re-edit. If you must transcribe, re-read the transcription cell by cell against the source before using it.

**Validate your program against every kept demo pair before submitting.** I saved, for each task, a `.json` of the pairs I kept and a `.py`. My routine was: write the pair file, run my `transform` on each input, assert it equals the output, and only then predict the test. If your program does not reproduce the demos exactly, do not submit its prediction — your rule is wrong or incomplete.

**Keep a `.json` pair file per task and a memory entry.** When a similar-looking task returns (tasks do repeat variants), reading my old rule notes instantly re-solved tasks. Write memory entries in this shape: task id, file paths, number of pairs, whether the program reproduces all of them, and the rule in one or two sentences. Update it after every submission — especially after a *wrong* one, so you remember which hypotheses are already dead.

**Track your wrong-attempt budget like money.** When you reach ~2/3 of the cap on a task, request demo pairs if allowed — extra demos often disambiguate faster than more guessing. When you are down to your last attempt, submit the *most conservative* prediction consistent with all demos (often the identity or the rule with the narrowest scope that still fits).

## 3. The recurring rule families (learn these cold)

I saw the same underlying structures again and again. Memorize these templates; when a new grid matches one, you solve in minutes.

**(a) Background + anchors + stamping.** Find the background color (`Counter(...).most_common(1)`). The largest non-background connected component is often a "seed" pattern; every other non-background cell is an anchor; the output stamps the seed (its bounding box, translated so the seed's center maps onto the anchor) at each anchor. I solved task-1b7868f1 this way — my saved `task-1b7868f1.py` is a clean reference. Generalize carefully: anchors might be single cells, small shapes, or colors; the seed might need mirroring rather than pure translation.

**(b) Separator / block decomposition.** Full uniform rows or columns split the grid into blocks. Variants I met: (i) output one condensed cell per block summarizing content (task-48898d06: block = 1 if it contains ≥2 stray pixels of the odd color, else background); (ii) two same-size halves compared cell-by-cell (task-026adbf3: output 3 where halves agree, else the shared dominant color); (iii) blocks tiled by a repeating pattern (task-8d84fe63: copy the "most complete" block's pattern into all blocks). The general skill: detect separator rows/cols, segment, then figure out what invariant relates the blocks.

**(c) Bounding boxes.** Fill the bounding box of each component with the component's color, clear everything else (task-b62da9e0). Or detect hollow rectangles and fill interiors with a color depending on area parity (task-aa5a69a0: even area → 2, odd → 7). Or fill enclosed background pockets with 4, where "enclosed" means a background component touching no border, and refine with shape conditions (task-3f4fb1a9: only *solid rectangular* pockets; 2-row-tall pockets also absorb their bottom wall under an extra condition).

**(d) Line-drawing between markers.** The rarest color's cells are "dots"; draw lines or fills strictly between dots (min/max per row and column), like task-5c839a47 (fill 3 between min and max dot per row and column). Or: background cell with the same non-background color on both sides in its row becomes 2 (task-b7641a67). Or: fill gaps of size ≤2 between consecutive marker cells along rows/columns, plus the markers' bounding-box perimeter (task-8625f9bc).

**(e) Symmetry / tiling constructions.** Row r → reverse(r)+r, then stack reversed/all/reversed (task-73499f5a). 2n×2n output: TL = input, TR = rot90cw, BL = rot90ccw, BR = rot180 (task-794e60f6). Diagonal stripe patterns: if every nonzero cell's value is consistent with a repeating period L along a diagonal (check both r+c and r−c keys mod L), tile the whole grid with that pattern (task-2e29965a).

**(f) Geometry with a special line.** A full line of color 2 splits the grid; the object slides toward the line until adjacent, and a full line of color 8 is drawn on the object's far side (task-77262100). My program handles all four orientations with the same skeleton — write such handlers direction-generically, not as four copies.

**(g) Shifting.** All non-background cells shift down one row; top row becomes background (task-efc2fba8). Check pure translations first for any "everything moved" appearance.

**(h) Relative-position reasoning.** In task-0f6e5a2f, a large thin L-shape is an arrow; among pairs of identical twin shapes, the member farther from the arrow's horizontal arm is recolored to the arrow's color. The general lesson: when one object is unique and distinguished, it is probably a *reference*, and other objects are ranked by position relative to it.

**(i) Rare-color seeds stamped into all-zero regions.** Find the least-common nonzero color's shape; stamp it at every offset where all its cells land on zeros (task-770f2daf).

**(j) Counting/pollution.** A line of one color cuts the grid; output cells encode whether their region contains "stray" pixels of another color (tasks 48898d06 and 5997d753 are cousins — see below for why one failed).

## 4. When the rule isn't obvious: a search procedure

When no template matches within a few minutes, don't guess blindly. Do this:

1. **Compare inputs and outputs cell-by-cell programmatically.** List every cell that changed and its (input color → output color) pair. Changed-cell counts, positions, and color pairs usually reveal the rule immediately. If nothing changed except one region, focus there.
2. **Check size changes.** Same size → in-place recolor/move. Output k× input → tiling/reflection construction (families e). Output 1/k → condensation (family b). Different aspect → the separator tasks.
3. **Hypothesize the simplest rule consistent with *all* demos**, and write it as one sentence before coding. If you can't state it, you don't have it — request a demo instead of guessing.
4. **Prefer rules that fail loudly.** If your hypothesis only fits demos under special conditions, code those conditions in and raise/return the input otherwise — a program that degrades to identity on ambiguous inputs loses fewer points than one that confidently applies a wrong rule.

## 5. Lessons from my failures (do not repeat them)

**task-5c839a47, lone-dot edge case.** My rule (fill 3 between min and max rare-color dots per row/column) reproduced 10/10 demos, but the test grid had a *single* dot, where my rule degenerates. I burned 8 attempts on identity, cross-fills, row-only, column-only, and other lone-dot extensions — all wrong, and I never cracked it. **Lesson: when your test input is structurally degenerate relative to the demos (e.g., fewer objects than any demo), that is a signal the true rule uses a different definition — not that your rule extends trivially.** Request demos early; try to get a demo containing the degenerate structure. If none is available, pick the single most principled interpretation and stop.

**task-5997d753, near-duplicate tasks.** This one looked like 48898d06 but its rule differed (marking *where* stray pixels align with reference rows, via best-shift matching). I reproduced all demos but predicted the test wrong and hit the attempt cap. **Lesson: "similar to a previous task" is a hypothesis to test, not a shortcut.** Run the old program on the new demos; if it fails even one, the tasks differ and you must derive the rule fresh.

**task-1b7868f1, wasted near-duplicate submissions.** My failed-candidates file shows I submitted several grids that differed by one or two cells — same rule, minor parameter tweaks. If two of your candidate predictions differ by only a couple of cells, the *rule family* is probably right and the *tie-breaking detail* is wrong; spend your remaining budget analyzing which detail (anchor choice, offset, boundary inclusion) rather than resubmitting variants blindly.

**Duplicate detection.** Before submitting, diff your new prediction against your previous wrong submissions. If it's a duplicate, don't waste the attempt.

## 6. Coding hygiene in the harness

- Write `transform(grid)` taking lists of lists of ints and returning the same. Pure function, no I/O, no global state.
- Wrap color logic in helpers: `background(g)`, `components(g, colors)` (I use both 4- and 8-connectivity — *check which one the task needs*; diagonal adjacency vs. not is a frequent silent killer), `bbox(comp)`.
- For component finding, flood-fill iteratively (stack/deque), not recursively — grids are big and Python recursion is shallow.
- Use `Counter` for background/rarest-color detection, but beware ties: `most_common` order for equal counts is insertion order. If two colors are nearly tied, don't silently assume which is background.
- Test on the demos with an assert loop; print the first mismatching cell, not just "wrong".
