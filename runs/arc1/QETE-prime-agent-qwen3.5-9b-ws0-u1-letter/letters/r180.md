## The rhythm of a task

Each task gives you an input grid and (usually) a few demo pairs. Your job is to write a `transform(grid)` program that reproduces the demos, then predict the test output. The workflow that works:

1. **Look before theorizing.** Dump the grids, diff the inputs against outputs cell by cell. Most rules are local: "this color becomes that," "this region is stamped elsewhere," "fill the enclosed background." Write the diff down mentally before inventing a fancy story.
2. **Solve for a rule that explains EVERY kept demo pair.** If your rule explains 2 of 3 pairs, it's wrong. My biggest losses came from patterns that fit one pair.
3. **Save your program and a .json of kept pairs immediately** (see file conventions below), and save a memory file when you've confirmed the rule. Future-you reads these.

## The recurring rules (ARC's greatest hits)

I've now seen ~30 tasks. The rule families repeat with reskins. When you see a new grid, check these first:

- **Background + components.** Background = most common color. Find non-background components (usually 4-connectivity; watch for tasks where 8-connectivity matters — diagonals touching). Then: which component is special? Largest, smallest, or the one with a unique shape/property.
- **Enclosed pockets.** A background component that touches the border is not a pocket; one fully surrounded by a solid color IS. Fill pockets (often with a specific color like 4). Sometimes a pocket drags its bottom wall too (task-3f4fb1a9: if pocket is 2 rows tall and the row below is background across its width, recolor that wall).
- **Stamping / translation.** One large "seed" component; every other non-bg cell is an anchor; stamp the seed's bounding box (translated so its center maps to the anchor). Watch whether the stamp is the bbox *as-is including holes/other colors* or just the seed cells. Both variants exist. In task-1b7868f1 the anchor was a single-cell pattern (like "554 / 858 / 850") repeated everywhere, and the rule was stamp a 3x3-ish motif at each anchor with the anchor cell as the motif's reference point.
- **Mosaic / guide lines.** Full rows or columns of one uniform color divide the grid into blocks. Output is one cell per block. Common: "count of stray color inside block ≥ 2 → 1, else bg" (task-48898d06); "four corner guide-line cells identical → that color, else bg" (task-bb30ebc2); "odd count of a color → 1 else 0" variants. Identify separator color and blocks via rows/cols that are single-valued.
- **Two halves compared.** A full uniform row or column (often centered) splits the grid; output compares the halves cellwise: same → some color, different → other (task-026adbf3, task-707635df: "both halves show their own dominant color here → 2 else 0").
- **Sorting / max-trick.** Two colors only: map higher to itself, lower to 0, or similar per-cell recoloring (task-2264bd4e).
- **Line extensions.** Runs of length ≥2 extend along rows/cols/diagonals until blocked (task-3b5f776f). Or fill cells strictly between min and max positions of the rarest color per row/col (task-5c839a47 — note: this rule breaks on a lone dot; see failures section).
- **Periodic tiling.** Diagonals (i+j or i-j) or rows carry a repeating color cycle; infer the period from the given cells and tile the whole grid (task-2e29965a). If every diagonal holds exactly one color, you've got it.
- **Rotation / symmetric doubling.** 2n×2n output from n×n input: quadrants = original, rot90, rot180, mirror. Or row r becomes reverse(r)+r, stacked palindromically (task-73499f5a). Check: does output width = 2×input? Does output look like mirror-and-stack?
- **Bbox/outline fills.** Fill background cells on the bounding box of some marker color, plus gaps ≤2 between same-color cells in a row/col (task-8625f9bc).
- **Object moves relative to a line.** A shape slides to touch a full-length vertical (or horizontal) line; its old area becomes background; a full line in some third color is drawn where it used to be (task-77262100). Watch which side it moves to and whether it overwrites other shapes.
- **Bar + dot targeting.** A long solid bar (or two) and single-cell dots. Each dot points at its nearest bar along one axis; the position along the bar determines a mirrored line on the other bar (task-d4079843).
- **Down-shift.** All non-bg cells shift down one row (task-efc2fba8). Simple but I initially wrote it as "color by cell below" — get the direction right.
- **Scale down by majority.** Divide grid into blocks (often 3×3); each output cell = most common non-bg color in its block (task-67dd046a).

## Failure modes I actually hit — learn these the cheap way

1. **Assuming a rule generalizes from insufficient demos.** A rule that fits 1 pair is a hypothesis, not a rule. Fit 2+ before trusting it, and prefer the SIMPLEST rule that fits all.
2. **The "single dot / edge case" trap.** If your rule says "between min and max of the rarest color" and the test has exactly one such cell, your rule is silent. Think about degenerate cases BEFORE submitting: one dot, zero dots, a component at the grid edge, two colors in equal counts.
3. **Connectivity confusion.** 4-conn vs 8-conn changes everything. If 4-conn splits a shape into pieces that look like one shape, try 8-conn. In one task the largest 8-conn component was the seed; with 4-conn it shattered and my whole pipeline broke.
4. **Anchor vs seed off-by-center.** "Stamp bbox centered on anchor cell" vs "anchor = top-left of stamp" vs "anchor = cell inside stamp that matches" — try all interpretations when the first fails. My task-1b7868f1 file had a comment about "+0->1" offsets — that's me discovering off-by-one anchor alignment cost a submission.
5. **Background detection.** Most common color works ~always, but beware grids where the intended bg is a solid separator color (e.g., a full line of 6s) — then "most common" might pick the separator. Exclude separators from the bg count (my task-48898d06 code does exactly this).
6. **Writing transform that returns the input on edge cases.** Some of my programs silently `return g` when they can't find their trigger (no L-shape, no separator). On the test input this means an identity guess — often wrong. If your trigger isn't found, fall back to the NEXT most plausible rule, not identity.
7. **Rotation direction.** When output looks like the input rotated, verify WHICH rotation by checking a single asymmetric cell, not the whole grid. TL/TR/BL/BR quadrant assembly (task-794e60f6) is easy to get clockwise-vs-counterclockwise wrong.
8. **Duplicates in your own notes.** I saved the same failed candidate twice. When writing failure notes, keep them short and factual: what was tried, what the observed diff was, what's untried.

## Practical heuristics for unknown tasks

When a grid stumps you, run this checklist mentally:

- Is the output a **same-size recolor**? Then look per-cell or per-component for recolor triggers (enclosure, adjacency to a special object, being the "farther twin" of a pair — one task recolored whichever of two identical-shape objects was farther from a unique anchor object; another recolored the twin pair's farther member. "Pair of identical shapes + tiebreak by distance/size" is a real pattern).
- Does the output have **different dimensions**? Then it's a crop, downscale, upscale, or tiling. Check output size ratios: 1/2? 1/3? 2×? Same? Count blocks between separator lines. If output = input with rows/cols removed, find which rows/cols were dropped (often guide lines).
- Is the output the input **translated/mirrored/rotated**? Compare sorted cell multisets.
- Is there exactly **one special component** (unique color count, unique shape, non-repeated)? It's probably the actor or the key.
- Are there **repeated motifs** (same small shape at many offsets)? One is the template; the rule is stamp/spread/copy-from-template.

## Writing code

Keep `transform(grid)` pure: takes list of lists of ints, returns same. Avoid heavy deps (I used numpy once — fine, but collections/deque suffice). Deterministic tiebreaks: prefer stable ordering (sort candidates, don't rely on dict insertion order for anything subtle). Test your transform against EVERY kept pair in a loop before submitting:

```python
import json
pairs = json.load(open("programs/task-XXX.json"))
for p in pairs:
    assert transform(p["input"]) == p["output"]
```

If an assert fails, your rule is wrong — don't submit. If it passes, submit the test prediction with confidence.
