## 1. The workflow that works

**Build the demo file first, always.** For each task you get a set of input/output pairs. Save them as `programs/task-<id>.json` and your program as `programs/task-<id>.py` with a single function `transform(grid)`. Before you ever submit a prediction on a fresh test input, **verify your program reproduces every kept demo pair exactly**. If it doesn't reproduce all demos, it is wrong — fix it or think again. This single habit is the difference between solving and failing.

**When a rule is ambiguous, prefer the variant that satisfies all demos.** If two plausible rules both fit, think about which generalizes more naturally, but never submit a test prediction from a program that fails a demo.

**If you can, ask for more demos when stuck** (I used demo requests sparingly; they're valuable when two very different rules both fit the demos you have).

**Keep memory notes.** After finishing a task, write a short memory file recording the rule and file paths. When a task family reappears (it happens), you'll thank yourself. Write the rule in one crisp sentence.

## 2. Rule families you will meet again and again

These appeared repeatedly in my stream. When a new grid comes in, check this list before inventing something exotic:

- **Color replacement by rank**: with exactly two non-background colors a < b, sometimes smaller→larger and larger→0. But *check*: role-based rules (majority/minority) sometimes fail where min/max works. Test both against demos.
- **Enclosed pockets**: background-colored regions not touching the border get filled with a fixed color (often 4). Careful with pockets that aren't solid rectangles — often only rectangular ones are filled, and sometimes a 2-tall pocket also absorbs its bottom wall row if the row below is background.
- **Stamping / tiling a seed shape**: find the largest (or the unique) non-background component; stamp its bounding-box pattern, centered (or corner-aligned), onto every anchor cell or into every empty region of matching size.
- **Separator splits**: a full row/column of one uniform non-background color divides the grid into blocks A and B. Common outputs: cellwise AND of masks (recolored to 2), 3 where A==B else the shared bg color, or the block with content tiled into all blocks.
- **Marker lines / gap filling**: a minority color appears in runs; fill background gaps between runs of length ≥2 along rows/columns, or recolor uniform full rows/columns to a fixed color (2).
- **Diagonal periodic fill**: colored cells sit on diagonals r+c ≡ k (mod L) or r−c ≡ k (mod L); fill the whole grid from a residue→color table. Try both diagonal directions.
- **Symmetry block**: output is a 2×2 arrangement of the input and its rotations: [[I, rot90cw],[rot90ccw, rot180]]. Also "each row becomes reverse(r)+r, stacked reversed/forward/reversed" (palindrome expansion, both axes).
- **Line/beam extension**: an endpoint cell of a small shape (degree-1 in 8-neighborhood) extends diagonally/straight to the grid edge, painting its color. Or: an object slides until it touches a 2-cell separator line, then a full line of 8s is drawn on its far side.
- **Between-dots fill**: a background cell becomes 3 iff it lies strictly between two dots (rarest color) in its row OR its column.
- **Downscale voting**: divide the grid into k×k blocks separated by uniform separator lines; each output cell is the most common non-separator color in the block (or 1 if ≥2 stray cells of a special color, else bg).
- **Hollow rectangle fill**: interiors of hollow rectangles get 2 if the interior area is even, else 7.
- **Component bbox fill**: any non-background component of size ≥3 gets its whole bounding box filled with its color; everything else becomes background.
- **Row shift**: shift everything down one row; the top row becomes the background color.
- **Ray reflection / mirroring toward edges**, **gravity**, **counting**: less common but real.

## 3. How to find the rule fast

1. **Count colors.** Background = most common. The rarest color is usually "the object" or "the dots". Which color is special, and how many components does each color have?
2. **Diff the pairs.** List exactly which cells changed and what they changed to. The changed cells' positions relative to unchanged structure (lines, corners, objects) almost always reveal the rule. I literally wrote the diff out cell by cell.
3. **Check geometry first**: is the output a rotation/translation/scale/mirror of the input? Check size changes (2× block, 3× palindrome, downscale by 3).
4. **Check for separators**: full uniform rows/columns are structural — they usually mean "split into blocks and do something per-block or between blocks".
5. **Think in terms of components** (4-connected or 8-connected — try both) with their bounding boxes. Many rules are "do X to each component's bbox".

## 4. Traps that cost me

- **Assuming the rule before checking all demos.** A rule that fits demo 1 but not demo 3 is wrong. Always run the full check.
- **Role-based color logic (majority/minority) when min/max fits better** — verify both.
- **Getting the tie-breaking wrong in "nearest/farthest" rules** — when comparing candidate objects, define the distance precisely (e.g., min Manhattan distance between member cells and the target arm) and check tie-breaks (e.g., larger size) against every demo.
- **Overfitting to one demo.** If your rule has an arbitrary-looking constant or special case that only demo 1 exercises, it's probably wrong.
- **Guessing on the test when unsure is often worse than the most-democratic simple rule.** Simple, clean, demos-consistent rules generalize; baroque ones don't. When I had 8 wrong attempts on one task, the program reproduced all demos but the test needed a different twist — the lesson: if demos are exhausted, prefer the simplest rule consistent with all of them, and be very suspicious of adding parameters.
- **Careful with connectivity**: 4- vs 8-connectivity changes components. Try both if counts look wrong.
- **Zero is a color too.** In grids with 0s, "background" may be nonzero (e.g., 3, 5, 8) and 0 is the special marker. Always compute background empirically, never assume 0.

## 5. Coding tips

- Keep `transform(grid)` self-contained, pure, returning a new list of lists. No printing, no file I/O.
- Write tiny helpers once and reuse: background counter, flood-fill components, bounding box, uniform-row/col detection, run-length gaps.
- For "stamp" rules, remember: stamp the bbox *as-is* including any interior 0s/holes — don't fill them in.
- For separator-block rules, handle both orientations (row separator or column separator) — the harness test may use the other one.
- When generating a large output (e.g., 2×2 rotation block, 3× palindrome), compute it programmatically, never by hand.

## 6. Mindset

Every task is solvable from its demos. If you feel stuck, go back and look at the diffs again — literally list changed cells. The answer is usually mechanical: some relationship between changed cells and nearby structure (a line, a corner, a dot, a bbox edge). Resist the urge to guess; a wrong submission wastes an attempt, and some tasks cap them.

You have your own copy of all my program files at the same paths. When a new task resembles one of those rule families, open the corresponding `.py` — adapting a verified program is far safer than writing from scratch.
