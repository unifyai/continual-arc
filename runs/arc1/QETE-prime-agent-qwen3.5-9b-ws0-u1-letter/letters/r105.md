## The harness, in brief

For each task you get a few input→output demo pairs, one test input, and a workspace. You must produce an output grid for the test. Your two strongest levers:

1. **Write a Python program** (`transform(grid)`) that reproduces every demo pair exactly, then run it on the test input. If it reproduces all demos, its test output is very likely right.
2. **Request more demos** when you're unsure between hypotheses. Demos are cheaper than wrong submissions. I burned attempts on task-5997d753 by submitting a guess instead of asking for demos — don't repeat that. Get the rule nailed down on all demos first.

Save a memory file per task (like `memory_task-XXXX.json` under `workspace/`) with the rule in plain words and the file paths. On a later task, glance at your memory: rules recur in families.

## How to find the rule — a reliable procedure

1. **Diff each pair.** Where does output differ from input? How many cells changed? What colors appear/disappear? This immediately tells you the scale of the rule (recolor a few cells? fill shapes? resize the grid? move things?).
2. **Check output size first.** If output dims ≠ input dims, it's a resize/tiling/mirror task: doubled width with mirroring, tripled height with reversal, 2x2 block of rotations, downscaling by a factor, block-summarization. I saw: `row → row[::-1]+row` and stack `reversed+orig+reversed` (task-73499f5a); 2x2 block `[[I, rot90cw],[rot90ccw, rot180]]` (task-794e60f6); downscale by 3 taking most common non-noise color per block (task-67dd046a); extract a sub-grid from separator lines (task-48898d06, task-bb30ebc2, task-707635df); overlay/AND of two halves split by a separator line (task-026adbf3, task-707635df).
3. **Identify colors by role, not by value.** Background = most common. But do NOT assume the smallest/largest color number has a fixed role. In task-2264bd4e the rule was literally "smaller color → larger color, larger → 0", and role-based (majority/minority) hypotheses failed. Test both conventions against demos.
4. **Find connected components** (4-connectivity usually; sometimes 8 — test). Ask: which components are repeated? Which is largest? Which is unique? Which touch the border?
5. **Bounding boxes are everywhere.** Fill the bounding box of a component with its color (task-b62da9e0); stamp a seed component's bbox at anchor cells (task-1b7868f1); fill bbox perimeter of marker cells plus gaps between marker runs (task-8625f9bc); detect hollow rectangles as components where `len(comp) == 2*(h+w) - 4` with dims ≥ 3 (task-aa5a69a0).

## Rule families I confirmed (search your `programs/` dir for details)

- **Fill enclosed regions**: flood background components not touching the border; fill with a target color. Task-3f4fb1a9: only *solid rectangular* pockets, with a special extra-wall rule — note the value of exact conditions and of rejecting non-rectangular pockets.
- **Recolor by geometry**: background cell between two identical non-background cells in a row → 2 (task-b7641a67); background between two dots in row OR column → 3, between min and max dot positions (task-5c839a47, note it applies to *all* background cells in the span, and the span can be wide).
- **Uniform rows/columns**: rows or columns that are a single color get recolored to a fixed color (task-47ed202e). Check both orientations.
- **Stamp/copy a pattern**: minority-color shape's bbox pattern stamped into every all-background region of the same size (task-770f2daf); or every non-bg cell anchors a translated copy of the largest component's bbox (task-1b7868f1 — careful: stamps overwrite, including partial off-grid clipping).
- **Diagonal periodic fill**: cells of L distinct colors mark residues of a diagonal; fill the whole grid by `P[(r+c) mod L]` or `P[(r-c) mod L]`, trying both (task-2e29965a).
- **Directional extension**: a component with a degree-1 endpoint extends that endpoint diagonally/straight to the grid edge (task-3b5f776f: extend each degree-1 cell away from its neighbor, painting as it goes).
- **Move + line**: object moves to touch a full 2-line, then a full 8-line is drawn on the far side over background (task-77262100).
- **Tiling one good block**: find the block (delimited by uniform separator rows/cols) with non-background content, tile it everywhere (task-8d84fe63).
- **Shift**: whole grid shifts down one row, top row = background (task-efc2fba8). Simple rules do occur.

## Practical engineering tips

- Write a small helper script that imports your `transform`, runs it on all demo pairs, and reports exact cell-by-cell diffs. Fix discrepancies one at a time; a program that reproduces 4/4 demos almost always gets the test right.
- Write your own 4- and 8-connectivity component finder once and reuse it.
- When several hypotheses fit demos, prefer the one that explains *why* each changed cell changed, and that uses the fewest arbitrary constants. Then still request a demo if the harness allows — confirmation is worth it.
- Beware ties: "most common color" for background, "second most common" for marker. Verify with a Counter against every demo.
- Keep failed ideas in a note (like my `task-1b7868f1_failed.json`): recording "clean anchors (13,7),(12,8) untried" saved me from re-testing duplicates.
- If a task has only 1 demo pair, the rule is usually simple and geometric — don't overfit. If it has 5–8 pairs, the rule has conditions; find what varies between pairs.

## Mindset

Be systematic, not clever. Diff → components → roles → hypothesis → verify on all demos → submit. Most of my wrong submissions came from submitting before verifying, or from assuming a rule from one demo. Your program files and memory are your durable advantage over the tasks themselves — use and maintain them.

Good luck. Solve cleanly, verify always, and write down what you learn for whoever comes after you.
