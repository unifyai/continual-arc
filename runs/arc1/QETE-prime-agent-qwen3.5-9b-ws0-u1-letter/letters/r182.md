You are about to play ARC tasks under the same harness rules I played them under. I've solved roughly 30 tasks and failed several; below is everything that actually mattered, distilled so a smaller model can use it. Read this carefully at the start of each task — the patterns repeat.

## 1. The harness loop that wins

- **Save demos immediately.** When you get demo pairs, write them to `programs/task-<id>.json` and your rule/program to `programs/task-<id>.py` and a memory file. When a task runs long or the context gets cut, these files are the only thing that survives. Several of my tasks were recovered purely because the JSON was on disk.
- **Test your program against the demos before submitting.** Write a small check: load the JSON, run `transform` on each input, compare to output. "Program reproduces all kept pairs" is your single best predictor of a correct submission. Nearly every rejection I suffered was a rule I had NOT verified on demos.
- **Memory files with a written `rule` field are gold.** The rule text lets you re-derive the program later if the file context is lost. Write it crisply: what objects, what selection, what transformation, edge cases.

## 2. The recurring rule families (memorize these)

Roughly 80% of tasks I met fell into one of these families. Check them in this order:

1. **Background = most common color.** Almost always true. Find it first.
2. **Components via BFS/DFS** (4- or 8-connected — check both if shapes look split). Classify: singletons, lines, rectangles, L-shapes, largest component.
3. **Symmetry/mirror completion:** output = grid mirrored (`[r[::-1] for r in grid][::-1] + grid + ...`), or shape-completion by symmetry about an axis.
4. **Stamp/translate a seed:** find the largest (or unique) component; stamp its bounding box at every other non-background cell (often centered on the anchor). I solved task-1b7868f1 this way and it reproduced 8–9 pairs.
5. **Separator lines split the grid** (a full row/column of one uniform color, sometimes centered with `2k+1 == dim`). Outputs are per-block summaries: odd/even counts of a stray color, mode color, agreement between two half-blocks (`A==B → 3 else common color`), corner colors at row/col guide intersections.
6. **Periodic fill:** infer period from colored cells along rows / anti-diagonals (`i+j`) / diagonals (`i-j`); assign per residue; tile everywhere.
7. **Runs extended along diagonals:** every same-color run of length ≥2 on a diagonal extends through background until blocked.
8. **Fill between markers:** cells strictly between the min and max position of the rarest color, per row and per column, get a fixed color (often 3). Gaps of size ≤2 between marker runs also recur.
9. **Enclosed regions:** flood-fill background; regions not touching the border get recolored (often 4), sometimes only if rectangular, sometimes with a 1-wide slot extension.
10. **Shape moves relative to a line:** shape shifts flush against a vertical separator line; old area becomes background; a new full-height line of a third color marks the old position.
11. **Down-shift:** all non-background cells shift one row down, top row becomes background. Trivially cheap to check first.
12. **Tiling/rotation outputs:** output = 2×2 block of the input and its rotations (`np.block([[I, rot270],[rot90, rot180]])`), or the input mirrored twice (reverse rows and reverse each row, concatenated).
13. **Two colors only:** keep the higher, map the lower to 0 (or swap per a rule). Check literal per-cell color mappings when the grid is sparse.

## 3. How to figure out an unknown rule

- **Diff the input and output cell by cell.** List every position that changed, with before → after values. The changed cells form a shape; the shape's geometry (line? ring? exactly the bounding box? only interior?) tells you the rule.
- **Count colors.** Rare color = usually the actor. Second-most-common = often the marker. Fixed output colors in these tasks are frequently 1, 2, 3, or 4.
- **Check geometry invariants:** bounding box, size of components, whether two components are exact translation twins (same canonical shape), Manhattan distances between components. Twin-pair tasks (pick the nearer pair to a special object, recolor the farther) exist — see my task-0f6e5a2f.
- **Try the simplest rules first:** down-shift, mirror, recolor-enclosed, mode-per-block. Cheap to code, cheap to reject.
- **Reuse prior tasks.** If a new task looks like a saved one (same structure, different colors), reread that memory file. The rule families above came from exactly this reuse.

## 4. Decision policy under limited attempts

- **If the rule reproduces all demos but you're unsure about an edge case in the test input, submit the demo-verified rule anyway.** The demo-verified rule beats an improvised special case almost always. My one big failure streak (task-5c839a47) came from improvising eight different special cases for a lone-dot test input; the correct move was to request demos early if the harness offers them, and otherwise trust the simplest consistent rule.
- **If demos contain degenerate cases (single dot, single pair, empty side), note them explicitly in your memory file** so a later instance doesn't catch you again.
- **Don't burn attempts re-submitting the same rule with cosmetic changes.** Change exactly one assumption at a time, and record which assumptions you've tried (see my `task-1b7868f1_failed.json` note format: "clean anchors X, Y untried").

## 5. Code habits

- Write `transform(grid)` taking a list of lists of ints, returning the same. Pure function, no I/O inside.
- Use `from collections import Counter, deque, defaultdict`. `Counter(...).most_common(1)[0][0]` for background. BFS with a deque and a `seen` matrix for components — I've written this component scan dozens of times; memorize it once.
- Guard against the input already satisfying the output (identity is sometimes the answer — check the diff before believing any transformation).
- For separator-based splits, build generic helpers: `sep_rows = [r for r in range(H) if len(set(grid[r]))==1]`, same for columns, then `segments()` over the remaining indices.

## 6. Final cautions

- Read output dimensions carefully: many rules change height/width (halving, 3×, 2×). The first thing to check after the diff is whether the output grid is a different size — that immediately tells you it's a tiling/block-summary task, not a recolor task.
- When writing memory, include: task id, file paths, number of kept pairs, whether the program reproduces all of them, the rule in one sentence, and any unresolved edge cases. Future-you (in a fresh context) can only work with what you wrote down.

You are smaller than me, but none of this requires size — it requires discipline: save, verify on demos, diff before theorizing, and trust the simplest consistent rule. Do that and you will outperform the model that wrote this letter on the tasks it got wrong.

Good luck.
