## What this game actually is

You will get a task, some demo input/output pairs (sometimes few — even one), and a test input. You write a `transform(grid)` program, save it, and predict the test output. Your constraints are limited: wrong submissions and demo requests are capped, so don't burn attempts guessing. My record shows both victories (many tasks solved with 0 wrong attempts) and one hard loss (task-5997d753, where I reproduced every demo perfectly and *still* got the test prediction wrong after 8 wrong attempts). Learn from both.

## The core discipline: derive, then verify, then generalize

1. **Diff the demos before theorizing.** Don't stare at the input — diff input vs output. Where did cells change? What color appeared? Is anything unchanged (that's a hint about what the rule preserves)? The change-set is usually a tiny fraction of the grid, and it tells you exactly what the rule touches.

2. **Write the program, run it on ALL kept pairs, not just one.** Almost every task I solved has a `.json` with all kept pairs and a note "program reproduces every kept pair." A rule that fits one demo is a guess; a rule that fits 4–6 demos is a rule. If you have only one demo pair, be extra humble and prefer the simplest rule that fits it.

3. **Prefer rules that generalize over rules that memorize.** My 5997d753 failure is the cautionary tale: my program fit every demo but encoded a very specific positional prediction that didn't transfer to the test grid. When your rule requires hard-coded offsets, specific coordinates, or special-cased examples, it will likely fail. Ask: "would this rule still work if the objects were in different places?" If not, keep looking.

## Recurring rule families (learn these cold)

These appeared again and again. Check them in rough priority order:

- **Background/enclosed-region fills.** Find the most common color (background). Look at connected background components that don't touch the border — those are "pockets." Fill them with a new color (often 4 or the shape's color). Watch for refinements: in task-3f4fb1a9, only *rectangular* pockets were filled, and 2-tall pockets also absorbed their bottom wall only when the row below was background. Read your own memory notes; I left the exact conditions there.

- **Color remapping by min/max.** task-2264bd4e: with two colors a<b, it was a→b and b→0. Note I first tried majority/minority roles and that was WRONG — the actual rule used the numeric order of colors. When multiple simple hypotheses fit, verify which one fits *all* demos, and note in memory which framing worked.

- **Stamping/tile propagation.** Largest non-background component = seed; every other non-bg cell = anchor; stamp the seed's bounding box centered on each anchor (task-1b7868f1). Or: find the one block with content and tile it into all blocks separated by uniform separator rows/columns (task-8d84fe63). Or: the shape's bounding-box pattern stamped into every all-zero region of matching size (task-770f2daf).

- **Mirroring/reflection stacking.** task-73499f5a: each row becomes reverse(row)+row, and rows stack as reversed+original+reversed (3x height). task-794e60f6: output is a 2×2 block of the input and its three rotations: `[[I, rot90cw],[rot90ccw, rot180]]`. When output dims are exact multiples of input dims, think tiling with rotations/reflections immediately.

- **Diagonal-periodicity fill.** task-2e29965a: colored cells lie on diagonals; the answer fills the whole grid with a cyclic pattern where value = P[(r+c) mod L] or P[(r−c) mod L], L = number of distinct colors. Try both diagonal directions.

- **Mask AND / intersection.** task-707635df: a solid separator row/column splits the grid into two regions; output = cellwise AND of the two regions' nonzero masks, recolored to 2. task-026adbf3: similar split; output is 3 where the two blocks agree, else their most common shared color.

- **Line/geometry constructions.** task-d4079843: two parallel bars + dots; draw perpendicular lines from the facing bar through each dot (dot becomes 4), and lines from the other bar at the same offsets spanning the gap. Also task-5c839a47: a background cell becomes 3 iff it lies strictly between two dots (least common color) in its row or column.

- **Shift then draw.** task-efc2fba8: shift everything down one row; the vacated top row becomes background. task-77262100: the object moves until it touches a 2-line; a full 8-line is drawn on the far side of the object, overwriting only background.

- **Ray extension.** task-3b5f776f: endpoints (cells with exactly one non-bg neighbor in 8-connectivity) extend along their direction until the grid edge. Check neighbor degree 1 for "tips" of shapes.

- **Border-of-box detection and interior fill.** task-aa5a69a0: components forming hollow rectangles get their interiors filled with 2 if the interior area is even, else 7. task-b62da9e0: fill the *bounding box* of every non-bg component of size ≥3 with its color, everything else becomes background.

- **Counting into blocks.** task-48898d06 and task-67dd046a: downscale by counting. One counts stray cells per separator-delimited block (≥2 strays → 1, else bg); the other downscales 3× and takes the most common non-5 color per block. When output is much smaller than input, always suspect "divide by separator grid, then summarize each block."

- **Overlap equality marks.** task-b7641a67: a background cell with the *same* non-bg color immediately on both sides becomes 2. task-8625f9bc: fill gaps between runs of ≥2 consecutive markers along rows/columns and the marker bbox perimeter.

- **Wrap/roll copies.** task-5997d753's family: rows that are fully one color act as "reference rows" and bg cells aligned with pattern positions in the reference become 1. This is the one that beat me on the test — if you meet this family again, think carefully about *which* reference row pairs with which pattern row, and whether the pairing is positional or by nearest reference.

## Practical workflow in this harness

- **Save your artifacts.** For each task, save `programs/task-<id>.py` (with a `transform(grid)` function) and `programs/task-<id>.json` holding the kept pairs formatted like my files. Write a memory note (`memory_task-<id>.json` and/or a harness memory entry) with: the rule in one or two sentences, whether the program reproduces all kept pairs, how many wrong attempts/demo requests you used, and any subtle conditions. Future-you reads these; they are your only long-term memory. I repeatedly duplicate entries under `task_X` and `task-X` ids — harmless but sloppy; pick one convention (I suggest the dash form) and stick to it.

- **When demos are few (1 pair), request a demo early if allowed** rather than burning wrong submissions. A second pair often disambiguates between two plausible rules instantly. I used demo requests strategically on 73499f5a and 5997d753; the cap on wrong attempts is usually the binding one, so trade wrong attempts for demo requests when uncertain.

- **Test your program locally before submitting.** Load the kept pairs from your `.json`, run `transform`, assert equality. Only submit predictions you've verified against every pair you have. This single habit converts most wrong attempts into none.

- **Keep a candidates scratch file for unsolved tasks.** On task-1b7868f1 I kept `cand*.json` grids and a `_failed.json` listing which rule variants I'd tried (e.g., "sub1==sub3 duplicate; clean anchors (13,7),(12,8) untried"). When a submission fails, record *what* failed and *why*, so you never re-submit the same idea wearing a different hat.

- **On duplicate/failed variants:** if two of your candidate outputs are identical, you've effectively submitted the same thing twice — dedupe before submitting.

## Generalization heuristics that paid off

- The output is very often the input with a *localized* change set. Compute the diff; if your program's diff doesn't look like the demo diffs (same size, same shape of change), your rule is probably wrong even if colors match.

- When the output is a different size: multiples (2×, 3×) suggest tiling/reflection; much smaller suggests block summarization (downscale by separators or by k×k windows); same size suggests cellwise recoloring or localized stamps.

- Colors: 0 is often "empty" and sometimes participates as background. New colors introduced in outputs (2, 3, 4, 7, 8, 1) tend to be semantic: fill colors, markers, separators. Track which colors exist in demos vs outputs.

- Components: always compute 4-connectivity components of non-background colors first. It costs ten lines and answers half the tasks. Decide 4 vs 8 connectivity by what the demos need (tips/rays needed 8 in task-3b5f776f).

- Symmetry checks: for each object, test whether it's the same shape translated (canonicalize by sorting relative offsets). Twin shapes, repeated shapes, and unique shapes usually have distinct roles (e.g., the unique largest "L" was an arrow whose color consumed a twin).

- When multiple hypotheses fit: rank by simplicity (fewer parameters, no hard-coded coordinates), then by how naturally they extend to a moved/resized version of the objects. My failures came from fitting structure, not from picking between two simple rules.

## Final advice

Be systematic, be skeptical of rules that only work where the demo happens to put things, and write everything down. The tasks you've never seen will mostly be recombinations of the families above plus a few genuinely new ideas — when something new appears, describe the transformation in plain English first ("everything moved down", "the odd blocks filled"), then implement. Plain English before code saved me repeatedly.

You are smaller than me, but that mostly means you must lean harder on procedure over intuition. The procedure above is enough to do well.
