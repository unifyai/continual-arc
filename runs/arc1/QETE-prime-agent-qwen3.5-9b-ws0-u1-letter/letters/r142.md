## 1. The workspace is your memory. Use it deliberately.

Everything under `state/workspace/programs/` persists across turns. When you solve or partially solve a task:

- Save a `task-<id>.py` with a `transform(grid)` function. This is the most valuable artifact — it's executable, checkable, and reusable.
- Save a `task-<id>.json` with the demo pairs you kept, so future-you (and future turns on the same task) can verify any new program against them.
- Write a short memory file (`memory_task-<id>.json` or similar) with the RULE in plain words, not just "solved". A one-sentence rule like *"fill enclosed rectangular pockets of the background color with 4"* is worth more than a paragraph of vague notes. When a later instance of the same task appears, you can often predict the test output by reading your own rule, without re-deriving anything.

Look at my saved files as examples: `task-77262100.py` (object slides to touch a 2-line, full 8-line drawn on the far side), `task-3f4fb1a9.py` (enclosed background pockets become 4, with a subtle 2-row-pocket exception), `task-d4079843.py` (draw lines from a bar toward seed dots). Each has a `.json` of demos to re-verify against. That pattern — program + demos + plain-language rule — is the loop that wins.

## 2. Always verify programs against kept demos before submitting.

I lost submissions to transcription typos, not bad rules. My memory for task-3b5f776f says it plainly: *"Both early 'wrong rule' failures were transcription typos. Programmatically verify submitted JSON equals program output before sending."* Concretely: run your `transform` on every demo input you kept and diff against the kept outputs. If even one mismatches, don't submit — you'll learn more by requesting a demo than by guessing. A program that reproduces all kept pairs is your strongest evidence; a hand-copied grid is not.

## 3. Request demos when the rule is uncertain; don't burn wrong attempts.

Wrong submissions are capped and expensive. Demo requests are cheap. My biggest failure (task-5997d753, 8 wrong attempts) came from pattern-matching to a rule that reproduced all demos but extrapolated wrongly to the test. My other failure (task-5c839a47) came from a test with a *lone dot* — a case no demo covered. The lesson I wrote down: **if you suspect an edge case the demos don't cover (single instance, degenerate object, off-grid clipping), request demos early rather than guessing.** Eight wrong attempts buys a lot of demos.

## 4. Heuristics that find rules fast.

Scan the grid for structure in this order:

- **Colors:** background = most common. The rarest color is usually the "actor" (dot, seed, marker). Second-most-common is often a marker/bar.
- **Lines and separators:** full uniform rows/columns often split the grid (compare halves — task-026adbf3, task-707635df), or mark bands whose cells summarize to a small output (task-48898d06, task-bb30ebc2). Check `len(set(row))==1` for every row and column; it's the single most common structural cue.
- **Connected components:** compute them (4-connectivity) early. Their count, sizes, and whether shapes repeat exactly (translation twins) drive many rules — task-0f6e5a2f recolors the *farther* of a twin pair from a large L-shaped arrow; task-b62da9e0 fills bounding boxes of components of size ≥3; task-1b7868f1 stamps the largest component's bbox centered on every other non-bg cell.
- **Symmetry/mirroring:** many tasks are pure geometry — mirror + tile (task-73499f5a: `reverse(r)+r`, rows reversed/original/reversed; task-794e60f6: input in TL quadrant with rotations filling TR/BL/BR). Check whether output dims are a simple multiple of input dims first.
- **Translation/stamping:** a rare-colored shape stamped wherever a condition holds (task-770f2daf: stamp wherever the shape's cells would all be background). Try "find shape, find valid placements, stamp."
- **Counting by region:** divide by separators, count stray pixels per block, output 1 or background (task-48898d06).

## 5. Beware the plausible-but-wrong rule.

The failure mode that matters most: a rule that fits every demo but is a *correlate* of the true rule, not the rule itself. Signals that you're at risk:

- Your rule has an arbitrary constant you chose to make demos fit (a specific offset like my doomed `dc=13`).
- Your rule ignores some structure in the input you can't explain (a color that never appears in outputs, an object that never moves).
- Demos are few (1–2 pairs). With few pairs, prefer rules that are simple, symmetric, and color-agnostic (the same rule works if colors are permuted) over ones tuned to specific values.

A good test: restate your rule with colors renamed (e.g. "the rare color" not "5"). If you can't, you may have overfit.

## 7. Failed files are information, not shame.

You'll find `task-1b7868f1_failed.json` in your workspace with four rejected grids and a note listing untried variants. When a submission fails, immediately record *which variants are now known-wrong* so you don't retry them. Iterate on the smallest difference between your output and what the failure implies.

## 8. Practical habits.

- Keep grids as lists of lists of ints; write small helpers once (components, most-common color, bbox, per-row/col uniform checks) and reuse them in every program.
- Handle both orientations (horizontal/vertical) in any directional rule — half my programs have an `if rows... else cols...` branch, and test inputs love flipping orientation.
- Clip safely: any stamping near edges must bounds-check (task-1b7868f1 does `if 0 <= rr < H and 0 <= cc < W`).
- If no rule fires, the safest fallbacks that occasionally *are* the answer: identity (task-efc2fba8's first demo pair is literally identity in a region), or a one-row shift.
