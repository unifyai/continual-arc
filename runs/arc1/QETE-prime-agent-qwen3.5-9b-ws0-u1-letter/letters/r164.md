## The workflow that works

## Reading a grid: the standard inventory

Before inventing anything exotic, check these in order. Most ARC tasks in this stream are one of these:

- **Background + components.** Background is almost always the most common color. Find connected components (4- or 8-connectivity — try both if one fails) of non-background colors.
- **Lines and separators.** Full uniform rows/columns (a row or column where `len(set(...))==1`). These split the grid into blocks. Tasks where blocks become cells of a small output are very common: I solved task-48898d06 (output cell = 1 if ≥2 stray-color cells in the block, else background), task-026adbf3 (split into two same-size halves A,B by a centered separator; output 3 where A==B, else the common color), task-bb30ebc2 (output = value at intersections of marker rows/cols where all four corner markers agree), task-707635df (halves; 2 where both halves have their own dominant color), task-67dd046a (downsample 3×3 blocks, mode of non-5 cells).
- **Symmetry / tiling.** task-73499f5a: each row becomes reverse+itself, and the output stacks reversed/orig/reversed. task-794e60f6: 2n×2n output = input, rot90, rot270, rot180 quadrants. task-8d84fe63: find the block whose pattern is most anomalous, tile it over all blocks.
- **Fills and stamps.** task-3f4fb1a9: fill enclosed *rectangular* background pockets with 4 (non-rectangular ones untouched!). task-b7641a67: fill background with 2 between the outermost non-background cells of each row. task-5c839a47: fill 3 strictly between min and max positions of the rarest color per row and per column. task-3b5f776f: extend runs (length ≥2) of one color along both diagonals until blocked. task-770f2daf: stamp the rarest color's bounding-box pattern into every all-background box of that size.
- **Movement toward a line.** task-77262100: object slides to touch the 2-line; a full 8-line is drawn just on the object's far side. task-efc2fba8: shift every non-background cell down one row.
- **Dot-and-bar geometry.** task-d4079843: two bars (one color, multi-cell) plus single-cell dots; each dot draws a stub toward the nearest bar, becomes 4, and a mirrored full line appears on the other bar at the clamped index.
- **Selection rules with twin objects.** task-0f6e5a2f: among exact-translation twin pairs of shapes, pick the pair whose nearer member is closest to a special object (a thin L/angle), recolor the *farther* member to the special object's color. Key trick: canonicalize shapes as `tuple(sorted((y-min(y), x-min(x))))` and group by that key.
- **Counting / parity.** task-47ed202e: uniform rows and columns become all 2. task-8625f9bc: fill background on a marker bbox and gaps of ≤2 between marker runs. task-b62da9e0: solid-fill any component's bounding box if component ≥3 cells, delete everything else. task-aa5a69a0: inside hollow rectangles (perimeter-complete), fill interior with 2 if area even else 7.

## Code habits

Use plain Python, no external deps beyond maybe `collections`/`math`. Write small helpers you reuse in every program:

```python
from collections import Counter, deque
def bg_of(g): return Counter(v for r in g for v in r).most_common(1)[0][0]
def comps(g, ok, neigh=4): # BFS components of cells where ok(cell)
```

Always compute the background as the most common color — never hardcode. Always copy the grid before mutating (`out=[row[:] for row in g]`). When the rule involves "nearest" or "twin", canonicalize by bounding box, and be careful about **tie-breaking**: if two hypotheses tie on the demos, they're probably both wrong or the tiebreak is size/color/order-of-discovery — try a different tiebreak before giving up.

## The mistakes I made, so you don't

- **Don't submit a guess that contradicts a kept demo pair.** I did this once and lost the task outright.
- **Degenerate test inputs are a signal.** If your rule requires two dots and the test has one, your rule is probably wrong for this instance. Request demos; if none are coming, think about what a lone dot would mean (identity? cross-shaped fill? something else entirely). I burned 8 attempts on task-5c839a47 trying identity, cross, row-only, column-only, mirror, everything.
- **Check for exact duplicates before submitting variants.** Two of my "different" candidates were byte-identical after a shift.
- **Overlapping stamps:** when stamping a pattern at many anchor cells, later stamps overwrite earlier ones — that's often the intended behavior (task-1b7868f1: stamp the seed's bbox centered at every non-bg cell, seed cells excluded), but check whether the seed itself should be protected.
- **Save failures, not just successes.** A rejected output tells you the true output differs from it — often only in a few cells. Diff it in your head: *where* was it wrong? A few wrong cells usually means a small rule tweak (color choice, one boundary, a tiebreak), not a new theory.

## Final advice

The rules in this stream are almost always *local, geometric, and deterministic*: lines, blocks, symmetry, fills, movement, counting. When stuck, describe the input in words — "a grid of blocks separated by lines, with a few stray cells" — and the rule usually falls out of the description. When two rules both fit the demos, prefer the simpler one, but not at the cost of a rejected submission; a cheap demo request beats a clever guess.
