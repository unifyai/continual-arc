## The workflow that works

1. **Read the input carefully before writing code.** Trace where every colored cell went in the outputs. Literally pick one non-background cell and ask "where is it in the output?" Work out the rule by hand first; code is only transcription. Most of my failures were from coding a guess before verifying it against every cell.

2. **Programs must be pure functions.** Write `def transform(grid): ...` in `programs/task-<id>.py` and save demo pairs you keep in `programs/task-<id>.json`. Test your program against every kept pair before submitting a prediction. If your program doesn't reproduce all kept pairs, you don't understand the rule yet — go back and look again. This habit alone is most of the win.

3. **When you request demos, you usually get 1–3 more pairs.** Don't burn requests early out of panic, but do request when genuinely ambiguous (see the lone-dot lesson below).

## Recurring rule families you will see again

Memorize these families; most tasks are a member of one:

- **Split by separators.** Full uniform rows/columns (a row that is one repeated color) divide the grid into blocks. Common outputs: one value per block (count of stray cells inside; 1 if odd, etc.); compare two stacked/side-by-side blocks cell-by-cell (output 3 where they agree, else shared color); or extract the color at row-guide/column-guide intersections.
- **Dot interpolation.** Find the least-common color ("dots"). Fill cells strictly between the min and max dot along each row and each column with a new color (often 3). Dots themselves and lone dots stay unchanged.
- **Component stamping.** Find the largest non-background component; treat its bounding box as a stamp; place it centered on every other non-background cell (or all cells of some class). Stamp the bbox *as-is*, including holes and zeros.
- **Line/ray extension.** A contiguous same-color run of length ≥2 extends along its own axis or diagonal, filling background until blocked by a non-background cell or the edge.
- **Enclosed pockets.** Background-colored regions not touching the border get filled with a new color (often 4); sometimes also the wall below a 2-tall pocket.
- **Translation twins.** Two components with the same normalized shape; one gets recolored based on distance to a singleton "arrow"/special shape.
- **Bbox borders.** The bounding box border of all non-background marks becomes color 2 (keeping the marks), plus broken straight mark-lines get completed.
- **Periodic tiling.** Colored cells lie on diagonals (i+j), anti-diagonals (i−j), or rows; infer period p and assign colors by position mod p; tile everywhere.
- **Symmetric composition.** Output is a 2×2 block: input, rot90³; rot90, rot90². Or each row becomes reverse+itself and rows mirror-stack.
- **Object + line.** An object moves to touch a colored line, and a full second line is drawn on the far side of the object.
- **Clipped pattern completion.** Two copies of a pattern, one cut off at the grid edge; fill the cut-off copy's missing cells (in a fixed color, usually 1) using the shift that best aligns the intact copy.
- **Recolor maps.** Two colors only: map one to 0 and the other to the first's value. **Warning: the direction of the map can vary per instance** (sometimes small→0, sometimes large→0). Check the demo outputs, don't assume.

## Habits that saved me (and ones that cost me)

- **Save memory files** after each task: a small JSON with the rule in one sentence, file paths, pair count, and whether your program reproduces all kept pairs. When a task ID recurs, read your memory first. The rule sentence is the valuable part — write it as if for someone who never saw the grids.
- **Record failed hypotheses.** In one task I saved a file listing every candidate rule I'd tried and which was untried; that prevented resubmitting the same wrong idea. Do this whenever you're on attempt 2+.
- **Watch for duplicate predictions.** Two of my candidate rules produced literally identical outputs (e.g., after removing a background color, a stamp and a recolor rule coincide). If your "new hypothesis" produces the same output as a rejected one, it is the same rule — think differently, don't resubmit.
- **The lone-dot lesson (important).** In one task the rule was "fill between min and max dots per row/col," and it reproduced 10/10 demo pairs perfectly — but the test had only *one* dot, where the rule is undefined. I burned 8 attempts guessing the lone-dot behavior (identity, cross, row-only, col-only, etc.). All wrong. **If your rule has an undefined or arbitrary edge case, and the test input hits that edge case, request demo pairs immediately instead of guessing.** "Reproduces all demos" is not enough if your rule doesn't cover the test's configuration.
- **Verify assumptions about "the" background or "the" seed.** Count colors explicitly (`Counter`), don't assume the top-left cell is background. Some tasks use grid[0][0] as background, some use the most common color; they usually agree but check.
- **Find the *largest* component, but confirm**: when multiple components exist, check whether the outputs show one stamped object or several. Count how many distinct objects the output contains — that tells you how many anchors there are.
- **Shape/feature checkers can be buggy.** My "is this an L-shape" checker had a subtle flaw I papered over with extra conditions. Prefer simpler discriminators: bbox aspect ratio, whether a color forms multiple components, distance between component centroids. Simple geometric predicates generalize better than clever cell-set logic.
- **When a grid looks like a scaled-down version** (e.g., 21×21 → 7×7), check for 3×3 (or k×k) downsampling: output cell = most common non-special color in the block, with a designated "ignore" color (often 5 or 0).
- **Grid-in-grid mosaics:** separators split the grid; each region has a dominant color and stray off-pattern cells; often the region containing strays defines a 2D pattern to be tiled across all regions.

## On the bigger picture

- If a demo pair's output differs from the input in only a few cells, diff them cell by cell — that diff *is* the rule. Write the diff out before coding.
- If outputs are smaller than inputs, look for extraction (one block, one value per block, downsample, half-size after comparing halves).
- If outputs are larger, look for tiling/rotation/mirroring.
- Colors in ARC carry meaning by frequency and by structure. Frequency: most-common = background, least-common = special marker. Structure: straight lines, rectangles, frames, corners.
- Don't forget degenerate cases: sometimes a rule's "do nothing" (identity) is correct, and sometimes it's a trap — check whether *any* cell changed in the demo outputs before proposing identity.

## On mistakes

My wrong submissions were almost always: (a) coding before tracing the diff, (b) an undefined edge case in the test, (c) resubmitting a cosmetically different version of the same wrong rule, or (d) a shape-detector bug. Right before submitting, ask: "Does my rule explain *every* changed cell and *every* unchanged cell in every kept pair?" If yes, submit. If you can't answer, request demos.

You're a smaller model than I am, but this work rewards careful bookkeeping more than raw capacity. Trace the diff, verify against all kept pairs, save your rule in memory, and never guess on an edge case when you can request a demo instead.
