## 1. The overall shape of the game

Each task gives you a test input; you must predict the output. You usually get limited attempts per task, and wrong submissions are costly. The work is: figure out the transformation rule, encode it as a program (`transform(grid)`), and verify it against any demonstration pairs you have before submitting.

**The single most important habit: before submitting anything, programmatically run your `transform` on every kept demo pair you have and check output == expected. I lost points twice to simple transcription typos (a row shifted by one column) that a verification run would have caught instantly. Never submit a grid you typed by hand when a program can produce it.**

## 2. A structured solving routine

Work through this checklist on each new task:

**a) Identify the background.** It is almost always the most common color (`Counter(...).most_common(1)`). Almost every rule I solved is stated in terms of "background" vs. "non-background objects."

**b) Find connected components** (4-connectivity for most tasks; try 8-connectivity if 4 fails). Ask of each object: size, bounding box, shape (is it a rectangle? an L? a line?), color, position.

**c) Count colors and components.** Common structural facts that trigger different rules:
- A color appearing as exactly **two components** is often a "bar" that mirrors or extends something.
- A color appearing once is often the "actor"; the rarest color is often the "seed/marker."
- **Exact-translation twin pairs** (two components with identical normalized shape) are a recurring motif: one member of the pair gets recolored, moved, or copied based on distance/position relative to another object.

**d) Look at the global structure.** Check for:
- **Full separator rows/columns** (a row or column of a single uniform color, possibly the background or a distinct color). These split the grid into blocks. Many tasks reduce to comparisons between blocks (cell-equal → 3, else shared color; or odd-count of stray pixels per block → 1).
- **Solid lines of one non-background color** dividing the grid — rules often act on which block a stray pixel falls in.
- **Symmetry between halves**: grids that split into two equal halves (a centered separator) often produce an output the size of one half, where each cell depends on the two stacked halves.

**e) Consider the classics first** (in rough order of frequency in my experience):
1. Recolor enclosed background regions (flood fill not touching border) to a fixed color (often 4).
2. Recolor or move objects: shift toward/away from a line until adjacent; draw a full line on the far side.
3. Stamp/copy: take the largest (or rarest) object's shape and stamp it at every anchor cell (often every non-background cell, or every position where the shape fits entirely in background).
4. Fill between markers: a background cell strictly between two same-colored markers in a row/column becomes a given color (often 2 or 3).
5. Per-row or per-column operations: rows that are single-colored become all-2; fill between min/max of the rarest color in each row and column.
6. Tile the input: output = input mirrored, reversed, rotated, stacked (reversed + original + reversed; or left+mirror of each row, etc.). Check output dimensions against input dimensions immediately — if the output is 2n×2n from an n×n input, think quarter-tiling with rotations; if 3n, think mirror-stacking.
7. Downsample: blocks separated by lines collapse to one cell per block based on a property (majority non-background color ignoring one noise color; presence/odd-count of a stray color).
8. Ray/line extension: same-color runs of length ≥2 extend along their diagonal/antidiagonal in both directions until blocked.
9. Shift everything one row/column (e.g., shift all non-background down one, top row becomes background).
10. Simple color mapping (swap/keep: e.g., of two colors present, one becomes 0 and the other stays).

**f) Output dimensions are a huge hint.** Always compute the output size vs. input size before anything else. Same size → in-place modification. Half size (rounded) → downsampling/block vote. Double → tiling/mirroring. And the demo outputs tell you if the transformation is position-preserving (most cells unchanged) vs. a rebuild (most cells changed).

## 3. Choosing between competing hypotheses

When several rules fit the demos, generate a concrete prediction for the test input under each and pick by principles like:
- Prefer the rule with a **simple, symmetric statement** ("fill pockets", "extend until blocked") over one with special cases.
- Prefer rules where **all demos are reproduced exactly** — never accept a rule that "almost" fits; keep searching or add the needed condition.
- If a rule needs an arbitrary constant (like "gaps of size ≤ 2"), check whether the demos pin it down; if not, you're guessing.

When truly stuck between two predictions and the harness allows it, use a demo request (if the harness offers one) rather than a wrong submission — demo requests are cheaper than wrong attempts. If the harness lets you keep failed attempts' info, record in a memory file which hypotheses were already rejected so future-you never re-tries them.

## 4. Use your workspace files (this is where big wins come)

You have persistent files. Use them deliberately:

- **`programs/task-<id>.py`**: the program. Make `transform(grid)` pure and self-contained.
- **`programs/task-<id>.json`**: the kept demo pairs, so future-you can re-verify.
- **Memory files** (e.g., `task-<id>.mem.json` or entries in harness memory): a short statement of the *rule* and status ("reproduces all kept pairs", "test prediction was X, rejected", "unresolved: lone-dot case"). 

Why this matters: **tasks recur in this stream.** I met the same task id again later; because I had a memory note and program, I solved the second instance in one turn. Write the rule in words, precisely, including the tricky conditions (e.g., "2-row-tall pockets also absorb their bottom wall row only when the row below is background across the pocket width"). Vague notes ("solved it, something about pockets") are nearly useless.

Also record **negative results**: which hypotheses were rejected and why. This prevents burning the same wrong attempt twice. Example from my notes: "identity, cross, row-only, col-only, mirror-row all wrong for lone-dot tests — if a test has a single marker, request demos early."

## 5. When a test input is degenerate

Rules verified on demos sometimes break on the test input because the test has an edge case the demos never exhibited: a single marker instead of many, an L-shaped pocket instead of rectangular, no twin pair, no separator line. Signs to watch:
- Only one instance of the "rare" color.
- The specific structure the rule keys on (separator, twin pair, bar) is absent.

In these cases, think about what the rule *means* rather than its mechanical trigger, and design the most natural generalization (a lone dot still "spans" itself, so identity may be right; or a single dot extends in one direction). But since you can't verify, this is exactly when a demo request (if available) beats a submission. And when the cap on wrong attempts is near, submit the prediction that keeps the most cells unchanged — degenerate inputs often reduce to near-identity.

## 6. Recurring concrete patterns worth memorizing

- **Colors 4, 3, 2, 8 are frequent output colors** (fill colors, separators). A rule statement like "recolor to 4" is common.
- **Enclosed region fill**: flood-fill background components from the border; those never touched and (often) rectangular get the fill color. Watch for the extra condition about adjacent wall rows.
- **"Slide to the line"**: an object moves toward a solid line (of color 2 in one task) until adjacent, then a full line of color 8 is drawn just beyond the object's far side. Handle all four orientations.
- **Mirror/stack transforms**: row r → reverse(r)+r; stack = reversed order, original, reversed again. Generalize: look at how output height/width relate to input.
- **Block-vote downsampling**: each cell of the small grid = 1 if the corresponding block contains an odd (or ≥2) count of the stray color, else background.
- **Two-block comparison**: split at the uniform separator row/column; output cell = 3 where the blocks agree, else the blocks' shared dominant color.
- **Quarter-tile with rotations** (2n×2n output): TL = input, TR = rot90cw, BL = rot90ccw, BR = rot180 — verify against demos before assuming the rotation directions.
- **Bbox fill for large components**: components of size ≥ 3 get their bounding box filled with their color; everything else becomes background. But small components (size < 3, often noise pixels) are erased.
- **Marker bbox + gaps**: fill background cells on the bounding box of all marker cells, and gaps of ≤2 between consecutive markers along rows/columns.

## 7. Writing robust `transform` code

- Always work on a copy: `out = [row[:] for row in grid]`.
- Compute background via `Counter`, not hardcoding.
- Write a small `components(g, colors)` helper once and reuse it (BFS/DFS, 4- or 8-connectivity).
- Guard against empty structures (no markers, no separator) — either raise cleanly or return the input unchanged; decide which behavior is safer given your hypotheses.
- Test the program on the demos in the same script that writes the prediction JSON.

## 8. Time and attempt management

- Spend your first minutes on structure detection (dimensions, background, separators, component census). Most rules become obvious from that census alone.
- Don't submit a guess you can't articulate as a rule. "It looks like it might be X" submissions waste attempts.
- When the demos contradict your favorite theory, believe the demos.
