## 1. What this harness actually is

Each task gives you a small number of demo input/output pairs (sometimes only one). You must write a Python `transform(grid)` program that reproduces every kept pair, then predict the test input's output. Wrong test predictions cost attempts; some tasks cap attempts, so don't burn them on guesses. Ask for more demos when genuinely stuck — but note some tasks never give more, so don't rely on it.

Your biggest structural advantage: **write programs, not answers**. A program that reproduces all demos is far more likely to be right on the test than a hand-drawn prediction, and it's reusable if the same task reappears.

## 2. The standard first moves (in order)

Almost every task here follows one of a few families. Check them in roughly this order:

1. **Background detection**: `bg = most common color`. Nearly everything is expressed relative to it.
2. **Connected components** (usually 4-connectivity; occasionally 8 — I got task-1b7868f1 wrong once with 4-connectivity assumptions; check whether diagonal-touching cells merge). Classify components by shape, size, color.
3. **Lines and separators**: a full row or column of a single color often splits the grid. I solved many tasks this way:
   - task-026adbf3: separator splits into two blocks A,B; output 3 where A==B else the shared color.
   - task-707635df: centered separator; output 2 where both halves hold their dominant color.
   - task-48898d06: 6-line grid makes blocks; output per-block from stray-color counts.
   - task-47ed202e: uniform rows/cols become all 2.
   - task-77262100: object moves flush against a full 2-line, old spot gets an 8-line.
4. **Marker/dot tasks**: the least-common color marks positions. task-5c839a47: fill 3 strictly between min and max marker per row/column. task-d4079843: dots draw stubs toward bars and mirror lines on the other bar. Rare colors matter.
5. **Shape/twin tasks**: find components with identical canonical shapes (normalize by min row/col, sort cells). If a shape appears exactly twice, the task usually transforms one of them (recolor, move, extend) — chosen by some relational property (distance to a special object, position, etc.).
6. **Tiling/mirroring**: check if output dims are multiples of input (task-73499f5a: row→reverse+row, stack = reversed/original/reversed; task-794e60f6: 2×2 block of the input and its three rotations — order was I, rot270 / rot90, rot180).
7. **Diagonal/anti-diagonal structure** (task-3b5f776f: extend same-color runs length ≥2 along r−c and r+c until blocked; task-2e29965a: output is a periodic tiling by anti-diagonal color, infer the period).
8. **Enclosed regions**: flood-fill background from the border; pockets not reached get filled (task-3f4fb1a9: fill enclosed rectangular bg pockets with 4, plus a 1-wide slot extension below 2-tall pockets).
9. **Box/mosaic summarization**: task-bb30ebc2 and task-67dd046a both reduce a grid to a small output — one by guide-line intersections, one by 3×3 blocks keeping the majority non-background color. When output is much smaller than input, look for grid lines or regular block partitions.
10. **Count/parity rules**: task-aa5a69a0 fills enclosed ring interiors with 2 if area even, 7 if odd. Parity shows up more than you'd expect.

## 3. How to actually solve an unseen task

- **Diff the pairs first.** For every demo pair, list exactly which cells changed. Cells that never change across all pairs are almost certainly untouched by the rule. The changed cells' colors, positions, and neighborhood context are the whole problem.
- **Compute simple statistics per pair**: color counts, component counts, bounding boxes, symmetry of outputs, output dims vs input dims. Output size is a massive hint — same size means local recoloring/extension; smaller means summarization; larger means tiling/replication.
- **Write a candidate program and run it on every kept pair before submitting.** Zero mismatches required. If it reproduces all demos but you're unsure about the test, think about which behavior of your program is *underdetermined* by the demos (e.g., what happens with a lone dot, an empty case, a tie) and choose the most natural/simple behavior.
- **Prefer the simplest rule that fits all demos.** When two rules both fit, the simpler one wins on the test more often. But also prefer rules that explain *why* the demo changes look the way they do (a semantic story beats a coordinate hack).
- **Generalize cautiously**: your program should handle the test's plausible variations (different counts, positions, sizes) but don't add speculative branches — untested branches are how wrong predictions happen.

## 4. Lessons from my failures (please learn from these)

- **task-5997d753, 8 wrong attempts**: I had a program that reproduced every demo but kept guessing wrong test predictions (a shifted-copy offset task). The lesson: when the demos underdetermine the rule, request demos *early* rather than guessing repeatedly. If wrong_attempts climb past 2–3 with the same program, the rule itself is probably subtly wrong, not the test handling — go back and rethink.
- **task-5c839a47 (first instance)**: the test had a *single* dot, which my between-min-and-max rule can't act on. I tried identity, crosses, arcs — all wrong. Lesson: when your rule needs ≥2 of something and the test may have fewer, think hard about degenerate cases *before* submitting, and consider whether the rule generalizes differently (e.g., nearest-pair instead of global min/max).
- **task-1b7868f1**: connectivity choice (4 vs 8) and anchor definition (bbox center vs a specific cell) both mattered. When a stamping/mirroring rule almost works, try: different anchor points, 8-connectivity, excluding holes vs including them, and translating bbox-as-is vs shape-only.
- **Subtle tie-breaks matter** (task-0f6e5a2f): "pick the pair whose nearer member is closest to the arrow; recolor the farther member." I needed precise tie-break logic (larger member size). Read the demos for evidence of tie-breaking before assuming.
- **Contamination warning**: early in my run I treated recovered "Demo pair" labels that came from other tasks as evidence. Don't do this — only trust pairs from the current task.

## 5. Practical workflow tips

- Keep a `.json` of kept pairs next to every program (path pattern: `workspace/programs/task-XXXX.py` and `.json`). Write a small local checker that loads the pairs and asserts your `transform` reproduces each. This is non-negotiable — it catches most bugs before submission.
- Save a memory file (like `task-XXXX.mem.json` or the harness memory entries) stating the rule in one crisp sentence plus whether all pairs reproduce. On repeat encounters you'll skip straight to the answer, and the one-sentence rule is often enough to re-derive the code.
- When a task is a *variant of a saved task* (same files present, new instance), trust your saved program — several of my instances were solved first-try this way (770f2daf, 0f6e5a2f, d4079843, 48898d06, b62da9e0, 3f4fb1a9, 2264bd4e).
- But re-verify: run the saved program on the new demos if any are provided. If a saved rule fails on a new demo, the task family may have a second rule — don't force the old one.
- Watch for duplicate/failed-attempt files (`*_failed.json`). I recorded which anchor choices I'd already tried wrong, so I wouldn't repeat them. Do the same: never resubmit an idea that already failed.

## 6. Code patterns worth copying

- Background: `Counter(v for row in g for v in row).most_common(1)[0][0]`.
- 4-connected flood fill with an explicit stack (fast, no recursion).
- Canonical shape key: `tuple(sorted((y-min_y, x-min_x) for y,x in cells))` — group components by this to find twins.
- Line detection: `rows where len(set(row))==1`, and contiguous bands between separators via a band-splitting helper.
- Always deep-copy the grid into `out` and mutate `out`, never `grid` — several rules need the original for lookups while writing.

## 7. Final advice

ARC tasks reward *careful observation over clever guessing*. Before writing any code, spend real effort staring at the demo pair diffs. The moment you can describe the change in one precise English sentence ("cells strictly between the two dots in each row become 3"), the code is trivial. If you can't write that sentence, you're not ready to submit.

When stuck, enumerate hypotheses systematically: recolor / move / extend / fill / copy / mirror / count / erase, and for each ask "do the demos rule this out?"

Good luck. The stream rewards patience, and your saved memories are your best weapon on repeat tasks — keep them accurate and terse.
