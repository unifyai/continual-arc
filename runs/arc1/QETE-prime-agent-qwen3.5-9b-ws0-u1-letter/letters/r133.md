## How the harness works (recap, plus the parts people forget)

1. You get a task with a few input/output demo pairs. You can write a program (`transform(grid)`) and request more demos. You submit a prediction for the test input; wrong submissions count against you and you can be locked out after ~8 wrong attempts.
2. **Request demos early when uncertain.** The most expensive mistakes I made were submitting predictions for degenerate test inputs (e.g., task-5c839a47: my rule only worked when there were ≥2 dots; the test had a *single* dot, and I burned 8 wrong attempts guessing what a lone dot should do). The moment your rule has an untested edge case — a degenerate input, a lone object, an empty region — that is exactly when to spend a demo request, not a submission.
3. **A program that reproduces all kept demo pairs is not enough.** In task-5997d753 my program reproduced 6/6 demos but the test prediction was still wrong. Demos are a sanity check, not proof. Always ask: "what inputs would break this rule, and is such an input plausible for this task?"

## What actually goes in the program

Write `transform(grid)` in `programs/task-XXXXXXX.py`, taking a list of lists of ints, returning the same shape (unless the task transforms dimensions, which happens — see task-73499f5a, task-707635df, task-47ed202e). Save demo pairs to `programs/task-XXXXXXX.json`, and write a memory JSON (`programs/task-XXXXXXX.mem.json` or the workspace memory file) with the rule in plain words. The memory file is your future self's best friend: next session you may meet the same task, and "rule: shift all non-background cells down one row, clearing originals" saves you 20 minutes.

## The recurring rule families (learn to recognize them fast)

Roughly in order of how often I saw them:

- **Background + objects.** Find the most common color (background). Components of non-background colors are objects. Then the rule is usually one of: fill bounding boxes, stamp a seed shape at anchor positions (task-1b7868f1: stamp largest component's bbox centered at each other non-bg cell), recolor based on distance/size (task-0f6e5a2f), translate objects until touching a line (task-77262100), extend lines from cells (task-3b5f776f: degree-1 cells extend diagonally to the edge), fill enclosed pockets (task-3f4fb1a9: fill enclosed rectangular background pockets with 4, with a special case for 2-row pockets absorbing their bottom wall).
- **Enclosed-region filling.** Flood-fill from the border to find cells *not* reachable; interior background regions get recolored (usually to 4). Watch for special cases: only rectangular pockets, only pockets of a certain height, whether a wall row gets absorbed too. These special cases are exactly where you should request a demo.
- **Grid-structure tasks.** Grid divided by solid separator rows/columns into blocks. Output is usually small: one cell per block, value = something counted inside (task-48898d06: 1 if odd count of stray color, else background). Variants: blocks contain a pattern copied from a source block (task-8d84fe63), A-vs-B comparison across a separator (task-026adbf3: 3 where the two halves agree, else their shared common color), corner-color voting (task-bb30ebc2: build a small output from the colors at the intersections of separator lines).
- **Symmetry/mirroring tasks.** task-73499f5a: each row becomes reverse(row)+row, then stack reversed+original+reversed. task-794e60f6: 2n×2n = input, rot90cw, rot90ccw, rot180 in quadrants. Check: is the output exactly double/triple the input? Is it mirror-symmetric?
- **Recolor-by-local-context.** task-b7641a67: a background cell with identical non-bg neighbors on both sides in a row becomes 2. task-47ed202e: any row or column that is a single uniform color becomes all 2. task-b62da9e0: components of size ≥3 fill their bbox; everything else becomes background. These are cheap to code; just get the exact predicate right.
- **Diagonal/periodic tiling.** task-2e29965a: cells arranged on diagonals with a period; complete the pattern by assigning each diagonal residue class its observed color. Variant: horizontal colored rows, tile by row index mod (number of distinct colored rows).
- **Drawing lines between anchors.** task-5c839a47: fill 3 strictly between min and max positions of the rarest color along each row/column. Simple, but check whether a single anchor exists — that broke me.
- **Object slides toward a line, then a new line is drawn** (task-77262100). Handle both orientations (row-line vs column-line) and both sides. My program looped over permutations of the two bars and returned the first consistent configuration — a good general technique when a task has 2–4 symmetric readings: try all, keep the one that's consistent with all cells.
- **Collision/overlap counting** (task-026adbf3, task-d4079843): compare two aligned structures; mark agreement points.

## Strategy habits that pay off

- **Identify background first**, always: most common color. Then enumerate the other colors and their component counts. Component shape (single cell, line, rectangle, L, ring) drives most rules. Write a tiny helper library in your head: components (4-conn), bbox, solid-rectangle check, is-line.
- **Check dimension changes first.** Compare input height/width to output height/width. If output is smaller, look for separators, blocks, downscaling (task-67dd046a: 3×3 blocks → majority non-5 color). If larger, look for mirroring/tiling/quadrants.
- **When a rule has a free parameter** (a distance, a count, a tiebreak), don't guess it — try to derive it from the demos, and if two readings both fit the demos, that's a demo-request signal, not a coin-flip.
- **Tiebreak ordering matters.** In task-0f6e5a2f I needed "the twin pair whose nearer member is closest to the arrow (tiebreak: larger size)". Encoding the tiebreak explicitly in the sort key was the difference between right and wrong.
- **Validate by brute force when cheap.** For stamping tasks, enumerate all offsets and check consistency against every demo cell. For sliding tasks, enumerate all translations and pick the one minimizing mismatches. My task-d4079843 and task-770f2daf programs do exactly this; it's more robust than clever logic.
- **A note on colors:** 4 appears suspiciously often as the "fill" color (pockets, lines, agreeing cells sometimes become 3, disagreement 2). If a rule needs a new color and the demos show one, copy it exactly; if demos never show it, that's ambiguity — request demos.

## Failure modes to avoid (from my own record)

- **Duplicate submissions.** I burned a submission on an identical grid (see the `_failed.json` note "sub1==sub3 duplicate"). Keep a list of every grid you've submitted; never resubmit a variant that differs from a previous one by less than you think.
- **Local tweaks without re-testing.** Changing a predicate (e.g., `0` vs `4` in one place) can break pairs it previously reproduced. Re-run all kept demos after *every* edit.
- **Anchoring on the wrong object.** "Largest component", "rarest color", "the singleton L-shape" — verify the choice is consistent across *all* demos, not just the first.
- **Unresolved degenerate cases.** Single dot, single object, all-background input, 1×N input. For each, decide what your program does and whether that's defensible; if not, demo it.

## Final practical points

- Keep programs self-contained (only stdlib: collections, itertools, math; numpy is available but not required).
- Grid sizes vary a lot (from 3×3 to 29×27); never hardcode dimensions.
- When the output is a strict function of the input everywhere (pure recolor), verify cell-by-cell against all demos with an assert loop before submitting.
- Log your attempts in a `*_failed.json` with a note about what was tried and what wasn't — I caught a missed hypothesis ("clean anchors (13,7),(12,8) and (12,7)+0->1 untried") only because I wrote it down.

The single biggest lever: **treat ambiguity as a demo request, and treat every submission as scarce.** Be curious about the weird inputs, careful with the edits, and generous with your notes. Good luck — the tasks are more repetitive than they look, and a fast read of the rule families above will carry you through most of them.
