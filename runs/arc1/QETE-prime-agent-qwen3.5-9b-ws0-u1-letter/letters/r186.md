2. **The core loop:** ask for demo pairs when unsure (you have a budget), write a `transform(grid)` function, verify it reproduces every kept pair *exactly*, then predict the test. Think about what makes the rule *natural* rather than merely consistent.

3. **Write the rule in prose into memory, not just the code.** "output 3 = cells strictly between min and max dot per row/column; dots and lone dots unchanged" is worth more to you later than the code is. Future-you needs to re-derive the rule when a slightly different test input appears.

## Rule families I've seen recur — recognition patterns

ARC rules cluster. When you see a new input, check these families in rough order of how often they show up:

- **Grid tiling / blocks:** grid split by solid separator rows/cols of one color (47ed202e, 48898d06, bb30ebc2, 026adbf3, 8625f9bc, 770f2daf, 8d84fe63, 707635df). Find full uniform rows/columns; split into blocks; each output cell summarizes its block (mode color, odd-count of stray color, marker value, equality of two halves). Very common.
- **Downscaling/mosaics:** bb30ebc2's answer was a tiny grid of block-corner colors; 67dd046a took 3x3 blocks' mode (excluding color 5). If output dims ≈ input/2 or /3, think block summarization.
- **Stamping/tiling a seed shape:** 1b7868f1 (largest component's bbox stamped centered at every other non-bg cell), 794e60f6 (2x2 block of the input rotated 90° each way), 73499f5a (mirror and triple). Look for repeated sub-shapes and translations.
- **Periodicity:** 2e29965a — colored anti-diagonals tiled periodically across the grid. If colored lines are evenly spaced and colored, infer the period and fill everything.
- **Diagonal extension:** 3b5f776f — same-color runs of length ≥2 extend along their diagonal until blocked. Runs + directional fill is a family.
- **Line/connector drawing:** d4079843 — dots draw stubs to nearest bars and mirrored lines on other bars. Objects "communicating" via lines toward each other.
- **Fill enclosed regions:** 3f4fb1a9 and aa5a69a0 — background pockets enclosed by a ring get a new fill color (flood fill from border to find non-enclosed bg). Classic; check whether bg regions touch the border.
- **Movement/translation:** 77262100 — shape slides to touch a line, old location becomes bg, a new full line is drawn at the old position. efc2fba8 — shift all non-bg cells down one. 0f6e5a2f — recolor one member of a twin-shape pair based on distance to a reference object.
- **Color mapping:** 2264bd4e — map the two colors (keep higher, lower→0); b7641a67 — recolor cells between pattern runs to a specific value.
- **Counting/geometry invariants:** aa5a69a0 — rectangle perimeters; fill inside with 2 or 7 depending on parity of interior area. Check perimeters, areas, parities.

## Concrete coding habits

- **Always find background first:** `bg = Counter(v for row in g for v in row).most_common(1)[0][0]`. Then find connected components (decide 4-conn vs 8-conn — some tasks need 8; 1b7868f1 used 8-conn). These two functions should be muscle memory; nearly every rule starts with them.
- **Canonicalize shapes:** to detect twin/rotated/repeated objects, sort the shape's cells relative to its top-left: `tuple(sorted((y-min_y, x-min_x) for ...))`. Works for translation-invariant comparison. For rotation/reflection invariance, generate all 8 transforms of the key.
- **Verify before submitting:** literally load your `task-<id>.json` pairs, run `transform` on each input, and assert equality with the output. Never submit a rule you haven't checked against all kept pairs. One exception from my notes: it *did* happen twice that all-pairs-reproduced still failed the test — that's the signal to request demos, not to submit anyway.
- **Keep transform pure and simple:** takes grid (list of lists of ints), returns grid. No file I/O inside transform.
- **Avoid overfit hacks:** my 0f6e5a2f program has some convoluted L-detection code with a leftover dead expression (`|{(y,cx) for y in vcol for x in []}`). It worked, but messy rules break on new inputs. Prefer the simplest rule that fits all pairs, then sanity-check it on a hypothetical new input you imagine.

## Priors on test inputs

- Test inputs often stress the rule's edge cases: a lone object, a shape touching the border, a missing separator, an odd size. When your rule has an obvious undefined case, decide it deliberately and, if demos are available, spend one request to check.
- Output dimensions are a huge hint. If output is smaller, you're summarizing blocks. If same size, it's recoloring/shifting/filling. If larger, it's tiling/replication (794e60f6 doubled, 73499f5a tripled).
- Colors are data too. A color appearing exactly once, or exactly twice, is almost always significant (the "dot" in 5c839a47, the twin pair in 0f6e5a2f, the seed in d4079843). Count color frequencies early.

## Budget management

Wrong attempts and demo requests are both limited per task. My rough policy: 
- 0–1 wrong attempt before asking for demos if the rule is uncertain.
- If the rule reproduces all demos but feels underdetermined (multiple natural rules fit), request demos rather than guess.
- If you've solved a similar task before and saved its program, run it first — several of my later-task wins were zero-cost reuses.

You're smaller than I am, so be disciplined where I could brute-force: don't keep 4 candidate outputs in your head — encode each hypothesis as a checkable program and let the demos arbitrate.
