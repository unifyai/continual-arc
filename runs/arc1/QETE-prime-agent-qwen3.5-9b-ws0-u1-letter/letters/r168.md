## The workflow that works

1. **Look before you write.** Read the input grid(s) carefully. Count colors, find the background (most common color), find the objects (non-background connected components). Most rules in this stream are expressible in one sentence about background + objects.

2. **Write the `transform(grid)` function** that maps input to output, put it in `programs/task-XXXX.py`, and save demo pairs you've deduced into `programs/task-XXXX.json`. Verify your program reproduces every pair you keep **before** submitting. A program that reproduces all kept pairs is your safety net: if a later test fails, you know the demos were right and the rule needs refinement, not abandonment.

3. **Request demos when unsure.** Extra demo pairs are far cheaper than wrong submissions. The strongest signal that you need demos: an unusual configuration in the test input (a case your demo pairs never exercised). See the lone-dot lesson below.

4. **Keep memory files** (`memory_task-XXXX.json` or `task-XXXX.mem.json`) with a one-sentence statement of the rule and pointers to your program/pairs files. When the same task family recurs, this turns a 10-attempt problem into a 1-attempt solve. Several tasks recurred for me and the second instance was solved instantly because the rule was written down.

5. **Record failed hypotheses in a `*_failed.json`** with a note listing what you've ruled out (see `cand8.json` / `task-1b7868f1_failed.json` style). When you burn attempts, you must not re-submit a near-duplicate of something already rejected. Duplicate submissions are pure waste.

## Rule families that keep appearing in this stream

Learn to recognize these shapes of problem — the same families return with different colors:

- **Stamping/tiling with a seed component.** The largest (or rarest-color) non-background component is a "seed"; every other non-background cell is an anchor, and the seed's bounding box (contents as-is, including zeros/holes) is stamped translated so the seed's center maps onto the anchor (task-1b7868f1).
- **Grid-of-blocks compression.** The grid is divided by full uniform separator rows/cols into blocks. Outputs are per-block: 1 if the block contains ≥2 stray-color cells, else background (task-48898d06); or the block value where all four corner markers agree; or mode of the 3×3 block excluding a background color (task-67dd046a is 3×3 downscaling with mode-excluding-5).
- **Two-block comparison.** A full uniform row/col splits the grid into two same-size halves A and B. Output compares them cellwise: mark where A == B in a special color, else background (task-026adbf3, task-707635df — the latter marks where *both* halves have their own dominant color).
- **Line/ray extension.** Same-color runs of length ≥2 extend along diagonals/antidiagonals through background until blocked (task-3b5f776f). Diagonal lines or rows of color define a period; fill the whole grid by cycling colors along the perpendicular coordinate mod the number of lines (task-2e29965a).
- **Gap filling between markers.** Along rows/columns, fill background cells between consecutive marker cells if the gap is small (≤2, or strictly between the min and max positions of the rarest color — task-5c839a47, task-8625f9bc, task-b7641a67).
- **Enclosed pocket filling.** Flood-fill background; components not touching the border are enclosed — fill them (task-3f4fb1a9: rectangular pockets become 4, with a quirk that a 2-tall pocket also recolors the wall row below). Enclosed pockets inside rectangles get a fill color depending on area parity (task-aa5a69a0).
- **Symmetrization/mirroring.** Row doubling with reversal, quadrant concatenation (TL, TR=rot90, BL=rot270, BR=rot180 — task-794e60f6), or reflections of the whole grid (task-73499f5a: r → reverse(r)+r per row, and rows reversed, original, reversed).
- **Downshift.** All non-background content shifts down one row (task-efc2fba8) — trivial but easy to overthink.
- **Object moves relative to a line.** A shape shifts horizontally to sit flush against a full-height colored line; old area becomes background; a new full-height line of a different color is drawn at the old position (task-77262100).
- **Recolor the twin that's farther from the arrow.** There's a singleton large "arrow" shape and several exact-translation twins of the same shape occurring exactly twice; pick the pair nearest the arrow by Manhattan distance and recolor the farther member to the arrow's color (task-0f6e5a2f). Generalize: *one singleton object + pairs of identical objects + a distance comparison*.
- **Two bars + dots.** Two long same-color bars (one horizontal, one vertical) plus single-cell dots. Each dot draws a stub toward the nearer bar, becomes a marker color, and a mirrored full line is drawn on the other bar at the clamped index (task-d4079843).
- **Noise removal / keep big components.** Components of size ≥3 keep their bounding box; everything else becomes background (task-b62da9e0).

If a new task doesn't match a family, start from primitives: background, component counting, bounding boxes, translation twins (compare canonicalized shapes sorted by (dy,dx) offsets — exact translation equality is `sorted((y-min y, x-min x))`), symmetric closure, and "recolor the exceptional one."

## Hard-won lessons

- **The lone-dot lesson (task-5c839a47):** my rule worked on 10 demo pairs but the test had a single dot, and *every* extension I tried (identity, cross, row-only, col-only, longer arc, mirror, full row) was wrong — 8 attempts burned. **If your rule was induced from ≥2 objects per structure and the test has a degenerate case (one object, one pair, empty half), request demos immediately.** Degenerate configurations are where rules hide extra clauses.
- **Beware contamination in recovered cross-task memories.** One of my memory files contained "Demo pair" labels that didn't come from this harness — treat external-looking pair labels with suspicion and verify against the actual harness output.
- **Don't guess small details when a pattern is underdetermined.** With only 1–2 demo pairs, both "recolor the farther twin" and "recolor the nearer twin" may reproduce them; the distance rule direction, the tiebreak (larger member size), and off-by-one clamping matter. If two readings both fit the demos, pick the one that also explains *why* the demos look the way they do (asymmetries, the single case that differs).
- **Verify with code, not eyes.** Write a tiny checker: load your json pairs, run `transform`, compare cell-by-cell, print mismatch coordinates. Eyes miss one cell in a 27×29 grid.
- **Reuse your own library.** The component-finding BFS, the canonical-shape key, the "most common = background" idiom, the run/gap scanners — I rewrote these a dozen times. They're short; keep a mental template and adapt.

## On style of rule-hunting

When stuck: describe the *difference* between input and output in one sentence before writing any code. "Output = input, except X cells become Y." If you can't say it in one sentence, you don't have the rule yet. If the sentence has a weird clause ("unless it's 2 rows tall, then also the wall below"), that clause is real — outputs in this stream do contain such clauses, and they're exactly what demo pairs are for.

Finally: the tasks are finite in variety. The families above plus careful one-sentence descriptions covered nearly everything I met. Keep the workspace tidy, keep the memory files honest (say what's verified and what isn't), and never submit twice on the same hypothesis.

Good luck — the stream rewards patience and one careful sentence more than cleverness.
