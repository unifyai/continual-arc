## The harness basics

- You play one task at a time. You write a Python program `transform(grid)`, keep demo pairs as JSON files under `workspace/programs/task-<id>.json`, and save a memory file when you crack a rule. The paths I used are shown in the files above — keep that convention (`task-<id>.py` + `task-<id>.json` + a memory file keyed by the task id).
- **Always verify your program against every kept demo pair before submitting.** Run it. A program that "should" work but fails a demo is the most common and most avoidable loss. Write a quick test loop that loads the JSON and asserts `transform(inp) == out` for every pair, including solved test inputs (record those in the JSON too — they become extra verification for future edits).
- When you request extra demos, have a concrete hypothesis first. Requests are limited; a demo without a hypothesis to confirm/deny is mostly wasted.

## Recurring rules (this is the gold — these families keep coming back)

 Memorize these shapes of rules; when a new task looks like one, try the matching algorithm immediately, then verify.

1. **Background/marker structure.** Almost every task has a background color (most common). Find it first with `Counter`. The interesting objects are non-background components (4-connectivity usually; sometimes 8-connectivity matters — if 4 fails on demos, try 8).

2. **Bounding-box fill (task-b62da9e0).** Each non-bg component of size ≥3: fill its bounding box with its color; everything else becomes bg. Simple, verify quickly.

3. **Hollow rectangle interiors (task-aa5a69a0).** Component that is a perfect hollow rectangle (check: `h>=3 and w>=3 and len(comp)==2*h+2*w-4`): fill interior bg with 2 if interior area even, else 7. The parity rule was the trick — count cells in the interior `(h-2)*(w-2)`.

4. **Enclosed pockets (task-3f4fb1a9).** Background components not touching the border, that are solid rectangles: recolor to 4. Special case: a 2-row-tall pocket also absorbs its bottom wall row if the row below that wall is all bg. Non-rectangular pockets are left alone.

5. **Seed stamping (task-1b7868f1, task-770f2daf).** Two variants:
   - Largest non-bg component = seed; every other non-bg cell is an anchor; stamp the seed's bbox translated so the seed's bbox center maps onto the anchor (copy the whole bbox including holes/zeros).
   - Rarest color = seed shape; stamp it at **all** offsets where all its cells land on background (0). Try "all offsets" and "at anchors" variants against demos.

6. **Lines through dots (task-d4079843).** Two bar segments of one color + scattered dots of another. From the bar facing the dots, draw a perpendicular line to each dot (dot becomes 4). From the opposite bar, draw lines at the same offsets spanning the gap between the bars, in dot color. Handle both orientations; the code in `task-d4079843.py` is a good template.

7. **Shape twins + a big L/arrow (task-0f6e5a2f).** A large thin angle (arms ≥3) is a "marker". Among pairs of identical shapes differing only by translation (same canonicalized shape, occurring exactly twice), recolor the one farther from the marker to the marker's color. Canonicalize shapes by `sorted((y-min_y, x-min_x))`.

8. **Slide toward a 2-line, draw an 8-line (task-77262100).** Full row/column of 2s. The object slides perpendicular until adjacent to the line; then a full row/column of 8s is drawn just on the object's far side (overwrite bg only).

9. **Symmetrization outputs (task-794e60f6, task-73499f5a).**
   - Output = 2×2 block of rotations: `[[I, rot90cw],[rot90ccw, rot180]]` via `np.block`.
   - Or mirror: each row → `row[::-1]+row`, stack = reversed + original + reversed again (height ×3, width ×2). Check dims: if output is 3× input height and 2× width, this is it.

10. **Two blocks comparison (task-026adbf3, task-707635df, task-5997d753, task-48898d06).** Grid split by a full uniform row/column separator into blocks:
    - Same-size blocks A,B: output = 3 where A==B, else the common bg color.
    - Nonzero masks AND'd: output cell = 2 where both nonzero, else 0.
    - Block counting: downscale — per block, odd count of a stray color → 1, else bg (task-48898d06). Or per 3×3 block of a 3× downscale, most common non-5 color.
    - If a block is a solid "reference" pattern row (task-5997d753 Regime A): bg cells in mixed rows matching the reference's pattern column become 1. Careful — I failed this one (8 wrong attempts). The general lesson: **when one block is entirely uniform-pattern, it's a lookup table for the other blocks.**

11. **Diagonal period fill (task-2e29965a).** Colored cells lie on diagonals; fill the whole grid with `P[(r+c) mod L]` or `P[(r-c) mod L]`, where L = number of distinct nonzero colors and P is built from the clue cells. Try both residues; accept whichever is consistent.

12. **Color remapping by min/max (task-2264bd4e).** Two colors a<b: a→b and b→0. Important: I first tried majority/minority roles and it failed. **Prefer structural/arithmetic rules (min/max) over frequency-role rules, and test both against demos.** This generalizes: task-707635df mapped low→2? No — check each task's mapping from demos; derive the mapping from color sets, not assumptions.

13. **Small-gap bridging (task-8625f9bc).** Between consecutive markers along any row/col, fill bg gaps of size ≤2 with 2; plus bg cells on the bounding-box perimeter of all markers. The "≤2" threshold mattered.

14. **Between-dots fill (task-5c839a47).** A cell becomes 3 iff strictly between two dots (rarest color) in its row or column. Include the dot itself unchanged. Simple: `min(dotidx) < i < max(dotidx)`.

15. **Between-same-color fill (task-b7641a67).** bg cell with identical non-bg neighbors left and right in its row → 2.

16. **Row shifts (task-efc2fba8).** Trivially: everything shifts down one; top row becomes bg. Check for trivial geometric transformations first — don't overcomplicate.

17. **Degenerate/anti-tasks (task-efc2fba8 candidate, task-026adbf3 uniform test).** Sometimes the test input is nearly all background or the demo output equals the input. Don't panic; the same rule still applies, or output ≈ input. Also, if a demo's output is identical to its input, your rule should preserve it — use that as a sanity check.

18. **Uniform row/col recolor (task-47ed202e).** Rows/columns entirely one color → 2, rest unchanged.

19. **Growing lines from deg-1 cells (task-3b5f776f).** Non-bg cells with exactly one non-bg 8-neighbor: extend from that cell in the direction away from its neighbor, to the grid edge, in the cell's color. Compute direction from the neighbor delta.

## Strategy and process

- **Always inspect dimensions first.** Output same size? Output = k× input size (→ rotation blocks / mirroring / tiling)? Output smaller (→ downscaling like 3×3 blocks, or grid-line extraction like task-bb30ebc2 / task-48898d06)? Output larger with a separator (task-8d84fe63: cells from a "source" block propagate to matching bands)? Dimension ratios are the fastest discriminator.
- **Count colors.** 2 colors → simple recolor/mapping. 3+ → find bg, marker, objects.
- **Look at the smallest demo pair first.** Small grids reveal structure fastest. Read the input/output cell by cell and describe the change in one English sentence before coding. Then code exactly that sentence. Then check the other demos — if it fails there, refine the sentence, not just the code.
- **Keep a scratch mental list of near-miss hypotheses per task** and write failed hypotheses into your memory file (`"note": "X untried"`) exactly like `task-1b7868f1_failed.json` does. When you return to a task (or meet a sibling), not repeating a failed idea is worth a lot. That file's format — a `failed` list plus a `note` of untried variants — is a good template.
- **When you keep demo pairs, keep them exactly** (the raw JSON structure: a list of `{"input": ..., "output": ...}`). A corrupted or truncated JSON is a silent killer.
- **Re-run verification after every code edit**, not just the first time. Edits fix one demo and break another surprisingly often.

## Common pitfalls

- **4- vs 8-connectivity.** Default 4; if components look wrong on a demo, switch.
- **Which color is "background."** Usually most common, but in some tasks the pattern color is a full-row solid (task-5997d753). Test both readings if the first fails.
- **Overwriting vs preserving.** Decide explicitly whether your fill overwrites existing colors or only background. Many rules are "overwrite bg only."
- **Edge effects.** Always bounds-check before writing (the stamping tasks clip at borders — check whether demos clip or assume in-bounds).
- **Ties and thresholds.** "≤2", "size ≥3", "arms ≥3" — these thresholds were all load-bearing. When a rule almost works, tune the threshold before abandoning the rule.
- **Role assignment ambiguity.** If two non-bg colors exist and the demos can't distinguish roles, the rule is probably symmetric or based on min/max — not frequency.

## On the failed task (task-5997d753) — what to learn from my loss

I burned the attempt cap. The pattern: the demos had alternating uniform rows (e.g., `888...` / `999...`), and the answer involved treating solid rows as references and mixed rows as predictions, with some alignment search. My program reproduced all demos but still got the test wrong — because multiple rules fit the demos. When that happens: prefer the **simplest** rule consistent with all demos, and think about which generalization the task designer most likely intended (usually the one that reads naturally: "solid rows are reference tables; below each reference, mixed rows get their bg cells turned into 1 where the reference has pattern color, at the best alignment"). Also: if you have any wrong-attempt budget left and two hypotheses both fit the demos, pick the one that also produces sensible output on degenerate inputs (all-bg, single block).

## Final habits checklist per task

1. Parse dims and colors. 2. Guess rule family from the list above. 3. Write the one-sentence rule. 4. Code it, run on all demos. 5. If mismatch, diagnose per-cell (diff input/output) rather than guessing. 6. Record solved pairs + rule in memory file. 7. Only then submit the test prediction. 8. Write failed hypotheses to notes.

You're a small model, and that's okay — the harness rewards methodical verification over cleverness. Most of my successes came from running the code against demos instead of reasoning "it should work." Do that every single time.
