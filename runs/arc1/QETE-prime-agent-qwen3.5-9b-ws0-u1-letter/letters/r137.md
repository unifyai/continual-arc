## How the harness works

Each turn you get a task. You may have some demo input/output pairs (kept pairs) and you must produce a `transform(g)` function and predict a test output. Key mechanics:

1. **Wrong predictions cost you.** There's a cap on wrong submissions per task (I hit it on task-5997d753 after 8 wrong attempts — task lost, all that work wasted). Before submitting a prediction on a test input, run your program on it and on every kept demo pair. Only submit when it reproduces all demos AND you've sanity-checked the prediction by eye.

2. **You can request demo pairs** when you have none or too few. If a task has zero demos, request some before guessing. Rule-hunting with no pairs is pure gambling. (On task-5c839a47 I burned many attempts on a test with a single lone dot — the lesson recorded there: if the test case looks unlike your demos, e.g. it has only one dot where demos had many, request demos early, don't extrapolate blindly.)

3. **Reload data programmatically.** Never hand-type a test grid from the session log into your script. A single transcription typo cost me a wrong attempt on task-5c839a47. Write a script that parses the grid from the log/file directly.

4. **Keep files tidy.** The convention I used: `programs/task-<id>.py` (with `transform`), `programs/task-<id>.json` (kept demo pairs), and a `programs/task-<id>.mem.json` or memory entry with the rule in plain words. When you re-encounter a task later (this stream re-visits tasks!), these files are how you reconstruct the solution instantly. Write the rule summary even when short.

5. **Save failed-candidate analysis.** On task-1b7868f1 I saved a `task-1b7868f1_failed.json` listing failed prediction grids with a note like "sub1==sub3 duplicate; clean anchors untried" — so I wouldn't resubmit a rejected guess. Do this. Duplicated wrong submissions waste attempts.

## General strategy for finding the rule

ARC rules are usually one of a small family. Check these in order:

- **Geometry:** translation, reflection, rotation, stacking (e.g. row r → reverse(r)+r, output = block + reversed(block) + block — task-73499f5a; 2n×2n quadrants with rot90cw/rot90ccw/rot180 — task-794e60f6; 3×3 downscaling by mode of non-background colors — task-67dd046a; stamping the rare-color shape at every offset where its cells are all background — task-770f2daf).
- **Color mapping / comparison:** split grid by a full uniform row/col separator into two same-size blocks A and B; output marks where A==B (task-026adbf3, task-026adbf3's "3 where equal"). Also: keep the higher of two colors, map lower to 0 (task-2264bd4e). Also: fill a background cell with 2 if its two neighbors in a row are identical non-background (task-b7641a67).
- **Fills:** fill enclosed rectangular pockets of background with 4 (task-3f4fb1a9 — but note the subtle rule: a 2-row-tall pocket also absorbs its bottom wall row only when the row below is background across the width; non-rectangular pockets stay unchanged). Fill bounding boxes of components ≥3 cells (task-b62da9e0). Fill gaps ≤2 between marker runs and the marker bounding-box perimeter with 2 (task-8625f9bc). Fill 3 strictly between min and max dot positions per row and per column (task-5c839a47).
- **Lines and periodicity:** full single-color rows/cols become all-2 (task-47ed202e); colored parallel diagonal/row lines define a periodic pattern by (i+j)%p or i%p (task-2e29965a); block grid with separator lines → output cell = 1 if odd count of stray color in block (task-48898d06).
- **Motion/anchor objects:** object slides until adjacent to a 2-line, then a full 8-line is drawn just outside its far side (task-77262100); stamp the largest component's bbox centered on every other non-bg cell (task-1b7868f1); among exact-translation twin pairs, recolor the member farther from an L-shaped arrow (task-0f6e5a2f); extend a degree-1 cell's line until the border (task-3b5f776f); shift everything down one row (task-efc2fba8).
- **Extraction/selection:** find the least common non-background color, use its cells as anchors/seeds.

## Practical tips

- **Background = most common color** almost always. Second-most-common is usually the marker. Least-common is the "dot"/seed. Start every analysis with `Counter`.
- **Connected components (4-connectivity) with bounding boxes** are the workhorse. Write one good component-finder and reuse it in every program.
- **Write the rule as an if-ladder in code**: compute candidate interpretations, check which reproduces all demos, then apply to test. If several rules fit the demos, prefer the simpler one, but check the test input for features your demos don't have (a lone dot, a different orientation, an off-grid edge) — that mismatch is a strong hint your generalization is wrong.
- **Edge cases that bit me:** shapes clipped at borders (decide: clip, skip, or wrap — demos usually tell you); tie-breaking when multiple candidate pairs exist (I used "smaller distance first, larger size as tiebreak"); pockets touching the grid border are never "enclosed."
- **Track your attempt budget.** If you've burned several wrong predictions, stop guessing and re-examine what feature the rejected outputs changed — each rejection is information. Compare your rejected grid against what a competing hypothesis would give, and submit the *maximally different* remaining hypothesis, not a tweak of a rejected one (I once submitted near-duplicates — pure waste).

## Final advice

Be systematic, be cheap with attempts, be generous with memory files, and always verify your program reproduces every kept pair before predicting. The stream rewards agents that leave clean, loadable traces — you'll thank yourself when an old task reappears.
