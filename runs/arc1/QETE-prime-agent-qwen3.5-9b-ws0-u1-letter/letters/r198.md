**Workflow that worked for me**

1. Look at the input. Ask: is it a grid of mostly one background color with scattered marks? Is it tiled by separator lines? Does it look like geometry (rectangles, lines, diagonals) or like a puzzle (patterns to copy, shifts to apply)?
2. If you have kept demo pairs, verify your hypothesis against ALL of them before submitting. Write the program, run it on the pairs, count mismatches. Every wrong submission on an unknown task burns an attempt; on some tasks the cap is low and a wrong guess means the task is lost forever (I lost task-5997d753 that way — 8 wrong attempts, then the final prediction was also wrong).
3. If your rule reproduces all kept pairs but you're unsure about an edge case in the test input (a lone dot, a shape touching the border), spend a demo request rather than guessing. Demos are cheap; wrong submissions are not.

**Rules I've seen repeatedly — check these first**

- **Fill enclosed pockets.** Background regions not touching the grid border get recolored (task-3f4fb1a9: fill with 4; only rectangular pockets, and sometimes extend one row below a 2-tall pocket). Background = most common color, always.
- **Stamping / tiling.** Find the largest non-background component; stamp its bounding box at every other non-background cell (task-1b7868f1). Or: find the region whose block deviates from a repeating pattern and tile that block across all regions (task-8d84fe63, task-770f2daf — rarest color's pattern stamped into every matching all-background box).
- **Diagonal extension.** Runs of length ≥2 along a diagonal or antidiagonal extend in both directions until blocked (task-3b5f776f). Same idea appears orthogonally.
- **Row/col between markers.** Cells strictly between the first and last occurrence of the rarest color in each row and column get filled with a fill color (task-5c839a47). Watch out: a test with a *single* dot breaks this — I burned 8 attempts on that and never resolved it. If the test has a degenerate count, request demos immediately.
- **Separator lines / mosaic.** Full uniform rows/columns split the grid. Variants: output block = 1 if odd/even count of stray marks inside (task-48898d06: I used "≥2", another version "odd"); output = intersection of row-guide and column-guide colors (task-bb30ebc2); split into two halves A,B and mark where A==B (task-026adbf3, task-707635df: 2 where both halves have their own dominant color).
- **Recolor by geometry.** Rectangular rings of size ≥3 fill their interior with a color depending on parity of area (task-aa5a69a0: 2 if even, 7 if odd). Components of size ≥3 become solid rectangles, everything else deleted (task-b62da9e0). Uniform rows/columns → all 2 (task-47ed202e).
- **Minority/majority color mapping.** Two-color grids: keep the majority color everywhere, minority becomes 0 (task-2264bd4e — trivially simple once spotted).
- **Scale down by 3.** 3×3 blocks → 1 cell: mode of the block ignoring the noise color (task-67dd046a).
- **Pattern completion.** An object shifted cyclically per band; find the offset by best match and extend (task-5997d753: fill clipped band with 1s where the reference band's pattern, best-shift aligned, extends past it).
- **Shift everything down one row** (task-efc2fba8). **Move object to touch a line, draw a marker line on the far side** (task-77262100). **Complete broken straight lines and draw the bounding-box border in a new color** (task-8625f9bc). **Arrow/angle singletons as selectors**: a singleton L-shape picks which of two identical twins gets recolored, by distance (task-0f6e5a2f).
- **Symmetry construction.** Output = reversed+concatenated rows, stacked three deep (task-73499f5a); output = 2×2 tiling of the input and its rotations (task-794e60f6). **Periodic diagonal coloring** from partial anti-diagonal hints (task-2e29965a).

**Coding habits that saved me**

- Write a `transform(grid)` that takes a list of lists of ints and returns the same. Keep a generic connected-components helper (4- or 8-connectivity — check which the task needs; diagonal-contact marks usually want 8).
- Find background with `Counter(...).most_common(1)[0][0]`. Find the rarest non-background the same way with `most_common()[-1]`.
- Test edge cases mentally: what if the pattern touches the border? What if there's only one instance of the selector? What if the fill would run off-grid? Clamp all writes with `0 <= r < H` checks — an IndexError is a wasted attempt just like a wrong answer.
- When reproducing demo pairs, print the diff (row, expected, got) rather than just a boolean. The first differing cell usually tells you which half of the rule is wrong.
- Beware counting duplicates: I once submitted the same wrong candidate twice because two "different" hypotheses produced identical outputs. If two candidate rules give the same output on the test input, they're one candidate — enumerate something genuinely different next (my notes for task-1b7868f1 list "clean anchors and a +0→1 shift untried" for exactly this reason).

**On staying alive**

- Wrong-attempt caps are real. If a task goes bad, write down what you tried and what's left untried in a `_failed.json` note — it's cheap insurance and it stops you looping.
- Contamination warning: once, labels in a demo response looked like cross-task hints ("Demo pair" from a different task). My own note says: recovered cross-task labels are contamination; trust only pairs that actually belong to the current task id.
- When the rule reproduces demos but the test prediction is rejected twice, don't keep patching the same family of rules. Step back and ask what *structure* of the input you're ignoring — usually it's a second object, a size relation, or a positional tiebreak (nearest, farthest, clamped index).

You are smaller than I am, so be disciplined: fewer, better-verified hypotheses beat many quick guesses. Verify before submitting, spend demos when uncertain, and reuse my saved programs whenever the task id matches.
