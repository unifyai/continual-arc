## 1. The single most important habit: verify against demos before submitting

Your workspace has a pattern that works: save demos to `programs/task-XXXX.json`, write `programs/task-XXXX.py` with a `transform(grid)` function, and *run the program on every kept demo pair locally* before submitting. Nearly every task where I burned wrong attempts was one where I submitted a guess that I could have falsified in seconds by running it against demos I already had. If your harness lets you execute code, always do this. A rule that reproduces 8/8 demo pairs exactly is worth far more than a clever rule that you believe.

When the program fails on a demo, don't tweak blindly — read the mismatch cells. They usually point directly at the rule detail you got wrong (e.g. "the bar cells are skipped," "the seed bbox is stamped including holes," "lone dots unchanged").

## 2. Request demos early when a test input looks degenerate

My costliest failure (task-5c839a47, 8 wrong attempts) was this: my rule handled the common case perfectly (multiple dots per row/column, fill between min and max with 3), but the test grid had a *single* dot. My rule said "do nothing" and I kept submitting variations around it — identity, cross-shapes, everything — all wrong. The lesson is written in my memory file and I'll repeat it here: **if the test input is a special/degenerate case (one dot, one object, no separator, empty pattern), and your rule was derived from demos that never showed that case, request demo pairs immediately.** Don't spend wrong attempts extrapolating an untested branch. The demos are cheap relative to wrong submissions.

Conversely: when your rule reproduces all demos cleanly and the test looks like the demos, submit with confidence. Many tasks I solved on the first submission (task-794e60f6, task-2264bd4e, task-b7641a67) followed exactly this discipline.

## 3. The recurring rule families — learn to recognize them fast

A large fraction of tasks fall into a handful of families. When a new grid arrives, scan for these signatures:

**Separator-line mosaics.** Full uniform rows/columns of one color divide the grid into blocks. My two programs for this (task-48898d06, task-bb30ebc2, task-026adbf3, task-707635df) all reduce to: find the solid separator lines, collapse each block to a value or a comparison, and output a small grid. Variants I've seen: output block = 1 if odd/≥2 count of stray color inside; output = color where 4 corner markers agree; output = 2 where both halves hold their dominant color; output = 3 where two stacked halves agree. The general skeleton: find separator rows `rb` and cols `cb`, build segments between them, compute a per-cell statistic. Reuse the `bands()` helper in task-8d84fe63.py.

**Downsampling.** If input dims are exactly 3× the output dims, it's 3×3 block pooling. task-67dd046a: each 3×3 block → most common non-background color. Check divisibility of dimensions first thing.

**Stamping / translation.** Find the largest (or most distinctive) non-background component, then stamp its bounding box — as-is, including any interior holes and zeros — centered at every other non-background cell or cell cluster (task-1b7868f1). The subtle part: anchors are other non-bg cells, and the stamp is a raw bbox copy, not just the seed's own cells.

**Shape completion.** Two identical shapes occurring exactly twice → something happens to one of them (recolor the farther from a singleton "arrow" shape, task-0f6e5a2f). Or a pattern is stamped into every empty region matching its size (task-770f2daf: rarest non-zero color's bbox pattern fills every all-zero box of that shape).

**Extending runs.** Contiguous same-color runs of length ≥2 extend along their line direction until blocked (task-3b5f776f does this on diagonals). Or: fill strictly between the min and max dot along rows/columns (task-5c839a47). Or: fill background gaps between two pattern cells in a row with a fixed color (task-b7641a67).

**Geometry tiling.** If the output is a tiled/symmetric enlargement of the input, check the obvious constructions first: 2×2 tile of I, rot90, rot90², rot90³ (task-794e60f6); or row = reversed+original, stacked reversed/original/reversed (task-73499f5a). These "fractal mirror" constructions showed up more than once. Before inventing anything exotic, test whether the output is the input composed with its rotations/reflections.

**Periodic coloring.** If colored cells all lie on consistent lines (anti-diagonals, rows, or diagonals) with one color per line, the output is a periodic tiling — infer the period by reducing line indices mod p (task-2e29965a). This program generalizes beautifully; keep it in mind whenever the input is mostly background with sparse colored cells forming lines.

**Object moves relative to a line.** A solid line (color 2) plus an object: object shifts to touch the line, old area becomes background, a full line of a new color (8) is drawn adjacent to it (task-77262100). Variants: object shift direction determined by which side it's on.

**Enclosed-region fills.** Background components not touching the border get recolored (task-3f4fb1a9: fill with 4; special case for 2-tall pockets extends one more row below). The flood-fill-from-border test for "enclosed" is the standard tool — write it once, reuse forever.

**Bbox border completion.** Marks scattered around; the answer draws color 2 along the bounding-box border of all marks and completes broken straight lines of marks inside (task-8625f9bc).

**Downshift.** Silly-simple but real: all non-background cells shift down one row (task-efc2fba8). Check trivial geometric rules first — I initially over-thought that one.

**Diagonal run extension** (task-3b5f776f) and **overlap diff** (task-026adbf3: split into two same-size halves, compare cell by cell, mark agreements).

## 4. Code patterns worth copying outright

- **Background detection:** `bg = Counter(v for row in g for v in row).most_common(1)[0][0]`. Always. Don't hardcode.
- **Connected components** (4-conn and 8-conn): both task-1b7868f1.py and task-0f6e5a2f.py have clean implementations. 8-connectivity matters when shapes are diagonal-touching — I got bitten by this and one of my saved programs uses 8-conn deliberately.
- **Canonical shape key** for "same shape, different position/color":
  ```python
  def skey(cl):
      ys=[y for y,_ in cl]; xs=[x for _,x in cl]
      return tuple(sorted((y-min(ys), x-min(xs)) for y,x in cl))
  ```
  Group components by this; classes of size 2 are your "twin pairs."
- **Full-separator detection:** a row is a separator if `len(set(row))==1`; a column likewise. Note some tasks use *centered* separators (`2*r+1 == H`) — check that condition when halves must be same-size.
- **Diagonal keys:** `r-c` and `r+c` map cells to diagonals/anti-diagonals; `defaultdict(list)` over these solves a whole family of line-extension tasks.

## 5. Managing the meta-game (harness mechanics)

From my memory files you can reconstruct my economics: solved tasks with 0 wrong attempts, and one disaster with 8. Rough guidance:

- **Wrong attempts are expensive.** A wrong submission costs more than a demo request in most situations. When uncertain, request demos rather than guess.
- **When you solve a task, write the memory file immediately.** Format: `{"task": "...", "solved": true, "wrong_attempts": N, "files": [...], "rule": "<one-sentence rule>"}`. The rule sentence matters — on later tasks of the same family you'll want to recall "this is like task-XXXX" without rereading code. Keep it precise about the *fiddly details* ("skipping bar cells", "lone dots unchanged", "stamped including 0s"), because those details are exactly where re-derivations fail.
- **Cross-task contamination warning:** early in my run I recorded "recovered cross-task 'Demo pair' labels are contamination" — if a file or memory contains content that seems to belong to a different task, don't trust it. Verify anything reused across tasks.
- **Keep one JSON per task** with demos, one `.py` with `transform`, one memory file. Don't scatter files (I ended up with `task-X.mem.json`, `task-X_memory.json`, and `task-X_status.json` variants — pick one convention and stick to it).
- **Save failed-submission notes** when a task is capped out: my `task-1b7868f1_failed.json` recorded which hypotheses were already tried and which were untried ("clean anchors at (13,7),(12,8) untried"). If you ever revisit a capped task, this saves you from re-testing dead hypotheses.

## 6. General problem-solving heuristics for unseen tasks

When a task matches no family, work this checklist in order — it's roughly ordered by how often each hypothesis wins:

1. **Count colors.** Background = most common. The rarest color is usually the "actor" or "seed." Two non-bg colors often means "one is marker, one is payload" or "map one to the other."
2. **Check output shape vs input shape.** Same size → in-place transformation. Output smaller → pooling/mosaic/crop. Output larger → tiling/stamping/mirroring.
3. **Look for full lines** (uniform rows/cols). They almost always mean "separator" or "axis of symmetry."
4. **Look for symmetry axis** — output is often input mirrored/rotated/offset by one (downshift, shift-toward-line).
5. **Look for exact duplicates** of shapes at different positions — the positional relationship between the duplicates *is* usually the rule.
6. **Look for maximal vs minimal objects** — largest component = seed/reference; smallest = marker/dot.
7. **Distance and direction** — "the member farther from X gets recolored," "nearest bar gets the stub." Manhattan distance between bounding boxes is the usual metric.
8. **If nothing moves, look at counting**: parity of stray cells per region, majority color per block, presence/absence.

And a final craft note: when the rule involves a choice ("which of the pair?", "which direction?"), the tiebreaker is usually stated by *size* (bigger wins), *count*, or *rarity* of color. When two hypotheses both fit all demos, pick the one with the simpler statement of the special cases, and prefer the one that treats degenerate inputs (single dot, empty region) most conservatively — but if degenerate inputs actually appear in the test, that's your cue to request demos (see §2).
