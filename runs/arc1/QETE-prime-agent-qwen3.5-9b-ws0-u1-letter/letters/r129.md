## The big picture

In this harness you get a task, some demonstration pairs (which grow as you request more), and eventually a test input you must predict. You can save files (programs, example JSONs, memory notes) under `.../workspace/programs/` and memory files under `.../workspace/`. The most valuable thing you can do is **keep accurate memory files**: a JSON of kept demo pairs, a `transform(grid)` Python program that reproduces every kept pair, and a short memory note stating the rule in one or two sentences. If your program reproduces all kept pairs, your test prediction is far more likely to be right — and if it's wrong, you'll know exactly which assumption broke.

## How to actually find the rule

Go through candidate rules in a rough order of likelihood. Most ARC tasks in this stream are one of these:

1. **Geometric transformations**: shift everything down/right by one; tile the grid (input becomes a 2x2 tiling of itself with rotations: TL=original, TR=rot90 CW, BL=rot90 CCW, BR=rot180); mirror each row and append; stack reversed+original+reversed; tile a 1D sequence.
2. **Color-cycling / pattern completion**: the grid contains a diagonal or row-based repeating pattern of colors with period L (number of distinct colors); fill every cell with `pattern[(r+c) % L]` or `pattern[r % num_colored_rows]`. Check periodicity on the colored cells first — if every nonzero cell in a task fits `key(r,c) % L` with a consistent color map, that IS the rule.
3. **Background + objects + one fill color**: find the most common color (background), find the rarest or second color, and ask what role each plays. Filling happens a lot: fill enclosed background pockets with 4; fill bounding boxes of components ≥3 cells with their own color; fill between two identical markers with 2; fill hollow rectangle interiors with 2 (even area) or 7 (odd area).
4. **Stamping/copying**: largest component is a seed; stamp its bounding box at every other non-background cell (centered on the anchor); or stamp a rare-colored shape at every offset where its cells all land on zeros; or copy one block's pattern into all blocks of a partitioned grid.
5. **Grid partition / compression**: the grid is divided by full solid separator rows/columns into blocks; the output is a much smaller grid summarizing each block (e.g. 1 if a stray color appears in the block, else background; or the corner-based color; or the mode of a 3x3 downsample ignoring color 5).
6. **Line/arrow dynamics**: an object slides until it touches a line, and a new full line of a different color is drawn just beyond it; or bars and dots — draw perpendicular lines from bars through dots.

## Concrete habits that pay off

- **Write the checker first.** Before submitting anything, run your `transform` on every kept pair and assert equality. A program that reproduces all kept demos is your only real evidence. If it fails on even one, don't submit.
- **Always compute the background as the most common color**, and treat "rarest color" or "second most common" carefully — sometimes it's the marker, sometimes it's the seed. Use `Counter(...).most_common()`.
- **Bounding boxes are everywhere.** Learn to compute them instantly: min/max of component rows and columns. Many rules are "fill the bbox", "stamp the bbox", "the bbox perimeter".
- **Connected components**: write one solid 4-connectivity flood fill (BFS with a deque) and reuse it in every task. Sometimes 8-connectivity is needed (I hit this once — check both if 4-conn components look wrong).
- **Rectangularity check**: a component fills its bbox iff `len(comp) == (r1-r0+1)*(c1-c0+1)`. This distinguishes "solid pockets" from "L-shaped or with stems" — which matters, because some rules only fill solid rectangles.
- **When two same-shape objects exist, compare them**: which is closer to a special object, which is larger, which pair is a translation twin. Distance from a candidate to an "arrow" anchor (min Manhattan distance between cell sets) decided a whole task for me.
- **Diagonal periodicity trick**: for tasks full of single-colored diagonal lines on zeros, try both `r+c` and `r-c` mod L with the map derived from colored cells only. If it's consistent, fill everything.
- **Separators**: full uniform rows or columns split the grid. Both halves are usually the same size, and the rule is often a cellwise comparison (equal → 3, else shared mode) or an AND of nonzero masks.

## Traps I fell into (learn from them)

- **Overfit rules to demos, then the test breaks them.** I once spent 8 wrong attempts on a task where my program reproduced all 6 demo pairs but my test prediction was wrong — the real rule involved a detail (an offset) I'd guessed. When your program reproduces demos but the test feels uncertain, prefer the *simplest* rule consistent with demos, not the most elaborate. Complexity that demos don't force is usually wrong.
- **Duplicate submissions count.** Two of my submissions to one task were identical — wasted attempts. Always diff against what you already submitted.
- **A note file with failed hypotheses is gold.** I kept a `..._failed.json` listing every wrong grid and a note like "clean anchors (13,7),(12,8) untried". When attempts are limited, knowing what you've already tried prevents repeats and points at the remaining hypothesis space (e.g., shifting an anchor by one, or treating 0 as 1 in the seed).
- **Don't forget edge handling**: rules often behave differently at grid borders (components touching the border vs. enclosed). Always track whether a component touches row 0/last or col 0/last.
- **Beware near-miss pattern detection**: "background cell strictly between two markers in its row OR column becomes 3" — the OR across both axes mattered. Test row-rule, column-rule, and both.

## Small technical details

- Save demos as JSON like `[{"input": [[...]], "output": [[...]]}]` in `programs/task-XXXX.json`, and the program as `programs/task-XXXX.py` with a top-level `def transform(grid)` taking a list of lists of ints and returning the same. The memory note (e.g., `task-XXXX.mem.json` or a `memory_task-XXXX.json`) should carry the one-sentence rule — future-you (and graders) read it first.
- When a rule is color-specific (2, 3, 4, 7, 8), hardcode it — the harness tasks use consistent fill colors — but derive colors from the input where you can (e.g., `fill = most_common != background`).
- Use `zip(*g[::-1])` for rotate; `r[::-1]+r` for mirrored doubling; `deque` for BFS.
- Test on tiny synthetic cases too: a 2x2 pocket, a pocket at the border, a component of size exactly 3. Off-by-one errors live at edges.

## Priority order when unsure

1. Geometric (shift/tiling/mirror) — cheapest to test.
2. Periodicity/diagonal fill.
3. Background-pocket or bbox fill with the constant 4 (or 2/7 for parity).
4. Stamp/copy from a seed.
5. Anything with two objects interacting (slide toward line, compare twins).

Write the program, run it against all kept pairs, submit only on a full match, and write the memory file *immediately* — even for tasks you fail, record what was tried. The next task often rhymes with a previous one, and your own notes are the best training data you'll have.

Good luck. Be systematic, be skeptical of your first hypothesis, and never submit without the checker passing.
