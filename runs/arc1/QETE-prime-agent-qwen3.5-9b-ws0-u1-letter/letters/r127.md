## The harness, concretely

- You write a Python file `programs/task-<id>.py` with a function `transform(grid)` (grid = list of lists of ints), plus `programs/task-<id>.json` holding the demo pairs you've been given. The harness checks your program against those pairs and then asks you to predict the test output.
- You can request more demos (costly) and you have a limited number of submission attempts. Wrong final submissions are capped — I burned out completely on task-5997d753 (8 wrong attempts, 3 demo requests) and got nothing. Do not guess at a test. Only submit a prediction when your rule is certain or nearly so; if uncertain, prefer a conservative, simple prediction that follows the dominant pattern rather than an exotic extrapolation.
- Write a memory file like `programs/task-<id>.mem.json` (or memory under the harness state) recording the task id, file paths, pair count, whether the program reproduces all kept pairs, and the rule in one sentence. I re-derived rules I'd already solved because I skipped this. Do it for every task, solved or not.
- `cand*.json` / `cand_*.json` files are candidate grids for a task in progress — use scratch files like this; they cost nothing.

## The verification loop that saved me

Always: (1) write `transform`, (2) run it on every kept demo pair and assert equality, (3) only then submit. Never submit a program that doesn't reproduce the demos, and never submit a test prediction produced by a rule that merely "seems" consistent. When two rules both fit the demos, pick the one that's simpler and that also predicts the *demos'* non-obvious details (color of fills, where fills stop).

## General technique, for tasks you've never seen

1. **Identify bg** = most common color; identify the rare "marker" colors. Most rules are phrased over bg vs. non-bg.
2. **Connectivity**: write one solid 4-connected component finder and reuse it (I have versions in several files — task-b62da9e0.py's is compact). Sometimes 8-connectivity is right (task-3b5f776f) — test both if unsure.
3. **Structural scans to run early**: full uniform rows/cols (separators), all-zero rows/cols, rows that are identical to each other, repeated shapes (key shapes by their sorted normalized cell tuples to find translation twins), counts of each color.
4. **Counting/aggregation outputs**: when the output is much smaller than the input, it's usually a per-block statistic (task-48898d06: parity of stray count; task-67dd046a: mode; task-707635df: mask AND). When output is same-size, it's usually a recolor/fill/shift. When output is larger, it's tiling/symmetry.
5. **Numeric outputs 2/3/4/1** are the common "fill/marker" colors in these tasks; the rare existing colors are usually the actors.
6. **When the rule is ambiguous**, generate your candidate output, then re-derive the rule from your candidate and check it doesn't contradict any demo detail (exact colors, exact positions, edge cells). A rule that explains 95% of cells is usually wrong about the 5% that matters.
7. **Keep code defensive**: return the input unchanged (not an exception) when no pattern matches, so a partial rule still scores the cells it gets right.
8. **Spend demos wisely**: one extra demo pair is worth more than three wrong submissions. If after reproducing all demos two very different rules both fit, that's exactly when to request a demo.

The single biggest factor in my success rate was discipline: reproduce demos before every submission, and write the memory file before moving on. The second biggest was having a library of component/block/symmetry utilities I could adapt in minutes instead of rewriting under pressure.

Good luck — the patterns repeat more than you'd expect.
