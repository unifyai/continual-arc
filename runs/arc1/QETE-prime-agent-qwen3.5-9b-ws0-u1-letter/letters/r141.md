## 1. The workflow that works

For each new task:

1. **Read the demo pairs carefully.** Count the colors, find the background (most common color), and locate every object.
2. **Guess a rule, then write a `transform(grid)` function and verify it reproduces every kept pair before submitting anything.** Verify programmatically — run the program on the demo inputs and compare outputs cell by cell.
3. **When writing predicted grids by hand (typing digits into JSON), always verify the JSON you built matches your program's output.** This is my single most expensive lesson: I failed two submissions of task-3b5f776f purely because of transcription typos — rows shifted by one column. The rule was right both times. Run the check, every time.

## 2. Rule families I've seen repeatedly in this stream

Knowing these families will speed up recognition:

- **Fills with color 4**: enclosed background pockets get filled with 4. If the pocket is a solid rectangle, fill it; sometimes a 2-row pocket also absorbs its bottom wall row if the row below is background (task-3f4fb1a9). Non-rectangular pockets are left alone.
- **Bounding boxes**: each component of size ≥ 3 gets its bounding box filled with its color; everything else becomes background (task-b62da9e0).
- **Stamping / translation**: the largest non-background component is a "seed"; every other non-background cell is an anchor, and the seed's bounding box is stamped centered on each anchor (task-1b7868f1). Variant: stamp the rare-color shape at every offset where all its cells are background (task-770f2daf).
- **Lines and separators**: a full uniform row/column is a separator. Grids get split into blocks; outputs summarize each block (count stray cells, odd→1; or block-comparison: 3 where A==B else common color, task-026adbf3, task-48898d06).
- **Mirror-and-tile**: row becomes reverse+itself, output stacks reversed/original/reversed (task-73499f5a); or 2n×2n quadrant constructions TL/TR/BL/BR with rotations (task-794e60f6).
- **Repeat-the-pattern**: the block with the most non-background cells is the template; copy it into every block position (task-8d84fe63).
- **Between-dots fills**: fill 3 strictly between min and max positions of the least common color per row and per column (task-5c839a47).
- **Slide-to-line**: object moves until adjacent to a solid 2-line; a full 8-line is drawn on its far side (task-77262100).
- **Recolor by role**: exactly two same-shape components exist in translation-twins; one is recolored to match a distinguished object (task-0f6e5a2f). Or simplest of all: two colors only — keep the higher, zero the lower (task-2264bd4e).
- **Marker connectivity**: background gaps of size ≤2 between markers on a row/column, plus the marker bounding box perimeter, get filled with 2 (task-8625f9bc).
- **Diagonal run extension**: same-color runs of length ≥2 extend along their diagonal until blocked (task-3b5f776f).
- **One-cell shifts**: all non-background cells shift down one row (task-efc2fba8).
- **Downsampling**: 3×3 blocks → most common non-5 color per block (task-67dd046a); separator-line grids → one cell per block (task-48898d06).
- **Periodic-diagonal detection**: if along some diagonal family each line has exactly one color, the output tiles the whole grid with the period (task-2e29965a).

## 3. Hard-won lessons

- **Unusual shapes demand unusual rules.** If the demo shapes don't match any family, don't force one. Look at what's unique: the *least common color*, the *largest component*, the *only rectangle*, the *component whose color appears in exactly two components*. In this stream the distinguished object is often identified by extremal statistics (size, rarity, shape class like "L with arms ≥3", solid-line detection).
- **The lone-object case is different.** In task-5c839a47 I learned the rule perfectly on multi-dot demos, then burned 8 wrong attempts on a test with a single dot. My memory note says: *if a test has a single dot, request demos early*. More generally: if your rule has a degenerate case (one object, zero objects, off-grid) that the demos never exercised, that case is exactly where the test will live. Think hard about what the rule means there, and don't be afraid to use demo requests to disambiguate — a wrong submission is permanent, a demo request is cheap.
- **Component identification**: use 4-connectivity for same-color components, 8-connectivity when colors of a multi-color sprite must stay glued (task-1b7868f1 uses 8-conn over non-background). Pick deliberately.
- **Count cells, then check exact rectangles**: `len(comp) == (r1-r0+1)*(c1-c0+1)` distinguishes solid rectangles from L-shapes — that single check saved task-3f4fb1a9.
- **Most-common-color = background** is almost always right, but not always (task-707635df splits halves and takes each half's dominant nonzero). When something seems off, question which color is background.
- **When a test input looks like an earlier solved task's rule, reuse that program.** Several of my successes were exactly that: recognize the family, adapt, verify against kept demos, submit.
- **If a submission fails, don't resubmit a near-duplicate of the same idea.** Record what was tried (see my task-1b7868f1_failed.json note format) and change a structural hypothesis, not a parameter. That failed file also shows the value of writing notes to yourself about *untried* variants — clean anchors, off-by-one shifts — so future-you doesn't re-tread.

## 4. Practical coding advice

- Write small helpers you'll reuse: `components(g, color, conn)`, background via `Counter(...).most_common(1)[0][0]`, bbox, canonical shape key `tuple(sorted((y-min_y, x-min_x) ...))` for shape comparison under translation.
- Use `skey` canonicalization plus grouping to find translation-twins — it generalizes far better than ad-hoc position checks.
- Validate shapes: many rules only fire under conditions (all dots off distinct offsets, no overlap, fits in grid). Encode those as `continue` guards, not exceptions.
- Test inputs can be any size; never hardcode dimensions.

## 5. Mindset

Every demo pair is a constraint; a rule that reproduces all pairs is *probably* right but the test is the judge. Prefer the simplest rule consistent with all pairs — but check degenerate cases first. And above all: **never submit a grid you didn't generate from a program and diff against your own output.**
