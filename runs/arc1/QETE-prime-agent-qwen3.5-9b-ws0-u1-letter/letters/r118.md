## 1. The shape of the harness, in brief

You'll get a stream of tasks. For each one you'll typically have some demonstration pairs (input → output), sometimes a test input you must predict, and a limited budget of wrong submissions before a task is locked out (I lost task-5997d753 to the attempt cap after 8 wrong attempts — don't be me). You have a workspace at `.../workspace/programs/` and a memory system at the harness level. Use both aggressively.

**The single most important discipline: never submit a prediction you haven't verified.** Write the rule as a Python program (`transform(grid)`), run it on every kept demo pair, and confirm it reproduces them exactly. If it reproduces all demos, your chance of matching the true rule is dramatically higher than if you just eyeball a pattern. Every task I solved, I solved this way: rule → program → verify against all pairs → only then predict the test.

## 2. The core workflow I used

1. **Read every demo pair carefully.** Grid dimensions, which colors appear, what changed and — crucially — what *didn't* change. Outputs are usually identical to inputs except in a small region. Diff them cell by cell.
2. **Identify the background color.** It's almost always the most common color. Almost every rule is phrased relative to the background: which cells are "objects" (non-bg), which bg cells get recolored, where objects move relative to lines.
3. **Identify the objects.** Connected components (usually 4-connectivity; occasionally 8 — try both if 4 fails). Get bounding boxes, sizes, colors, counts.
4. **Formulate a rule in words first.** Say it out loud: "background cells strictly between two dots in their row/column become 3" or "each object slides to touch the 2-line and an 8-line is drawn on its far side."
5. **Write it as a program.** Make the program derive *everything* from the grid — background color by `Counter().most_common(1)`, marker color as second most common, object components by flood fill. Do **not** hardcode colors or coordinates if you can avoid it; tasks vary them, and a hardcoded rule fails silently.
6. **Verify on all kept pairs.** If even one fails, the rule is wrong or incomplete. A rule that fits all demos but is "a coincidence" is far rarer than a rule that fails a demo.
7. **Save the program and a JSON of the pairs** under `programs/task-<id>.py` and `.json`, and write a memory entry with the rule in one sentence. Future-you (and your memory retrieval) will thank you.

## 3. A catalogue of rules I actually saw

ARC recycles *families* of rules. Here are the ones from my run, grouped — when you see a new task, scan this list mentally.

**Geometric tiling / symmetry:**
- Output = 2×2 block of the input and its rotations: `np.block([[I, rot90(I,-1)],[rot90(I), rot90(I,2)]])` (task-794e60f6).
- Each row becomes `reverse(row)+row`, and the stack is `reversed(rows)+rows+reversed(rows)` — triple height, double width (task-73499f5a).
- A 1D sequence tiled/mirrored; check both `r+c` and `r-c` diagonals with period = number of colors (task-2e29965a: colored cells sit on diagonals; fill the whole grid by `P[(r±c) mod L]`).
- Stamp a rare-color shape at every offset where all its cells currently equal the background (task-770f2daf).
- Largest non-bg component is a "seed"; stamp its bounding box, translated so the seed's center lands on each other non-bg cell (task-1b7868f1).

**Counting / downsampling:**
- Divide grid into blocks separated by full uniform separator rows/columns; each output cell is a statistic of its block (odd/even count of stray color → 1 or bg; most common non-separator color; count ≥ 2). Task-48898d06 and task-67dd046a (3×3 downscale, mode per block ignoring one distractor color).

**Intersection / comparison of two halves:**
- Split grid on a full solid separator row or column into two same-size blocks A and B. Output = cellwise combination: AND of nonzero masks (recolor to 2), or `3 where A==B else the shared bg` (task-707635df, task-026adbf3). The separator row/col itself is discarded; find it by scanning for rows/columns of a single uniform color that isn't the region color.

**Region detection:**
- Enclosed rectangular pockets of background → fill with a color (often 4); special-case: a 2-row pocket also absorbs its bottom wall when the row below is bg across the pocket width (task-3f4fb1a9).
- Hollow rectangles (perimeter of one color on bg): fill interior with 2 if the interior area is even, else 7 (task-aa5a69a0).
- Fill the bounding box of each non-bg component of size ≥ 3 with its color; everything else → bg (task-b62da9e0).
- Background cells strictly between two rare-color dots in their row OR column become 3 (task-5c839a47).
- Rows or columns that are entirely uniform become 2 (task-47ed202e); similarly, a bg cell flanked by identical non-bg neighbors in a row becomes 2 (task-b7641a67).
- Fill bg gaps of size ≤ 2 between marker cells along rows/columns, plus the bg perimeter of the markers' bounding box (task-8625f9bc).
- Color remapping by min/max: with exactly two colors a<b, map a→b and b→0 (task-2264bd4e). Note: majority/minority reasoning failed here; the *ordered pair* of colors was the key.

**Movement / lines:**
- Two parallel bars of one color + scattered dots of another: from the bar facing the dots, draw perpendicular lines through each dot (dot becomes 4); from the opposite bar, draw lines at the same offsets spanning the full gap in the dot color (task-d4079843).
- An object slides toward a full line of color 2 until adjacent, and a full line of color 8 is drawn just outside the object's far side (task-77262100).
- Pattern shifted down one row, top row becomes bg (task-efc2fba8).
- Single-neighbor (degree-1) cells of a small cluster extend diagonally away to the grid edge (task-3b5f776f).
- Among translation-twin shape pairs, the one farther from a distinguished "arrow" L-shape gets recolored to the arrow's color (task-0f6e5a2f).
- Grid → grayscale-style summarization of a noisy mask (task-026adbf3-style comparisons).

**Sub-grid extraction:**
- Blocks delimited by separator rows/cols; extract a mini-grid where each cell = corner color if all four corners match, else bg (task-bb30ebc2).

Notice the recurring scaffolding: **background color, connected components, bounding boxes, separators, most-common/least-common colors, translation twins, parity of counts.** When stuck, enumerate combinations of these primitives before inventing anything exotic.

## 4. Traps that cost me wrong submissions

- **Role-based vs. identity-based rules.** I assumed "minority color changes" when the real rule was "smaller number → bigger number." Always try the *value-based* interpretation (min/max, numeric ordering) alongside the *role-based* one (bg/fg, rare/common) and check which reproduces the demos.
- **Almost-right variants.** On one task I produced four candidate grids differing in tiny details (a 0 where a 5 belonged, an anchor at column 7 vs 8). I wasted the attempts. The fix: enumerate candidate variants *before* submitting, and if the harness lets you test, test; if not, pick the variant that's most consistent with the demos' internal logic, and prefer the variant that keeps more of the input unchanged (ARC outputs are usually minimal edits).
- **Special cases hiding in plain sight.** In task-3f4fb1a9, the rule had a bonus clause (2-row pockets absorbing their bottom wall) that only appeared in some demos. If one demo pair seems to need "just a little extra," that extra IS part of the rule — encode it explicitly with a condition, not as a fudge.
- **Overfitting to one demo.** With only 1–2 pairs, prefer the simplest rule that fits; but with 5+ pairs, a rule that misses even one is wrong. My successful memory entries all record "reproduces all kept pairs: N/N."
- **Don't trust a rule that leaves the test mostly unchanged unless the demos say so.** Some tasks genuinely output `input` almost unchanged (task-efc2fba8's demo output was input shifted by one row; one candidate literally was the input). Minimal edits are common, but "copy input" is usually NOT the answer — find the *small* systematic change.

## 5. General heuristics for unseen tasks

- **Count colors first.** 2 colors → likely remap or mask. 3 colors → likely bg + object + special. Many colors → likely one distinguished object (largest, or rarest, or the only non-rectangular one) plus copies of it.
- **Check output dimensions.** Same dims → in-place transformation. Double/triple dims → tiling/mirroring. Fractional dims → downsampling by blocks. Width 2× or 3× with same height → per-row mirror tricks.
- **Look for twins.** If the same shape appears exactly twice, one is usually a "source" and one a "target" (recolor, move, delete). Distinguish them by position relative to a landmark (a line, a unique shape, the grid edge).
- **Lines are powerful landmarks.** Full rows/columns of one color (especially 2, 6, 8) are almost always structural — separators, rails, targets.
- **Colors 0, 1, 2, 4 are "output" colors suspiciously often.** When a rule recolors something and you can't tell the target color from the demos, it's frequently 1, 2, 3, or 4. But never guess blindly — if demos show it, use it.
- **Parity and counting.** Odd/even counts, "exactly two occurrences," "size ≥ 3" — these threshold conditions appear constantly.
- **Diagonals.** If colored cells lie on diagonals, compute `r+c` and `r-c` residues; a consistent residue→color map with period L means fill the whole grid.

## 6. Pre-submission checklist

Before every submission:
1. Does my program reproduce **every** kept demo pair exactly?
2. Is everything derived (bg, marker, components) or justifiably hardcoded?
3. Did I try the value-based alternative to my role-based rule?
4. Did I diff my predicted test output against the test input and sanity-check the change is small and systematic?
5. Have I saved the program, the pairs JSON, and a one-sentence rule in memory?

## 7. A final word

You will see tasks I never saw. When that happens, fall back on the primitives: components, bboxes, counts, separators, symmetry, translation, parity. Describe the transformation as a sentence a child could follow, then translate the sentence to code mechanically. If your program reproduces all demos, submit with confidence. If it doesn't, don't submit a hopeful variant — fix the rule or enumerate variants and choose by evidence.
