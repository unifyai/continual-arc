## The harness loop, in practice

You will get a task. You can inspect grids, write a program (`transform(grid)` in a `.py` file), save demo pairs to a `.json` file, and submit a test prediction. The single most valuable habit: **before submitting, run your program on every kept demo pair and verify it reproduces them exactly.** Almost every wrong submission I made was a rule that fit my intuition but not the demos. If your program doesn't reproduce all kept pairs, don't submit — fix the rule or request more demos.

Save your work: a `task-XXXX.json` with the demo pairs and a `task-XXXX.py` with the program. If you solve the test, write a short memory file with the rule in words. Future-you reads those; a one-line rule description is worth more than the code.

## Detecting the rule: a checklist

Most tasks here are one of a small family. When you see a grid, check these in rough order of frequency (based on the tasks I saw):

1. **Two stacked/adjacent copies of the same object with an offset.** Find the offset (try all shifts, count matches, take the best). Output = fill what's missing in one copy using the other. (task-5997d753, task-8d84fe63, task-707635df variants)
2. **A seed pattern stamped at anchor points.** Find the largest non-background component (the seed), find other small non-background cells or components (anchors), translate the seed so its center/anchor aligns. Stamp as-is, including background cells inside the bbox. (task-1b7868f1)
3. **Grid partitioned by full uniform separator rows/columns** into blocks; output is a small summary grid per block (parity of stray cells, corner-uniformity, mode color). (task-48898d06, task-bb30ebc2, task-67dd046a)
4. **Split into two halves by a centered separator**; compare cells positionally. (task-026adbf3, task-707635df)
5. **Lines/rays extended or filled.** Same-color runs extended along diagonals/antidiagonals until blocked (task-3b5f776f); background gaps of size ≤2 between markers filled (task-8625f9bc); dots connect via lines (task-d4079843).
6. **Counting/selection rules.** E.g. among translation-twin shape pairs, pick the one closest to a distinguished object and recolor it (task-0f6e5a2f). These need careful bookkeeping — write helper functions for connected components (4-conn and 8-conn; try both) and bounding boxes.
7. **Mirror/kaleidoscope constructions.** Input square → output 2n×2n with rotations; or rows reversed-and-doubled (task-794e60f6, task-73499f5a). Check output dims immediately — H×2W or 2H×W almost always means mirror/rotation composition.
8. **Simple recolors:** cells strictly between two markers of a rare color become a fill color (task-5c839a47); enclosed background regions become a fill color (task-3f4fb1a9); uniform rows/cols recolored (task-47ed202e); lower-of-two-colors mapped to background (task-2264bd4e).

The utility of checking output dimensions first cannot be overstated. Same dims → local recolor/fill rule. Double dims → mirror/rotation. Third/scaled dims → tiling or summarization.

## Programming discipline

Keep a mental (or literal) library of helpers:

```python
from collections import Counter, deque
def components(g, bg=None, conn=4): ...   # flood fill, return list of cell lists
def bbox(comp): ...
def canon(comp):  # sorted rel coords, for shape comparison
    ys=[y for y,x in comp]; xs=[x for y,x in comp]
    return tuple(sorted((y-min(ys), x-min(xs)) for y,x in comp))
```

Background is almost always the most common color (`Counter(v for r in g for v in r).most_common(1)[0][0]`). The "special" color is often the rarest, or the second most common.

When comparing shapes across the grid, use the canonical form above so translations don't fool you. When a rule says "closest to X", compute min Manhattan distance over all pairs of cells — that matched on task-0f6e5a2f where Chebyshev or center-distance didn't.

Be careful with tie-breaking. When multiple candidates fit the demos equally, prefer the simplest rule; if the test fails, try the next-simplest. Track what you've tried so you don't repeat (I kept a `_failed.json` noting untried variants — do this).

## When demos are few or ambiguous

If you have only 1–2 demo pairs, the rule is underdetermined. Before submitting a guess on a test with an unusual configuration (e.g. a lone marker, a single dot, a degenerate case), **request more demos if the harness allows it.** I burned 8 wrong attempts on task-5c839a47 because the test had a single dot and every extension of the multi-dot rule I tried was wrong. The lesson, which I wrote into memory: if the test input has a configuration never seen in demos, request demos early.

Conversely, when demos are consistent and your program reproduces all of them, trust it and submit — first-try correct submissions happened for me on task-77262100, task-8625f9bc, and others precisely because I verified against demos first.

## Common pitfalls I hit so you don't have to

- **Fill stamping includes interior background.** When translating a seed bbox, copy the whole bbox including background cells inside it, not just the non-background cells.
- **Cells on edges / touching borders matter.** "Enclosed" means the background component doesn't touch the grid border. Flood-fill from the border to find non-enclosed background quickly.
- **Gaps: "size ≤ 2" vs "any gap".** Check the demos to see whether small or all gaps are filled; both appeared in different tasks.
- **Directional asymmetry.** Some tasks shift everything down one row (top row becomes background); some move shapes to touch a line. Always ask: which direction, and what happens to vacated cells?
- **The 8-line/2-line style rules.** A distinguished full line (often a distinctive color like 2 or 8) acts as a magnet or reference. Objects move flush to it; a full line of another color is drawn at the object's old position.
- **Don't overfit to colors as literals where avoidable** — use bg/marker detection — but do note that fill colors are often fixed constants (2, 3, 4, 8) that appear in the demos. If demos always fill with 4, fill with 4.

## Verification workflow, concretely

1. Look at all demo pairs. Diff input vs output for each (write a tiny script if helpful): list exactly which cells changed and what they changed to.
2. State the rule in one sentence in words. If you can't, you don't have the rule yet.
3. Write `transform`. Run it on every demo input; assert equality with every demo output.
4. Only then predict the test.

Diffing is the highest-leverage step. Humans (and big models) see patterns in the whole grid; the diff shows you the actual transformation surface, which is usually tiny and local.

## A note on memory files

When you finish a task, write `memory_task-XXXX.json` with the rule in words and the file paths. When you start a task, if a memory file for it exists, read it and reuse the saved program directly — several of my tasks were repeat visits of the same underlying task ID, and reloading the saved program gave instant first-try solves (task-770f2daf, task-3f4fb1a9). Also keep the general lessons: e.g. "lone-dot/unusual-config test → request demos early."
