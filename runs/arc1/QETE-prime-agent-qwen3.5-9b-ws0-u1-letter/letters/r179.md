## The workflow that wins

The harness gives you a few tools: request demo pairs, submit a test prediction, save memory files. The single most valuable habit: **request demos early when a rule is ambiguous, and only submit once your program reproduces every kept demo pair.** Wrong submissions are expensive; demo requests are cheap. I burned 8 wrong attempts on one task because the test input had a degenerate case (a single dot) that my demos never covered — I should have requested more demos the moment I noticed the test was unlike any demo.

Structure of a good solve:

1. **Inventory the grids.** Most common color = background. Count colors, find objects (4-connected components of same color), find full rows/columns of a single color (separators).
2. **Compare input vs output cell-by-cell on demos.** Which cells changed? What colors changed? What shapes appear? The diff is the task.
3. **Write a hypothesis as a program, verify on ALL kept demos, only then predict the test.** If it fails one pair, don't guess a tweak — understand which pair and why.
4. **Save memory files with the rule stated in one or two sentences plus file paths.** Future-you (you, later in the stream) reads these; make them crisp. Include the failure modes too ("identity, cross, row-only all wrong"), not just the answer.

## Rule families that repeat (ARC's favorite shapes)

**Separators and blocks.** Full uniform rows/columns divide the grid into blocks. Many tasks reduce to one value per block: parity of stray cells, most-common color, whether two halves agree cell-by-cell, corner colors at guide intersections. Learn to extract separators first — it collapses huge grids to tiny ones. Tasks 48898d06, 026adbf3, 707635df, 8625f9bc, bb30ebc2, 67dd046a are all this family.

**Stamp / translate a motif.** Find the largest non-background component (the "seed"), find anchor cells, stamp the seed's bounding box — contents and all, including holes and zeros — translated so the seed's center (or the anchor itself) lines up. Careful: stamp the whole bbox as-is, not just the seed's colored cells. (task-1b7868f1, task-770f2daf: rarest color's bbox pattern stamped into every empty box of that size.)

**Extend lines / fill gaps.** Recurring: extend a run of length ≥2 along its own direction (row, column, diagonal r−c, antidiagonal r+c) until blocked; fill background gaps between markers in a row/column (usually gap size ≤ some small number, or always); shift shapes to sit flush against a separator line and mark their old position.

**Reflection/tiling symmetry.** Check: is the output a horizontal mirror, vertical mirror, or 180° rotation of the input tiled or combined? task-73499f5a: each row becomes reverse+row, and the block is stacked as reversed+original+reversed. task-794e60f6: quadrant concatenation with rotations. When output is 2× or 3× the input size, try "input plus its mirrors/rotations" first.

**Periodic color fields.** If the output is a periodic pattern (e.g. by anti-diagonal i+j with period p), infer p and the mapping from the input's colored cells, then fill everything. (task-2e29965a.)

**Threshold/size rules.** Cells or objects above/below a size threshold get treated differently: small components deleted, large ones kept or expanded (task-b62da9e0: keep components ≥3 cells as filled bounding-box rectangles, delete everything else). Check component sizes early — a lone dot vs a 5-cell blob often distinguishes signal from noise.

**Map one color to another.** Sometimes the whole rule is a recolor: lower color → 0, or "the farther twin of a duplicated shape gets recolored." Don't overcomplicate: with two colors, try swap/keep-higher/keep-lower on demos first.

## Heuristics I learned the hard way

- **Background is the most common color.** Almost always. But check for full uniform lines (color 2, 6, 4, 9 are common separator colors) before treating everything as scattered objects.
- **When output dims shrink**, think: summarization (one cell per block), deduplication, or "intersection/agreement of two halves." When output dims grow, think: tiling with symmetry, stamping, or expansion of runs.
- **The least-common color is usually the seed/key**, not the background. Gaps strictly between the min and max positions of the rarest color per row and per column are a very common fill pattern.
- **Degenerate inputs are the trap.** If the test grid has only one instance of the key object (one dot, one component) and your demos all had several, be suspicious. Try the simplest rule that handles both cases, or ask for demos. My 8-failure task was exactly this: the rule for a lone dot was something none of my guesses covered.
- **Exact-translation twins:** group components by canonical shape (sorted relative coords). Shapes appearing exactly twice are often a pair with one being transformed (recolored, moved, kept) based on distance to some anchor object.
- **Anchor = center of the seed's bounding box** works more often than anchor = seed's own centroid, because seeds are often asymmetric.
- **Bounding-box fill:** a component's bbox being fully "occupied" (hollow rectangle detection: len(comp) == 2*(h+w)−4) is a common special-shape test. Hollow rectangles often get their interior filled with a color chosen by an area-parity or position rule.
- **Enclosed background regions** (background components not touching the border) get filled with a specific color; components touching the border are left alone. Sometimes with an extra condition for narrow slots. (task-3f4fb1a9.)
- **Verify with code, not eyeballs.** Write the transform, run it on every demo, print mismatches. One mismatch means your rule is subtly wrong — often an edge case like gap size 1, gap size 0 (adjacent cells), or what happens at the grid border.
- **Keep the "note" field in your failed-attempt records.** I wrote things like "clean anchors (13,7),(12,8) untried" — reading my own notes saved me from re-deriving hypotheses. When a submission fails, immediately record: what hypothesis, what the diff between prediction and expectation might be, what's untried.

## Why your program is your memory

Don't just save the answer grid — save the *program* plus the demo pairs JSON plus a one-line rule. A program that reproduces all kept pairs is your best evidence the rule is right, and it makes the next instance of the same task a one-liner. Reuse saved programs directly: if a new task's grids look structurally like a saved one (check colors, separator layout, output-shape ratio), load that program, run it on the new demos, and see if it reproduces them before inventing anything.

## On the puzzles themselves

Don't fear big grids. Most of them are a tiny rule seen through a big lens: a 27×27 grid reducing to a 7×7 block summary, or a 20-row grid that's really one 3×3 motif stamped 6 times. Find the period, the separator, or the motif first, and the size stops mattering.

When you're stuck, enumerate the output's relationship to input dimensions: same size → local edit or recolor; smaller → summary; larger → symmetry/tiling/stamp. That trichotomy resolves half the search space in a minute.

And be honest in your memory files about what you don't know. My most useful notes are the ones that say "untried options were X and Y" or "test had a degenerate case, rule for it unknown." Future-you can't afford to rediscover a dead end.

Work methodically, verify before submitting, and spend demo requests freely — they are the cheapest currency you have.
