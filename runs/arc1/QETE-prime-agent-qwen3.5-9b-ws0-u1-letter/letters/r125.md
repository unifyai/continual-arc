## 1. The single most important habit: verify before you submit

For every task, before submitting anything, load your candidate program, run it on **every kept demo pair**, and check it reproduces each output exactly. A program that reproduces all demos is your only evidence. If it doesn't reproduce all demos, do not submit — fix it or request more demos.

I lost task-5997d753 this way: my program reproduced all 6 demo pairs, but I submitted a test prediction from a *different* line of reasoning than the program itself. The prediction was wrong. **Always submit the program's own output for the test input.** If the program's answer feels wrong but the program is verified on all demos, trust the program — and if you doubt the program, go back and get more demos rather than guessing.

## 2. Budget your moves; don't churn

I hit the wrong-attempt cap on one task (8 wrong attempts on 5997d753) because I kept proposing small variations of the same rule instead of stepping back. When you're wrong twice with related hypotheses, stop and:

1. Re-read the demo pairs from scratch, writing the rule in plain words first.
2. Ask what *global structure* the task has (see §3).
3. If truly stuck, request demos — I found demo requests often clarified rules instantly and were cheap relative to a wrong submission.

Keep a note in your memory file of tried-and-failed hypotheses so you never re-propose one. In the failed file for task-1b7868f1 you'll find exactly this: "sub1==sub3 duplicate" — I burned a submission re-testing a hypothesis I'd already tried. Write down what failed and *why*, at submission time.

## 3. Look for global structure before local rules

Many tasks I solved had a "frame" you should check for first. Roughly in order of frequency across my run:

**a) Separator lines and tiling.** If the grid is divided by full uniform rows or columns, everything downstream is block-structured:
- task-026adbf3: split by a uniform separator row/col into two equal blocks A and B; output compares them cellwise (equal → 3, else the common color).
- task-48898d06: uniform separator lines partition the grid; each block of output is 1 if the block contains stray-colored cells (count ≥ 2), else the background.
- task-bb30ebc2: line rows/cols form a lattice; the answer is a small grid where each cell comes from the corner colors at that lattice intersection.
- task-707635df: a centered separator; output = cellwise AND of the two halves' nonzero masks, recolored to 2.
- task-47ed202e: rows or columns that are a single repeated color become all 2 — but note the output kept the *other* cells unchanged, so "which cells change" and "to what" are separate questions.
- task-8d84fe63: uniform separator rows/cols define a block grid; find the block with the most non-background cells (the "source pattern") and copy that block's cell values across the whole block grid position-by-position.

**b) Component analysis with bounding boxes.** The default opening move: find the background (most common color), find connected components (4-connectivity usually; some tasks need 8 — task-1b7868f1's seed needed diagonal adjacency, check the demos), and look at bounding boxes. Variants I saw:
- task-b62da9e0: fill the bounding box of each non-bg component of size ≥ 3 with its color; everything else becomes background.
- task-aa5a69a0: hollow rectangles (perimeter components); fill interior with 2 if the interior area is even, else 7. The parity rule is unusual — it came from the demos, not from intuition. When a rule seems arbitrary, test simple numeric properties (size parity, size mod 3, distance) against the demos.
- task-8625f9bc: fill background cells on the bounding box perimeter of the marker color, plus small gaps (≤ 2) between consecutive markers along rows/cols, all with color 2.

**c) Anchors and stamping.** One component is a "seed" (usually the largest or the only one with a distinctive shape); other cells mark where copies go:
- task-1b7868f1: largest non-bg component is the seed; every other non-bg cell is an anchor; stamp the seed's bbox translated so the seed's bbox center lands on the anchor. Stamping means copying the bbox *as-is*, including background cells inside it.
- task-0f6e5a2f: a large thin L/angle is an "arrow"; among exactly-two-member translation-twin shape pairs, recolor the member *farther* from the arrow (min Manhattan distance from the member to the arrow's horizontal arm) to the arrow's color. Note the tie-breaks: I used larger member size. Rules often need a distance or size tie-break — derive it from demos by constructing near-misses.
- task-770f2daf: take the rarest color's shape, and stamp it at every offset where all its cells would land on background (0). Simple, robust: enumerate all valid translations.

**d) Symmetric mirroring / tiling of the whole grid.**
- task-73499f5a: rows become reversed+original (width doubles), then the row stack is reversed, original, reversed again (height triples). When output dims are a multiple of input dims, immediately try mirror/rotate tilings.
- task-794e60f6: 2×2 tiling of rotations: TL = original, TR = rot90 CW, BL = rot90 CCW, BR = rot180. Check whether output is exactly 2× the input's height and width.

**e) Line-drawing between landmarks.**
- task-d4079843: two bars of one color, scattered dots of another. From the bar facing the dots, draw a perpendicular line to each dot (the dot becomes 4); from the other bar, draw lines at the same relative offsets spanning the gap between bars, in the dot color. Key mechanics: assign roles by component counts (two components = bar, many singletons = dots), determine facing by whether dots are all above/below (or left/right) the bar, and copy offsets relative to the bar's start onto the mirror bar.
- task-3b5f776f: endpoints (degree-1 cells in the 8-neighborhood graph of non-bg cells) extend a ray outward in their degree direction until the edge of the grid, painting their own color.
- task-77262100: an object slides until adjacent to a full 2-line, then a full 8-line is drawn on the object's far side. Careful bookkeeping: erase the object first, compute the slide delta, repaint, then draw the 8-line just outside its far edge, overwriting only background.
- task-5c839a47: a background cell becomes 3 iff it lies strictly between two occurrences of the rarest color in its row or in its column. This "between markers in row or column" pattern is cheap to code and appears in many forms; learn it.
- task-b7641a67: same idea but strictly-adjacent: a background cell with identical non-bg immediate left and right neighbors becomes 2.

**f) Background regions / enclosure.**
- task-3f4fb1a9: background components not touching the border ("pockets") get filled with 4 — but only *solid rectangular* pockets; and a 2-row-tall pocket also absorbs its bottom wall row (to 4) only if the row below that wall is background across the pocket's full width. Notice how specific the exceptions were: I needed demos to discover them. The general skill: compute bg components with a flood fill, check border contact, then test geometric predicates (rectangularity, height) and refine with demos.

**g) Shifts.**
- task-efc2fba8: trivially, shift every non-background cell down one row. Before inventing something clever, check the dumbest geometric transformations: shift by 1 in each direction, mirror, rotate, transpose. Compare against one demo pair cheaply.

**h) Recolor by value ordering.**
- task-2264bd4e: with exactly two colors a < b: a→b and b→0. Critical lesson recorded in my memory: I first tried a majority/minority rule and it failed; the min/max-of-color-values rule worked. When few colors exist, try rules indexed by *color value* (min/max, odd/even value) before rules indexed by frequency. Both are one-liners; test both.

**i) Periodic completion.**
- task-2e29965a: scattered colored cells determine a cyclic pattern; if along diagonals (r+c or r−c mod L) each residue maps to exactly one color consistently, tile that pattern over the whole grid. A general trick: sparse colored cells + large output often = periodic structure; test diagonal, row, and column periods.

## 4. Implementation patterns that prevented bugs

- **Always work on a copy**: `out = [row[:] for row in grid]`. Mutating the input mid-loop causes order-dependent bugs.
- **Background = most common color** (`Counter(...).most_common(1)[0][0]`). Rarest non-bg color = `Counter` ascending. But remember §3h: sometimes rules use color values, not frequency — if frequency-based fails, try value-based.
- **Flood fill component finder**: write it once, reuse verbatim (see task-b62da9e0.py or task-3f4fb1a9.py for compact versions). Both 4- and 8-connectivity; pick per task by checking whether demo shapes stay connected.
- **Canonical shape keys for twin detection**: `tuple(sorted((y-min(ys), x-min(xs)) for y,x in cells))` — translations map to the same key. Group components by this key to find "twin" classes, which drive recolor-one-of-a-pair rules (0f6e5a2f).
- **Write self-contained `transform(grid)` functions** that take a list of lists of ints and return the same. Keep them small and readable; when a task comes back around (some do, in variants), you'll re-read your own code.
- **Guard your rules with validity checks and fall back**: e.g., task-d4079843 tries both bar orientations and both facings, checks offsets are distinct and in-bounds, and only commits when a consistent assignment exists. If no hypothesis cleanly fits, return the input unchanged rather than garbage — sometimes "no change" is close to correct on odd test inputs (see task-efc2fba8's second demo, where output ≈ input).

## 5. Reading demos efficiently

Write a tiny helper mentally: for each demo pair, compute `output minus input` as a set of changed cells, and characterize: which cells changed (by color, position, role) and what they became. Most of my rules fell out of that one diff, plus checking what did *not* change (equally informative — the unchanged parts define the rule's scope).

When outputs have different dimensions from inputs, dimension arithmetic usually tells you the operation: H×2, W×2 (tiling/mirroring), H//3 × W//3 (downsampling — see task-67dd046a: 3×3 blocks, output cell = most common non-5 color in the block), same size (local recolor), half (split-and-compare). task-67dd046a is a good template: downsample by block mode with an ignore color, and note the fallback (block of all-ignore → the ignore color).

## 6. Memory and files: use them

Your workspace persists. When you solve a task, write a memory file with: task id, paths of the .py and .json, a one-sentence rule, and whether the program reproduces all kept pairs. My harness_state.json is full of these and they saved me repeatedly when variant tasks appeared. Also record failed hypotheses with the reason — the cheapest way to not repeat a mistake. Keep the JSON of demo pairs next to the program; you'll want to re-verify after any edit.

## 7. Traps I specifically fell into

- **Assuming a rule from one demo.** One pair can be consistent with many rules. Fit against all pairs, and construct hypothetical near-miss inputs to distinguish them before submitting.
- **Role confusion (majority vs. value).** Try both frequency-based and value-based role assignments (§3h).
- **Forgetting holes/stamps.** When stamping a bbox, background cells inside the bbox are part of the stamp (1b7868f1) — or sometimes aren't; the diff will tell you.
- **Connectivity mistakes.** Diagonals matter in some tasks and not others; check by whether demo components would split under 4-connectivity.
- **Duplicate submissions.** Track attempted submissions per task in a scratch file; re-reading "untried: (13,7),(12,8) anchors" style notes saved me actual submissions.
- **Edge behavior.** Many rules change only interior cells (5c839a47's "strictly between", b7641a67's j from 1 to w-2). Check borders explicitly.
- **Wall-row absorption quirks** (3f4fb1a9): rules can have a second clause that fires only under a geometric condition. If your first clause reproduces most cells but not all, look for a conditional extension rather than a new rule.

## 8. A default opening sequence

For a new task, I suggest literally this order:

1. Print dims and color counts of every kept pair; note input/output dims relation.
2. Scan for full uniform rows/cols (separators) and for single-color rows/cols.
3. Diff each pair; list changed cells grouped by (input color → output color, position pattern).
4. Find components of non-bg colors; count them; look at their shapes and sizes.
5. Hypothesize from §3's catalogue, roughly in the order the catalogue is written — separators first, then components/bboxes, then stamping/lines, then global transforms.
6. Implement as `transform(grid)`, verify on all pairs, and only then predict the test input *using the program*.
7. Submit. If wrong, update the failure note, and change *hypothesis class*, not just parameters.

You are a smaller model than I am, and that is fine: this game rewards careful bookkeeping over cleverness. Verify everything, prefer simple geometric rules, let the demos — not your intuition — decide between hypotheses, and never submit an unverified guess.
